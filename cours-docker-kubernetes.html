Phase 0 - 1 à 2 jours

Bases essentielles : comprendre Docker et Kubernetes

Avant de toucher la moindre ligne de configuration, il faut avoir un modèle mental correct de ce que font vraiment Docker et Kubernetes. Sans ce modèle, vous passerez des heures à lutter contre des outils que vous ne comprenez pas réellement.

Qu'est-ce qu'un container ?

Un container n'est pas une machine virtuelle allégée. C'est un processus Linux isolé. Docker utilise deux mécanismes fondamentaux du noyau Linux :

  • namespaces - créent l'illusion d'isolation (réseau propre, PID propre, filesystem propre)
  • cgroups (control groups) - limitent et comptabilisent les ressources CPU, mémoire, I/O

Le container voit un filesystem indépendant, une interface réseau virtuelle, sa propre table de processus. Mais il partage le noyau du système hôte avec tous les autres containers.

Machine Virtuelle (VM)
  • Noyau OS complet embarqué
  • Boot en 20–60 secondes
  • 512 MB – 4 GB RAM minimum
  • Isolation complète (hyperviseur)
  • Chaque VM = une copie entière de l'OS
Container Docker
  • Partage le noyau de l'hôte
  • Démarrage en millisecondes
  • 10–100 MB typiquement
  • Isolation via namespaces/cgroups
  • Portable : same image, same behavior
Pourquoi c'est révolutionnaire pour un dev
Avec Docker, vous empaquetez votre application avec son environnement d'exécution exact (JRE, librairies native, config). L'image tourne de façon identique sur votre machine locale, le CI/CD et le serveur de production. Le fameux "ça marche chez moi" disparaît.

Image vs Container : la distinction fondamentale

C'est la confusion la plus fréquente chez les débutants. Voici la règle absolue :

Règle fondamentale
Une image est une template en lecture seule. Un container est une instance en cours d'exécution de cette image. La relation est identique à celle entre une classe Java et un objet.
Dockerfile ──── docker build ────▶ Image
Image ──── docker run ─────▶ Container (processus isolé)
Image ──── docker push ────▶ Registry (Docker Hub / ECR / GCR)
Registry ─── docker pull ─────▶ Image locale

Le système de layers (couches)

Une image Docker est composée de couches immuables empilées. Chaque instruction du Dockerfile (FROM, RUN, COPY…) crée une nouvelle couche. Docker met ces couches en cache : si rien n'a changé dans une couche, elle est réutilisée lors d'un rebuild. C'est pourquoi l'ordre des instructions dans un Dockerfile a une importance capitale pour la performance du build.

Layer 0 base OS (debian:slim) - 50 MB
+ Layer 1 JRE 21 installé - 180 MB
+ Layer 2 COPY app.jar - 45 MB
= Image finale 275 MB

Registry et Docker Hub

Un registry est un serveur qui stocke et distribue des images Docker. Docker Hub est le registry public officiel, mais il en existe d'autres :

Registry Hébergement Usage typique
Docker Hub Cloud public Images officielles, projets open source
Amazon ECR AWS Applications déployées sur AWS/EKS
Google GCR / Artifact Registry Google Cloud Applications déployées sur GKE
GitHub Container Registry (GHCR) GitHub Intégration CI/CD GitHub Actions
Harbor Self-hosted Entreprises avec contraintes on-premise

Docker pour développeur

L'objectif de cette phase est concret : vous êtes capable de livrer une application Spring Boot + Angular + base de données entièrement containerisée, avec un seul docker compose up.

Dockeriser Spring Boot

Le Dockerfile naïf (à éviter)

La première tentation est de copier le JAR et de le lancer. Ça fonctionne, mais génère une image lourde et un cache Docker inutilisable.

dockerfile Dockerfile - version naïve à NE PAS copier 
# NON - tout dans une seule couche, JDK complet inutile en prod
FROM eclipse-temurin:21-jdk
COPY target/app.jar /app.jar
ENTRYPOINT ["java", "-jar", "/app.jar"]
# Résultat : ~600 MB, rebuild total à chaque changement de code

Le Dockerfile professionnel avec multi-stage build

Le multi-stage build est la pratique standard en entreprise. Le principe : utiliser plusieurs étages dans le même Dockerfile. L'étage build contient le JDK et Maven pour compiler. L'étage runtime ne contient que le strict nécessaire pour exécuter. Le résultat final n'embarque pas Maven, le JDK, les sources ou les tests.

dockerfile Dockerfile - Spring Boot production-ready 
# ─── Stage 1 : Build ───────────────────────────────────────────
FROM eclipse-temurin:21-jdk-alpine AS builder

WORKDIR /build

# Copier les descripteurs de dépendances EN PREMIER
# Trick : tant que pom.xml ne change pas, Maven télécharge
# les dépendances depuis le cache Docker - énorme gain de temps
COPY pom.xml .
COPY .mvn/ .mvn/
COPY mvnw .
RUN chmod +x mvnw
RUN ./mvnw dependency:go-offline -B

# Maintenant seulement, copier les sources
COPY src/ src/

# Build sans tests (les tests tournent dans le pipeline CI)
RUN ./mvnw package -DskipTests -B

# Extraire les layers Spring Boot pour optimiser encore plus le cache
RUN java -Djarmode=layertools -jar target/*.jar extract --destination extracted

# ─── Stage 2 : Runtime ─────────────────────────────────────────
FROM eclipse-temurin:21-jre-alpine AS runtime

# Bonne pratique sécurité : ne jamais tourner en root
RUN addgroup --system appgroup && adduser --system --ingroup appgroup appuser

WORKDIR /app

# Copier les layers dans l'ordre du moins au plus fréquemment modifié
# Kubernetes et Docker peuvent ainsi réutiliser les couches base et libs
COPY --from=builder /build/extracted/dependencies/ ./
COPY --from=builder /build/extracted/spring-boot-loader/ ./
COPY --from=builder /build/extracted/snapshot-dependencies/ ./
COPY --from=builder /build/extracted/application/ ./

USER appuser

EXPOSE 8080

# Healthcheck intégré
HEALTHCHECK --interval=30s --timeout=5s --start-period=60s --retries=3 \
  CMD wget -qO- http://localhost:8080/actuator/health || exit 1

ENTRYPOINT ["java", \
  "-XX:+UseContainerSupport", \
  "-XX:MaxRAMPercentage=75.0", \
  "-Djava.security.egd=file:/dev/./urandom", \
  "org.springframework.boot.loader.launch.JarLauncher"]
Les options JVM expliquées
  • -XX:+UseContainerSupport - depuis JDK 10, la JVM respecte les limits cgroup. Sans ça, elle calcule ses heaps en regardant la RAM totale du host et non du container.
  • -XX:MaxRAMPercentage=75.0 - alloue 75% de la RAM container au heap. Laisse 25% pour Metaspace, threads, off-heap.
  • -Djava.security.egd=file:/dev/./urandom - accélère le démarrage en Linux en évitant l'attente d'entropie.
Activer Spring Boot Actuator
Le healthcheck Docker et les liveness/readiness probes Kubernetes nécessitent que spring-boot-starter-actuator soit dans le pom.xml et que l'endpoint /actuator/health soit exposé dans application.yml.
yaml application.yml - Configuration Actuator 
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics
  endpoint:
    health:
      show-details: when-authorized
      probes:
        enabled: true   # active /actuator/health/liveness et /readiness

Dockeriser Angular

Une application Angular compilée est un ensemble de fichiers statiques (HTML, JS, CSS). On n'a pas besoin de Node.js en production - simplement d'un serveur web performant. Nginx est le choix standard.

dockerfile Dockerfile - Angular + Nginx production-ready 
# ─── Stage 1 : Build Angular ───────────────────────────────────
FROM node:20-alpine AS builder

WORKDIR /app

# Copier les descripteurs de dépendances EN PREMIER (cache npm)
COPY package.json package-lock.json ./
RUN npm ci --prefer-offline

# Copier les sources et builder en mode production
COPY . .
RUN npm run build -- --configuration production

# ─── Stage 2 : Servir avec Nginx ───────────────────────────────
FROM nginx:1.27-alpine AS runtime

# Supprimer la config par défaut
RUN rm /etc/nginx/conf.d/default.conf

# Notre config personnalisée (SPA routing + gzip + sécurité)
COPY nginx.conf /etc/nginx/conf.d/default.conf

# Copier le build Angular
COPY --from=builder /app/dist/<nom-projet>/browser /usr/share/nginx/html

EXPOSE 80

HEALTHCHECK --interval=30s --timeout=3s \
  CMD wget -qO- http://localhost/index.html || exit 1

CMD ["nginx", "-g", "daemon off;"]
nginx nginx.conf - Configuration SPA optimisée 
server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;

    # Compression gzip
    gzip on;
    gzip_vary on;
    gzip_types text/plain text/css application/json application/javascript
               text/xml application/xml application/xml+rss text/javascript;

    # Cache long pour les assets hashés par Angular
    location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff2)$ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # SPA routing - toujours renvoyer index.html pour les routes Angular
    location / {
        try_files $uri $uri/ /index.html;
    }

    # Sécurité : ne pas exposer la version de Nginx
    server_tokens off;

    # Headers de sécurité basiques
    add_header X-Frame-Options "SAMEORIGIN";
    add_header X-Content-Type-Options "nosniff";
    add_header X-XSS-Protection "1; mode=block";
}
Config runtime vs build time

Angular compile l'environnement à la build - les valeurs environment.ts sont figées dans le JS. Pour une vraie config runtime (URL d'API différente par environnement) :

  • Solution simple : un fichier assets/config.json chargé au lancement de l'app par APP_INITIALIZER.
  • Solution Docker : un script shell dans le container injecte les variables d'env dans un fichier JSON au démarrage de Nginx.

Docker Compose

Docker Compose est l'outil indispensable pour orchestrer plusieurs containers en développement. Un seul fichier docker-compose.yml décrit toute l'infrastructure locale.

yaml docker-compose.yml - Stack complète Spring Boot + Angular + PostgreSQL 
services:

  # ── Base de données ──────────────────────────────────────────
  db:
    image: postgres:16-alpine
    container_name: taskflow-db
    environment:
      POSTGRES_DB: taskflow
      POSTGRES_USER: taskflow_user
      POSTGRES_PASSWORD: ${DB_PASSWORD:-changeme_local}
    volumes:
      - postgres_data:/var/lib/postgresql/data
      # Script d'initialisation (optionnel)
      - ./db/init.sql:/docker-entrypoint-initdb.d/init.sql:ro
    ports:
      - "5432:5432"          # exposé seulement en dev pour Datagrip / DBeaver
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U taskflow_user -d taskflow"]
      interval: 10s
      timeout: 5s
      retries: 5
    networks:
      - backend-net

  # ── Backend Spring Boot ──────────────────────────────────────
  api:
    build:
      context: ./backend
      dockerfile: Dockerfile
    container_name: taskflow-api
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/taskflow
      SPRING_DATASOURCE_USERNAME: taskflow_user
      SPRING_DATASOURCE_PASSWORD: ${DB_PASSWORD:-changeme_local}
      SPRING_JPA_HIBERNATE_DDL_AUTO: validate
      JWT_SECRET: ${JWT_SECRET:-dev_secret_change_in_prod_please}
      SPRING_PROFILES_ACTIVE: docker
    ports:
      - "8080:8080"
    depends_on:
      db:
        condition: service_healthy   # attend que db passe son healthcheck
    healthcheck:
      test: ["CMD-SHELL", "wget -qO- http://localhost:8080/actuator/health || exit 1"]
      interval: 30s
      timeout: 5s
      start_period: 60s
      retries: 3
    networks:
      - backend-net
      - frontend-net
    restart: unless-stopped

  # ── Frontend Angular ─────────────────────────────────────────
  frontend:
    build:
      context: ./frontend
      dockerfile: Dockerfile
    container_name: taskflow-frontend
    environment:
      API_URL: http://api:8080
    ports:
      - "4200:80"
    depends_on:
      api:
        condition: service_healthy
    networks:
      - frontend-net
    restart: unless-stopped

# ── Volumes persistants ────────────────────────────────────────
volumes:
  postgres_data:
    driver: local

# ── Réseaux isolés ────────────────────────────────────────────
networks:
  backend-net:        # db <-> api (le frontend ne voit pas la DB directement)
    driver: bridge
  frontend-net:       # api <-> frontend
    driver: bridge

Phase 2 - 2 à 3 jours

Docker avancé - Production-Ready

La Phase 1 vous a donné une app fonctionnelle. La Phase 2 vous apprend à la rendre fiable, sécurisée et maintenable comme en entreprise.

Volumes : persister les données

Docker propose trois mécanismes de stockage. Comprendre leurs différences est critique pour ne jamais perdre des données en production.

TypeSyntaxeGéré parUsage recommandé
Named Volume postgres_data:/var/lib/postgresql/data Docker Engine BDD, données persistantes
Bind Mount ./src:/app/src OS hôte Dev uniquement - hot reload
tmpfs type=tmpfs,target=/tmp RAM hôte Données temporaires sensibles
Erreur classique
Ne jamais utiliser de bind mount en production. Sur le CI/CD ou en Kubernetes, il n'y a pas de répertoire ./src sur le serveur. Utilisez toujours des named volumes ou des images immuables.

Networks : architécturer la communication

Par défaut, tous les containers du même Compose partagent un réseau bridge. Créer des réseaux séparés permet d'imposer des règles de sécurité en limitant qui peut parler à qui.

Internet ──▶ frontend (port 80) ──▶ api (port 8080)
api est sur frontend-net ET backend-net
api ──▶ db (port 5432)
frontend ne peut PAS accéder à db (réseaux différents)
Résolution DNS interne
Dans un réseau Docker Compose, les services se parlent par leur nom de service. L'URL JDBC jdbc:postgresql://db:5432/taskflow fonctionne car Docker maintient un DNS interne où db résout vers l'IP du container PostgreSQL.

Phase 3 - 3 à 5 jours

Introduction à Kubernetes

Kubernetes (K8s) est le standard de l'industrie pour orchestrer des containers en production. Avant d'apprendre les commandes, il faut absolument comprendre son modèle mental - autrement dit, pourquoi K8s existe et ce qu'il résout.

Pourquoi Kubernetes alors que Docker Compose existe ?

Docker Compose fait tourner des containers sur une machine. Kubernetes orchestre des containers sur un cluster de machines, gère les pannes, scalabilise automatiquement, effectue les rolling updates sans downtime, route le trafic intelligemment et gère la configuration à grande échelle.

Les concepts clés - absolument obligatoires

Pod - l'unité de base

Distinction CRITIQUE
Kubernetes ne gère pas des containers. Kubernetes gère des Pods. Un Pod est un groupe de un ou plusieurs containers qui partagent le même réseau et le même filesystem. La quasi-totalité du temps, un Pod = un container.

Les Pods sont éphémères. Quand un Pod meurt (crash, node défaillant), Kubernetes en crée un nouveau avec une nouvelle IP. C'est pourquoi on n'accède jamais directement à un Pod mais toujours via un Service.

Pod
  • 1 ou N containers
  • IP unique dans le cluster
  • Éphémère - peut mourir
  • Unité d'scheduling
Deployment
  • Gère N replicas de Pods
  • Auto-healing (redémarre)
  • Rolling updates
  • Rollback possible
Service
  • IP stable (VIP)
  • Load balancing entre Pods
  • DNS interne au cluster
  • Types : ClusterIP, NodePort, LB
Namespace
  • Isolation logique
  • RBAC par namespace
  • Quotas de ressources
  • Multi-équipes / multi-projets

Votre premier Deployment YAML

yaml deployment-api.yaml - Spring Boot sur Kubernetes 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: taskflow-api
  namespace: taskflow
  labels:
    app: taskflow-api
    version: "1.0"
spec:
  replicas: 2                         # 2 instances pour la haute dispo
  selector:
    matchLabels:
      app: taskflow-api               # sélectionne les Pods à gérer
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1                     # max 1 Pod supplémentaire pendant update
      maxUnavailable: 0               # jamais de downtime
  template:
    metadata:
      labels:
        app: taskflow-api
        version: "1.0"
    spec:
      containers:
        - name: api
          image: ghcr.io/moncompte/taskflow-api:1.0
          ports:
            - containerPort: 8080
          env:
            - name: SPRING_DATASOURCE_URL
              value: "jdbc:postgresql://taskflow-db-svc:5432/taskflow"
            - name: SPRING_DATASOURCE_USERNAME
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: username
            - name: SPRING_DATASOURCE_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: password
          resources:
            requests:
              memory: "256Mi"
              cpu: "250m"
            limits:
              memory: "512Mi"
              cpu: "500m"
          livenessProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            initialDelaySeconds: 60
            periodSeconds: 30
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 10
            failureThreshold: 3
      restartPolicy: Always
Liveness vs Readiness vs Startup Probes
  • livenessProbe - "est-ce que le container est vivant ?" Si elle échoue, Kubernetes redémarre le container.
  • readinessProbe - "est-ce que le container est prêt à recevoir du trafic ?" Si elle échoue, le Pod est retiré du load balancer du Service mais il n'est pas redémarré.
  • startupProbe - donne le temps au container de démarrer avant que liveness/readiness ne commencent. Idéal pour les apps Java lentes au démarrage.
yaml service-api.yaml - Exposer le Deployment 
apiVersion: v1
kind: Service
metadata:
  name: taskflow-api-svc
  namespace: taskflow
spec:
  selector:
    app: taskflow-api          # tous les Pods avec ce label
  ports:
    - name: http
      port: 80                 # port du Service (interne cluster)
      targetPort: 8080         # port du container
  type: ClusterIP              # accessible seulement depuis l'intérieur du cluster

ConfigMap & Secret - Gérer la configuration

ObjetUsageEncodageExemple
ConfigMap Config non sensible Texte brut URL d'API, feature flags, niveaux de log
Secret Données sensibles base64 (+ chiffrement etcd en prod) Mots de passe, JWT secret, API keys

Sécurité des Secrets Kubernetes
Les Secrets K8s ne sont pas chiffrés par défaut dans etcd - simplement encodés en base64. En production, activez le Encryption at Rest pour etcd, ou utilisez des solutions externes comme HashiCorp Vault, AWS Secrets Manager, ou le Sealed Secrets operator pour committer des secrets chiffrés dans Git.

Persistance : PersistentVolume & PersistentVolumeClaim

Pour persister les données d'une base de données en Kubernetes, il faut comprendre le modèle de stockage en trois couches.

StorageClass ── définit le type de stockage (SSD local, NFS, EBS, GCE PD…)
PersistentVolume (PV) ── volume réel provisionné (admin ou automatique)
PersistentVolumeClaim (PVC) ── demande de stockage par l'application
Pod ── monte le PVC
yaml postgres-storage.yaml - PVC + StatefulSet PostgreSQL 
---
# Demande de stockage
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-pvc
  namespace: taskflow
spec:
  accessModes:
    - ReadWriteOnce          # 1 seul node peut écrire à la fois (correct pour une DB)
  storageClassName: standard  # "standard" sur Minikube / gp2 sur AWS
  resources:
    requests:
      storage: 5Gi
---
# StatefulSet pour PostgreSQL (garde l'identité réseau entre restarts)
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: taskflow-db
  namespace: taskflow
spec:
  serviceName: taskflow-db-svc
  replicas: 1
  selector:
    matchLabels:
      app: taskflow-db
  template:
    metadata:
      labels:
        app: taskflow-db
    spec:
      containers:
        - name: postgres
          image: postgres:16-alpine
          ports:
            - containerPort: 5432
          env:
            - name: POSTGRES_DB
              value: taskflow
            - name: POSTGRES_USER
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: username
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: password
            - name: PGDATA
              value: /var/lib/postgresql/data/pgdata  # sous-dossier requis
          volumeMounts:
            - name: postgres-data
              mountPath: /var/lib/postgresql/data
          resources:
            requests:
              memory: "256Mi"
              cpu: "100m"
            limits:
              memory: "512Mi"
              cpu: "500m"
          readinessProbe:
            exec:
              command: ["pg_isready", "-U", "taskflow_user", "-d", "taskflow"]
            initialDelaySeconds: 15
            periodSeconds: 10
      volumes:
        - name: postgres-data
          persistentVolumeClaim:
            claimName: postgres-pvc
---
apiVersion: v1
kind: Service
metadata:
  name: taskflow-db-svc
  namespace: taskflow
spec:
  selector:
    app: taskflow-db
  ports:
    - port: 5432
      targetPort: 5432
  type: ClusterIP              # DB jamais exposée hors du cluster

Exposition externe : NodePort, LoadBalancer, Ingress

TypeAccessible depuisUsageLimitations
ClusterIP Intérieur du cluster uniquement Communication inter-services Pas d'accès externe
NodePort IP du Node + port 30000-32767 Dev, tests rapides Port moche, un port par service
LoadBalancer IP publique cloud Chez un cloud provider (AWS, GCP, Azure) 1 IP publique (et facture) par service
Ingress Domaine HTTP/HTTPS Production avec routing par host/path Requiert un Ingress Controller

En production, Ingress est la solution standard. Un seul LoadBalancer (une seule IP publique) fait entrer tout le trafic, et l'Ingress Controller route vers les bons Services selon le domaine ou le chemin HTTP.

yaml ingress.yaml - Routing HTTP pour TaskFlow 
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: taskflow-ingress
  namespace: taskflow
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
    # Redirection HTTPS automatique
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    # Rate limiting (bonus sécurité)
    nginx.ingress.kubernetes.io/limit-rps: "50"
spec:
  ingressClassName: nginx
  rules:
    # Route par sous-domaine
    - host: taskflow.local             # ajouter dans /etc/hosts en dev
      http:
        paths:
          - path: /                    # frontend Angular
            pathType: Prefix
            backend:
              service:
                name: taskflow-frontend-svc
                port:
                  number: 80
    - host: api.taskflow.local
      http:
        paths:
          - path: /                    # API Spring Boot
            pathType: Prefix
            backend:
              service:
                name: taskflow-api-svc
                port:
                  number: 80
  tls:
    - hosts:
        - taskflow.local
        - api.taskflow.local
      secretName: taskflow-tls-secret  # cert-manager le crée automatiquement

Scaling & HPA (Horizontal Pod Autoscaler)

Kubernetes permet de scaler manuellement ou automatiquement.

bash Scaling manuel et automatique 
# Scaling manuel immédiat
kubectl scale deployment taskflow-api --replicas=5 -n taskflow

# Vérifier le rollout
kubectl rollout status deployment/taskflow-api -n taskflow

# Créer un HPA - scale entre 2 et 10 replicas si CPU > 70%
kubectl autoscale deployment taskflow-api \
  --cpu-percent=70 --min=2 --max=10 -n taskflow

# Voir le HPA
kubectl get hpa -n taskflow

# Simuler de la charge pour voir le HPA en action
kubectl run -it --rm load-test --image=busybox --restart=Never -- \
  sh -c "while true; do wget -qO- http://taskflow-api-svc/api/tasks; done"
yaml hpa.yaml - HPA déclaratif avec métriques custom 
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: taskflow-api-hpa
  namespace: taskflow
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: taskflow-api
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70    # scale up si CPU moyen > 70%
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 30   # attend 30s avant de scale up
      policies:
        - type: Pods
          value: 2
          periodSeconds: 60             # max +2 Pods par minute
    scaleDown:
      stabilizationWindowSeconds: 300  # attend 5min avant de scale down

Helm - Le gestionnaire de packages Kubernetes

Dès que vous avez plusieurs environnements (dev, staging, prod) ou plusieurs équipes, les YAML bruts deviennent ingérables. Helm résout ce problème en templatisant les manifestes Kubernetes.

Helm en une phrase
Helm est à Kubernetes ce que Maven/Gradle est à Java : un gestionnaire de dépendances + un système de build pour packages Kubernetes, appelés Charts.

├── Chart.yaml          # métadonnées du chart (nom, version, description)

├── values-dev.yaml     # surcharges pour dev
├── values-prod.yaml    # surcharges pour prod
└── templates/

yaml .github/workflows/deploy.yml - Pipeline complet 
name: Build, Push & Deploy

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository_owner }}/taskflow-api

jobs:
  # ── Job 1 : Tests ──────────────────────────────────────────────
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16-alpine
        env:
          POSTGRES_DB: taskflow_test
          POSTGRES_USER: test
          POSTGRES_PASSWORD: test
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5
        ports: ["5432:5432"]
    steps:
      - uses: actions/checkout@v4

      - name: Setup Java 21
        uses: actions/setup-java@v4
        with:
          java-version: '21'
          distribution: 'temurin'
          cache: maven

      - name: Run tests
        run: ./mvnw test -B
        env:
          SPRING_DATASOURCE_URL: jdbc:postgresql://localhost:5432/taskflow_test
          SPRING_DATASOURCE_USERNAME: test
          SPRING_DATASOURCE_PASSWORD: test
          SPRING_JPA_HIBERNATE_DDL_AUTO: create-drop

  # ── Job 2 : Build & Push image Docker ─────────────────────────
  build-and-push:
    runs-on: ubuntu-latest
    needs: test
    if: github.ref == 'refs/heads/main'
    permissions:
      contents: read
      packages: write
    outputs:
      image-tag: ${{ steps.meta.outputs.version }}
    steps:
      - uses: actions/checkout@v4

      - name: Log in to GitHub Container Registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Extract metadata (tags, labels)
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=sha,prefix=,format=short
            type=raw,value=latest,enable=${{ github.ref == 'refs/heads/main' }}

      - name: Build and push Docker image
        uses: docker/build-push-action@v5
        with:
          context: ./backend
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha              # cache GitHub Actions
          cache-to: type=gha,mode=max

  # ── Job 3 : Déploiement Kubernetes ────────────────────────────
  deploy:
    runs-on: ubuntu-latest
    needs: build-and-push
    if: github.ref == 'refs/heads/main'
    environment: production                # approbation manuelle possible
    steps:
      - uses: actions/checkout@v4

      - name: Setup kubectl
        uses: azure/setup-kubectl@v3
        with:
          version: 'v1.30.0'

      - name: Configure kubeconfig
        run: |
          echo "${{ secrets.KUBECONFIG_B64 }}" | base64 -d > kubeconfig.yaml
          echo "KUBECONFIG=$(pwd)/kubeconfig.yaml" >> $GITHUB_ENV

      - name: Deploy with Helm
        run: |
          helm upgrade --install taskflow ./taskflow-chart \
            --namespace taskflow \
            --create-namespace \
            --set image.tag=${{ needs.build-and-push.outputs.image-tag }} \
            --set image.repository=${{ env.REGISTRY }}/${{ env.IMAGE_NAME }} \
            --wait --timeout 5m

      - name: Verify deployment
        run: |
          kubectl rollout status deployment/taskflow -n taskflow --timeout=3m
          kubectl get pods -n taskflow
Secrets GitHub Actions
Ne jamais stocker de secrets dans les YAML. Utilisez les GitHub Secrets (ou Variables d'environnement GitHub Environments) pour toutes les valeurs sensibles : KUBECONFIG_B64, clés de déploiement, tokens d'API. Ils sont chiffrés et masqués dans les logs.

GitOps avec Argo CD

Le GitOps est un paradigme où Git est la seule source de vérité pour l'état désiré de l'infrastructure. Argo CD surveille en continu un dépôt Git et synchronise automatiquement le cluster Kubernetes avec l'état décrit dans Git.

Principe GitOps
Push du code → Git → Argo CD détecte le changement → apply des manifestes → cluster mis à jour. Aucun accès direct au cluster depuis le pipeline CI/CD. Tout passe par Git - ce qui donne un audit trail complet et un rollback trivial (git revert).
Développeur ── git push ──▶ GitHub (App Repo)
↓
GitHub Actions ── build image + push registry ──▶
↓ update image tag
GitHub (Config Repo) ── détecté par ──▶ Argo CD ──▶ Kubernetes Cluster
bash Installation Argo CD sur Minikube 
# Installer Argo CD
kubectl create namespace argocd
kubectl apply -n argocd -f \
  https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

# Attendre que tout soit prêt
kubectl wait --for=condition=Available deployment --all -n argocd --timeout=300s

# Récupérer le mot de passe admin initial
kubectl get secret argocd-initial-admin-secret -n argocd \
  -o jsonpath="{.data.password}" | base64 -d

# Accéder à l'UI (port-forward)
kubectl port-forward svc/argocd-server -n argocd 8443:443

# Naviguer sur https://localhost:8443 (user: admin, pwd: ci-dessus)
yaml argocd-app.yaml - Application Argo CD 
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: taskflow
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/moncompte/taskflow-config

    path: k8s/overlays/prod          # kustomize ou helm chart dans ce dossier
  destination:
    server: https://kubernetes.default.svc
    namespace: taskflow

    automated:
      prune: true              # supprimer les ressources non présentes dans Git
      selfHeal: true           # corriger les drifts manuels
    syncOptions:
      - CreateNamespace=true
      - PrunePropagationPolicy=foreground

Monitoring : Prometheus & Grafana

En production, vous avez besoin de réponses à deux questions : "Est-ce que mon app tourne ?" (Alerting) et "Comment se comporte-t-elle ?" (Observabilité). La stack Prometheus + Grafana est le standard open source de l'industrie.

Prometheus
  • Scrape les métriques (/actuator/prometheus)
  • Stockage time-series
  • Langage de requête PromQL
  • Alerting rules
Grafana
  • Dashboards visuels
  • Sources multiples (Prometheus, Loki, etc.)
  • Alerting graphique
  • Dashboards communautaires
Loki (bonus)
  • Agrégation de logs
  • Requêtes LogQL
  • Intégration native Grafana
  • Alternative légère à ELK
AlertManager
  • Routage des alertes
  • Dédup / grouping
  • Slack, email, PagerDuty
  • Silences & inhibitions

Service Mesh avec Istio (avancé)

Un service mesh ajoute une couche infrastructure entre les microservices pour gérer : chiffrement mTLS, load balancing avancé, circuit breaking, observabilité distribuée (tracing). Istio est le service mesh le plus répandu en entreprise.

Niveau de complexité
Istio est puissant mais complexe. Ne l'adoptez qu'à partir d'une dizaine de microservices en production. Pour une app simple à 2-3 services, les features natives de Kubernetes suffisent largement.
FeatureK8s natifIstio
Load balancingRound-robin basiqueWeighted, least request, consistent hash
Sécurité inter-servicesNetworkPolicymTLS automatique
ObservabilitéLogs + métriques basiquesTracing distribué (Jaeger/Zipkin)
Traffic managementNonCanary, A/B testing, fault injection
Circuit breakerNonOui (Outlier Detection)
Référence

Glossaire technique

Container
Processus Linux isolé via namespaces et cgroups. Partage le noyau de l'hôte, démarre en millisecondes, portable entre machines.
Image
Template immuable en lecture seule composée de couches (layers). Sert de base pour créer des containers. Stockée dans un Registry.
Dockerfile
Fichier texte décrivant comment construire une image Docker. Chaque instruction crée une nouvelle couche.
Registry
Serveur de stockage et distribution d'images Docker. Docker Hub, GitHub Container Registry (GHCR), Amazon ECR sont les plus courants.
Docker Compose
Outil pour définir et lancer des applications multi-containers via un fichier YAML. Standard pour le développement local.
Multi-stage build
Technique Dockerfile utilisant plusieurs étages FROM. L'étape de build contient les outils de compilation, l'étape finale ne contient que le runtime - image plus petite et plus sécurisée.
Pod
Unité de base de Kubernetes. Groupe de 1+ containers partageant le même réseau et filesystem. Éphémère - peut être recréé avec une nouvelle IP.
Deployment
Objet Kubernetes déclarant l'état désiré d'un ensemble de Pods. Gère les replicas, rolling updates et rollbacks.
Service
Abstraction Kubernetes fournissant une IP et un DNS stables devant un ensemble de Pods éphémères. Fait office de load balancer interne.
Ingress
Objet Kubernetes gérant l'accès HTTP/HTTPS externe vers les services internes. Route selon le domaine ou le chemin URL. Nécessite un Ingress Controller (NGINX, Traefik…).
ConfigMap
Objet Kubernetes stockant des données de configuration non-sensibles sous forme de clé-valeur ou fichiers. Injecté dans les Pods via env ou volume.
Secret
Comme ConfigMap mais pour les données sensibles. Stocké encodé en base64 dans etcd. Chiffrement at-rest recommandé en production.
PersistentVolume
Volume de stockage réel provisionné dans Kubernetes (disque cloud, NFS, local). Indépendant du cycle de vie des Pods.
PV / PVC
PersistentVolume = stockage physique. PersistentVolumeClaim = demande de stockage par une app. Séparation permettant à l'infra d'être découplée des apps.
HPA
Horizontal Pod Autoscaler - ajuste automatiquement le nombre de replicas d'un Deployment selon des métriques (CPU, mémoire, métriques custom).
Helm
Gestionnaire de packages Kubernetes. Permet de templatiser, versionner et déployer des configurations Kubernetes via des Charts paramétrables.
Liveness Probe
Vérification périodique par Kubernetes qu'un container est vivant. En cas d'échec, le container est redémarré.
Readiness Probe
Vérification que le container est prêt à recevoir du trafic. En cas d'échec, le Pod est retiré du load balancer du Service sans être redémarré.
Namespace
Isolation logique dans un cluster Kubernetes. Permet de séparer les ressources par équipe, application ou environnement (dev/staging/prod).
StatefulSet
Comme un Deployment mais pour les applications avec état (bases de données). Maintient une identité réseau stable et des volumes persistants par Pod.
GitOps
Paradigme où Git est la seule source de vérité pour l'état del'infrastructure. Argo CD ou Flux synchronisent le cluster avec les manifestes stockés dans Git.
Rolling Update
Stratégie de déploiement Kubernetes remplaçant progressivement les anciens Pods par les nouveaux, sans downtime. Configurable via maxSurge et maxUnavailable.
Service Mesh
Infrastructure découplée gérant la communication entre microservices (mTLS, tracing distribué, circuit breaking). Istio et Linkerd sont les solutions les plus connues.
