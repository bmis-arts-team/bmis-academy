3.1 Pourquoi DevOps est indispensable

Sans DevOps, un projet microservices comme TaskFlow accumule rapidement les problèmes :

  • Déploiements risqués et manuels - chaque mise en production est un événement stressant, source d'erreurs humaines
  • Services qui tombent sans alerte - un microservice peut crasher silencieusement pendant des heures avant que quelqu'un ne s'en aperçoive
  • Bugs qui passent inaperçus - sans tests automatisés ni pipeline, les régressions arrivent en production
  • Temps perdu en tâches répétitives - build manuel, copie de fichiers, configuration serveur à la main
DevOps en une phrase

DevOps = automatisation + surveillance + livraison continue. L'objectif est de déployer rapidement, en toute confiance, avec une visibilité totale sur le système.

3.2 Infrastructure as Code (IaC)

L'Infrastructure as Code consiste à décrire toute l'infrastructure dans des fichiers versionnés. Plus besoin de configurer manuellement des serveurs - tout est reproductible et versionné.

Docker Compose pour TaskFlow

Voici le fichier docker-compose.yml qui orchestre l'ensemble des services TaskFlow :

docker-compose.yml

services:

      - "8081:8080"

      - SPRING_PROFILES_ACTIVE=docker

  project-service:

    environment:
      - SPRING_PROFILES_ACTIVE=docker

    ports:
      - "8083:8080"

      - SPRING_PROFILES_ACTIVE=docker

  notification-service:
    build: ./notification-service

Dockerfile pour task-service

task-service/Dockerfile
FROM eclipse-temurin:17-jdk-alpine AS build
WORKDIR /app
COPY build.gradle settings.gradle ./
COPY gradle ./gradle
COPY gradlew .
RUN ./gradlew dependencies --no-daemon
COPY src ./src
RUN ./gradlew bootJar --no-daemon

FROM eclipse-temurin:17-jre-alpine
WORKDIR /app
COPY --from=build /app/build/libs/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
Multi-stage build

Le Dockerfile utilise un multi-stage build : la première étape compile le projet, la seconde ne copie que le JAR final. Résultat : une image légère (~200 Mo au lieu de ~800 Mo).

3.3 Pipeline CI/CD

Un pipeline CI/CD automatise tout le chemin entre le code source et la production :

  Push main → Build + Tests → Scan sécurité → Docker build → Push registry → Deploy
       │            │              │               │              │            │
       ▼            ▼              ▼               ▼              ▼            ▼
   Développeur   Gradle       Trivy/Snyk    docker build    ghcr.io      staging
   git push     ./gradlew     CVE scan      multi-stage     registry   → prod

GitHub Actions - Pipeline complet

.github/workflows/ci-cd.yml
name: CI/CD Pipeline

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Java 17
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: 17

      - name: Build project
        run: ./gradlew build --no-daemon

      - name: Run tests
        run: ./gradlew test --no-daemon

  docker-build:
    needs: build-and-test
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Login to GitHub Container Registry
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and push images
        run: |
          docker-compose build
          docker-compose push
Sécurité des secrets

Les secrets (tokens, mots de passe) ne sont jamais stockés dans le code. GitHub Actions les injecte via secrets.GITHUB_TOKEN qui est automatiquement disponible dans chaque workflow.

3.4 Déploiement sur Kubernetes

Une fois les images Docker construites et poussées dans le registry, Kubernetes les déploie et les gère automatiquement.

k8s/task-service-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: task-service
  labels:
    app: task-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: task-service
  template:
    metadata:
      labels:
        app: task-service
    spec:
      containers:
        - name: task-service
          image: ghcr.io/taskflow/task-service:latest
          ports:
            - containerPort: 8080
          resources:
            requests:
              memory: "256Mi"
              cpu: "250m"
            limits:
              memory: "512Mi"
              cpu: "500m"
          readinessProbe:
            httpGet:
              path: /actuator/health
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /actuator/health
              port: 8080
            initialDelaySeconds: 60
            periodSeconds: 30
Résilience automatique

Avec replicas: 3, Kubernetes maintient toujours 3 instances du service. Si un pod crashe, il est automatiquement redémarré. Si un nœud tombe, les pods sont reschédulés sur un autre nœud.

3.5 Observabilité et métriques

L'observabilité est la capacité à comprendre l'état interne d'un système à partir de ses sorties. Elle repose sur trois piliers :

PilierOutilRôle
Logs centralisés ELK Stack (Elasticsearch, Logstash, Kibana) Collecter, indexer et rechercher les logs de tous les services
Métriques Prometheus + Grafana Collecter des métriques numériques (CPU, mémoire, requêtes/s) et les visualiser
Tracing distribué Jaeger / Zipkin Suivre une requête à travers tous les microservices qu'elle traverse

Configuration Spring Boot pour l'observabilité

application.yml - Observabilité
management:
  endpoints:
    web:
      exposure:
        include: health, info, prometheus, metrics
  endpoint:
    health:
      show-details: always
  metrics:
    tags:
      application: task-service

logging:
  level:
    root: INFO
    com.taskflow: DEBUG
  pattern:
    console: "%d{{ '{' }}yyyy-MM-dd HH:mm:ss{{ '}' }} [%thread] %-5level %logger - %msg%n"
Endpoint Prometheus

L'endpoint /actuator/prometheus expose toutes les métriques au format Prometheus. Grafana se connecte à Prometheus pour créer des dashboards visuels en temps réel.
