Contexte métier - TaskFlow

TaskFlow est notre projet fil rouge. C'est une API REST de gestion de tâches qui nous servira à appliquer concrètement chaque concept du parcours : architecture propre, microservices, DevOps et observabilité.

Objectifs fonctionnels

  • Gérer des utilisateurs (inscription, authentification)
  • Créer et organiser des projets
  • Créer, assigner et suivre des tâches avec statuts

Modélisation métier

EntitéAttributsRelations
User id, name, email, password 1 → N Tasks (assignation)
Project id, name, description 1 → N Tasks
Task id, title, description, status N → 1 User, N → 1 Project

Structure du projet

Arborescence TaskFlow
com.example.taskflow/
├── domain/
│   ├── model/              ← Task, Project, User, TaskStatus
│   └── repository/         ← TaskRepository, ProjectRepository (interfaces)
├── application/
│   ├── usecase/            ← CreateTaskUseCase, AssignTaskUseCase...
│   └── dto/                ← CreateTaskRequest, TaskResponse...
├── infrastructure/
│   └── persistence/        ← JpaTaskRepository, JpaProjectRepository
└── web/
    ├── controller/         ← TaskController, ProjectController
    └── exception/          ← GlobalExceptionHandler, ErrorResponse
Convention

Les interfaces de repository sont dans domain/ (ports). Les implémentations JPA sont dans infrastructure/ (adaptateurs). C'est le principe de l'architecture hexagonale.

Exercice 1 - Création d'un Use Case propre

Objectif : Implémenter le use case CreateTaskUseCase en respectant la séparation des couches.

Consigne : Créez le DTO de requête, le use case et le contrôleur correspondant.

Voir la correction

public record CreateTaskRequest(
    @NotBlank(message = "Le titre est obligatoire")
    @Size(max = 100)
    String title,
    String description,
    @NotNull Long projectId

CreateTaskUseCase.java
@Service
@RequiredArgsConstructor
public class CreateTaskUseCase {{ '{' }}

    private final TaskRepository taskRepository;
    private final ProjectRepository projectRepository;

    public Task execute(CreateTaskRequest request) {{ '{' }}
        Project project = projectRepository.findById(request.projectId())
            .orElseThrow(() -> new ProjectNotFoundException(request.projectId()));

        Task task = Task.builder()
            .title(request.title())
            .description(request.description())
            .status(TaskStatus.TODO)
            .project(project)
            .build();

        return taskRepository.save(task);
    {{ '}' }}
{{ '}' }}
TaskController.java
@RestController
@RequestMapping("/api/tasks")
@RequiredArgsConstructor
public class TaskController {{ '{' }}

    private final CreateTaskUseCase createTaskUseCase;

    @PostMapping
    public ResponseEntity<Task> create(@Valid @RequestBody CreateTaskRequest request) {{ '{' }}
        Task task = createTaskUseCase.execute(request);
        return ResponseEntity.status(HttpStatus.CREATED).body(task);
    {{ '}' }}

Exercice 3 - Analyse d'une mauvaise architecture

Objectif : Identifier les problèmes dans le code ci-dessous.

TaskController.java - Anti-pattern
@RestController
public class TaskController {{ '{' }}

    @Autowired
    private TaskRepository repo;

    @PostMapping("/tasks")
    public Task create(@RequestBody Task task) {{ '{' }}
        if (task.getTitle() == null) {{ '{' }}
            throw new RuntimeException("Titre manquant");
        {{ '}' }}
        task.setStatus(TaskStatus.TODO);
        return repo.save(task);
    {{ '}' }}
{{ '}' }}
Voir les problèmes identifiés
  • ❌ Entité JPA comme DTO - l'entité Task est reçue directement du client
  • ❌ Logique métier dans le contrôleur - la validation et le statut initial sont gérés dans le controller
  • ❌ Validation manuelle - pas d'utilisation de @Valid et Bean Validation
  • ❌ RuntimeException générique - pas d'exception métier dédiée
  • ❌ Pas de use case - accès direct au repository depuis le contrôleur
  • ❌ Pas de @RequestMapping au niveau classe - URLs dispersées

    // ...

Recommandation

Préférez l'approche déclarative (@NotBlank) pour les validations de format, et l'approche impérative pour les règles métier complexes (ex : vérifier qu'un projet n'a pas atteint sa limite de tâches).

Mini-projet autonome

Mettez en pratique tout ce que vous avez appris en créant les éléments suivants :

Use cases à implémenter

  1. Création d'un projet - POST /api/projects
  2. Création d'une tâche - POST /api/tasks
  3. Liste paginée des tâches - GET /api/tasks?page=0&size=10

Contraintes

  • Utiliser des DTOs pour chaque requête et réponse
  • Chaque opération passe par un use case dédié
  • Validation avec Bean Validation sur tous les DTOs
  • Exception handler centralisé avec @RestControllerAdvice

Bonus

  • Pagination avec Pageable de Spring Data
  • Filtrage par statut (?status=TODO)
  • Logs structurés avec SLF4J
