2.1 - Pourquoi passer des monolithes aux systèmes distribués

Un monolithe bien conçu est un excellent point de départ. Mais à mesure que l'équipe et le produit grandissent, ses limites apparaissent :

LimiteImpact
Goulot d'étranglement d'équipe Plusieurs équipes travaillent sur le même codebase, les conflits se multiplient
Scalabilité difficile Impossible de scaler uniquement le module qui en a besoin - tout doit scaler ensemble
Déploiements risqués Chaque déploiement embarque tout le système - un bug dans un module bloque tout
Maintenance complexe Le code grossit, les dépendances internes deviennent un labyrinthe
Attention

Les microservices ne sont pas une solution universelle. Ils ajoutent de la complexité opérationnelle. Commencez par un monolithe modulaire, puis découpez quand c'est justifié.

2.2 - Monolithe vs Microservices

Monolithe

  • Un seul déploiable
  • Une seule base de données
  • Communication interne (appels de méthodes)
  • Simple à développer au début
  • Difficile à scaler indépendamment

Microservices

  • Plusieurs services indépendants
  • Chaque service a sa propre base
  • Communication réseau (REST, messaging)
  • Complexe à mettre en place
  • Scalable service par service
Exemple concret : e-commerce 
  Monolithe                              Microservices
┌──────────────────┐          ┌──────────────┐  ┌──────────────┐
│  Users           │          │ user-service  │  │ order-service│

2.3 - Communication entre services

Les microservices communiquent via le réseau. Deux approches principales :

TypeTechnologieCaractéristiquesCas d'usage
Synchrone REST (HTTP) Simple, couplage temporel, requête/réponse Lecture de données, opérations simples
Synchrone gRPC Performant, typage fort (Protobuf), streaming Communication inter-services haute performance
Asynchrone RabbitMQ File d'attente, routage flexible, acknowledgment Tâches asynchrones, notifications
Asynchrone Apache Kafka Log distribué, haute performance, replay Event streaming, audit, analytics
Règle d'or

Utilisez la communication synchrone quand vous avez besoin d'une réponse immédiate, et asynchrone quand l'opération peut être traitée en arrière-plan.

2.4 - Brokers de messages

RabbitMQ

  • Modèle push (le broker pousse vers le consommateur)
  • Routage flexible (direct, topic, fanout)
  • Messages supprimés après consommation
  • Idéal pour les tâches et notifications

Apache Kafka

  • Modèle pull (le consommateur tire les messages)
  • Log immutable avec rétention configurable
  • Replay possible des événements
  • Idéal pour l'event streaming et l'audit

Producteur Kafka avec Spring Boot

2.5 - Patterns d'architecture essentiels

PatternProblème résoluPrincipe
Event-Driven Couplage fort entre services Les services communiquent par événements via un broker
Saga Transactions distribuées Séquence de transactions locales avec compensations en cas d'échec
Circuit Breaker Propagation des pannes Coupe-circuit qui détecte les échecs et évite les appels inutiles
CQRS Performance lecture/écriture Séparer les modèles de lecture et d'écriture

2.6 - Cas pratique : découper TaskFlow en microservices

Notre monolithe TaskFlow peut être découpé en services indépendants qui communiquent via Kafka :

┌──────────────┐     ┌──────────────────┐     ┌──────────────┐
│ user-service │     │ project-service  │     │ task-service  │
│   :8081      │     │     :8082        │     │    :8083      │
└──────┬───────┘     └────────┬─────────┘     └──────┬───────┘

       │                      │           ▼
       │              ┌───────────────────────────┐

                      └────────────┬──────────────┘
                                   │
                              consume │
                                   ▼
                      ┌──────────────────────┐
                      │notification-service  │
                      │       :8084          │
                      └──────────────────────┘

Principes de découpage

  • Un service = un domaine métier - chaque service gère une responsabilité claire
  • Base de données par service - pas de base partagée entre services
  • Communication asynchrone - les événements transitent via Kafka
  • Déploiement indépendant - chaque service a son propre cycle de vie
