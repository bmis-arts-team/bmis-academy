4.2 Scalabilité horizontale et verticale

La scalabilité est la capacité d'un système à gérer une charge croissante. Il existe deux approches fondamentalement différentes :

Scalabilité Verticale

  • Ajouter plus de CPU / RAM à une seule machine
  • Coûteux - matériel haut de gamme
  • Single point of failure - si la machine tombe, tout tombe
  • Limite physique - on ne peut pas ajouter indéfiniment
  • Simple à mettre en œuvre - pas de changement d'architecture

Scalabilité Horizontale

  • Ajouter plus d'instances (pods, conteneurs)
  • Load balancer / HPA distribue la charge
  • Nécessite des services stateless
  • Scalabilité quasi illimitée
  • Résilience naturelle - si une instance tombe, les autres prennent le relais
Prérequis : services stateless

Pour scaler horizontalement, chaque instance doit être interchangeable. Aucun état ne doit être stocké en mémoire locale (session, cache local). Utilisez Redis pour le cache partagé et une base de données externe pour la persistance.

4.3 Event Broker avancé - Kafka

Apache Kafka va bien au-delà d'un simple broker de messages. C'est une plateforme de streaming d'événements distribuée avec des caractéristiques uniques :

  • Topics partitionnés - les messages sont répartis en partitions pour paralléliser le traitement
  • Persistance durable - les événements sont stockés sur disque, rejouables à volonté
  • Consumer groups - plusieurs consommateurs se partagent le traitement des partitions

Producteur d'événements avec clé de partition

TaskEventProducer.java
@Service
public class TaskEventProducer {{ '{' }}

    private final KafkaTemplate<String, TaskEvent> kafkaTemplate;

    public TaskEventProducer(KafkaTemplate<String, TaskEvent> kafkaTemplate) {{ '{' }}
        this.kafkaTemplate = kafkaTemplate;
    {{ '}' }}

    public void publishTaskCreated(Task task) {{ '{' }}
        TaskEvent event = new TaskEvent(
            task.getId(),
            task.getTitle(),
            task.getProjectId(),
            EventType.TASK_CREATED
        );

        // La clé de partition = projectId
        // Toutes les tâches d'un même projet vont dans la même partition
        // → Garantit l'ordre des événements par projet
        kafkaTemplate.send("task-events", task.getProjectId(), event);
    {{ '}' }}
{{ '}' }}
Clé de partition et ordering

En utilisant projectId comme clé de partition, tous les événements d'un même projet sont traités dans l'ordre par le même consommateur. C'est essentiel pour maintenir la cohérence : la tâche doit être créée avant d'être assignée.

4.4 Patterns distribués avancés

SAGA - Transactions distribuées

Dans un système monolithique, une transaction SQL garantit l'atomicité. Dans un système distribué, c'est impossible. Le pattern SAGA orchestre des transactions distribuées sans verrou global, avec compensation en cas d'échec.

  SAGA : Création de tâche dans TaskFlow

  1. Task Service crée la tâche
     └──→ Publie événement « TaskCreated »

  2. Project Service consomme l'événement
     └──→ Met à jour le compteur de tâches du projet
     └──→ Publie « ProjectUpdated »

  3. Notification Service consomme l'événement
     └──→ Envoie email de notification à l'assigné

  4. ⚠ Si Project Service échoue :
     └──→ Publie « TaskCreationFailed »
     └──→ Compensation : Task Service annule la tâche
     └──→ Compensation : Notification Service annule l'email

CQRS - Command Query Responsibility Segregation

CQRS sépare les opérations de lecture et d'écriture en deux modèles distincts, chacun optimisé pour son usage :

Command (Écriture)

  • Base de données normalisée (PostgreSQL)
  • Validations strictes et règles métier
  • Événements publiés après chaque modification
  • Optimisée pour la cohérence

Query (Lecture)

  • Vues dénormalisées, pré-calculées
  • Cache Redis pour les requêtes fréquentes
  • Pas de validations - lecture seule
  • Optimisée pour la performance

Circuit Breaker avec Resilience4j

Le Circuit Breaker protège un service contre les appels répétés vers un service défaillant. Après plusieurs échecs, le circuit s'ouvre et les appels sont court-circuités vers un fallback.

NotificationServiceClient.java
@Service
public class NotificationServiceClient {{ '{' }}

    private final WebClient webClient;

    public NotificationServiceClient(WebClient.Builder webClientBuilder) {{ '{' }}
        this.webClient = webClientBuilder
            .baseUrl("http://notification-service:8084")
            .build();
    {{ '}' }}

    @CircuitBreaker(name = "notificationService", fallbackMethod = "fallbackNotify")
    public void notifyUser(String userId, String message) {{ '{' }}
        webClient.post()
            .uri("/api/notifications")
            .bodyValue(new NotificationRequest(userId, message))
            .retrieve()
            .bodyToMono(Void.class)
            .block();
    {{ '}' }}

    private void fallbackNotify(String userId, String message, Throwable t) {{ '{' }}
        // Fallback : enregistrer la notification en file d'attente
        // pour réessayer plus tard
        log.warn("Notification service indisponible, mise en file d'attente: {{ '{' }}{{ '}' }}", t.getMessage());
    {{ '}' }}
{{ '}' }}

4.5 Cache distribué avec Redis

Redis est une base de données clé-valeur in-memory utilisée comme cache distribué. Spring Boot s'intègre nativement avec Redis via les annotations de cache.

TaskQueryService.java
@Service
public class TaskQueryService {{ '{' }}

    private final TaskRepository taskRepository;

    public TaskQueryService(TaskRepository taskRepository) {{ '{' }}
        this.taskRepository = taskRepository;
    {{ '}' }}

    @Cacheable(value = "tasks", key = "#projectId")
    public List<Task> getTasksByProject(String projectId) {{ '{' }}
        // Cette méthode n'est appelée que si le cache est vide
        // Sinon, Redis retourne directement le résultat
        return taskRepository.findByProjectId(projectId);
    {{ '}' }}

    @CacheEvict(value = "tasks", key = "#task.projectId")
    public Task createTask(Task task) {{ '{' }}
        // Invalide le cache du projet quand une tâche est créée
        return taskRepository.save(task);
    {{ '}' }}

    @CacheEvict(value = "tasks", allEntries = true)
    public void clearAllCache() {{ '{' }}
        log.info("Cache des tâches entièrement vidé");
    {{ '}' }}
{{ '}' }}

Configuration Redis

application.yml - Redis Cache
spring:
  data:
    redis:
      host: redis
      port: 6379
  cache:
    type: redis
    redis:
      time-to-live: 300000
      cache-null-values: false
TTL de 5 minutes

time-to-live: 300000 (millisecondes) = 5 minutes. Après ce délai, le cache est automatiquement invalidé et la prochaine requête ira chercher les données en base. Choisissez un TTL adapté à la fréquence de modification de vos données.

4.6 Observabilité avancée

En production, l'observabilité est votre radar. Voici les trois composantes essentielles :

ComposanteOutilRôle dans TaskFlow
Tracing distribué Jaeger / Zipkin Suivre une requête de l'API Gateway jusqu'au dernier microservice
Métriques Prometheus + Grafana Dashboards temps réel : latence, throughput, taux d'erreurs, usage mémoire
Alerting Alertmanager Notifications automatiques si un seuil est dépassé (latence > 2s, erreurs > 5%)
