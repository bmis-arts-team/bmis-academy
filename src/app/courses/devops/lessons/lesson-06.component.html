Le problème : configuration hardcodée

❌ Hardcodé dans le code

application.yml
spring:
  datasource:
    url: jdbc:postgresql://prod-db:5432/mydb
    username: admin
    password: SuperSecret123!

✅ Externalisé via K8s

application.yml
spring:
  datasource:
    url: ${{ '{' }}SPRING_DATASOURCE_URL{{ '}' }}
    username: ${{ '{' }}DB_USERNAME{{ '}' }}
    password: ${{ '{' }}DB_PASSWORD{{ '}' }}

Kubernetes résout ce problème avec deux ressources : ConfigMap pour les données non-sensibles et Secret pour les données sensibles.

ConfigMap - Configuration non-sensible

Créer un ConfigMap

configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: api-config
data:
  APP_NAME: "my-application"
  LOG_LEVEL: "INFO"
  SPRING_PROFILES_ACTIVE: "production"
  SERVER_PORT: "8080"
  SPRING_DATASOURCE_URL: "jdbc:postgresql://postgres-headless:5432/app_db"
  SPRING_DATA_REDIS_HOST: "redis-service"

Utiliser en variables d'environnement

deployment.yaml - extrait
spec:
  containers:
    - name: api
      image: myregistry/api-backend:1.0.0
      envFrom:
        - configMapRef:
            name: api-config

Monter comme fichier

deployment.yaml - volume mount
spec:
  containers:
    - name: api
      volumeMounts:
        - name: config-volume
          mountPath: /app/config
          readOnly: true
  volumes:
    - name: config-volume
      configMap:
        name: api-config

Secret - Données sensibles

Les Secrets ne sont pas chiffrés par défaut

Les Secrets Kubernetes sont encodés en base64, pas chiffrés. Activez le chiffrement au repos (EncryptionConfiguration) ou utilisez un gestionnaire externe (HashiCorp Vault, AWS Secrets Manager, Sealed Secrets).

bash - Créer un Secret
# Depuis des valeurs littérales
kubectl create secret generic db-credentials \
  --from-literal=username=app_user \
  --from-literal=password='P@ssw0rd!'

# Depuis un fichier
kubectl create secret generic tls-cert \
  --from-file=tls.crt=./cert.pem \
  --from-file=tls.key=./key.pem

Utiliser dans un Deployment

deployment.yaml - extrait
spec:
  containers:
    - name: api
      env:
        - name: DB_USERNAME
          valueFrom:
            secretKeyRef:
              name: db-credentials
              key: username
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: db-credentials
              key: password
Bonnes pratiques
  • Ne committez jamais de Secrets en clair dans Git
  • Utilisez Sealed Secrets (Bitnami) pour stocker des secrets chiffrés dans Git
  • Séparez les ConfigMaps et Secrets par environnement (dev, staging, prod)
  • Limitez l'accès aux Secrets via RBAC

Travaux Pratiques — ConfigMaps & Secrets

Prérequis : Cluster Kind k8s-lab. Ces labs montrent comment externaliser la configuration d'une app et modifier sa config à chaud, sans rebuilder l'image.

Lab 1 Injecter ConfigMap & Secret dans un pod ~20 min

Objectifs

  • Créer un ConfigMap avec des paramètres applicatifs
  • Créer un Secret avec des données sensibles
  • Les injecter dans un pod et vérifier qu'ils sont disponibles
  • Modifier la config à chaud sans rebuilder l'image

Étape 1 — Créer le ConfigMap

app-config.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_ENV: "staging"
  LOG_LEVEL: "DEBUG"
  MAX_CONNECTIONS: "25"
  API_ENDPOINT: "http://backend-service:8080"

Étape 2 — Créer le Secret

bash
# K8s encode automatiquement en Base64
kubectl create secret generic app-secret \
  --from-literal=DB_PASSWORD=MonMotDePasse123 \
  --from-literal=JWT_SECRET=ma-cle-jwt-secrete

# Vérifier (valeurs masquées)
kubectl get secret app-secret -o yaml

Étape 3 — Pod consommant ConfigMap + Secret

config-demo.yaml
apiVersion: v1
kind: Pod
metadata:
  name: config-demo
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "env | sort && sleep 3600"]
      envFrom:
        - configMapRef:
            name: app-config
        - secretRef:
            name: app-secret
bash
kubectl apply -f app-config.yaml
kubectl apply -f config-demo.yaml

# Vérifier les variables injectées dans le conteneur
kubectl logs config-demo | grep -E "APP_ENV|LOG_LEVEL|DB_PASSWORD"
# APP_ENV=staging
# DB_PASSWORD=MonMotDePasse123
# LOG_LEVEL=DEBUG

# Entrer dans le conteneur
kubectl exec -it config-demo -- sh
# / # echo $JWT_SECRET
# ma-cle-jwt-secrete

Étape 4 — Modifier la config sans rebuilder

bash
# Modifier le ConfigMap en live
kubectl edit configmap app-config
# Changer LOG_LEVEL: DEBUG → INFO, sauvegarder

# Redémarrer le pod pour prendre la nouvelle config
kubectl delete pod config-demo
kubectl apply -f config-demo.yaml

# Vérifier
kubectl logs config-demo | grep LOG_LEVEL
# LOG_LEVEL=INFO
✓ Résultat attendu

Le pod affiche toutes les variables de config et de secret sans qu'elles soient dans l'image Docker. Changer le ConfigMap et redémarrer suffit pour modifier la configuration en production.
