Stratégie de repositories

Avant d'écrire le moindre manifeste, une décision d'architecture s'impose : où vivent les fichiers Kubernetes ? Ce choix impacte la sécurité, la collaboration et la maintenabilité à long terme.

Trois approches — une seule recommandée en production
  • Mono-repo — tout dans un seul dépôt : simple au départ, mais la CI/CD devient ingérable et les droits d'accès impossibles à segmenter.
  • Infra dans chaque repo applicatif — les manifestes vivent à côté du code : pratique en apparence, mais duplication massive et vision globale de l'infrastructure impossible.
  • Repo infra dédié repo-infra — les manifestes de tous les environnements vivent dans un repo séparé, accès restreint DevOps uniquement. C'est le standard de l'industrie.

Dans notre cas : les repos repo-frontend et repo-backend ne contiennent que le code source et le Dockerfile. Les manifestes Kubernetes vivent exclusivement dans repo-infra.

Matrice des accès par rôle

La séparation des repos permet une gestion fine des permissions :

  • Développeur frontend — Write sur repo-frontend, Read sur repo-backend
  • Développeur backend — Write sur repo-backend, Read sur repo-frontend
  • DevOps junior — Write sur repo-infra (hors production)
  • DevOps senior — Write sur repo-infra (tous environnements)
  • CI/CD (GitHub Actions) — Write limité sur repo-infra (mise à jour des tags d'image uniquement)

Les développeurs n'ont aucun accès à repo-infra en production.

Déployer le Backend Spring Boot

Voici le manifeste complet du backend. Chaque section est expliquée - pas de copier-coller aveugle.

repo-infra/apps/base/backend/deployment.yaml
# La version de l'API Kubernetes à utiliser pour cette ressource.
# "apps/v1" est le groupe stable pour les workloads (Deployment, StatefulSet, DaemonSet...)
apiVersion: apps/v1

# Le type de ressource à créer.
# Deployment = gère un ensemble de pods identiques avec rolling update, rollback, scaling.
kind: Deployment

metadata:
  # Nom unique du Deployment dans le namespace Kubernetes (dev / staging / prod).
  # kubectl get deployment backend -n deleevx-prod
  #
  # Convention adoptée : 1 namespace par app × environnement (app-env).
  # → deleevx-prod et nouvelle-app-prod sont deux namespaces distincts :
  #   chacun peut avoir son propre "backend" sans aucun conflit.
  name: backend

  # Labels appliqués AU Deployment lui-même (pas aux pods).
  # Utiles pour filtrer/organiser les ressources : kubectl get deploy -l app=backend
  labels:
    app: backend
    tier: api

spec:
  # Nombre de réplicas (pods identiques) à maintenir en permanence.
  # Si un pod crash, Kubernetes en recrée un immédiatement pour atteindre ce chiffre.
  # Valeur surchargée dans overlays/prod (3 replicas) et overlays/dev (1 replica).
  replicas: 2

  # Le selector définit quels pods ce Deployment "possède" et gère.
  # Il cherche les pods ayant le label app=backend.
  # DOIT correspondre exactement aux labels du template ci-dessous.
  selector:
    matchLabels:
      app: backend

  # Stratégie de mise à jour quand on change l'image ou la config.
  strategy:
    # RollingUpdate = remplace les pods un par un, sans coupure de service.
    # Alternative : Recreate (coupe tous les pods, puis recrée) → utile si l'app
    # ne supporte pas 2 versions en parallèle (migrations DB bloquantes par ex.)
    type: RollingUpdate
    rollingUpdate:
      # 0 = on ne retire AUCUN pod existant avant d'en avoir un nouveau Ready.
      # Garantit qu'on a toujours 2 pods actifs pendant le déploiement.
      maxUnavailable: 0
      # 1 = on peut créer 1 pod de plus que replicas pendant l'update.
      # Avec replicas=2 : on passe temporairement à 3 pods, puis retire les anciens.
      maxSurge: 1

  # Le template décrit le pod que Kubernetes va créer (et recréer si besoin).
  template:
    metadata:
      # Ces labels sont appliqués AUX PODS créés par ce Deployment.
      # Le selector ci-dessus utilise ces labels pour identifier "ses" pods.
      # Règle : les labels du template DOIVENT contenir les labels du selector.
      labels:
        app: backend
        tier: api

    spec:
      containers:
        # Un pod peut avoir plusieurs conteneurs (sidecar pattern).
        # Ici un seul : le backend Spring Boot.
        - name: backend

          # Image Docker à utiliser. Format : registry/owner/image:tag
          # ghcr.io = GitHub Container Registry (inclus dans tout compte GitHub gratuit)
          # owner = nom de l'organisation GitHub (ITCloud-Consulting)
          image: ghcr.io/ITCloud-Consulting/deleevx-backend:latest

          ports:
            # Port sur lequel le processus dans le conteneur écoute.
            # "name: http" permet d'y référer par nom dans le Service et les probes.
            - containerPort: 8080
              name: http

          env:
            # Variables d'environnement injectées dans le conteneur au démarrage.
            # Spring Boot les lit pour surcharger application.yml.

            # Active le profil Spring "prod" → charge application-prod.yml
            - name: SPRING_PROFILES_ACTIVE
              value: "prod"

            # URL JDBC de la base. "postgres" est le nom DNS du Service PostgreSQL
            # dans le même namespace → Kubernetes résout automatiquement ce nom.
            - name: SPRING_DATASOURCE_URL
              value: "jdbc:postgresql://postgres:5432/mydb"

            # Ne jamais mettre un mot de passe en clair ici.
            # valueFrom.secretKeyRef lit la valeur depuis un Secret Kubernetes.
            # "db-credentials" = nom du Secret, "username" = clé dans ce Secret.
            - name: SPRING_DATASOURCE_USERNAME
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: username

            - name: SPRING_DATASOURCE_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: password

            # "redis" = nom DNS du Service Redis dans le namespace.
            # Spring Data Redis s'y connecte sur le port 6379 par défaut.
            - name: SPRING_DATA_REDIS_HOST
              value: "redis"

          resources:
            # requests = ressources GARANTIES. Kubernetes utilise ces valeurs pour
            # décider sur quel nœud placer le pod (scheduling). Si le nœud n'a pas
            # assez de CPU/RAM disponibles, le pod reste en Pending.
            requests:
              cpu: "250m"     # "250 millicores" = 0.25 vCPU garanti en permanence
              memory: "512Mi" # 512 MiB de RAM garantis

            # limits = plafond absolu. Si le conteneur dépasse :
            # - CPU limit → il est throttlé (ralenti), pas tué
            # - memory limit → OOMKill immédiat (le pod redémarre)
            limits:
              cpu: "1000m"    # Max 1 vCPU (le conteneur peut burster jusqu'ici)
              memory: "1Gi"   # Max 1 GiB → la JVM doit rester en dessous

          # Les 3 probes permettent à Kubernetes de savoir dans quel état est l'app.

          # livenessProbe : "le conteneur est-il encore vivant ?"
          # Si cette probe échoue failureThreshold fois → le conteneur est REDÉMARRÉ.
          # Utile pour détecter un deadlock : l'app répond encore au réseau mais est bloquée.
          livenessProbe:
            httpGet:
              path: /actuator/health/liveness  # Endpoint Spring Boot Actuator dédié
              port: 8080
            initialDelaySeconds: 30  # Attendre 30s après le démarrage avant la 1ère vérif
            periodSeconds: 10        # Vérifier toutes les 10 secondes
            failureThreshold: 3      # 3 échecs consécutifs → redémarrage du conteneur

          # readinessProbe : "le conteneur est-il prêt à recevoir du trafic ?"
          # Si cette probe échoue → le pod est RETIRÉ des endpoints du Service.
          # Aucune requête ne lui est envoyée tant qu'il n'est pas Ready.
          # Ne redémarre PAS le conteneur → il attend juste qu'il soit prêt.
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            initialDelaySeconds: 20  # Spring Boot met ~20s à être prêt
            periodSeconds: 5
            failureThreshold: 3

          # startupProbe : "le conteneur a-t-il fini de démarrer ?"
          # BLOQUE liveness et readiness tant qu'elle n'est pas OK.
          # Indispensable pour les apps lentes à démarrer (JVM, chargement de contexte Spring).
          # Sans ça, livenessProbe tuerait le pod avant qu'il ait fini de démarrer.
          startupProbe:
            httpGet:
              path: /actuator/health
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 5
            failureThreshold: 30  # 30 essais × 5s = 150s max pour démarrer

          # Monte le volume "uploads" sur le chemin où Spring Boot écrit les fichiers.
          # Doit correspondre à la propriété file.upload-dir dans application.yml.
          volumeMounts:
            - name: uploads
              mountPath: /app/uploads

      # Volumes attachés au pod → déclarés au niveau du pod (pas du conteneur).
      # Ce PVC est créé séparément dans uploads-pvc.yaml.
      volumes:
        - name: uploads
          persistentVolumeClaim:
            claimName: backend-uploads
Les 3 probes expliquées
  • startupProbe — Laisse le temps au Spring Boot de démarrer (jusqu'à 150s). Bloque les autres probes tant que le startup n'est pas OK.
  • readinessProbe — L'application est-elle prête à recevoir du trafic ? Si non → retirée du Service, pas de trafic.
  • livenessProbe — L'application est-elle vivante ? Si non → le conteneur est redémarré.

Volume persistant pour les fichiers uploadés

Le backend stocke les fichiers uploadés dans le dossier uploads/ à la racine du projet. Dans un pod Kubernetes, le système de fichiers est éphémère : si le pod redémarre, tous les fichiers sont perdus. Il faut monter un PersistentVolume.

repo-infra/apps/base/backend/uploads-pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: backend-uploads
spec:
  # local-path = StorageClass intégrée à K3s, provisionne un dossier sur le disque du nœud.
  # Pas besoin de configuration supplémentaire sur un VPS avec K3s.
  storageClassName: local-path

  # ReadWriteOnce = ce volume est monté en lecture/écriture par UN SEUL nœud.
  # Conséquence directe : le Deployment backend doit avoir replicas: 1.
  # (Voir callout ci-dessous pour la solution multi-replicas.)
  accessModes:
    - ReadWriteOnce

  resources:
    requests:
      # Taille initiale du volume. Ajustable par overlay selon l'environnement.
      # La valeur de prod est surchargée dans overlays/production/backend/patch-uploads-pvc.yaml.
      storage: 5Gi
ReadWriteOnce impose replicas: 1 pour le backend

ReadWriteOnce signifie qu'un seul nœud peut monter le volume en écriture simultanément. Avec replicas: 2, le second pod resterait en Pending s'il est schedulé sur un nœud différent. Deux solutions :

  • replicas: 1 en production (le plus simple sur un VPS nœud unique) — le rolling update crée le nouveau pod, il monte le volume, puis l'ancien est supprimé. Zéro perte de fichier, mais une courte fenêtre sans pod pendant la transition.
  • Migrer vers un object storage (MinIO auto-hébergé ou S3 AWS) — recommandé si vous avez besoin de haute disponibilité ou de plusieurs nœuds. Spring Boot se connecte à l'API S3 ; les fichiers ne sont plus sur le disque local.
repo-infra/apps/overlays/production/backend/patch-uploads-pvc.yaml
# Surcharge la taille du volume pour la production.
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: backend-uploads
spec:
  resources:
    requests:
      storage: 20Gi   # Plus d'espace en prod qu'en dev (5Gi)

repo-infra/apps/base/backend/service.yaml
# "v1" = API core de Kubernetes (pas de groupe "apps/").
# Services, ConfigMaps, Secrets, Namespaces sont tous dans le groupe "v1".
apiVersion: v1

# Un Service expose un ensemble de pods sous une adresse IP stable et un nom DNS.
# Sans Service, les pods sont inaccessibles — ils n'ont que des IPs éphémères.
kind: Service

metadata:
  # Ce nom devient le nom DNS dans le cluster.
  # "namespace" dans les exemples ci-dessous = namespace Kubernetes (dev/staging/prod).
  #
  # Forme courte   : http://backend:80
  #   → fonctionne depuis un pod du MÊME namespace (ex: depuis le frontend dans deleevx-prod)
  # Forme complète : http://backend.deleevx-prod.svc.cluster.local:80
  #   → fonctionne depuis n'importe où dans le cluster
  #   → format : {service}.{namespace-k8s}.svc.cluster.local
  #   → sans ambiguïté : backend.deleevx-prod ≠ backend.nouvelle-app-prod
  name: backend
  labels:
    app: backend

spec:
  # ClusterIP = IP virtuelle accessible UNIQUEMENT à l'intérieur du cluster.
  # C'est le type par défaut — ne jamais exposer le backend directement à internet.
  # L'Ingress Controller est le seul point d'entrée externe.
  # Autres types : NodePort (expose sur chaque nœud), LoadBalancer (cloud uniquement).
  type: ClusterIP

  # Le Service route le trafic vers les pods qui ont ce label.
  # Correspond aux labels définis dans template.metadata.labels du Deployment.
  # Kubernetes maintient automatiquement la liste des pods Ready matchant ce selector.
  selector:
    app: backend

  ports:
    # port : le port sur lequel le Service lui-même écoute.
    # Les autres pods font : http://backend:80
    - port: 80

      # targetPort : le port du CONTENEUR vers lequel le trafic est redirigé.
      # Ici 80 (Service) → 8080 (Spring Boot). On peut aussi écrire name: http
      # pour référencer le nom déclaré dans containerPort du Deployment.
      targetPort: 8080

      protocol: TCP

      # Nommer le port est important pour Prometheus (ServiceMonitor) et
      # pour les Ingress rules qui référencent le port par nom.
      name: http

Ressources Angular vs Spring Boot

NGINX servant des fichiers statiques consomme très peu de ressources (50m CPU, 64Mi RAM). Spring Boot a besoin de beaucoup plus — à cause de la JVM (250m CPU, 512Mi RAM minimum). Ajustez selon vos observations en production.

PostgreSQL et Redis

repo-infra/apps/base/backend/postgres-statefulset.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
  labels:
    app: postgres
spec:
  serviceName: postgres
  replicas: 1
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
        - name: postgres
          image: postgres:16-alpine
          ports:
            - containerPort: 5432
          env:
            - name: POSTGRES_DB
              value: "mydb"
            - name: POSTGRES_USER
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: username
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: password
            - name: PGDATA
              value: "/var/lib/postgresql/data/pgdata"
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"
          volumeMounts:
            - name: postgres-data
              mountPath: /var/lib/postgresql/data
  # volumeClaimTemplates est SPÉCIFIQUE aux StatefulSets — absent des Deployments.
  # Pour chaque replica, Kubernetes crée automatiquement un PersistentVolumeClaim (PVC)
  # DISTINCT et PERSISTANT. Même si le pod est supprimé et recréé, il retrouve son volume.
  # Avec un Deployment classique, il faudrait gérer le PVC séparément.
  volumeClaimTemplates:
    - metadata:
        # Nom du PVC généré : postgres-data-postgres-0, postgres-data-postgres-1...
        # Le suffixe -0, -1 correspond à l'index ordinal du pod StatefulSet.
        name: postgres-data
      spec:
        # ReadWriteOnce = ce volume ne peut être monté en écriture que par UN seul nœud.
        # Adapté pour PostgreSQL (1 replica). Pour un stockage partagé entre pods,
        # on utiliserait ReadWriteMany (NFS, CephFS...).
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 10Gi  # Taille du disque alloué. Irréversible sans manipulation manuelle.

Secrets avec Sealed Secrets

Jamais de secrets en clair dans Git

Un Secret Kubernetes n'est qu'encodé en base64 — pas chiffré. Le committer dans Git exposerait directement vos credentials. La solution : Sealed Secrets, qui chiffre avec la clé publique du cluster. Seul le cluster peut déchiffrer. Le fichier résultant est safe à commiter.

1 — Installer le contrôleur Sealed Secrets (une seule fois)

Terminal - VPS
helm repo add sealed-secrets https://bitnami-labs.github.io/sealed-secrets
helm install sealed-secrets sealed-secrets/sealed-secrets   -n kube-system   --set fullnameOverride=sealed-secrets-controller

# Vérifier
kubectl get pods -n kube-system | grep sealed
# sealed-secrets-controller-xxx   1/1   Running   0   30s

2 — Créer un secret chiffré

repo-infra/scripts/seal-secret.sh
#!/bin/bash
# Usage: ./scripts/seal-secret.sh production backend db-credentials username "myapp"

NAMESPACE=$1    # ex: production
APP=$2          # ex: backend
SECRET_NAME=$3  # ex: db-credentials
KEY=$4          # ex: username
VALUE=$5        # ex: myapp

kubectl create secret generic ${SECRET_NAME}   --from-literal=${KEY}="${VALUE}"   --namespace=${NAMESPACE}   --dry-run=client   -o yaml | kubeseal   --controller-namespace kube-system   --controller-name sealed-secrets-controller   --format yaml > apps/overlays/${NAMESPACE}/${APP}/sealed-secret.yaml

echo "Secret scellé → apps/overlays/${NAMESPACE}/${APP}/sealed-secret.yaml"
echo "Ce fichier est safe à commiter dans Git."
repo-infra/apps/overlays/production/backend/sealed-secret.yaml (résultat)
# Safe à commiter — chiffré avec la clé publique du cluster.
# Seul le cluster peut le déchiffrer avec sa clé privée.
apiVersion: bitnami.com/v1alpha1
kind: SealedSecret
metadata:
  name: db-credentials
  namespace: production
spec:
  encryptedData:
    username: AgBj3k9...    # Valeur chiffrée — illisible sans la clé privée
    password: AgCx7m2...
  template:
    metadata:
      name: db-credentials
      namespace: production
    type: Opaque
Sauvegardez la clé maître — point de défaillance critique

Si le contrôleur Sealed Secrets est supprimé sans sauvegarde de sa clé privée, tous les secrets chiffrés deviennent irrécupérables. Exportez la clé et stockez-la dans un gestionnaire de mots de passe (1Password, Bitwarden) : 

# Exporter la clé maître (stocker HORS Git)
kubectl get secret   -n kube-system   -l sealedsecrets.bitnami.com/sealed-secrets-key   -o yaml > sealed-secrets-master-key.yaml

# Chiffrer avec GPG avant de stocker
gpg --encrypt --recipient votre@email.com sealed-secrets-master-key.yaml
