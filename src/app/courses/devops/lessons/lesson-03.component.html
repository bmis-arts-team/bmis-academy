Pourquoi Kubernetes ?

Docker est excellent pour exécuter des conteneurs individuels. Mais en production, vous avez besoin de :

  • Scaling automatique - Ajouter/retirer des instances selon la charge
  • Self-healing - Redémarrer automatiquement les conteneurs crashés
  • Service discovery - Trouver les services sans IP codées en dur
  • Rolling updates - Déployer sans interruption de service
  • Load balancing - Distribuer le trafic entre les réplicas

C'est exactement ce que fait Kubernetes (souvent abrégé K8s).

Control Plane - Le cerveau du cluster

kube-apiserver

Le point d'entrée unique du cluster. Toutes les opérations passent par l'API REST. kubectl, le dashboard et les composants internes communiquent exclusivement via l'API Server.

etcd

Base de données clé-valeur distribuée qui stocke tout l'état du cluster : configurations, secrets, état des pods, etc. C'est la seule source de vérité.

Sauvegardez etcd

Si etcd est perdu, tout l'état du cluster est perdu. Programmez des snapshots réguliers : etcdctl snapshot save backup.db

kube-scheduler

Décide sur quel node un nouveau pod sera placé, en tenant compte des ressources disponibles, des affinités et des contraintes.

kube-controller-manager

Exécute les boucles de contrôle : ReplicaSet controller (maintenir le bon nombre de pods), Node controller (détecter les nodes défaillants), Endpoint controller, etc.

Worker Nodes - L'exécution

kubelet

Agent présent sur chaque node. Il reçoit les instructions de l'API Server et s'assure que les conteneurs demandés sont en cours d'exécution.

kube-proxy

Gère les règles réseau sur chaque node. Il permet aux Services Kubernetes de router le trafic vers les bons pods (via iptables ou IPVS).

Container Runtime

Le moteur qui exécute réellement les conteneurs : containerd (standard), CRI-O, ou d'autres runtimes compatibles CRI.

Pods - L'unité atomique

Un Pod est la plus petite unité déployable dans Kubernetes. Il encapsule un ou plusieurs conteneurs qui partagent le réseau et le stockage.

pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: api-backend
  labels:
    app: api-backend
    version: "1.0"
spec:
  containers:
    - name: api
      image: myregistry/api-backend:1.0.0
      ports:
        - containerPort: 8080
      resources:
        requests:
          memory: "256Mi"
          cpu: "250m"
        limits:
          memory: "512Mi"
          cpu: "500m"
      livenessProbe:
        httpGet:
          path: /actuator/health/liveness
          port: 8080
        initialDelaySeconds: 30
        periodSeconds: 10
      readinessProbe:
        httpGet:
          path: /actuator/health/readiness
          port: 8080
        initialDelaySeconds: 10
        periodSeconds: 5
Ne déployez jamais de Pods seuls

En production, utilisez toujours un Deployment ou un StatefulSet. Un pod seul ne sera pas recréé s'il crash ou si le node tombe.

kubectl - L'outil de commande

bash - Commandes essentielles
# Contexte et cluster
kubectl cluster-info
kubectl config get-contexts

# Créer des ressources
kubectl apply -f pod.yaml

# Lister les ressources
kubectl get pods
kubectl get pods -o wide          # avec IP et node
kubectl get all                   # pods, services, deployments...

# Détails d'un pod
kubectl describe pod api-backend

# Logs
kubectl logs api-backend -f       # follow
kubectl logs api-backend -c api   # conteneur spécifique

# Exécuter une commande
kubectl exec -it api-backend -- /bin/sh

# Supprimer
kubectl delete pod api-backend

Installation locale avec Kind

Kind (Kubernetes in Docker) crée un cluster K8s complet dans des conteneurs Docker. Idéal pour le développement local.

kind-config.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: dev-cluster
nodes:
  - role: control-plane
    extraPortMappings:
      - containerPort: 30080
        hostPort: 80
  - role: worker
  - role: worker
bash
# Créer le cluster
kind create cluster --config kind-config.yaml

# Vérifier
kubectl get nodes

# Supprimer
kind delete cluster --name dev-cluster

Namespaces

Les namespaces isolent logiquement les ressources dans un cluster. Par défaut, tout est dans le namespace default.

bash
# Créer un namespace
kubectl create namespace staging
kubectl create namespace production

# Déployer dans un namespace spécifique
kubectl apply -f deployment.yaml -n staging

# Lister les pods d'un namespace
kubectl get pods -n production

# Changer le namespace par défaut
kubectl config set-context --current --namespace=staging
Bonnes pratiques des namespaces

Utilisez des namespaces pour séparer les environnements (staging, production) ou les équipes. Appliquez des quotas de ressources par namespace pour éviter qu'un service consomme toutes les ressources du cluster.
