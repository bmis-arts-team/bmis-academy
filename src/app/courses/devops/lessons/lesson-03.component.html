Pourquoi Kubernetes ?

Docker résout le problème de l'empaquetage : une application + ses dépendances dans un conteneur portable. Mais en production réelle, vous ne gérez pas un seul conteneur - vous en gérez des dizaines, des centaines, sur plusieurs machines. C'est là que Docker seul atteint ses limites.

Scénario concret sans Kubernetes

Votre API reçoit un pic de trafic à 14h. Il faut lancer 5 instances supplémentaires manuellement sur différents serveurs, configurer le load balancer, surveiller si les conteneurs tournent, redémarrer ceux qui crashent, puis réduire les instances à 17h. En production, c'est insoutenable à la main.

Kubernetes (souvent abrégé K8s, car il y a 8 lettres entre K et s) automatise tout cela :

Sans Kubernetes

  • Lancement manuel des conteneurs par SSH
  • Redémarrage manuel en cas de crash
  • IP statiques codées en dur dans la config
  • Mise à jour = coupure de service
  • Scaling = intervention humaine nocturne
  • Aucune isolation entre les équipes

Avec Kubernetes

  • Scaling automatique (HPA) basé sur CPU/mémoire/métriques custom
  • Self-healing : pod crashé → recréé en quelques secondes
  • Service discovery DNS natif : mon-service.mon-namespace.svc.cluster.local
  • Rolling updates : déploiement progressif sans downtime
  • Load balancing intégré entre tous les réplicas d'un pod
  • Namespaces pour isoler équipes, environnements, ressources

Kubernetes est devenu le standard de l'industrie pour l'orchestration de conteneurs. Google, qui a créé K8s en interne sous le nom « Borg », l'a ouvert en open-source en 2014. Aujourd'hui, il est géré par la Cloud Native Computing Foundation (CNCF) et supporté par tous les cloud providers (GKE, EKS, AKS).

Vue d'ensemble de l'architecture

Architecture d'un cluster Kubernetes avec Control Plane et deux Worker Nodes.

Control Plane - Le cerveau du cluster

Le Control Plane est l'ensemble des composants qui prennent les décisions globales sur le cluster (planification, détection de pannes, réponse aux événements). En production, il tourne sur des nœuds dédiés, séparés des nœuds applicatifs, souvent répliqués en HA (3 instances) pour la tolérance aux pannes.

1. kube-apiserver - La porte d'entrée unique

Tous les échanges dans un cluster Kubernetes passent par l'API Server - sans exception. Que vous lanciez kubectl apply, que le scheduler place un pod, ou qu'un kubelet remonte son statut, tout transite par cet unique point d'entrée HTTP/REST.

Lorsqu'une requête arrive, l'API Server l'évalue en trois phases :

  1. Authentification - Qui êtes-vous ? (certificat TLS, token Bearer, OIDC, ServiceAccount…)
  2. Autorisation (RBAC) - Avez-vous le droit de faire cette action sur cette ressource ? Un développeur peut lire les pods de son namespace mais pas supprimer des nœuds.
  3. Admission Controllers - Des plugins qui valident ou mutent la ressource avant persistance. Par exemple, LimitRanger applique des limites CPU/mémoire par défaut si vous ne les avez pas définies.

Une fois validée, la ressource est écrite dans etcd, et l'API Server notifie tous les composants abonnés via un mécanisme de watch (longue requête HTTP/2).

Cluster requis — Les commandes ci-dessous nécessitent un cluster opérationnel et kubectl configuré. Si ce n'est pas encore le cas, créez votre cluster local via le Lab 0 & Lab 1 en bas de page.

# Explorer l'API directement via proxy local

2. etcd - La mémoire du cluster

etcd est une base de données distribuée clé-valeur, basée sur le protocole de consensus Raft. Elle stocke l'intégralité de l'état du cluster : quels pods existent, leurs specs, les secrets, les configmaps, les rôles RBAC, etc.

etcd ne reçoit d'écriture que de l'API Server - aucun autre composant n'y accède directement. En mode HA, un cluster etcd nécessite un nombre impair de membres (3 ou 5) pour que le quorum fonctionne. Avec 3 membres, vous tolérez 1 panne. Avec 5, vous en tolérez 2.

Sauvegardez etcd régulièrement

Si etcd est perdu sans backup, tout l'état du cluster est définitivement perdu : déploiements, secrets, configurations, tout. En production, automatisez des snapshots toutes les heures et stockez-les hors cluster (S3, GCS…). 

# Créer un snapshot

ETCDCTL_API=3 etcdctl snapshot save /backup/etcd-$(date +%Y%m%d-%H%M).db \

  --endpoints=https://127.0.0.1:2379 \

  --cacert=/etc/kubernetes/pki/etcd/ca.crt \

  --cert=/etc/kubernetes/pki/etcd/server.crt \

  --key=/etc/kubernetes/pki/etcd/server.key



# Vérifier le snapshot

etcdctl snapshot status /backup/etcd-backup.db --write-out=table

3. kube-scheduler - L'algorithme de placement

Quand un pod est créé, il est d'abord dans l'état Pending - aucun node ne lui est assigné. Le Scheduler surveille en permanence ces pods en attente et décide sur quel node les placer.

L'algorithme se déroule en deux phases :

  1. Filtering (filtrage) - Éliminer les nodes incompatibles : pas assez de CPU/mémoire disponible, le node est tainté, les contraintes d'affinité ne sont pas satisfaites, le PersistentVolume requis n'est pas accessible depuis ce node, etc. Résultat : une liste de nodes éligibles.
  2. Scoring (notation) - Parmi les nodes éligibles, attribuer un score à chacun selon des critères : balance la charge entre les nodes, favorise le node qui a déjà l'image Docker en cache, respecte les règles de spread (répartir les réplicas sur différents nodes ou zones d'availability). Le pod est assigné au node avec le score le plus élevé.
pod-avec-affinite.yaml - Exemple de contrainte de scheduling
spec:

  affinity:

    # Forcer la répartition sur des nodes différents

    podAntiAffinity:

      requiredDuringSchedulingIgnoredDuringExecution:

        - labelSelector:

            matchLabels:

              app: api-backend

          topologyKey: kubernetes.io/hostname

    # Préférer les nodes en zone eu-west-1a

    nodeAffinity:

      preferredDuringSchedulingIgnoredDuringExecution:

        - weight: 1

          preference:

            matchExpressions:

              - key: topology.kubernetes.io/zone

                operator: In

                values:

                  - eu-west-1a

4. kube-controller-manager - Le moteur de réconciliation

Le Controller Manager exécute en permanence une série de boucles de contrôle (control loops). Chaque contrôleur observe l'état actuel du cluster et agit pour le rapprocher de l'état désiré défini dans les specs - c'est le principe fondamental de Kubernetes.

Le principe de réconciliation

Vous ne dites pas à Kubernetes quoi faire étape par étape. Vous lui déclarez ce que vous voulez (« 3 réplicas de ce pod ») et les contrôleurs font en sorte que la réalité corresponde à la déclaration, en permanence, même si des nœuds tombent ou redémarrent.

Parmi les contrôleurs importants :

  • ReplicaSet Controller - Surveille le nombre de pods en cours d'exécution. Si un pod est tué, il en crée un nouveau. Si vous en avez trop, il en supprime.
  • Deployment Controller - Orchestre les mises à jour progressives (rolling update) : crée un nouveau ReplicaSet, monte ses réplicas progressivement, descend l'ancien. Gère aussi les rollbacks.
  • Node Controller - Surveille la santé des nodes. Si un node ne répond plus pendant node-monitor-grace-period (40s par défaut), il marque le node NotReady, puis après un délai supplémentaire, évacue les pods (eviction) vers des nodes sains.
  • Endpoints Controller - Met à jour la liste d'IPs dans un Service à chaque fois qu'un pod démarre ou s'arrête, assurant que le load balancing est toujours à jour.

Worker Nodes - L'exécution

Les Worker Nodes sont les machines (VMs ou physiques) qui font tourner vos applications. Chaque node exécute trois composants système obligatoires : kubelet, kube-proxy, et un container runtime. Un cluster de production possède généralement entre 3 et plusieurs centaines de nodes selon la charge.

kubelet - L'agent de terrain

Le kubelet est un agent qui tourne sur chaque node. C'est lui qui traduit les instructions de l'API Server en appels concrets au container runtime.

Son cycle de travail est le suivant :

  1. S'enregistre auprès de l'API Server au démarrage du node
  2. Surveille en permanence les PodSpecs assignées à son node (via le mécanisme de watch)
  3. Demande au container runtime de démarrer/arrêter les conteneurs correspondants
  4. Exécute les liveness probes et readiness probes définies dans les specs
  5. Si une probe échoue : redémarre le conteneur (liveness) ou le retire du Service (readiness)
  6. Remonte régulièrement le statut des pods vers l'API Server

Le kubelet communique avec le container runtime via l'interface standardisée CRI (Container Runtime Interface), ce qui lui permet de fonctionner avec n'importe quel runtime compatible.

bash - Voir les logs du kubelet sur un node
# Sur le node directement

sudo journalctl -u kubelet -f



# Vérifier l'état des nodes depuis kubectl

kubectl get nodes -o wide



# Détails d'un node (ressources, conditions, events)

kubectl describe node worker-node-1

kube-proxy - Le réseau virtuel

kube-proxy tourne sur chaque node et maintient les règles réseau qui permettent aux Services Kubernetes de fonctionner. Quand vous créez un Service avec une IP virtuelle (ClusterIP), c'est kube-proxy qui écrit les règles qui redirigent ce trafic vers les pods correspondants.

Il fonctionne dans deux modes :

  • Mode iptables (par défaut) - Écrit des règles iptables sur le node. Sélection aléatoire parmi les pods disponibles. Simple, éprouvé, mais peut devenir lent sur les très grands clusters (milliers de services).
  • Mode IPVS (recommandé pour les grands clusters) - Utilise le module noyau IPVS (IP Virtual Server). Plus performant, offre plusieurs algorithmes de load balancing (round-robin, least connection, IP hash…), gère mieux les clusters avec des milliers de services.

Container Runtime - Le moteur d'exécution

Le container runtime est le logiciel qui exécute réellement les conteneurs. Depuis Kubernetes 1.24, Docker ne peut plus être utilisé directement - Kubernetes passe par l'interface CRI.

  • containerd (standard actuel) - Runtime léger extrait de Docker. C'est ce qu'utilisent GKE, EKS et AKS par défaut.
  • CRI-O - Runtime minimaliste développé par Red Hat, optimisé pour Kubernetes. Utilisé par défaut sur OpenShift.

Pods - L'unité atomique de Kubernetes

Un Pod est la plus petite unité déployable dans Kubernetes. Il ne contient pas directement une application - il contient un ou plusieurs conteneurs qui partagent :

  • Le même réseau - tous les conteneurs du pod ont la même adresse IP et peuvent communiquer via localhost
  • Le même espace de stockage - ils peuvent monter les mêmes volumes
  • Le même cycle de vie - ils démarrent et s'arrêtent ensemble
Pattern Sidecar

Un pod peut avoir un conteneur principal + un ou plusieurs conteneurs secondaires (sidecars). Exemple classique : votre API dans le conteneur principal, et un agent de log collector (Fluentd) ou un proxy Envoy (service mesh) en sidecar. Ils partagent les fichiers de logs via un volume commun.

Cycle de vie d'un Pod

Un pod passe par plusieurs phases durant son existence :

  • Pending - Le pod est créé dans etcd mais pas encore schedulé, ou ses images sont en téléchargement
  • Running - Tous les conteneurs ont démarré, au moins un est en cours d'exécution
  • Succeeded - Tous les conteneurs se sont terminés avec succès (code 0). Pour les Jobs.
  • Failed - Au moins un conteneur s'est terminé en erreur et ne sera pas redémarré
  • Unknown - L'API Server ne peut plus communiquer avec le kubelet du node (node en panne)

Init Containers

Les init containers s'exécutent avant les conteneurs principaux, en séquence. Ils servent à des tâches d'initialisation : attendre qu'une base de données soit prête, télécharger des fichiers de config, exécuter des migrations, etc.

pod-complet.yaml
apiVersion: v1

kind: Pod

metadata:

  name: api-backend

  labels:

    app: api-backend

    version: "1.0"

    tier: backend

spec:

  # Init container : attend que la BDD soit prête

  initContainers:

    - name: wait-for-db

      image: busybox:1.35

      command: ['sh', '-c',

        'until nc -z postgres-service 5432; do echo waiting for postgres; sleep 2; done']



  containers:

    - name: api

      image: myregistry/api-backend:1.0.0

      ports:

        - containerPort: 8080



      # Variables d'environnement

      env:

        - name: SPRING_PROFILES_ACTIVE

          value: "prod"

        - name: DB_PASSWORD

          valueFrom:

            secretKeyRef:

              name: db-secret

              key: password



      # Ressources : requests = ce dont le pod a besoin (pour le scheduling)

      #              limits    = le maximum absolu autorisé

      resources:

        requests:

          memory: "256Mi"

          cpu: "250m"       # 250 millicores = 0.25 vCPU

        limits:

          memory: "512Mi"

          cpu: "500m"



      # Liveness probe : si elle échoue → conteneur redémarré

      livenessProbe:

        httpGet:

          path: /actuator/health/liveness

          port: 8080

        initialDelaySeconds: 30   # Attendre 30s avant la 1ère vérification

        periodSeconds: 10         # Vérifier toutes les 10s

        failureThreshold: 3       # 3 échecs consécutifs → redémarrage



      # Readiness probe : si elle échoue → pod retiré du Service (plus de trafic)

      readinessProbe:

        httpGet:

          path: /actuator/health/readiness

          port: 8080

        initialDelaySeconds: 10

        periodSeconds: 5

        failureThreshold: 2



    # Sidecar : collecte les logs applicatifs

    - name: log-collector

      image: fluent/fluent-bit:2.1

      volumeMounts:

        - name: app-logs

          mountPath: /var/log/app



  volumes:

    - name: app-logs

      emptyDir: {}      # Volume temporaire partagé entre conteneurs du pod
Ne déployez jamais un Pod seul en production

Un pod nu n'est pas recréé s'il crash ou si son node tombe. Utilisez toujours un Deployment (pour les applications stateless) ou un StatefulSet (pour les bases de données, queues…). Ces ressources créent et gèrent automatiquement les pods via un ReplicaSet.

Installation locale avec Kind

kind-config.yaml - Cluster multi-nodes avec port mapping
kind: Cluster

apiVersion: kind.x-k8s.io/v1alpha4

name: dev-cluster

nodes:

  - role: control-plane

    # Expose le port 80 du node sur localhost:80 pour l'Ingress

    extraPortMappings:

      - containerPort: 80

        hostPort: 80

      - containerPort: 443

        hostPort: 443

  - role: worker

  - role: worker

Pods statiques vs Pods ordinaires

etcd, kube-apiserver, kube-scheduler et kube-controller-manager sont des static pods : gérés directement par le kubelet du control-plane node, pas par l'API Server lui-même. Ils survivent même si l'API Server redémarre — c'est ce qui rend le cluster auto-réparant.

Étape 2 — Inspecter un composant en détail

bash
# Config complète du kube-apiserver : flags de sécurité, ports, certificats

kubectl describe pod -n kube-system kube-apiserver-k8s-lab-control-plane



# Logs du scheduler : voir comment il choisit les nodes

kubectl logs -n kube-system kube-scheduler-k8s-lab-control-plane --tail=20



# Logs du controller-manager : boucles de réconciliation en action

kubectl logs -n kube-system kube-controller-manager-k8s-lab-control-plane --tail=20

Étape 3 — Inspecter les nodes

bash
# Détail d'un Worker : kubelet version, capacité CPU/RAM, taints, conditions

kubectl describe node k8s-lab-worker



# Vue synthétique de la capacité de chaque node

kubectl get nodes -o custom-columns="NAME:.metadata.name,CPU:.status.capacity.cpu,RAM:.status.capacity.memory,ROLES:.metadata.labels.kubernetes\.io/role"



# Quels pods tournent sur quel node ?

kubectl get pods -n kube-system -o wide --sort-by=.spec.nodeName

Étape 4 — Lancer votre premier Pod et observer le scheduling

Créez un Pod nginx et regardez le scheduler le placer sur un Worker :

bash
# Lancer un pod nginx simple (sans Deployment)

kubectl run web --image=nginx:alpine --restart=Never



# Observer la progression en temps réel : Pending → ContainerCreating → Running

kubectl get pod web -w      # Ctrl+C pour arrêter le watch



# Sur quel node est-il placé ?

kubectl get pod web -o wide

# NAME   READY   STATUS    IP          NODE

# web    1/1     Running   10.244.x.x  k8s-lab-worker



# Lire les Events pour comprendre ce qui s'est passé :

# Scheduled → scheduler a choisi le node

# Pulling   → kubelet télécharge l'image

# Started   → containerd a démarré le conteneur

kubectl describe pod web | tail -20
Le Control Plane n'exécute jamais vos applications

Remarquez que le pod web est sur un Worker, jamais sur le control-plane. Le control-plane node a un taint node-role.kubernetes.io/control-plane:NoSchedule qui empêche les pods applicatifs d'y être placés. C'est une règle de sécurité fondamentale.

Nettoyage

bash
kubectl delete pod web

# En fin de session, supprimer le cluster complet

kind delete cluster --name k8s-lab
