ReplicaSet - La base

Un ReplicaSet garantit qu'un nombre exact de réplicas d'un pod sont en cours d'exécution à tout moment. Si un pod crash, le ReplicaSet en crée un nouveau automatiquement.

replicaset.yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: api-backend
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api-backend
  template:
    metadata:
      labels:
        app: api-backend
    spec:
      containers:
        - name: api
          image: myregistry/api-backend:1.0.0
          ports:
            - containerPort: 8080
En pratique

Vous ne créez presque jamais un ReplicaSet directement. Le Deployment en crée un pour vous et ajoute la gestion des mises à jour.

Deployment - Le workload standard

Le Deployment est la ressource la plus utilisée. Il gère un ReplicaSet et permet les rolling updates, les rollbacks et le scaling.

deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-backend
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api-backend
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
      maxSurge: 1
  template:
    metadata:
      labels:
        app: api-backend
        version: "1.0.0"
    spec:
      containers:
        - name: api
          image: myregistry/api-backend:1.0.0
          ports:
            - containerPort: 8080
          resources:
            requests:
              memory: "256Mi"
              cpu: "250m"
            limits:
              memory: "512Mi"
              cpu: "500m"
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            initialDelaySeconds: 10
          livenessProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            initialDelaySeconds: 30

Rolling Update & Rollback

Le rolling update remplace les pods un par un. À chaque instant, l'application reste disponible :

  Étape 1:  [v1] [v1] [v1]           ← 3 pods v1
  Étape 2:  [v1] [v1] [v1] [v2]     ← maxSurge=1, nouveau pod v2
  Étape 3:  [v1] [v1] [v2]          ← ancien pod supprimé
  Étape 4:  [v1] [v2] [v2]          ← continue...
  Étape 5:  [v2] [v2] [v2]          ← migration terminée
bash - Mise à jour et rollback
# Mettre à jour l'image
kubectl set image deployment/api-backend api=myregistry/api-backend:1.1.0

# Suivre le déploiement
kubectl rollout status deployment/api-backend

# Historique des versions
kubectl rollout history deployment/api-backend

# Rollback à la version précédente
kubectl rollout undo deployment/api-backend

# Rollback à une révision spécifique
kubectl rollout undo deployment/api-backend --to-revision=2

# Scaling manuel
kubectl scale deployment/api-backend --replicas=5

StatefulSet - Pour les workloads avec état

Le StatefulSet est conçu pour les applications avec état : bases de données, caches, systèmes de messaging. Contrairement au Deployment, il garantit :

  • Identité stable - Noms de pod prédictibles : postgres-0, postgres-1, postgres-2
  • Déploiement ordonné - Les pods sont créés séquentiellement (0 → 1 → 2)
  • Stockage persistant - Chaque pod a son propre PVC qui survit aux redémarrages
statefulset-postgres.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres-headless
  replicas: 1
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
        - name: postgres
          image: postgres:16-alpine
          ports:
            - containerPort: 5432
          env:
            - name: POSTGRES_DB
              value: "app_db"
            - name: POSTGRES_USER
              valueFrom:
                secretKeyRef:
                  name: postgres-credentials
                  key: username
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: postgres-credentials
                  key: password
          volumeMounts:
            - name: postgres-storage
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
    - metadata:
        name: postgres-storage
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 10Gi

DaemonSet, Job & CronJob

DaemonSet

Exécute exactement un pod par node. Utilisé pour les agents de monitoring, collecteurs de logs, ou plugins réseau.

Job

Exécute un pod jusqu'à complétion. Idéal pour les migrations de base de données, les tâches batch, etc.

migration-job.yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migration
spec:
  backoffLimit: 3
  template:
    spec:
      restartPolicy: OnFailure
      containers:
        - name: migrate
          image: myregistry/api-backend:1.1.0
          command: ["java", "-jar", "app.jar", "--spring.flyway.enabled=true"]
          env:
            - name: SPRING_DATASOURCE_URL
              value: "jdbc:postgresql://postgres-headless:5432/app_db"

CronJob

Exécute un Job selon un planning cron. Exemple : sauvegarde quotidienne de la base de données.

backup-cronjob.yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: db-backup
spec:
  schedule: "0 2 * * *"    # Tous les jours à 2h du matin
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: postgres:16-alpine
              command:
                - /bin/sh
                - -c
                - pg_dump -h postgres-headless -U app_user app_db > /backup/dump_$(date +%Y%m%d).sql
              volumeMounts:
                - name: backup-volume
                  mountPath: /backup
          volumes:
            - name: backup-volume
              persistentVolumeClaim:
                claimName: backup-pvc

Travaux Pratiques - Workloads Kubernetes

Prérequis : Cluster Kind k8s-lab en cours d'exécution (voir Leçon 3 - Lab 1). Ces exercices couvrent les workloads essentiels : Deployment, self-healing et rolling update.

Lab 1 Déployer une application avec 3 réplicas ~15 min

Objectifs

  • Créer un Deployment multi-réplicas
  • Vérifier la distribution des pods sur les worker nodes
  • Observer le ReplicaSet créé automatiquement
httpbin-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: httpbin
  namespace: default
spec:
  replicas: 3
  selector:
    matchLabels:
      app: httpbin
  template:
    metadata:
      labels:
        app: httpbin
    spec:
      containers:
        - name: httpbin
          image: kennethreitz/httpbin:latest
          ports:
            - containerPort: 80
          resources:
            requests:
              memory: "64Mi"
              cpu: "50m"
            limits:
              memory: "128Mi"
              cpu: "200m"
bash
kubectl apply -f httpbin-deployment.yaml

# Voir les 3 pods et sur quel node ils tournent
kubectl get pods -o wide

# Voir le ReplicaSet créé automatiquement
kubectl get replicaset

# Accéder à l'app
kubectl port-forward deployment/httpbin 8080:80
# → http://localhost:8080
✓ Résultat attendu

3 pods Running, répartis entre les 2 workers. Un ReplicaSet httpbin-xxxxxxx apparaît avec DESIRED=3 CURRENT=3 READY=3.

Lab 2 Observer le Self-Healing en action ~10 min

Objectifs

  • Confirmer que Kubernetes ne laisse jamais un pod mort
  • Tuer un pod manuellement et observer sa recréation immédiate
  • Simuler la panne d'un node entier
bash - Terminal 1 : observer en temps réel
kubectl get pods -w
bash - Terminal 2 : tuer un pod
# Récupérer le nom d'un pod
kubectl get pods

# Le supprimer (simule un crash)
kubectl delete pod <nom-du-pod>

# Dans le Terminal 1 vous verrez :
# httpbin-xxx   Terminating
# httpbin-yyy   Pending → ContainerCreating → Running   ← recréé automatiquement
bash - Simuler la panne d'un node
# Stopper le conteneur Docker d'un worker (simule une panne machine)
docker stop k8s-lab-worker

# Attendre ~1 min
kubectl get nodes
# k8s-lab-worker   NotReady

kubectl get pods -o wide
# Les pods du worker tombé sont re-schedulés sur worker2

# Redémarrer le node
docker start k8s-lab-worker
✓ Résultat attendu

Le cluster maintient toujours 3 pods Running. Même avec un node en panne, K8s replace les pods sur les nodes disponibles. C'est la boucle de réconciliation en action.

Lab 3 Rolling Update & Rollback sans downtime ~15 min

Objectifs

  • Mettre à jour une application sans interruption de service
  • Observer le remplacement progressif des pods
  • Faire un rollback instantané en cas de problème
bash - Terminal 1 : watcher
kubectl get pods -l app=httpbin -w
bash - Terminal 2 : mise à jour et rollback
# Changer l'image (simule une nouvelle version)
kubectl set image deployment/httpbin httpbin=nginx:1.25

# Suivre le déploiement
kubectl rollout status deployment/httpbin

# Consulter l'historique
kubectl rollout history deployment/httpbin

# Rollback immédiat vers la version précédente
kubectl rollout undo deployment/httpbin

# Vérifier
kubectl describe deployment/httpbin | grep Image
✓ Résultat attendu

Les pods sont remplacés un à un. L'application reste disponible pendant toute la durée du déploiement. Le rollback remet l'image précédente en quelques secondes.
