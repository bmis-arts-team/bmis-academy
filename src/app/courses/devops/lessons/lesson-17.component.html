Le contexte : votre système actuel

Vous avez une application en production qui fonctionne - mais sur une architecture fragile. Cette leçon marque le début d'une migration complète vers Kubernetes, en partant d'un système réel déployé sur un VPS unique.

Ce que vous avez aujourd'hui
  • Frontend : Angular (web) + Flutter (2 apps mobiles)
  • Backend : Spring Boot monolithe (JAR)
  • Données : PostgreSQL + Redis
  • Infra : VPS Hostinger KVM8, NGINX reverse proxy, systemd, GitHub Actions CI/CD
  • Pas de Docker, pas de Kubernetes
Les problèmes de cette architecture
  • Pas d'isolation entre les services - un crash peut tout affecter
  • Scaling impossible sans intervention manuelle lourde
  • Rollback = redéployer manuellement l'ancien JAR
  • Aucune observabilité centralisée
  • Un seul environnement (prod) - pas de staging

L'objectif de ce chapitre : migrer vers une architecture conteneurisée orchestrée par Kubernetes (k3s), avec 3 environnements (dev, staging, prod), de l'autoscaling, de l'observabilité et un vrai pipeline CI/CD.

Pourquoi 3 repos ?
  • Indépendance - Un fix CSS ne redéploie pas le backend Java
  • Permissions - L'équipe front n'a pas besoin d'accéder aux Secrets K8s
  • CI/CD scopé - Chaque repo a son propre workflow GitHub Actions
  • Infra as Code - Les manifestes K8s sont versionnés séparément, modifiables sans rebuild
Alternative : sans repo infra

Si un 3ème repo vous semble excessif, placez le dossier k8s/ dans le repo backend. Les workflows utilisent kubectl set image qui ne nécessite pas d'accéder aux YAML - seul le déploiement initial demande un kubectl apply -k.

Dockerfile Spring Boot - Production-Grade

Le Dockerfile du backend utilise un multi-stage build pour séparer la compilation de l'image finale. L'astuce clé : copier les fichiers de dépendances avant le code source pour exploiter le cache Docker.

backend/Dockerfile
# ============================================
# STAGE 1 : Build avec Maven
# ============================================
FROM eclipse-temurin:21-jdk AS build

WORKDIR /app

# 1. Copier UNIQUEMENT les fichiers de dépendances
#    → Ce layer est mis en cache tant que pom.xml ne change pas
COPY pom.xml mvnw ./
COPY .mvn .mvn

# 2. Télécharger toutes les dépendances (layer cachée)
RUN chmod +x mvnw && ./mvnw dependency:go-offline -B

# 3. Copier le code source (invalide le cache uniquement ici)
COPY src src

# 4. Build le JAR sans les tests (on les exécute dans le CI)
RUN ./mvnw package -DskipTests -B

# ============================================
# STAGE 2 : Image finale minimale
# ============================================
FROM eclipse-temurin:21-jre-alpine

WORKDIR /app

# Créer un utilisateur non-root pour la sécurité
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

# Copier le JAR depuis le stage de build
COPY --from=build /app/target/*.jar app.jar

# Changer pour l'utilisateur non-root
USER appuser

# Port exposé (documentation)
EXPOSE 8080

# Health check intégré
HEALTHCHECK --interval=30s --timeout=3s --start-period=40s \
  CMD wget -qO- http://localhost:8080/actuator/health || exit 1

# Démarrage avec options JVM optimisées pour les conteneurs
ENTRYPOINT ["java", \
  "-XX:+UseContainerSupport", \
  "-XX:MaxRAMPercentage=75.0", \
  "-Djava.security.egd=file:/dev/./urandom", \
  "-jar", "app.jar"]

Pourquoi chaque instruction compte

Optimisations Build

  • dependency:go-offline - Télécharge tout en un layer caché
  • -DskipTests - Les tests sont dans le CI, pas dans le build Docker
  • -B (batch mode) - Pas d'output interactif = logs plus propres

Optimisations Runtime

  • jre-alpine - ~200 MB au lieu de ~800 MB avec le JDK
  • USER appuser - Jamais root en production
  • UseContainerSupport - La JVM respecte les cgroups du conteneur
  • MaxRAMPercentage=75% - Laisse 25% au système

Dockerfile Angular - Build + NGINX + Config Runtime

Angular produit des fichiers statiques (HTML, CSS, JS). En production, Node.js n'est plus nécessaire. On utilise NGINX comme serveur web ultra-léger.

Le piège classique : les URLs d'API figées dans le build

Angular compile les fichiers environment.ts dans le bundle JS au moment du build. Si vous faites ng build --configuration=production, l'URL de l'API prod est codée en dur dans le JS. Résultat : vous devez rebuilder une image Docker différente pour chaque environnement → ça casse le principe "build once, deploy anywhere".

La solution : configuration runtime via environment.json

Au lieu d'utiliser les environment.ts d'Angular, on charge un fichier environment.json au démarrage de l'application. Ce fichier est injecté au lancement du conteneur via des variables d'environnement — une seule image Docker pour tous les environnements.

1. Le service de configuration Angular

frontend/src/app/core/services/app-config.service.ts
import { Injectable } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { firstValueFrom } from 'rxjs';

export interface AppConfig {
  apiUrl: string;
  environment: string;
}

@Injectable({ providedIn: 'root' })
export class AppConfigService {
  private config!: AppConfig;

  constructor(private http: HttpClient) {}

  // Appelé au démarrage de l'app via APP_INITIALIZER
  async loadConfig(): Promise<void> {
    this.config = await firstValueFrom(
      this.http.get<AppConfig>('/assets/environment.json')
    );
  }

  get apiUrl(): string {
    return this.config.apiUrl;
  }

  get environment(): string {
    return this.config.environment;
  }
}
frontend/src/app/app.config.ts — Charger la config au démarrage
import { APP_INITIALIZER, ApplicationConfig } from '@angular/core';
import { AppConfigService } from './core/services/app-config.service';

export const appConfig: ApplicationConfig = {
  providers: [
    {
      provide: APP_INITIALIZER,
      useFactory: (configService: AppConfigService) =>
        () => configService.loadConfig(),
      deps: [AppConfigService],
      multi: true,
    },
    // ... vos autres providers
  ],
};
frontend/src/assets/environment.json — Valeurs par défaut (dev local)
{
  "apiUrl": "http://localhost:8080",
  "environment": "development"
}
Comment ça fonctionne ?

Au lieu de environment.apiUrl, vos services utilisent appConfigService.apiUrl. Le fichier environment.json est chargé via HTTP au démarrage (avant le rendu du premier composant). En dev local, il lit le fichier statique. En conteneur, NGINX le génère dynamiquement au lancement.

2. Le Dockerfile avec injection de config

frontend/Dockerfile
# ============================================
# STAGE 1 : Build Angular
# ============================================
FROM node:20-alpine AS build

WORKDIR /app

# 1. Copier les fichiers de dépendances d'abord (cache)
COPY package.json package-lock.json ./

# 2. Installer les dépendances (layer cachée)
RUN npm ci --no-audit

# 3. Copier le code source
COPY . .

# 4. Build production (UNE SEULE image pour tous les envs)
RUN npm run build -- --configuration=production

# ============================================
# STAGE 2 : Servir avec NGINX
# ============================================
FROM nginx:alpine

# Copier la config NGINX personnalisée
COPY nginx.conf /etc/nginx/conf.d/default.conf

# Copier les fichiers buildés depuis le stage précédent
COPY --from=build /app/dist/frontend/browser /usr/share/nginx/html

# Copier le script d'injection de config
COPY docker-entrypoint.sh /docker-entrypoint.sh
RUN chmod +x /docker-entrypoint.sh

# Variables d'environnement avec valeurs par défaut
ENV API_URL=http://localhost:8080
ENV APP_ENV=production

# Port exposé
EXPOSE 80

# Le script génère environment.json puis lance NGINX
ENTRYPOINT ["/docker-entrypoint.sh"]

3. Le script d'entrypoint

frontend/docker-entrypoint.sh
#!/bin/sh

# Générer environment.json à partir des variables d'environnement
cat > /usr/share/nginx/html/assets/environment.json <<EOF
{
  "apiUrl": "$API_URL",
  "environment": "$APP_ENV"
}
EOF

echo "Config generated: API_URL=$API_URL, APP_ENV=$APP_ENV"

# Lancer NGINX en foreground
exec nginx -g "daemon off;"
Résultat : UNE image, TOUS les environnements

frontend/nginx.conf
server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;

    # Compression GZIP
    gzip on;
    gzip_types text/plain text/css application/json
               application/javascript text/xml application/xml
               application/xml+rss text/javascript;
    gzip_min_length 1000;

    # Cache agressif pour les assets hashés (main.abc123.js)
    location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff2?)$ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # PAS de cache pour environment.json (il change par environnement)
    location = /assets/environment.json {
        add_header Cache-Control "no-cache, no-store, must-revalidate";
    }

    # SPA fallback : toute route inconnue → index.html
    location / {
        try_files $uri $uri/ /index.html;
    }

    # Désactiver le cache pour index.html (toujours frais)
    location = /index.html {
        add_header Cache-Control "no-cache, no-store, must-revalidate";
    }

    # Health check
    location /health {
        return 200 'ok';
        add_header Content-Type text/plain;
    }
}

Taille des images

Avec le multi-stage build, l'image Angular fait environ 25-40 MB (nginx:alpine + fichiers statiques). L'image Spring Boot fait environ 200-250 MB (JRE Alpine + JAR). Comparez avec une image Ubuntu + JDK qui ferait 800+ MB.
