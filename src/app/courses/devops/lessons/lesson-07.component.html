Le défi du stockage dans Kubernetes

Les conteneurs sont éphémères, mais les bases de données ont besoin de persistance. Kubernetes résout ce problème avec un système en trois couches :

  Pod (consommateur)
    │
    └──▶ PVC (PersistentVolumeClaim) ─── "Je veux 10Gi en RWO"
           │
           └──▶ PV (PersistentVolume) ─── Disque réel (EBS, GCE PD, NFS)
                  │
                  └──▶ StorageClass ─── Provisionneur dynamique

PersistentVolume (PV)

Un PV représente un disque physique dans le cluster. Il est créé par l'administrateur ou dynamiquement par une StorageClass.

pv.yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: postgres-pv
spec:
  capacity:
    storage: 20Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: standard
  hostPath:
    path: /data/postgres    # Dev local uniquement
Access ModeAbréviationDescription
ReadWriteOnceRWOUn seul node en lecture/écriture
ReadOnlyManyROXPlusieurs nodes en lecture seule
ReadWriteManyRWXPlusieurs nodes en lecture/écriture (NFS, CephFS)

PersistentVolumeClaim (PVC)

Un PVC est une demande de stockage par un pod. Kubernetes trouve un PV compatible ou en provisionne un dynamiquement.

pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
  storageClassName: standard
deployment.yaml - utilisation du PVC
spec:
  containers:
    - name: postgres
      image: postgres:16-alpine
      volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: postgres-pvc

StorageClass - Provisionnement dynamique

La StorageClass automatise la création de PV. Plus besoin de pré-créer des disques manuellement.

storageclass.yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: kubernetes.io/aws-ebs    # ou pd.csi.storage.gke.io
parameters:
  type: gp3
  iopsPerGB: "50"
reclaimPolicy: Retain
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
WaitForFirstConsumer

Ce mode retarde la création du disque jusqu'à ce qu'un pod le demande. Cela garantit que le disque est créé dans la même zone de disponibilité que le pod.

Namespaces - Isolation logique

Les namespaces divisent un cluster en espaces logiques isolés. Chaque namespace a ses propres ressources, quotas et politiques d'accès.

namespace.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:
    environment: production
---
apiVersion: v1
kind: ResourceQuota
metadata:
  name: production-quota
  namespace: production
spec:
  hard:
    requests.cpu: "8"
    requests.memory: 16Gi
    limits.cpu: "16"
    limits.memory: 32Gi
    pods: "50"
Organisation recommandée
  • default - Ne pas utiliser en production
  • kube-system - Composants système (DNS, proxy, etc.)
  • staging - Environnement de pré-production
  • production - Environnement live
  • monitoring - Prometheus, Grafana, ELK

Travaux Pratiques — Stockage & Namespaces

Prérequis : Cluster Kind k8s-lab. Ces labs couvrent la persistance des données avec les PersistentVolumeClaims et l'isolation entre environnements avec les namespaces.

Lab 1 PersistentVolumeClaim avec PostgreSQL ~20 min

Objectifs

  • Créer un PVC et le monter dans un pod PostgreSQL
  • Insérer des données, supprimer le pod et vérifier la persistance
  • Observer le cycle de vie du PVC indépendamment du pod
postgres-pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-pvc
  namespace: default
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
  storageClassName: standard   # StorageClass fournie par Kind
---
apiVersion: v1
kind: Pod
metadata:
  name: postgres
  namespace: default
spec:
  containers:
    - name: postgres
      image: postgres:16-alpine
      env:
        - name: POSTGRES_DB
          value: myapp
        - name: POSTGRES_USER
          value: dev
        - name: POSTGRES_PASSWORD
          value: devpass
      volumeMounts:
        - name: pgdata
          mountPath: /var/lib/postgresql/data
  volumes:
    - name: pgdata
      persistentVolumeClaim:
        claimName: postgres-pvc
bash
kubectl apply -f postgres-pvc.yaml

# Vérifier que le PVC est Bound
kubectl get pvc
# NAME           STATUS   VOLUME       CAPACITY
# postgres-pvc   Bound    pvc-xxx...   1Gi

# Créer des données
kubectl exec -it postgres -- psql -U dev -d myapp
# CREATE TABLE demo (id SERIAL, val TEXT);
# INSERT INTO demo(val) VALUES ('test-persistance');
# \q

# Supprimer le pod (PAS le PVC)
kubectl delete pod postgres

# Recréer le pod
kubectl apply -f postgres-pvc.yaml

# Les données sont toujours là !
kubectl exec -it postgres -- psql -U dev -d myapp -c "SELECT * FROM demo;"
✓ Résultat attendu

Après suppression et recréation du pod, la table demo et ses données existent toujours. Le PVC survit indépendamment du cycle de vie des pods.

Lab 2 Isoler des environnements avec les namespaces ~10 min

Objectifs

  • Créer des namespaces staging et production
  • Déployer la même app dans les deux, confirmer l'isolation
  • Appliquer un ResourceQuota sur staging
bash
kubectl create namespace staging
kubectl create namespace production

# Déployer httpbin dans les deux namespaces
kubectl create deployment httpbin --image=kennethreitz/httpbin -n staging
kubectl create deployment httpbin --image=kennethreitz/httpbin -n production

# Les pods de staging ne voient PAS ceux de production
kubectl get pods -n staging
kubectl get pods -n production

# Appliquer un quota sur staging
kubectl apply -f - <<EOF
apiVersion: v1
kind: ResourceQuota
metadata:
  name: staging-quota
  namespace: staging
spec:
  hard:
    pods: "5"
    requests.cpu: "1"
    requests.memory: "1Gi"
EOF

# Vérifier le quota
kubectl describe resourcequota staging-quota -n staging
✓ Résultat attendu

Les deux déploiements coexistent sans interférence. Toute tentative de dépasser le quota dans staging est bloquée par Kubernetes avec un message d'erreur clair.
