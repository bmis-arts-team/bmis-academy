Le problème de la persistance

Par défaut, les données d'un conteneur sont éphémères. Quand un conteneur est supprimé, toutes les données écrites dans son filesystem disparaissent. Pour les bases de données et le stockage de fichiers, c'est inacceptable.

  Container (lecture/écriture)
  ├── /app/data     ← Perdu à la suppression !
  └── /var/lib/...  ← Perdu aussi !

  Volume Docker (persistant)
  ├── /var/lib/postgresql/data  ← Survit au conteneur
  └── /data/redis               ← Survit aussi

Types de volumes Docker

TypeSyntaxeUsagePersistant
Named Volume-v my-data:/dataBases de données, fichiers applicatifs✅ Oui
Bind Mount-v ./src:/app/srcDéveloppement local (hot-reload)✅ Oui
tmpfs--tmpfs /tmpDonnées temporaires sensibles❌ Non
Règle d'or

En production, utilisez toujours des named volumes. Les bind mounts sont réservés au développement.

Volumes en pratique - PostgreSQL

bash
# Créer un named volume
docker volume create postgres-data

# Lancer PostgreSQL avec le volume
docker run -d \
  --name my-postgres \
  -e POSTGRES_DB=app_db \
  -e POSTGRES_USER=app_user \
  -e POSTGRES_PASSWORD=secret \
  -v postgres-data:/var/lib/postgresql/data \
  -p 5432:5432 \
  postgres:16-alpine

# Vérifier le volume
docker volume inspect postgres-data

Même après docker rm my-postgres, les données persistent dans le volume postgres-data.

Volumes en pratique - Redis

bash
docker run -d \
  --name my-redis \
  -v redis-data:/data \
  -p 6379:6379 \
  redis:7-alpine \
  redis-server --appendonly yes --maxmemory 256mb
AOF vs RDB

--appendonly yes active l'Append Only File pour une persistance durable. Redis écrit chaque opération dans un fichier journal. Combinez avec des snapshots RDB pour un équilibre performance/durabilité.

Docker Networking - Les fondamentaux

Docker offre plusieurs drivers réseau pour connecter les conteneurs entre eux et avec l'extérieur.

DriverDescriptionUsage
bridgeRéseau privé isoléCommunication entre conteneurs sur un même hôte
hostPartage le réseau de l'hôtePerformance maximale (pas de NAT)
overlayRéseau multi-hôtesDocker Swarm, clusters
nonePas de réseauConteneurs totalement isolés

DNS intégré

Dans un réseau bridge personnalisé, Docker fournit un serveur DNS intégré. Les conteneurs peuvent se résoudre par nom :

bash
# Créer un réseau
docker network create app-network

# Lancer les services sur le même réseau
docker run -d --name postgres --network app-network postgres:16-alpine
docker run -d --name redis --network app-network redis:7-alpine
docker run -d --name api --network app-network \
  -e SPRING_DATASOURCE_URL=jdbc:postgresql://postgres:5432/app_db \
  -e SPRING_DATA_REDIS_HOST=redis \
  my-api:1.0.0
Résolution DNS

Le conteneur api peut atteindre PostgreSQL via postgres:5432 et Redis via redis:6379. Le DNS résout automatiquement les noms des conteneurs en adresses IP.

Architecture réseau multi-services

              ┌──── app-network (bridge) ────┐
              │                               │
  ┌───────┐   │  ┌─────────┐  ┌───────────┐  │
  │Client ├───┼─▶│  API    ├─▶│ PostgreSQL│  │

    :8080     │  └────┬────┘  └───────────┘  │
              │       │                       │
              │       ▼                       │
              │  ┌─────────┐                  │
              │  │  Redis  │                  │
              │  │  :6379  │                  │
              │  └─────────┘                  │
              └───────────────────────────────┘
Sécurité réseau

Ne publiez pas les ports des services internes (PostgreSQL, Redis) vers l'hôte. Seul le service exposé aux utilisateurs (API, reverse proxy) doit avoir un mapping -p.
