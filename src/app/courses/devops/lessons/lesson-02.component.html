Comprendre le filesystem d'un conteneur

Dans la leçon précédente, nous avons vu qu'une image Docker est composée de couches (layers) en lecture seule. Lorsque vous démarrez un conteneur à partir de cette image, Docker ajoute automatiquement une couche supplémentaire au-dessus : la couche d'écriture (writable layer). C'est dans cette couche que toutes les modifications apportées au filesystem du conteneur sont stockées - nouveaux fichiers, modifications, suppressions.

Ce mécanisme est géré par OverlayFS (le driver de stockage par défaut de Docker). Il présente les couches en lecture seule et la couche d'écriture comme un seul filesystem unifié, transparent pour les processus du conteneur.

Copy-on-Write (CoW)

Quand un processus du conteneur modifie un fichier existant dans une couche inférieure (lecture seule), OverlayFS copie d'abord le fichier dans la writable layer puis applique la modification - sans toucher aux couches de l'image. C'est pourquoi plusieurs conteneurs peuvent partager la même image sans interférer.

Le problème de la persistance

Le problème vient du fait que la writable layer est liée au cycle de vie du conteneur. Quand vous exécutez docker rm mon-conteneur, cette couche est supprimée définitivement avec toutes les données qu'elle contient. Pour une API sans état, ça n'est pas un problème. Mais pour une base de données ou un service de fichiers, c'est inacceptable.

Un volume est un mécanisme qui permet de monter un répertoire externe (géré par Docker ou issu de l'hôte) dans le filesystem du conteneur. Les données écrites dans ce répertoire contournent la writable layer et persistent indépendamment du cycle de vie du conteneur.

Les drivers de volumes - qu'est-ce que c'est ?

Tout comme les drivers réseau déterminent comment Docker connecte les conteneurs, un driver de volume détermine où et comment Docker stocke physiquement les données d'un volume. Par défaut, Docker utilise le driver local qui écrit sur le disque de la machine hôte. Mais selon l'infrastructure - serveur unique, cloud, cluster - d'autres drivers permettent de stocker les données sur un NAS, un bucket S3, un système de fichiers distribué, etc.

Vous choisissez le driver au moment de déclarer le volume, avec l'option --driver (ou -d). En Docker Compose, c'est la clé driver: sous la déclaration du volume.

bash
# Créer un volume avec un driver explicite
docker volume create --driver local    my-data      # disque local (défaut)
docker volume create --driver nfs      my-nfs-data  # partage NFS distant
docker volume create --driver vieux/sshfs my-remote # dossier SSH distant (plugin)

# En Docker Compose
volumes:
  my-data:
    driver: local   # explicite mais équivalent à ne rien mettre

Driver local avec options NFS - exemple concret

Le driver local accepte des options de montage Linux directement dans Docker Compose :

docker-compose.yml
volumes:
  uploads-data:
    driver: local
    driver_opts:
      type: nfs
      o: addr=192.168.1.100,rw,nfsvers=4   # IP du NAS, lecture/écriture, NFS v4
      device: ":/volume1/app-uploads"       # chemin exporté sur le NAS
Quel driver choisir ?

Pour un serveur unique ou un VPS, local est le bon choix dans 95% des cas. N'utilisez un driver tiers que si vous avez un besoin concret de stockage partagé entre plusieurs machines (cluster) ou de persistance indépendante de l'hôte (cloud). En Kubernetes, les volumes sont gérés par des PersistentVolumes et des StorageClasses - les drivers Docker ne s'appliquent plus.

Volumes en pratique - PostgreSQL

bash
# Créer un named volume
docker volume create postgres-data

# Lancer PostgreSQL avec le volume
docker run -d \
  --name my-postgres \
  -e POSTGRES_DB=app_db \
  -e POSTGRES_USER=app_user \
  -e POSTGRES_PASSWORD=secret \
  -v postgres-data:/var/lib/postgresql/data \
  -p 5432:5432 \
  postgres:16-alpine

# Vérifier le volume
docker volume inspect postgres-data

Même après docker rm my-postgres, les données persistent dans le volume postgres-data.

Volumes en pratique - Redis

bash
docker run -d \
  --name my-redis \
  -v redis-data:/data \
  -p 6379:6379 \
  redis:7-alpine \
  redis-server --appendonly yes --maxmemory 256mb
AOF vs RDB

--appendonly yes active l'Append Only File pour une persistance durable. Redis écrit chaque opération dans un fichier journal. Combinez avec des snapshots RDB pour un équilibre performance/durabilité.

Comprendre l'isolation réseau de Docker

Quand Docker démarre, il crée une interface réseau virtuelle sur l'hôte appelée docker0. C'est un commutateur (switch) logiciel qui joue le rôle de passerelle entre les conteneurs et l'extérieur. Par défaut, chaque conteneur lancé sans option --network est connecté à ce réseau bridge par défaut.

Chaque conteneur reçoit sa propre adresse IP privée dans le sous-réseau du bridge. Pour communiquer, les conteneurs passent par docker0 qui fait du NAT (Network Address Translation) vers l'extérieur. C'est pourquoi, sans publier de port, un conteneur est accessible depuis l'hôte mais pas depuis l'extérieur.

Publication de ports (-p)

L'option -p 8080:80 demande à Docker d'ajouter une règle iptables sur l'hôte : tout trafic arrivant sur le port 8080 de l'hôte est redirigé vers le port 80 du conteneur. Le conteneur lui-même n'est pas conscient de ce mapping - il écoute toujours sur son port 80.

Le problème du bridge par défaut

Quand vous lancez un conteneur sans préciser de réseau, Docker le connecte automatiquement au réseau bridge par défaut. Ce réseau a une limitation majeure : il n'a pas de serveur DNS, donc les conteneurs ne peuvent pas se résoudre par nom. Ils ne connaissent que les adresses IP, qui changent à chaque redémarrage du conteneur. Pour faire communiquer une API avec sa base de données, c'est ingérable.

La solution est de créer manuellement un réseau bridge personnalisé avec docker network create, puis de rattacher explicitement chaque conteneur à ce réseau via l'option --network. Ce n'est pas automatique : si vous oubliez --network sur un conteneur, il tombe dans le bridge par défaut et ne sera pas visible par les autres.

bash
# Étape 1 - créer le réseau (une seule fois)
docker network create app-network

# Étape 2 - rattacher chaque conteneur à ce réseau avec --network
docker run -d --name postgres --network app-network postgres:16-alpine
docker run -d --name redis    --network app-network redis:7-alpine
docker run -d --name api      --network app-network my-api:1.0.0

# Sans --network, le conteneur va dans le bridge par défaut
# et ne verra pas postgres ni redis !

Une fois tous les conteneurs sur le même réseau personnalisé, Docker active automatiquement un serveur DNS embarqué qui enregistre chaque conteneur sous son --name comme entrée DNS. Les conteneurs se trouvent donc par nom, de façon stable.

Les drivers réseau - qu'est-ce que c'est ?

Un driver réseau est le composant qui détermine comment Docker construit et gère le réseau d'un conteneur au niveau du système d'exploitation. Concrètement, quand vous créez un réseau avec docker network create, Docker délègue la création des interfaces virtuelles, les règles de routage et l'isolation à un driver. C'est lui qui décide :

  • comment les paquets transitent entre les conteneurs,
  • si le conteneur est isolé de l'hôte ou non,
  • si la communication peut traverser plusieurs machines physiques.

Vous choisissez le driver au moment de créer le réseau, avec l'option --driver (ou -d). Si vous ne précisez rien, Docker utilise bridge par défaut.

bash
# Créer un réseau avec un driver explicite
docker network create --driver bridge app-network
docker network create --driver host   host-network   # rarement utile en pratique
docker network create --driver overlay swarm-network  # requiert Docker Swarm

# Sans --driver, bridge est utilisé automatiquement
docker network create app-network  # équivalent à --driver bridge

Les quatre drivers disponibles

DriverCe que fait concrètement DockerQuand l'utiliserExemple applicatif
bridge Crée une interface réseau virtuelle (docker0 ou une interface nommée) sur l'hôte. Chaque conteneur reçoit une IP privée dans ce sous-réseau. Les paquets sortants passent par du NAT pour accéder à l'extérieur. Les conteneurs du même réseau se voient directement. Cas standard - tous vos services tournent sur un seul hôte Une API Spring Boot, une base PostgreSQL et un Redis qui tournent ensemble sur votre serveur de développement ou un petit VPS
host Supprime toute isolation réseau. Le conteneur utilise directement les interfaces réseau de l'hôte (eth0, lo…). Il n'y a ni interface virtuelle, ni NAT, ni sous-réseau séparé. Un service qui écoute sur le port 8080 du conteneur écoute sur le port 8080 de la machine physique. Performance critique (le NAT a un coût), outils de monitoring qui doivent voir le réseau hôte Prometheus Node Exporter qui collecte les métriques réseau réelles de la machine hôte, ou un proxy Nginx à très haut trafic où le surcoût du NAT est mesurable
overlay Crée un réseau virtuel qui s'étend sur plusieurs machines physiques en encapsulant les paquets dans du VXLAN (UDP port 4789). Les conteneurs sur des hôtes différents se voient comme s'ils étaient sur le même réseau local. Nécessite Docker Swarm ou un orchestrateur compatible. Clusters multi-hôtes, Docker Swarm - pas utile en dehors de ce contexte Un cluster Docker Swarm de 5 nœuds où les réplicas d'un service web (sur les nœuds 1, 2, 3) doivent communiquer avec une base de données (nœud 4) comme s'ils étaient sur le même LAN
none Docker ne crée aucune interface réseau dans le conteneur (seulement lo, la loopback locale). Le conteneur ne peut ni envoyer ni recevoir de trafic réseau depuis l'extérieur. Traitements isolés (calcul, compression, chiffrement), sécurité maximale Un job de génération de rapport PDF à partir de données déjà injectées en volume - il n'a aucune raison d'accéder au réseau, l'isoler réduit la surface d'attaque
Quel driver choisir ?

Dans 90% des cas, bridge personnalisé est le bon choix. N'utilisez host que si vous avez mesuré un problème de performance lié au NAT. overlay est réservé aux environnements Swarm.

Kubernetes n'utilise pas ces drivers Docker. Il gère son propre modèle réseau via un plugin CNI (Container Network Interface) - Calico, Flannel, Cilium. Ce sont ces plugins qui prennent en charge la communication entre pods, y compris sur plusieurs nœuds. Vous n'avez donc pas à choisir un driver Docker dans un cluster Kubernetes.

Créer et utiliser un réseau bridge personnalisé

bash
# Créer un réseau dédié à l'application
docker network create app-network

# Inspecter le réseau (sous-réseau, passerelle, conteneurs connectés)
docker network inspect app-network

# Lancer les services sur ce réseau - ils se voient par nom
docker run -d --name postgres --network app-network postgres:16-alpine
docker run -d --name redis    --network app-network redis:7-alpine
docker run -d --name api      --network app-network \
  -e SPRING_DATASOURCE_URL=jdbc:postgresql://postgres:5432/app_db \
  -e SPRING_DATA_REDIS_HOST=redis \
  -p 8080:8080 \
  my-api:1.0.0

Notez que seul le conteneur api expose un port vers l'hôte (-p 8080:8080). postgres et redis n'ont aucun port publié - ils sont accessibles uniquement depuis l'intérieur du réseau app-network, ce qui est la bonne pratique.

Résolution DNS en pratique

Dans la variable d'environnement SPRING_DATASOURCE_URL, on utilise directement postgres comme hostname. Docker DNS traduit ce nom en l'IP courante du conteneur postgres. Si vous redémarrez ce conteneur (nouvelle IP), la résolution reste valide - ce qui ne serait pas le cas avec une IP codée en dur.

Architecture réseau multi-services

Règle de sécurité fondamentale

Ne publiez jamais les ports de vos services internes (postgres, redis) vers l'hôte avec -p. Un port publié est accessible depuis n'importe quelle machine sur le réseau de l'hôte. Vos bases de données ne doivent être joignables que depuis les conteneurs applicatifs, via le réseau Docker interne.

Travaux Pratiques - Volumes & Réseau Docker

Prérequis : Docker Desktop installé. Ces labs montrent comment persister les données d'une base de données et faire communiquer plusieurs conteneurs via un réseau Docker nommé.

Lab 1 PostgreSQL avec persistance de données ~15 min

Objectifs

  • Lancer PostgreSQL dans un conteneur avec un volume nommé
  • Créer une table et insérer des données
  • Redémarrer le conteneur et vérifier que les données persistent

Étape 1 - Lancer PostgreSQL avec un volume

bash
# Créer le volume nommé (géré par Docker)
docker volume create pg-data

# Lancer PostgreSQL
docker run -d \
  --name postgres-dev \
  -e POSTGRES_DB=myapp \
  -e POSTGRES_USER=dev \
  -e POSTGRES_PASSWORD=devpass \
  -v pg-data:/var/lib/postgresql/data \
  -p 5432:5432 \
  postgres:16-alpine

docker ps  # vérifier qu'il tourne

Étape 2 - Créer des données

bash
# Se connecter à psql dans le conteneur
docker exec -it postgres-dev psql -U dev -d myapp

-- Dans psql :
CREATE TABLE users (id SERIAL PRIMARY KEY, name TEXT);
INSERT INTO users (name) VALUES ('Alice'), ('Bob');
SELECT * FROM users;
-- id | name
-- 1  | Alice
-- 2  | Bob
\q

Étape 3 - Redémarrer et vérifier la persistance

bash
# Supprimer le conteneur (PAS le volume)
docker rm -f postgres-dev

# Relancer avec le même volume
docker run -d \
  --name postgres-dev \
  -e POSTGRES_DB=myapp \
  -e POSTGRES_USER=dev \
  -e POSTGRES_PASSWORD=devpass \
  -v pg-data:/var/lib/postgresql/data \
  -p 5432:5432 \
  postgres:16-alpine

docker exec -it postgres-dev psql -U dev -d myapp -c "SELECT * FROM users;"
# Les données Alice et Bob sont toujours là !
✓ Résultat attendu

Après suppression et recréation du conteneur, les données sont intactes grâce au volume pg-data. Sans le -v, elles auraient disparu.

Lab 2 Communication inter-conteneurs avec docker-compose ~20 min

Objectifs

  • Déclarer un stack multi-services dans un docker-compose.yml
  • Faire communiquer une API avec sa base de données par nom de service
  • Observer que les conteneurs s'isolent sur leur propre réseau

docker-compose.yml

docker-compose.yml
services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: myapp
      POSTGRES_USER: dev
      POSTGRES_PASSWORD: devpass
    volumes:
      - pg-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD", "pg_isready", "-U", "dev"]
      interval: 5s
      retries: 5

  redis:
    image: redis:7-alpine
    command: redis-server --appendonly yes
    volumes:
      - redis-data:/data

  api:
    build: .
    ports:
      - "8080:8080"
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/myapp
      SPRING_DATASOURCE_USERNAME: dev
      SPRING_DATASOURCE_PASSWORD: devpass
      SPRING_REDIS_HOST: redis   # Nom du service = hostname réseau
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_started

volumes:
  pg-data:
  redis-data:

Commandes essentielles

bash
# Démarrer le stack complet
docker compose up -d

# Voir l'état de tous les services
docker compose ps

# Logs d'un service spécifique
docker compose logs -f api

# Tester la communication : l'API atteint postgres par son nom
docker compose exec api ping postgres
docker compose exec api ping redis

# Vérifier le réseau créé automatiquement
docker network ls
docker network inspect monprojet_default

# Arrêter (sans supprimer les volumes)
docker compose down

# Arrêter ET supprimer les volumes
docker compose down -v
✓ Résultat attendu

Les trois services démarrent dans l'ordre. L'API se connecte à PostgreSQL via le hostname postgres sans aucune IP codée en dur. docker network inspect confirme qu'ils partagent le même réseau privé.
