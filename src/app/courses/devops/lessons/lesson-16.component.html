Pourquoi le Chaos Engineering ?

En 2010, Netflix migre vers AWS et se retrouve face à une question existentielle : comment savoir si notre système tiendra si un datacenter tombe en panne ? La réponse de leur équipe : le provoquer intentionnellement. Chaos Monkey est né - un outil qui tue des instances en production de façon aléatoire pour forcer les ingénieurs à construire des systèmes réellement résilients.

L'idée centrale est brutalement honnête : les pannes sont inévitables. La question n'est pas si un composant va tomber, mais quand et comment votre système survit. Espérer que tout ira bien n'est pas une stratégie. Le Chaos Engineering consiste à prouver la résilience avant que vos utilisateurs ne la testent à votre place.

Sans Chaos Engineering
  • Découvrir les pannes en production
  • Hypothèses jamais vérifiées
  • Résilience théorique seulement
  • Panique lors d'un incident réel
  • Runbooks jamais testés
Avec Chaos Engineering
  • Pannes provoquées, contrôlées, apprises
  • Hypothèses validées par l'expérimentation
  • Résilience prouvée par des données
  • Équipes entraînées aux incidents
  • Runbooks maintenus et testés
Le Chaos Engineering dans la CNCF

Chaos Mesh et Litmus Chaos sont tous deux des projets CNCF (Cloud Native Computing Foundation), ce qui témoigne de la maturité de la discipline. Le chaos engineering est aujourd'hui une pratique standard dans les équipes SRE (Site Reliability Engineering) des grandes organisations.

La Steady State Hypothesis

Avant d'injecter le moindre chaos, vous devez définir l'état stable (Steady State) de votre système : un ensemble de métriques mesurables qui caractérisent un comportement normal. C'est la base scientifique du chaos engineering.

1
Définir l'état stable

Identifiez vos métriques clés : taux de succès HTTP (> 99%), latence p99 (< 200ms), nombre de pods Ready, throughput (req/s). Ces métriques doivent être mesurables dans Prometheus/Grafana (cf. Leçon 10).

2
Formuler l'hypothèse

"Si je tue 1 pod sur 3, le système maintient son état stable grâce au self-healing et au load balancing." C'est une hypothèse précise et falsifiable.

3
Injecter le chaos - dans un périmètre contrôlé

Commencez par un seul pod, dans un namespace de staging. Augmentez le blast radius progressivement au fil des itérations.

4
Vérifier - l'état stable tient-il ?

Observer les métriques pendant et après l'expérience. Si l'état stable est maintenu : ✓ l'hypothèse est confirmée. Si non : ✗ vous venez de trouver une vraie faiblesse avant vos utilisateurs.

5
Analyser, corriger, recommencer

Documentez les résultats. Si une faiblesse est trouvée, corrigez-la (retry logic, circuit breaker, réplication) puis recommencez l'expérience.

Blast Radius - Contrôler l'impact

Le blast radius est le périmètre d'impact d'une expérience chaos. La règle d'or : commencer le plus petit possible et augmenter progressivement. Ne jamais commencer en production.

Niveau Cible Impact potentiel Quand ?
1 - Pod Un seul pod dans un namespace isolé Aucun sur le trafic réel Premiers tests, tout le temps
2 - Deployment N% des pods d'un deployment Dégradation partielle possible Staging validé, équipe prête
3 - Service Latence réseau sur un service entier Ralentissement global Staging seulement
4 - Node Un worker node complet Rescheduling de tous les pods Après validation complète staging
5 - Production Expériences en production réelle Impact utilisateurs possible Seulement avec kill switch + on-call
Toujours avoir un kill switch

Toute expérience chaos doit pouvoir être annulée immédiatement. Chaos Mesh propose une pause/suppression d'expérience en un clic. En production, un chaos engineer doit être disponible pendant toute la durée de l'expérience, avec un runbook de rollback prêt.

Chaos Mesh - Architecture & Types d'expériences

Chaos Mesh est un framework CNCF de chaos engineering natif Kubernetes. Il s'appuie sur des CRDs (Custom Resource Definitions) pour décrire les expériences en YAML, exactement comme n'importe quelle ressource Kubernetes.

Architecture

  ┌─────────────────────────────────────────────────────────────────┐
  │                     Chaos Mesh                                  │
  │                                                                 │
  │  ┌──────────────────┐     ┌─────────────────────────────────┐  │
  │  │  Chaos Dashboard  │────▶│    Chaos Controller Manager     │  │
  │  │   (Web UI)        │     │  (watches CRDs, orchestrates)  │  │
  │  └──────────────────┘     └────────────────┬────────────────┘  │
  │                                            │                   │
  │                           ┌───────────────▼──────────────┐    │
  │                           │        Chaos Daemon           │    │
  │                           │ (DaemonSet - 1 pod/node)      │    │
  │                           │  injecte le chaos sur le node │    │
  │                           └───────────────────────────────┘    │
  │                                                                 │
  │  CRDs: PodChaos  NetworkChaos  StressChaos  IOChaos  TimeChaos │
  └─────────────────────────────────────────────────────────────────┘

Types d'expériences

CRD Ce que ça teste Exemples de scénarios
PodChaos Self-healing, haute disponibilité Kill aléatoire, crash loop, container kill
NetworkChaos Résilience réseau, retry, timeouts Latence, perte de paquets, partition réseau, corruption
StressChaos Comportement sous charge, OOM handling CPU spike à 80%, memory pressure, combiné
IOChaos Résilience I/O, persistence Latence disque, erreurs de lecture, corruption fichiers
TimeChaos Gestion du temps, caches, JWT expiration Décalage horloge, skew de temps entre pods
KernelChaos Appels système, bas niveau Erreurs malloc, erreurs open() fichiers

Une expérience Chaos Mesh en YAML

Chaque expérience est une ressource Kubernetes standard. Exemple : tuer un pod toutes les 30 secondes.

pod-chaos.yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata:
  name: kill-api-pods
  namespace: chaos-testing
spec:
  action: pod-kill          # pod-kill | pod-failure | container-kill
  mode: one                 # one | all | fixed | fixed-percent | random-max-percent
  selector:
    namespaces:
      - default
    labelSelectors:
      app: api-backend
  scheduler:
    cron: "@every 30s"      # Répétition toutes les 30 secondes
  duration: "10s"           # Durée de l'expérience
network-chaos.yaml - Latence 500ms
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: api-network-delay
  namespace: chaos-testing
spec:
  action: delay
  mode: one
  selector:
    namespaces:
      - default
    labelSelectors:
      app: api-backend
  delay:
    latency: "500ms"        # Latence injectée
    correlation: "25"       # 25% de corrélation entre paquets
    jitter: "50ms"          # ± variation
  direction: to             # to | from | both
  duration: "60s"
stress-chaos.yaml - CPU spike
apiVersion: chaos-mesh.org/v1alpha1
kind: StressChaos
metadata:
  name: cpu-stress-api
  namespace: chaos-testing
spec:
  mode: one
  selector:
    namespaces:
      - default
    labelSelectors:
      app: api-backend
  stressors:
    cpu:
      workers: 2            # Nombre de goroutines stressant le CPU
      load: 80              # % de charge CPU cible
    memory:
      workers: 1
      size: "256MB"         # Pression mémoire
  duration: "120s"

L'observabilité est un prérequis

Le chaos engineering sans monitoring, c'est comme piloter à l'aveugle. Vous devez pouvoir mesurer l'état stable avant, pendant et après chaque expérience. C'est pour ça que cette leçon vient après Prometheus & Grafana (Leçon 10) et le logging (Leçon 11).

Ce que vous injectez Ce que vous mesurez dans Grafana Métrique PromQL
Pod kill Pods Ready, taux d'erreurs HTTP kube_deployment_status_replicas_ready
Latence réseau 500ms Latence p99 des requêtes histogram_quantile(0.99, http_request_duration)
CPU stress 80% CPU throttling, latence applicative rate(container_cpu_cfs_throttled_seconds_total[5m])
Memory pressure OOM kills, restarts des pods kube_pod_container_status_restarts_total
Créez un dashboard Grafana dédié au chaos

Avant chaque expérience, ouvrez un dashboard avec : taux de succès HTTP, latence p50/p99, pods Ready/Total, et restarts. Annotez le début et la fin de l'expérience dans Grafana (feature "Annotations") pour visualiser exactement l'impact sur les métriques.

Game Days - Entraîner les équipes

Un Game Day est un exercice planifié où toute l'équipe (dev, ops, on-call) participe à une session de chaos engineering. L'objectif est autant de tester les systèmes que de tester les humains et les processus.

1
Planification (J-7)

Définir le scénario, le blast radius, les métriques d'état stable, l'équipe impliquée, le kill switch.

2
Briefing (J0 matin)

Présenter le scénario à l'équipe. Désigner un "chaos engineer" (injecte) et un "observateur" (surveille les dashboards).

3
Exécution

Injecter le chaos. L'équipe réagit comme pour un vrai incident : détection, investigation, mitigation.

4
Post-mortem (J0 après-midi)

Rédiger un post-mortem blameless : timeline, impact, causes profondes, actions correctives. C'est le livrable le plus important du Game Day.

Travaux Pratiques - Chaos Engineering sur Kind

Prérequis : Cluster Kind opérationnel (Leçon 3), Helm installé (Leçon 10). Lab 1 ne nécessite aucun outil supplémentaire. Lab 2 installe Chaos Mesh sur votre cluster Kind.

Lab 1 Chaos manuel - kubectl comme outil de chaos ~20 min

Objectifs

  • Observer le self-healing de Kubernetes sous stress
  • Simuler la perte d'un node et la migration des pods
  • Mesurer le temps de récupération (MTTR)

Étape 1 - Déployer une application cible

bash
# Déployer l'app cible avec 3 réplicas
kubectl create deployment chaos-target \
  --image=nginx:alpine \
  --replicas=3

kubectl expose deployment chaos-target --port=80 --type=ClusterIP

# Vérifier l'état stable (steady state)
kubectl get pods -l app=chaos-target -w
# NAME                            READY   STATUS    RESTARTS
# chaos-target-5d8f9b9c6d-abc12   1/1     Running   0
# chaos-target-5d8f9b9c6d-def34   1/1     Running   0
# chaos-target-5d8f9b9c6d-ghi56   1/1     Running   0

Étape 2 - Expérience 1 : Kill d'un pod

Hypothèse : Si je supprime 1 pod, Kubernetes le recrée en moins de 15 secondes.

bash - terminal 1 : observer en continu
kubectl get pods -l app=chaos-target -w
bash - terminal 2 : injecter le chaos
# Récupérer un pod et le supprimer
POD=$(kubectl get pods -l app=chaos-target -o name | head -1)
echo "Killing: $POD"
kubectl delete $POD

# Observer dans terminal 1 :
# Le pod passe Terminating → nouveau pod Running en ~5-10s
# Le ReplicaSet maintient toujours 3 réplicas
bash - mesurer le MTTR
START=$(date +%s)
kubectl delete $(kubectl get pods -l app=chaos-target -o name | head -1)
kubectl wait --for=condition=ready pods -l app=chaos-target --timeout=60s
END=$(date +%s)
echo "MTTR: $((END - START)) secondes"

Étape 3 - Expérience 2 : Kill de tous les pods simultanément

Hypothèse : Si je supprime les 3 pods en même temps, le service reste disponible le temps du restart.

bash - terminal 1 : tester la disponibilité en continu
# Lancer un pod de test qui curl en boucle
kubectl run load-test --image=busybox --restart=Never -it --rm -- \
  sh -c 'while true; do wget -q -O- http://chaos-target || echo "FAIL"; sleep 0.5; done'
bash - terminal 2 : chaos total
# Supprimer tous les pods d'un coup
kubectl delete pods -l app=chaos-target

# Observer dans terminal 1 : combien de FAILs avant que tout revienne ?
# Conclusion : sans PodDisruptionBudget, la dispo n'est pas garantie

Étape 4 - Corriger avec un PodDisruptionBudget

pdb.yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: chaos-target-pdb
spec:
  minAvailable: 2           # Au moins 2 pods toujours disponibles
  selector:
    matchLabels:
      app: chaos-target
bash
kubectl apply -f pdb.yaml

# Re-tester : kubectl delete pods -l app=chaos-target
# Cette fois, au moins 2 pods restent opérationnels pendant l'éviction

Étape 5 - Expérience 3 : Drain d'un node

bash
# Lister les nodes
kubectl get nodes
# NAME                     STATUS   ROLES
# k8s-lab-control-plane    Ready    control-plane
# k8s-lab-worker           Ready    <none>
# k8s-lab-worker2          Ready    <none>

# Drainer un worker (simule une maintenance)
kubectl drain k8s-lab-worker --ignore-daemonsets --delete-emptydir-data

# Tous les pods du node sont évincés et reschedulés sur l'autre worker
kubectl get pods -l app=chaos-target -o wide

# Remettre le node en service
kubectl uncordon k8s-lab-worker
✓ Résultats attendus

MTTR pod kill < 15s. Avec PDB, au minimum 2 pods restent disponibles en toutes circonstances. Après drain, tous les pods migrent sur le node restant - aucune intervention manuelle.

Lab 2 Chaos Mesh - Expériences réseau et pod sur Kind ~40 min

Objectifs

  • Installer Chaos Mesh via Helm sur votre cluster Kind
  • Créer une expérience PodChaos (kill aléatoire)
  • Créer une expérience NetworkChaos (latence 500ms)
  • Observer l'impact via le Chaos Dashboard

Étape 1 - Installer Chaos Mesh

Chaos Mesh s'installe en un seul chart Helm dans un namespace dédié.

bash - Linux / macOS
helm repo add chaos-mesh https://charts.chaos-mesh.org
helm repo update

# Créer le namespace
kubectl create namespace chaos-mesh

# Installer - runtime=containerd pour Kind
helm install chaos-mesh chaos-mesh/chaos-mesh \
  --namespace chaos-mesh \
  --set chaosDaemon.runtime=containerd \
  --set chaosDaemon.socketPath=/run/containerd/containerd.sock \
  --version 2.6.3

# Attendre que tous les pods soient Ready
kubectl get pods -n chaos-mesh -w
bash - macOS

Étape 3 - Déployer l'application cible

bash
# Réutiliser l'app du Lab 1 ou redéployer
kubectl create namespace chaos-testing
kubectl create deployment api-backend \
  --image=nginx:alpine \
  --replicas=3 \
  -n chaos-testing

# Lancer un générateur de trafic continu
kubectl run traffic-gen -n chaos-testing \
  --image=busybox --restart=Never -- \
  sh -c 'while true; do wget -q -O- http://api-backend 2>&1; sleep 1; done'

Étape 4 - Expérience PodChaos : kill aléatoire toutes les 30s

pod-chaos-experiment.yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata:
  name: kill-backend-pods
  namespace: chaos-testing
spec:
  action: pod-kill
  mode: one               # Tuer 1 pod à la fois
  selector:
    namespaces:
      - chaos-testing
    labelSelectors:
      app: api-backend
  scheduler:
    cron: "@every 30s"
  duration: "5m"          # Arrête automatiquement après 5 minutes
bash
kubectl apply -f pod-chaos-experiment.yaml

# Observer dans le Dashboard → Experiments → kill-backend-pods
# Observer les pods qui se recréent
kubectl get pods -n chaos-testing -w

# Vérifier que le trafic reste disponible malgré les kills
kubectl logs traffic-gen -n chaos-testing | tail -20

# Arrêter l'expérience
kubectl delete podchaos kill-backend-pods -n chaos-testing

Étape 5 - Expérience NetworkChaos : latence 500ms

network-chaos-experiment.yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: api-latency
  namespace: chaos-testing
spec:
  action: delay
  mode: all               # Appliquer à tous les pods matchés
  selector:
    namespaces:
      - chaos-testing
    labelSelectors:
      app: api-backend
  delay:
    latency: "500ms"
    jitter: "100ms"
  direction: to           # Latence sur les requêtes ENTRANTES
  duration: "2m"
bash
kubectl apply -f network-chaos-experiment.yaml

# Tester la latence depuis un pod client
kubectl run latency-test -n chaos-testing --image=curlimages/curl --restart=Never --rm -it -- \
  sh -c 'for i in $(seq 1 10); do time curl -s http://api-backend > /dev/null; done'

# Vous devriez voir ~500ms de latence sur chaque requête
# Si Grafana est configuré (Leçon 10), observer le p99 augmenter

# Nettoyer
kubectl delete networkchaos api-latency -n chaos-testing

Étape 6 - Nettoyer

bash
# Supprimer le namespace de test
kubectl delete namespace chaos-testing

# Désinstaller Chaos Mesh
helm uninstall chaos-mesh -n chaos-mesh
kubectl delete namespace chaos-mesh
✓ Résultats attendus

Expérience PodChaos : les pods sont tués toutes les 30s et recréés automatiquement, le trafic continue sans interruption visible grâce au self-healing. Expérience NetworkChaos : latence de ~500ms mesurable sur chaque requête. Le Dashboard Chaos Mesh montre la timeline des expériences et leur statut.
