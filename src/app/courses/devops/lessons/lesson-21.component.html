Logging centralisé - stdout + Loki

Dans Kubernetes, la règle d'or du logging est simple : tout sur stdout/stderr. Les conteneurs sont éphémères - les fichiers de log disparaissent avec le pod. Le container runtime (containerd) capture automatiquement stdout et le rend accessible via kubectl logs.

Configurer Spring Boot pour stdout

backend/src/main/resources/application.yml
# Spring Boot log sur stdout par défaut - mais en JSON pour Loki
logging:
  pattern:
    console: >-
      {"timestamp":"%d{ISO8601}",
      "level":"%level",
      "logger":"%logger{36}",
      "message":"%msg",
      "thread":"%thread"}%n
Pourquoi le format JSON ?

Les logs en texte brut sont difficiles à parser pour les collecteurs. En JSON structuré, Loki peut indexer par champs (level, logger, message) et permettre des requêtes précises comme {app="backend"} |= "ERROR".

kubectl logs - L'outil de base

Terminal
# Logs du pod le plus récent
kubectl logs deployment/backend -n prod

# Logs en temps réel (streaming)
kubectl logs -f deployment/backend -n prod

# Logs de tous les pods d'un Deployment
kubectl logs -l app=backend -n prod --all-containers

# Logs des 30 dernières minutes
kubectl logs deployment/backend -n prod --since=30m

# Logs du pod précédent (après un crash)
kubectl logs deployment/backend -n prod --previous

Installer Loki + Promtail

Terminal - VPS
# Ajouter le repo Grafana
helm repo add grafana https://grafana.github.io/helm-charts
helm repo update

# Installer Loki Stack (Loki + Promtail)
helm install loki grafana/loki-stack \
  --namespace monitoring \
  --set loki.persistence.enabled=true \
  --set loki.persistence.size=5Gi \
  --set promtail.enabled=true \
  --set loki.resources.requests.memory=128Mi \
  --set loki.resources.limits.memory=256Mi

# Vérifier
kubectl get pods -n monitoring -l app=loki
# NAME                    READY   STATUS    RESTARTS   AGE
# loki-0                  1/1     Running   0          1m

kubectl get pods -n monitoring -l app=promtail
# NAME                 READY   STATUS    RESTARTS   AGE
# loki-promtail-xxx    1/1     Running   0          1m
Comment ça fonctionne
  • Promtail - DaemonSet qui tourne sur chaque nœud, collecte les logs de /var/log/pods/ et les envoie à Loki
  • Loki - Stocke et indexe les logs par labels (namespace, pod, container), pas en full-text
  • Grafana - Visualise les logs avec le langage de requête LogQL

Configurer Grafana pour Loki

Terminal - Ajouter Loki comme data source
# Si Grafana est installé avec kube-prometheus-stack,
# Loki doit être ajouté comme data source.

# Option 1 : Via l'interface Grafana
# Configuration → Data Sources → Add → Loki
# URL : http://loki:3100

# Option 2 : Via Helm values (recommandé)
# Ajoutez lors de l'installation de Grafana :
# --set grafana.additionalDataSources[0].name=Loki
# --set grafana.additionalDataSources[0].type=loki
# --set grafana.additionalDataSources[0].url=http://loki:3100

Requêtes LogQL dans Grafana

Exemples LogQL
# Tous les logs du backend en prod
{namespace="prod", app="backend"}

# Uniquement les erreurs
{namespace="prod", app="backend"} |= "ERROR"

# Logs contenant "timeout" ou "connection refused"
{namespace="prod", app="backend"} |~ "timeout|connection refused"

# Parser les logs JSON et filtrer par level
{namespace="prod", app="backend"} | json | level="ERROR"

# Compter les erreurs par minute (métrique depuis les logs)
rate({namespace="prod", app="backend"} |= "ERROR" [1m])

CI/CD - Pipeline GitHub Actions (2 repos séparés)

Dans notre architecture, le backend (Spring Boot) et le frontend (Angular) vivent dans deux dépôts GitHub distincts. Chaque repo a son propre workflow qui build, push et déploie de façon indépendante. Le dossier k8s/ (manifestes Kubernetes) peut être dans un troisième repo dédié ou dupliqué dans chaque repo - ici on le met dans le repo backend car c'est le plus critique.

Pourquoi 2 repos = 2 workflows ?
  • Un fix CSS ne redéploie pas le backend Java (et inversement)
  • Chaque équipe (front/back) peut release indépendamment
  • Les cycles de build sont plus rapides (pas de build inutile)
  • Les permissions GitHub (GITHUB_TOKEN) sont scopées au repo

Workflow Backend (repo Spring Boot)

.github/workflows/deploy.yml - Repo Backend
name: Backend - Build & Deploy

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

env:
  REGISTRY: ghcr.io
  IMAGE: ghcr.io/${{ github.repository }}

jobs:
  # ================================
  # JOB 1 : Tests
  # ================================
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Java 21
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: 21
          cache: maven

      - name: Run Tests
        run: ./mvnw verify -B

  # ================================
  # JOB 2 : Build & Push Docker Image
  # ================================
  build:
    needs: test
    runs-on: ubuntu-latest
    if: github.event_name == 'push'
    permissions:
      contents: read
      packages: write
    outputs:
      tag: ${{ steps.tag.outputs.TAG }}
    steps:
      - uses: actions/checkout@v4

      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Set image tag
        id: tag
        run: echo "TAG=$(echo $GITHUB_SHA | head -c 7)" >> $GITHUB_OUTPUT

      - name: Build & Push
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: |
            ${{ env.IMAGE }}:${{ steps.tag.outputs.TAG }}
            ${{ env.IMAGE }}:latest

  # ================================
  # JOB 3 : Deploy to Kubernetes
  # ================================
  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set environment
        id: env
        run: |
          if [ "$GITHUB_REF" = "refs/heads/main" ]; then
            echo "ENV=prod" >> $GITHUB_OUTPUT
          else
            echo "ENV=staging" >> $GITHUB_OUTPUT
          fi

      - name: Setup kubectl
        uses: azure/setup-kubectl@v3

      - name: Configure kubeconfig
        run: |
          mkdir -p ~/.kube
          echo "${{ secrets.KUBECONFIG }}" | base64 -d > ~/.kube/config
          chmod 600 ~/.kube/config

      - name: Deploy backend
        run: |
          TAG=${{ needs.build.outputs.tag }}
          NS=${{ steps.env.outputs.ENV }}

          # Mettre à jour l'image du Deployment backend
          kubectl set image deployment/backend \
            backend=${{ env.IMAGE }}:$TAG \
            -n $NS

          # Attendre que le rollout soit terminé
          kubectl rollout status deployment/backend \
            -n $NS --timeout=120s

      - name: Verify
        run: |
          kubectl get pods -n ${{ steps.env.outputs.ENV }} -l app=backend
          echo "Backend ${{ needs.build.outputs.tag }} deployed to ${{ steps.env.outputs.ENV }}"

Où placer les manifestes K8s ?

3 options pour le dossier k8s/
  • Option 1 (recommandée) - Un 3ème repo dédié infra-k8s contenant uniquement les manifestes. Les deux workflows y accèdent via kubectl set image sans toucher aux YAML.
  • Option 2 - Dans le repo backend (le plus critique). Le workflow frontend fait juste kubectl set image sans checkout du repo backend.
  • Option 3 - Dupliqué dans les deux repos (à éviter, source de désynchronisation).

Avec kubectl set image, les workflows n'ont pas besoin d'accéder aux fichiers YAML. Ils mettent à jour directement l'image du Deployment existant sur le cluster. Le déploiement initial (première fois) se fait manuellement avec kubectl apply -k depuis le repo contenant les manifestes.

# Copier le résultat

# Sur GitHub (à faire dans les 2 repos) :

# Name : KUBECONFIG
# Value : (coller le base64)

# Le GITHUB_TOKEN est automatique - pas besoin de le créer
Sécurité : limiter le kubeconfig

Plutôt que de donner un accès admin complet, créez un ServiceAccount Kubernetes dédié au CI/CD avec des permissions limitées (uniquement update les Deployments dans les namespaces staging et prod).

Terminal - Créer un ServiceAccount CI/CD (optionnel mais recommandé)
# Créer le ServiceAccount
kubectl create serviceaccount github-deployer -n prod

# Créer un Role limité
kubectl create role deployer \
  --namespace=prod \
  --verb=get,list,watch,update,patch \
  --resource=deployments,pods,replicasets

# Lier le Role au ServiceAccount
kubectl create rolebinding github-deployer-binding \
  --namespace=prod \
  --role=deployer \
  --serviceaccount=prod:github-deployer

# Répéter pour staging
kubectl create role deployer \
  --namespace=staging \
  --verb=get,list,watch,update,patch \
  --resource=deployments,pods,replicasets

kubectl create rolebinding github-deployer-binding \
  --namespace=staging \
  --role=deployer \
  --serviceaccount=staging:github-deployer

# Générer le kubeconfig limité pour ce ServiceAccount
# → Utiliser ce kubeconfig dans le secret KUBECONFIG de GitHub

CDN - Cloudflare devant NGINX

Un CDN met en cache les assets statiques (JS, CSS, images) sur des serveurs répartis mondialement. Les utilisateurs récupèrent les fichiers depuis le point de présence le plus proche, réduisant la latence et la charge sur votre VPS.

Pourquoi ça fonctionne avec Angular

Angular produit des fichiers avec un content hash dans le nom : main.abc123def.js. Quand le code change, le hash change, donc l'URL change. On peut donc mettre un cache agressif (1 an) sur ces fichiers - ils ne seront jamais périmés car leur nom change à chaque build.

Configuration Cloudflare

Étapes chez Cloudflare (interface web)
  1. Ajouter votre domaine dans Cloudflare
  2. Changer les nameservers chez votre registrar vers ceux de Cloudflare
  3. Mettre le proxy en mode Proxied (nuage orange) sur les enregistrements A
  4. Activer SSL/TLS → Full (Strict) (car vous avez déjà HTTPS avec cert-manager)
  5. Page Rules ou Cache Rules :
    • mondomaine.com/*.js → Cache Everything, Edge TTL 1 month
    • mondomaine.com/*.css → Cache Everything, Edge TTL 1 month
    • mondomaine.com/assets/* → Cache Everything, Edge TTL 1 month
    • api.mondomaine.com/* → Bypass Cache (ne jamais cacher l'API !)

Vérifier que le CDN fonctionne

Terminal
# Vérifier les headers de cache
curl -I https://mondomaine.com/main.abc123.js

# Résultat attendu (avec Cloudflare) :
# cf-cache-status: HIT          ← Servi depuis le cache Cloudflare
# cache-control: public, max-age=31536000, immutable
# cf-ray: xxx-CDG               ← Edge server (CDG = Paris)

# Premier accès :
# cf-cache-status: MISS          ← Pas encore en cache, récupéré depuis le VPS
# Deuxième accès :
# cf-cache-status: HIT           ← En cache !
Ne jamais cacher l'API

Les requêtes vers api.mondomaine.com ne doivent JAMAIS être mises en cache par le CDN. Chaque requête API doit atteindre le backend pour retourner des données fraîches. Cloudflare bypass automatiquement les requêtes avec un header Authorization, mais configurez aussi une Page Rule explicite par sécurité.
