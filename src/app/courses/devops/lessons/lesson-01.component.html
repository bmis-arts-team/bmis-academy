Qu'est-ce que Docker ?

Docker est une plateforme de conteneurisation qui permet d'empaqueter une application et toutes ses dépendances dans une unité standardisée appelée conteneur. Contrairement aux machines virtuelles, les conteneurs partagent le kernel de l'hôte, ce qui les rend beaucoup plus légers.

Les trois piliers de l'isolation

TechnologieRôleExemple

Images Docker en profondeur

Une image Docker est un template en lecture seule composé de couches (layers) empilées. Chaque instruction dans un Dockerfile crée une nouvelle couche.

Le système de layers

  Layer 4 (R/W)  ─── Container Layer (éphémère)
  Layer 3 (R/O)  ─── COPY app.jar → /app/app.jar
  Layer 2 (R/O)  ─── RUN apt-get install curl
  Layer 1 (R/O)  ─── FROM eclipse-temurin:21-jre-alpine
Optimisation du cache

Docker met en cache chaque layer. Si une instruction n'a pas changé, Docker réutilise le cache. Placez les instructions qui changent rarement en haut du Dockerfile.

Inspecter les layers

bash
# Voir l'historique des layers
docker history my-api:1.0.0

# Taille détaillée
docker image inspect my-api:1.0.0 --format='{{.Size}}'

Dockerfile - Production Grade

Un bon Dockerfile suit le principe du multi-stage build : une étape pour compiler, une étape minimale pour exécuter.

❌ Mauvaise pratique

Dockerfile
FROM eclipse-temurin:21-jdk
COPY . /app
WORKDIR /app
RUN ./mvnw package
EXPOSE 8080
CMD ["java", "-jar", "target/app.jar"]

Image de ~800 Mo avec JDK + sources + Maven cache.

✅ Bonne pratique

Dockerfile
FROM eclipse-temurin:21-jdk-alpine AS build
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn package -DskipTests

FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
COPY --from=build /app/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

Image de ~180 Mo avec JRE uniquement.

Commandes essentielles

bash - Gestion des conteneurs
# Créer et démarrer
docker run -d --name my-api -p 8080:8080 my-api:1.0.0

# Voir les logs en temps réel
docker logs -f my-api

# Exécuter une commande dans le conteneur
docker exec -it my-api /bin/sh

# Arrêter proprement (SIGTERM → SIGKILL après 10s)
docker stop my-api

# Supprimer
docker rm my-api

# Tout nettoyer (conteneurs arrêtés, images orphelines)
docker system prune -f

Dockeriser Spring Boot + PostgreSQL + Redis

Voici un docker-compose.yml complet pour une architecture classique :

docker-compose.yml
services:
  api:
    build: .
    ports:
      - "8080:8080"
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/app_db
      SPRING_DATASOURCE_USERNAME: app_user
      SPRING_DATASOURCE_PASSWORD: secret
      SPRING_DATA_REDIS_HOST: redis
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_started
    networks:
      - backend

  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: app_db
      POSTGRES_USER: app_user
      POSTGRES_PASSWORD: secret
    volumes:
      - postgres-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app_user -d app_db"]
      interval: 5s
      timeout: 3s
      retries: 5
    networks:
      - backend

  redis:
    image: redis:7-alpine
    command: redis-server --maxmemory 128mb --maxmemory-policy allkeys-lru
    volumes:
      - redis-data:/data
    networks:
      - backend

volumes:
  postgres-data:
  redis-data:

networks:
  backend:
    driver: bridge
Healthcheck

Utilisez depends_on avec condition: service_healthy pour que l'API attende que PostgreSQL soit réellement prêt avant de démarrer.

Registry & Distribution

Une fois votre image construite, vous devez la stocker dans un registry pour la rendre disponible aux autres environnements.

RegistryTypeUsage
Docker HubPublic / PrivéImages open-source, projets personnels
GitHub GHCRPrivé / PublicIntégré à GitHub Actions
AWS ECRPrivéIntégré à EKS, Fargate
HarborSelf-hostedEntreprises, scanning de vulnérabilités
bash - Push vers un registry
# Tagger l'image
docker tag my-api:1.0.0 ghcr.io/my-org/my-api:1.0.0

# Se connecter au registry
echo $GHCR_TOKEN | docker login ghcr.io -u USERNAME --password-stdin

# Pousser l'image
docker push ghcr.io/my-org/my-api:1.0.0
Ne jamais utiliser :latest en production

Le tag :latest est mutable et rend les rollbacks impossibles. Utilisez des tags sémantiques : 1.0.0, 1.0.1, ou le SHA du commit.
