Qu'est-ce que Docker ?

Docker est une plateforme de conteneurisation qui permet d'empaqueter une application et toutes ses dépendances dans une unité standardisée appelée conteneur. Contrairement aux machines virtuelles, les conteneurs partagent le kernel de l'hôte, ce qui les rend beaucoup plus légers.

Images Docker en profondeur

Une image Docker est un template en lecture seule composé de couches (layers) empilées. Chaque instruction dans un Dockerfile crée une nouvelle couche.

Le système de layers

Chaque instruction Dockerfile crée un layer en lecture seule. Seule la couche container est modifiable.

Optimisation du cache

Docker met en cache chaque layer. Si une instruction n'a pas changé, Docker réutilise le cache. Placez les instructions qui changent rarement en haut du Dockerfile.

Inspecter les layers

bash
# Voir l'historique des layers
docker history my-api:1.0.0

# Taille détaillée
docker image inspect my-api:1.0.0 --format='{{.Size}}'

Dockerfile - Production Grade

Un bon Dockerfile suit le principe du multi-stage build : une étape pour compiler, une étape minimale pour exécuter.

❌ Mauvaise pratique

Dockerfile
FROM eclipse-temurin:21-jdk
COPY . /app
WORKDIR /app
RUN ./mvnw package
EXPOSE 8080
CMD ["java", "-jar", "target/app.jar"]

Image de ~800 Mo avec JDK + sources + Maven cache.

✅ Bonne pratique

Dockerfile
FROM eclipse-temurin:21-jdk-alpine AS build
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn package -DskipTests

FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
COPY --from=build /app/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

Image de ~180 Mo avec JRE uniquement.

Cycle de vie des Containers

Machine à états du cycle de vie d'un conteneur Docker.

Commandes essentielles

bash - Gestion des conteneurs
# Créer et démarrer
docker run -d --name my-api -p 8080:8080 my-api:1.0.0

# Voir les logs en temps réel
docker logs -f my-api

# Exécuter une commande dans le conteneur
docker exec -it my-api /bin/sh

# Arrêter proprement (SIGTERM → SIGKILL après 10s)
docker stop my-api

# Supprimer
docker rm my-api

# Tout nettoyer (conteneurs arrêtés, images orphelines)
docker system prune -f

Dockeriser Spring Boot + PostgreSQL + Redis

Voici un docker-compose.yml complet pour une architecture classique :

docker-compose.yml
services:
  api:
    build: .
    ports:
      - "8080:8080"
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/app_db
      SPRING_DATASOURCE_USERNAME: app_user
      SPRING_DATASOURCE_PASSWORD: secret
      SPRING_DATA_REDIS_HOST: redis
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_started
    networks:
      - backend

  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: app_db
      POSTGRES_USER: app_user
      POSTGRES_PASSWORD: secret
    volumes:
      - postgres-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app_user -d app_db"]
      interval: 5s
      timeout: 3s
      retries: 5
    networks:
      - backend

  redis:
    image: redis:7-alpine
    command: redis-server --maxmemory 128mb --maxmemory-policy allkeys-lru
    volumes:
      - redis-data:/data
    networks:
      - backend

volumes:
  postgres-data:
  redis-data:

networks:
  backend:
    driver: bridge
Healthcheck

Utilisez depends_on avec condition: service_healthy pour que l'API attende que PostgreSQL soit réellement prêt avant de démarrer.

Registry & Distribution

Une fois votre image construite, vous devez la stocker dans un registry pour la rendre disponible aux autres environnements.

RegistryTypeUsage
Docker HubPublic / PrivéImages open-source, projets personnels
GitHub GHCRPrivé / PublicIntégré à GitHub Actions
AWS ECRPrivéIntégré à EKS, Fargate
HarborSelf-hostedEntreprises, scanning de vulnérabilités
bash - Push vers un registry
# Tagger l'image
docker tag my-api:1.0.0 ghcr.io/my-org/my-api:1.0.0

# Se connecter au registry
echo $GHCR_TOKEN | docker login ghcr.io -u USERNAME --password-stdin

# Pousser l'image
docker push ghcr.io/my-org/my-api:1.0.0
Ne jamais utiliser :latest en production

Le tag :latest est mutable et rend les rollbacks impossibles. Utilisez des tags sémantiques : 1.0.0, 1.0.1, ou le SHA du commit.

Travaux Pratiques - Docker en local

Prérequis : Docker Desktop installé et en cours d'exécution. Ces exercices couvrent les gestes du quotidien : builder une image, la lancer, l'inspecter et la distribuer.

Lab 1 Builder et exécuter votre première image ~15 min

Objectifs

  • Écrire un Dockerfile multi-stage pour une app Spring Boot
  • Builder l'image et vérifier qu'elle apparaît dans docker images
  • Lancer le conteneur, mapper un port, vérifier la réponse HTTP
  • Inspecter les layers de l'image

Étape 1 - Créer le Dockerfile

À la racine d'un projet Spring Boot (ou copiez ce squelette) :

Dockerfile
# ── Stage 1 : Build ───────────────────────────────────
FROM eclipse-temurin:21-jdk-alpine AS builder
WORKDIR /app
COPY .mvn/ .mvn/
COPY mvnw pom.xml ./
RUN ./mvnw dependency:go-offline -q
COPY src/ src/
RUN ./mvnw package -DskipTests -q

# ── Stage 2 : Runtime ─────────────────────────────────
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
COPY --from=builder /app/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

Étape 2 - Builder l'image

bash
# Builder avec un tag sémantique (jamais :latest en prod)
docker build -t mon-api:1.0.0 .

# Vérifier l'image produite
docker images mon-api
# REPOSITORY   TAG       IMAGE ID       SIZE
# mon-api      1.0.0     a3f1b2c4d5e6   180MB

# Inspecter les layers (multi-stage = image finale légère)
docker history mon-api:1.0.0

Étape 3 - Lancer et tester le conteneur

bash
# -d : detached, -p : map port host:container, --name : nom lisible
docker run -d -p 8080:8080 --name mon-api-dev mon-api:1.0.0

# Vérifier qu'il tourne
docker ps

# Tester l'endpoint
curl http://localhost:8080/actuator/health
# {"status":"UP"}

# Lire les logs en temps réel
docker logs -f mon-api-dev

# Entrer dans le conteneur pour debug
docker exec -it mon-api-dev sh

# Arrêter et supprimer
docker stop mon-api-dev
docker rm mon-api-dev

Étape 4 - Pousser sur un registry local (optionnel)

bash
# Lancer un registry Docker en local
docker run -d -p 5000:5000 --name local-registry registry:2

# Tagger l'image pour le registry local
docker tag mon-api:1.0.0 localhost:5000/mon-api:1.0.0

# Pousser
docker push localhost:5000/mon-api:1.0.0

# Vérifier
curl http://localhost:5000/v2/mon-api/tags/list
# {"name":"mon-api","tags":["1.0.0"]}
✓ Résultat attendu

L'image est buildée en deux stages (image finale < 200MB), le conteneur répond sur localhost:8080, et les logs Spring Boot s'affichent correctement.
