La mentalité Production

Passer en production, c'est accepter que tout peut échouer. L'objectif n'est pas d'empêcher les pannes, mais de les détecter rapidement et de s'en remettre automatiquement.

SLI / SLO / SLA

ConceptDéfinitionExemple
SLI (Indicator)Métrique mesuréeLatence P99, taux d'erreur, disponibilité
SLO (Objective)Cible interne99.9% de disponibilité, P99 < 500ms
SLA (Agreement)Engagement contractuel99.5% garanti aux clients
Error Budget

Si votre SLO est 99.9%, vous avez un budget d'erreur de 0.1% - soit ~43 minutes d'indisponibilité par mois. Tant que vous restez dans ce budget, vous pouvez déployer rapidement. Si le budget est épuisé, concentrez-vous sur la fiabilité.

Horizontal Pod Autoscaler (HPA)

Le HPA ajuste automatiquement le nombre de réplicas d'un Deployment en fonction des métriques observées.

hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-backend
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60
      policies:
        - type: Pods
          value: 2
          periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
        - type: Percent
          value: 25
          periodSeconds: 60
stabilizationWindow

Le scaleDown.stabilizationWindowSeconds: 300 empêche le HPA de réduire trop vite après un pic. Cela évite les oscillations (flapping) entre scale up et scale down.

Resource Limits - La base de tout

Chaque conteneur doit déclarer ses requests (minimum garanti) et limits (maximum autorisé).

ComposantCPU RequestCPU LimitMem RequestMem Limit
Spring Boot API250m500m256Mi512Mi
PostgreSQL250m1000m256Mi1Gi
Redis100m250m128Mi256Mi
NGINX Ingress100m500m128Mi256Mi
OOMKilled

Si un conteneur dépasse sa memory limit, Kubernetes le tue immédiatement (OOMKilled). Fixez les limits mémoire avec une marge suffisante. Pour la CPU, le conteneur est simplement throttlé (ralenti), pas tué.

Zero-Downtime Deployments

Pour garantir zéro interruption pendant les mises à jour :

Checklist déploiement sans interruption
  • readinessProbe - Le pod ne reçoit du trafic que quand il est prêt
  • Rolling update - maxUnavailable: 0 garantit que tous les anciens pods restent actifs jusqu'à ce que les nouveaux soient prêts
  • PodDisruptionBudget - Protège contre les évictions pendant les maintenances du cluster
  • preStop hook - Donne au pod le temps de terminer les requêtes en cours
  • Graceful shutdown - server.shutdown=graceful dans Spring Boot
pdb.yaml - Pod Disruption Budget
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-pdb
spec:
  minAvailable: 2    # Au moins 2 pods toujours disponibles
  selector:
    matchLabels:
      app: api-backend
deployment.yaml - preStop hook
spec:
  containers:
    - name: api
      lifecycle:
        preStop:
          exec:
            command: ["/bin/sh", "-c", "sleep 10"]
  terminationGracePeriodSeconds: 30
