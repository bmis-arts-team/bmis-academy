CI/CD — Pipeline GitHub Actions

Dans les leçons précédentes, nous avons établi l'architecture : les manifestes Kubernetes vivent dans repo-infra, Flux CD synchronise le cluster depuis Git. Le pipeline CI/CD n'a qu'une seule responsabilité : construire l'image Docker et mettre à jour le tag dans repo-infra. Flux fait le reste.

Ce que fait la CI — et rien d'autre
  1. Exécuter les tests (Maven / Angular)
  2. Construire l'image Docker et la pousser sur GHCR avec un tag immutable
  3. Cloner repo-infra, mettre à jour le newTag dans l'overlay concerné, committer et pousser

La CI ne parle jamais directement au cluster. Elle n'a pas besoin de kubeconfig ni de token Kubernetes. Flux détecte le changement dans repo-infra et applique.

Stratégie de déploiement par branche

  • Push sur develop → image taguée develop-<sha> → mise à jour de l'overlay staging dans repo-infra → Flux déploie automatiquement sur deleevx-staging
  • Push sur main → image taguée v<sha> → mise à jour de l'overlay production → approbation manuelle requise via GitHub Environments → Flux déploie sur deleevx-prod

Les deux pipelines (backend et frontend) sont indépendants. Un fix CSS ne touche pas les overlays backend. Un changement de schéma DB ne redéploie pas le frontend.

Le secret INFRA_REPO_TOKEN

Un PAT avec accès Write sur repo-infra

Le GITHUB_TOKEN automatique n'a accès qu'au repo courant. Pour écrire dans repo-infra depuis repo-backend ou repo-frontend, créez un Fine-grained Personal Access Token (ou un GitHub App Token) avec :

  • Repository : ITCloud-Consulting/repo-infra
  • Permission : Contents → Read & Write

Ajoutez ce token sous le nom INFRA_REPO_TOKEN dans les secrets de chaque repo applicatif (backend et frontend).

Préférez un GitHub App Token en production : il est lié à l'organisation, ne dépend pas d'un compte personnel et peut être révoqué sans impacter les accès humains.

Approbation manuelle pour la production

GitHub Environments — comment ça fonctionne

Le job update-infra-prod déclare environment: production. Dans les paramètres GitHub du repo, configurez cet environnement avec :

  • Required reviewers : les DevOps seniors autorisés à valider un déploiement prod
  • Wait timer : optionnel — délai de sécurité avant exécution
  • Deployment branches : restreindre à main uniquement

Lorsqu'un push arrive sur main, le pipeline s'arrête avant ce job et envoie une notification. Le reviewer approuve (ou rejette) depuis l'interface GitHub. Flux ne déploie en prod que si un humain a validé le commit dans repo-infra.

Vue d'ensemble de l'architecture complète

Flux de bout en bout — du commit au pod
  1. repo-backend ou repo-frontend : push sur develop ou main
  2. GitHub Actions : tests → build image → push GHCR
  3. GitHub Actions : clone repo-infra, kustomize edit set image dans l'overlay cible, commit, push
  4. repo-infra : PR de validation auto déclenchée (workflow validate.yaml vu en leçon 20)
  5. Flux CD : détecte le nouveau commit dans repo-infra toutes les 5m
  6. Flux applique l'overlay modifié → rolling update sur le namespace cible
  7. Kubernetes : kubectl rollout status confirme la mise à jour

La CI ne connaît pas l'adresse du cluster. Le cluster n'est pas exposé à internet pour les déploiements. Git est l'unique source de vérité.

CDN & Distribution

Sujet traité dans la leçon théorique

La stratégie CDN complète (Cloudflare, caching des assets Angular, rules par type de fichier, bypass de l'API) est couverte en détail dans la Leçon 14 — CDN & Distribution.

Pour DeleevX, l'intégration se résume à trois étapes :

  1. Mettre Cloudflare en proxy Proxied devant votre domaine.
  2. Créer des Cache Rules ciblant *.js, *.css, assets/* — TTL 1 mois.
  3. Ajouter un bypass explicite sur api.* pour ne jamais cacher les réponses API.
