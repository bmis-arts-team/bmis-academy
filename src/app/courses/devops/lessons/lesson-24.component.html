Resource Quotas & Limit Ranges

En production, il faut empêcher un seul Deployment de consommer toutes les ressources du VPS. Deux mécanismes complémentaires permettent ça : les ResourceQuotas (budget total du namespace) et les LimitRanges (contraintes par conteneur).

apps/overlays/production/resource-quota.yaml (dans repo-infra)
apiVersion: v1
kind: ResourceQuota
metadata:
  name: deleevx-prod-quota
  namespace: deleevx-prod
spec:
  hard:
    requests.cpu: "4"           # Total CPU demandé max dans le namespace
    requests.memory: "6Gi"      # Total RAM demandée max
    limits.cpu: "6"             # Total CPU limit max
    limits.memory: "8Gi"        # Total RAM limit max
    pods: "20"                  # Nombre max de pods dans le namespace
    services: "10"              # Nombre max de Services
    persistentvolumeclaims: "5" # Nombre max de PVCs
apps/overlays/production/limit-range.yaml (dans repo-infra)
apiVersion: v1
kind: LimitRange
metadata:
  name: deleevx-prod-limits
  namespace: deleevx-prod
spec:
  limits:
    - type: Container
      default:                  # Limites par défaut si non spécifiées
        cpu: "500m"
        memory: "256Mi"
      defaultRequest:           # Requests par défaut si non spécifiées
        cpu: "100m"
        memory: "128Mi"
      min:                      # Minimum autorisé
        cpu: "50m"
        memory: "64Mi"
      max:                      # Maximum autorisé
        cpu: "2000m"
        memory: "2Gi"
Terminal - Appliquer et vérifier
# Appliquer (opération initiale — Flux gère les mises à jour ensuite)
kubectl apply -f apps/overlays/production/resource-quota.yaml
kubectl apply -f apps/overlays/production/limit-range.yaml

# Vérifier le quota
kubectl describe resourcequota deleevx-prod-quota -n deleevx-prod
# Name:                   prod-quota
# Resource                Used   Hard
# --------                ----   ----
# limits.cpu              3500m  6
# limits.memory           3Gi    8Gi
# pods                    7      20
# requests.cpu            1150m  4
# requests.memory         1.5Gi  6Gi

# Tester : créer un pod qui dépasse le quota
# → Erreur : "exceeded quota: prod-quota"
Quota vs LimitRange en résumé

ResourceQuota = « le namespace deleevx-prod ne peut pas utiliser plus de 8 Gi de RAM au total ».
LimitRange = « chaque conteneur dans deleevx-prod doit demander entre 64 Mi et 2 Gi de RAM ».

Gestion des Secrets

Les Secrets Kubernetes sont encodés en base64 - pas chiffrés. Quiconque a accès au cluster peut les lire. Voici les bonnes pratiques pour les protéger.

Option 1 : Sealed Secrets (recommandé pour Git)

Terminal - Installer Sealed Secrets
# Installer le contrôleur
helm repo add sealed-secrets \
  https://bitnami-labs.github.io/sealed-secrets
helm install sealed-secrets sealed-secrets/sealed-secrets \
  --namespace kube-system

# Installer l'outil CLI kubeseal
# macOS : brew install kubeseal
# Linux : wget https://github.com/bitnami-labs/sealed-secrets/releases/...

# Créer un Secret classique (ne pas committer celui-ci !)
kubectl create secret generic db-credentials \
  --namespace=deleevx-prod \
  --from-literal=username=myapp \
  --from-literal=password='SuperSecret123!' \
  --dry-run=client -o yaml > secret.yaml

# Le chiffrer avec kubeseal
kubeseal --format yaml < secret.yaml > sealed-secret.yaml

# sealed-secret.yaml peut être commité dans Git !
# Seul le contrôleur sur VOTRE cluster peut le déchiffrer

# Appliquer
kubectl apply -f sealed-secret.yaml
# Le contrôleur déchiffre et crée le Secret classique automatiquement

# Supprimer le secret en clair
rm secret.yaml

Option 2 : External Secrets Operator

Pour les environnements cloud

Si vous avez accès à AWS Secrets Manager, Azure Key Vault ou HashiCorp Vault, l'External Secrets Operator synchronise automatiquement les secrets depuis ces services vers des Secrets Kubernetes. Plus sécurisé que Sealed Secrets pour les grandes équipes.

Network Policies - Isolation réseau

Par défaut, tous les pods d'un cluster Kubernetes peuvent communiquer entre eux. Les NetworkPolicies ajoutent des règles de pare-feu pour isoler les namespaces et restreindre les communications.

k8s/apps/deleevx/overlays/prod/network-policy.yaml
# Politique par défaut : bloquer tout trafic entrant dans prod
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: deleevx-prod
spec:
  podSelector: {}           # S'applique à TOUS les pods du namespace
  policyTypes:
    - Ingress
---
# Autoriser le trafic de l'Ingress Controller vers le frontend
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-ingress-to-frontend
  namespace: deleevx-prod
spec:
  podSelector:
    matchLabels:
      app: frontend
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: ingress-nginx
      ports:
        - port: 80
---
# Autoriser le trafic de l'Ingress Controller vers le backend
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-ingress-to-backend
  namespace: deleevx-prod
spec:
  podSelector:
    matchLabels:
      app: backend
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: ingress-nginx
      ports:
        - port: 8080
---
# Autoriser le backend à contacter PostgreSQL et Redis
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-backend-to-data
  namespace: deleevx-prod
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
    - Egress
  egress:
    - to:
        - podSelector:
            matchLabels:
              app: postgres
      ports:
        - port: 5432
    - to:
        - podSelector:
            matchLabels:
              app: redis
      ports:
        - port: 6379
    - to:                          # Autoriser DNS (CoreDNS)
        - namespaceSelector: {}
      ports:
        - port: 53
          protocol: UDP
        - port: 53
          protocol: TCP
Terminal - Appliquer et tester
# Appliquer
kubectl apply -f k8s/apps/deleevx/overlays/prod/network-policy.yaml

# Tester : depuis un pod dev, essayer de contacter la BDD prod
kubectl run test-pod -n deleevx-dev --rm -it --image=busybox -- sh
# Dans le pod :
wget -qO- --timeout=3 http://postgres.deleevx-prod:5432
# Résultat attendu : timeout (bloqué par la NetworkPolicy)

# Depuis un pod deleevx-prod backend :
kubectl exec -it deployment/backend -n deleevx-prod -- sh
wget -qO- --timeout=3 http://postgres:5432
# Résultat attendu : connexion établie

Rate Limiting & TLS

Rate limiting au niveau Ingress

k8s/apps/deleevx/base/ingress.yaml - Annotations de sécurité
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: main-ingress
  annotations:
    # HTTPS
    cert-manager.io/cluster-issuer: "letsencrypt-prod"
    nginx.ingress.kubernetes.io/ssl-redirect: "true"

    # Rate limiting
    nginx.ingress.kubernetes.io/limit-rps: "10"         # 10 req/sec par IP
    nginx.ingress.kubernetes.io/limit-burst-multiplier: "5"  # Burst de 50

    # Sécurité headers
    nginx.ingress.kubernetes.io/configuration-snippet: |
      more_set_headers "X-Frame-Options: DENY";
      more_set_headers "X-Content-Type-Options: nosniff";
      more_set_headers "X-XSS-Protection: 1; mode=block";
      more_set_headers "Referrer-Policy: strict-origin-when-cross-origin";
      more_set_headers "Permissions-Policy: camera=(), microphone=(), geolocation=()";

    # Taille max du body (uploads)
    nginx.ingress.kubernetes.io/proxy-body-size: "10m"

    # Timeouts
    nginx.ingress.kubernetes.io/proxy-connect-timeout: "10"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "30"
    nginx.ingress.kubernetes.io/proxy-send-timeout: "30"
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - mondomaine.com
        - api.mondomaine.com
      secretName: tls-certificate
  rules:
    - host: mondomaine.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend
                port:
                  number: 80
    - host: api.mondomaine.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: backend
                port:
                  number: 80

Sauvegardes automatiques de la base de données

En production, la base de données doit être sauvegardée automatiquement. On configure un CronJob Kubernetes qui exécute un pg_dump deux fois par jour et stocke le fichier dans un bucket Google Cloud Storage (GCS).

Firebase Storage, Google Drive ou GCS ?
  • Firebase Storage — non recommandé pour des backups : plan gratuit limité à 1 GB, conçu pour les assets applicatifs (images, vidéos), pas pour du scripting CLI robuste.
  • Google Drive — possible avec rclone, mais l'API Drive n'est pas conçue pour des backups automatisés fiables.
  • Google Cloud Storage (GCS) — recommandé. Stockage objet durable, CLI gsutil intégré, lifecycle policies (suppression auto), ~0,02 $/GB/mois. Votre compte Google Workspace donne déjà accès à GCP — aucun abonnement supplémentaire.

1. Créer le bucket et le Service Account GCP

Terminal — gcloud CLI
# Créer le bucket dans la région de votre VPS
gsutil mb -l europe-west1 gs://deleevx-backups-prod

# Rétention : lifecycle.json = { "rule": [{ "action": {"type":"Delete"}, "condition": {"age":30} }] }
gsutil lifecycle set lifecycle.json gs://deleevx-backups-prod

# Créer un Service Account dédié (principe du moindre privilège)
gcloud iam service-accounts create deleevx-backup-sa \
  --display-name="DeleevX Backup SA"

# Droit d'écriture sur CE bucket uniquement — pas sur le reste du projet GCP
gsutil iam ch \
  serviceAccount:deleevx-backup-sa@VOTRE_PROJECT_ID.iam.gserviceaccount.com:objectCreator \
  gs://deleevx-backups-prod

# Générer la clé JSON du Service Account
gcloud iam service-accounts keys create ./sa-backup-key.json \
  --iam-account=deleevx-backup-sa@VOTRE_PROJECT_ID.iam.gserviceaccount.com

2. Stocker la clé dans un Secret Kubernetes

Terminal — namespace deleevx-prod uniquement
kubectl create secret generic gcs-backup-credentials \
  --namespace=deleevx-prod \
  --from-literal=bucket-name=deleevx-backups-prod \
  --from-file=service-account-key=./sa-backup-key.json

# Supprimer la clé locale — ne jamais la committer dans Git
rm ./sa-backup-key.json

3. CronJob Kubernetes

Le job utilise un initContainer pour le pg_dump et un conteneur principal pour l'upload sur GCS. Les deux partagent un volume emptyDir temporaire. Si le dump échoue, l'upload ne démarre jamais.

k8s/apps/deleevx/overlays/prod/backup-cronjob.yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: postgres-backup
  # Dans overlays/prod/ uniquement — les backups ne tournent qu'en production
spec:
  schedule: "0 2,14 * * *"      # 2h et 14h UTC (4h et 16h heure Paris en été)
  concurrencyPolicy: Forbid      # Pas de job concurrent si le précédent tourne encore
  successfulJobsHistoryLimit: 7
  failedJobsHistoryLimit: 3

  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: OnFailure

          volumes:
            - name: backup-tmp
              emptyDir: {}      # Volume temporaire partagé entre initContainer et conteneur principal

          initContainers:
            # ── Étape 1 : pg_dump ────────────────────────────────────────────
            - name: pg-dump
              image: postgres:16-alpine
              command:
                - sh
                - -c
                - |
                  TIMESTAMP=$(date +%Y%m%d_%H%M%S)
                  pg_dump -h postgres -U $PGUSER -d $PGDATABASE -F c \
                    -f /backup/backup_$TIMESTAMP.dump
                  echo "$TIMESTAMP" > /backup/timestamp.txt
                  echo "Dump OK : $(du -sh /backup/backup_$TIMESTAMP.dump | cut -f1)"
              env:
                - name: PGUSER
                  valueFrom:
                    secretKeyRef:
                      name: db-credentials
                      key: username
                - name: PGDATABASE
                  value: "mydb"
                - name: PGPASSWORD
                  valueFrom:
                    secretKeyRef:
                      name: db-credentials
                      key: password
              volumeMounts:
                - name: backup-tmp
                  mountPath: /backup

          containers:
            # ── Étape 2 : upload vers GCS ────────────────────────────
            - name: gcs-upload
              image: google/cloud-sdk:alpine
              command:
                - sh
                - -c
                - |
                  TIMESTAMP=$(cat /backup/timestamp.txt)
                  echo "$GCS_SA_KEY" > /tmp/sa-key.json
                  gcloud auth activate-service-account \
                    --key-file=/tmp/sa-key.json --quiet
                  gsutil cp /backup/backup_$TIMESTAMP.dump \
                    gs://$GCS_BUCKET/deleevx/prod/$TIMESTAMP.dump
                  echo "Upload OK : gs://$GCS_BUCKET/deleevx/prod/$TIMESTAMP.dump"
                  rm /tmp/sa-key.json
              env:
                - name: GCS_BUCKET
                  valueFrom:
                    secretKeyRef:
                      name: gcs-backup-credentials
                      key: bucket-name
                - name: GCS_SA_KEY
                  valueFrom:
                    secretKeyRef:
                      name: gcs-backup-credentials
                      key: service-account-key
              volumeMounts:
                - name: backup-tmp
                  mountPath: /backup
              resources:
                requests:
                  cpu: "100m"
                  memory: "128Mi"
                limits:
                  cpu: "200m"
                  memory: "256Mi"
Pourquoi initContainer pour le dump ?

Les initContainers s'exécutent séquentiellement avant le conteneur principal et doivent réussir pour que le job continue. En cas d'échec du pg_dump (base inaccessible, disque plein…), le conteneur d'upload ne démarre jamais — aucun fichier vide ou corrompu ne sera envoyé sur GCS.
