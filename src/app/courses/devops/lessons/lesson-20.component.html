Autoscaling avec HPA

Le HorizontalPodAutoscaler (HPA) ajuste automatiquement le nombre de réplicas d'un Deployment en fonction de métriques observées (CPU, mémoire, métriques custom). Sur un VPS, l'autoscaling est limité par les ressources physiques - mais il permet de maximiser l'utilisation de ce qui est disponible.

Pré-requis

Le Metrics Server doit être installé. Avec k3s, il est inclus par défaut. Vérifiez avec : kubectl top nodes

k8s/overlays/prod/hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: backend-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: backend
  minReplicas: 2              # Minimum en prod (haute dispo)
  maxReplicas: 5              # Max réaliste pour un VPS 8GB
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70    # Scale up quand CPU > 70%
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80    # Scale up quand RAM > 80%
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60    # Attendre 60s avant de scale up
      policies:
        - type: Pods
          value: 1                       # +1 pod à la fois
          periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 300   # Attendre 5min avant de scale down
      policies:
        - type: Pods
          value: 1
          periodSeconds: 120

Explication des paramètres

Scale Up

  • averageUtilization: 70 - Si la moyenne CPU de tous les pods dépasse 70%, on ajoute un pod
  • stabilizationWindow: 60s - Évite les oscillations rapides
  • +1 pod par minute max - Scaling progressif, pas brutal

Scale Down

  • stabilizationWindow: 300s - Attend 5 minutes de calme avant de réduire
  • -1 pod toutes les 2 min - Réduit progressivement pour éviter les pics de retour

Tester l'autoscaling manuellement

Terminal - Simuler de la charge
# Appliquer le HPA
kubectl apply -f k8s/overlays/prod/hpa.yaml

# Vérifier le statut du HPA
kubectl get hpa -n prod
# NAME          REFERENCE        TARGETS   MINPODS   MAXPODS   REPLICAS   AGE
# backend-hpa   Deployment/backend   25%/70%   2         5         2          1m

# Simuler de la charge CPU avec un pod de stress
kubectl run stress-test -n prod --rm -it \
  --image=busybox -- sh -c \
  "while true; do wget -q -O- http://backend/api/health; done"

# Dans un autre terminal, observer le scaling
kubectl get hpa -n prod --watch
# TARGETS augmente... puis REPLICAS passe de 2 à 3, 4...

# Arrêter le stress (Ctrl+C)
# Après ~5 minutes, le HPA scale down progressivement

# Vérifier les événements
kubectl describe hpa backend-hpa -n prod
# Events:
#   Normal  SuccessfulRescale  ...  New size: 3; reason: cpu resource utilization above target

Observabilité - Prometheus & Grafana

Prometheus collecte les métriques en scrappant les endpoints /metrics. Grafana les visualise dans des dashboards. Ensemble, ils forment le standard de l'observabilité dans l'écosystème Kubernetes.

Installation via Helm

Terminal - VPS
# Ajouter le repo Helm
helm repo add prometheus-community \
  https://prometheus-community.github.io/helm-charts
helm repo update

# Installer le stack complet (Prometheus + Grafana + AlertManager)
helm install monitoring prometheus-community/kube-prometheus-stack \
  --namespace monitoring \
  --create-namespace \
  --set prometheus.prometheusSpec.retention=7d \
  --set prometheus.prometheusSpec.resources.requests.memory=256Mi \
  --set prometheus.prometheusSpec.resources.limits.memory=512Mi \
  --set grafana.resources.requests.memory=128Mi \
  --set grafana.resources.limits.memory=256Mi \
  --set alertmanager.enabled=true

# Vérifier l'installation
kubectl get pods -n monitoring
# NAME                                                     READY   STATUS    RESTARTS   AGE
# monitoring-grafana-xxx                                   3/3     Running   0          2m
# monitoring-kube-prometheus-operator-xxx                  1/1     Running   0          2m
# monitoring-kube-state-metrics-xxx                        1/1     Running   0          2m
# monitoring-prometheus-node-exporter-xxx                  1/1     Running   0          2m
# prometheus-monitoring-kube-prometheus-prometheus-0        2/2     Running   0          2m
# alertmanager-monitoring-kube-prometheus-alertmanager-0    2/2     Running   0          2m

Accéder à Grafana

Terminal
# Méthode 1 : Port-forward (debug rapide)
kubectl port-forward svc/monitoring-grafana 3000:80 -n monitoring
# Accessible sur http://localhost:3000

# Récupérer le mot de passe admin
kubectl get secret monitoring-grafana -n monitoring \
  -o jsonpath="{.data.admin-password}" | base64 -d
# Login : admin / (le mot de passe affiché)

# Méthode 2 : Ingress dédié pour un accès permanent
# Ajoutez cette règle dans votre ingress.yaml :
# - host: grafana.mondomaine.com
#   http:
#     paths:
#       - path: /
#         pathType: Prefix
#         backend:

#             port:
#               number: 80

Exposer les métriques Spring Boot

backend/pom.xml - Dépendance
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
backend/src/main/resources/application.yml
management:
  endpoints:
    web:
      exposure:
        include: health, prometheus, info
  metrics:
    tags:
      application: myapp-backend

ServiceMonitor pour scraper le backend

k8s/base/backend-servicemonitor.yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: backend-monitor
  labels:
    release: monitoring    # DOIT matcher le label du Prometheus Operator
spec:
  selector:
    matchLabels:
      app: backend
  endpoints:
    - port: http
      path: /actuator/prometheus
      interval: 15s
Terminal - Vérifier
# Appliquer le ServiceMonitor
kubectl apply -f k8s/base/backend-servicemonitor.yaml

# Vérifier que Prometheus scrape le backend
# Ouvrir Grafana → Explorer → Prometheus
# Requête PromQL :
# up{job="backend"}
# Résultat attendu : 1 (le target est UP)

Métriques essentielles à surveiller

Métriques Système

  • node_cpu_seconds_total - Utilisation CPU du nœud
  • node_memory_MemAvailable_bytes - RAM disponible
  • node_disk_io_time_seconds_total - I/O disque
  • kubelet_running_pods - Nombre de pods actifs

Métriques Application

  • http_server_requests_seconds_count - Nombre de requêtes HTTP
  • http_server_requests_seconds_sum - Temps total de réponse
  • jvm_memory_used_bytes - Mémoire JVM utilisée
  • hikaricp_connections_active - Connexions DB actives
