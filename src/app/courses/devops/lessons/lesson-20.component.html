Sur un VPS unique (pas de LoadBalancer cloud), on utilise hostNetwork: true pour que le contrôleur NGINX écoute directement sur les ports 80 et 443 du VPS.

L'Ingress de base — structure sans domaine

La base/ définit la structure de l'Ingress (services cibles, annotations). Les noms de domaine sont injectés par chaque overlay via un patch — sinon vous auriez les URLs de prod codées en dur dans la base, ce qui est faux pour dev et staging.

repo-infra/apps/base/backend/ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: main-ingress
  annotations:
    cert-manager.io/cluster-issuer: "letsencrypt-prod"
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/proxy-body-size: "10m"
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - placeholder.com          # Remplacé par chaque overlay
        - api.placeholder.com
      secretName: tls-certificate
  rules:
    - host: placeholder.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend
                port:
                  number: 80
    - host: api.placeholder.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: backend
                port:
                  number: 80

Ingress dédié pour les SSE (Server-Sent Events)

Problème : NGINX bufférise les réponses par défaut

Le backend Spring Boot expose des endpoints SSE (ex: /api/events). NGINX bufférise les réponses HTTP — il attend d'avoir un buffer plein avant de transmettre au client. Résultat : les événements SSE sont bloqués ou retardés, et la connexion est coupée après le timeout par défaut de 60 secondes.

La solution : un second Ingress ciblant uniquement les routes SSE du backend, avec les annotations adaptées. On ne modifie pas l'Ingress principal pour ne pas impacter le frontend et les autres endpoints.

repo-infra/apps/base/backend/ingress-sse.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: backend-sse-ingress
  annotations:
    cert-manager.io/cluster-issuer: "letsencrypt-prod"
    nginx.ingress.kubernetes.io/ssl-redirect: "true"

    # Désactiver le buffering — indispensable pour SSE
    # Sans ça, NGINX retient les événements jusqu'à remplir le buffer
    nginx.ingress.kubernetes.io/proxy-buffering: "off"

    # Timeout de lecture élevé — les connexions SSE sont longues
    # 3600s = 1h, ajustez selon vos besoins
    nginx.ingress.kubernetes.io/proxy-read-timeout: "3600"
    nginx.ingress.kubernetes.io/proxy-send-timeout: "3600"

    # Désactiver le cache pour ces routes
    nginx.ingress.kubernetes.io/configuration-snippet: |
      add_header Cache-Control "no-cache";
      add_header X-Accel-Buffering "no";
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - api.placeholder.com      # Remplacé par chaque overlay
      secretName: tls-certificate
  rules:
    - host: api.placeholder.com
      http:
        paths:
          - path: /api/events      # Adaptez au(x) chemin(s) SSE de votre backend
            pathType: Prefix
            backend:
              service:
                name: backend
                port:
                  number: 80
X-Accel-Buffering: no

Ce header demande à NGINX de désactiver le buffering au niveau du proxy upstream. C'est le mécanisme standard reconnu par NGINX, Varnish et d'autres proxies. Spring Boot peut aussi l'émettre lui-même depuis le contrôleur SSE : 

@GetMapping(value = "/api/events", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter stream(HttpServletResponse response) {
    response.setHeader("X-Accel-Buffering", "no");
    response.setHeader("Cache-Control", "no-cache");
    SseEmitter emitter = new SseEmitter(Long.MAX_VALUE);
    // ...
    return emitter;
}

Ajoutez ingress-sse.yaml dans base/kustomization.yaml et créez un patch par overlay pour substituer le host (même pattern que l'Ingress principal).

Spécificités K3s

K3s est une distribution Kubernetes allégée, idéale pour les VPS. Elle intègre plusieurs composants qui diffèrent d'un cluster cloud standard (EKS, GKE).

Traefik vs NGINX Ingress

K3s inclut Traefik par défaut

Contrairement à un cluster cloud, K3s déploie automatiquement Traefik comme Ingress Controller. Deux options :

  • Utiliser Traefik — remplacez ingressClassName: nginx par ingressClassName: traefik dans vos Ingress.
  • Remplacer par NGINX — désactivez Traefik au bootstrap et installez NGINX Ingress Controller (comme dans ce cours). Plus de flexibilité, annotations familières.
Terminal - Désactiver Traefik au bootstrap K3s
# Installer K3s sans Traefik intégré
curl -sfL https://get.k3s.io | sh -s - --disable traefik

# Puis installer NGINX Ingress Controller
helm install ingress-nginx ingress-nginx/ingress-nginx   --namespace ingress-nginx --create-namespace   --set controller.hostNetwork=true

Stockage persistant avec local-path

StorageClass local-path intégrée

K3s inclut la StorageClass local-path qui provisionne automatiquement des volumes sur le disque local du nœud. Aucune configuration supplémentaire n'est nécessaire — c'est ce qui permet au StatefulSet PostgreSQL de fonctionner sans infrastructure de stockage externe. 

# Vérifier les StorageClasses disponibles
kubectl get storageclass
# NAME                   PROVISIONER             RECLAIMPOLICY
# local-path (default)   rancher.io/local-path   Delete

Sauvegarde du control plane

K3s utilise SQLite — pas etcd

Par défaut, K3s stocke l'état du cluster dans un fichier SQLite (/var/lib/rancher/k3s/server/db/state.db). Ce fichier et la clé maître Sealed Secrets sont vos deux points de défaillance critiques. Automatisez leur sauvegarde. 

# Sauvegarder la DB K3s automatiquement chaque nuit
echo "0 3 * * * root cp /var/lib/rancher/k3s/server/db/state.db   /backup/k3s-$(date +%Y%m%d).db" >> /etc/cron.d/k3s-backup

GitOps avec Flux CD

Appliquer kubectl apply manuellement en production est une source d'erreurs et d'inconsistances. Flux CD synchronise automatiquement l'état du cluster avec Git : ce qui est dans la branche main est ce qui tourne en production.

Le cycle de déploiement GitOps
  1. Développeur push du code → GitHub Actions build l'image Docker
  2. L'image est publiée sur GHCR avec un tag précis (ex : v1.4.2)
  3. La CI ouvre une PR sur repo-infra pour mettre à jour le tag d'image
  4. PR revue et mergée → Flux détecte le changement dans Git
  5. Flux applique le manifeste mis à jour → rolling update automatique

En production, on n'utilise jamais le tag latest — toujours un tag précis et immutable (v1.4.2, sha-abc123). latest est acceptable uniquement en développement local.

Déploiement automatique sur la branche develop

Chaque push sur develop déclenche un pipeline qui, si le build passe, met à jour automatiquement le tag d'image dans l'overlay development de repo-infra. Flux détecte la modification et déploie sur l'environnement dev sans intervention humaine.

Séquence complète push → déploiement dev
  1. Push sur develop dans repo-backend
  2. GitHub Actions build l'image et la pousse sur GHCR avec le tag develop-<sha>
  3. Le pipeline met à jour newTag dans l'overlay development de repo-infra et commit
  4. Flux détecte le commit dans repo-infra et applique le manifeste
  5. Rolling update automatique sur le namespace development

Le tag develop-<sha> (ex : develop-a3f9c12) est immutable et traçable — on sait exactement quel commit est déployé sur dev.

repo-backend/.github/workflows/deploy-dev.yaml
Créer le secret INFRA_REPO_TOKEN

Le pipeline doit écrire dans repo-infra depuis repo-backend. Le GITHUB_TOKEN par défaut n'a accès qu'au repo courant. Créez un Personal Access Token (PAT) ou un GitHub App Token avec accès Write sur repo-infra et stockez-le dans les secrets de repo-backend sous le nom INFRA_REPO_TOKEN.

Même logique pour repo-frontend → overlay development/frontend.

Pourquoi ne pas déployer directement avec kubectl depuis la CI ?

La CI n'a pas besoin de connaître l'adresse du cluster ni d'avoir un kubeconfig. Elle fait une seule chose : mettre à jour un fichier dans Git. Flux fait le reste. Cette séparation est le cœur du pattern GitOps — le cluster tire ses déploiements depuis Git, il ne les reçoit pas en push depuis l'extérieur.

Validation CI/CD des manifestes

Toute PR sur repo-infra déclenche une validation automatique. Deux vérifications essentielles : conformité des manifestes Kubernetes et absence de secrets en clair.

repo-infra/.github/workflows/validate.yaml
name: Validate Manifests

on: [pull_request]

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install kustomize
        run: |
          curl -s "https://raw.githubusercontent.com/kubernetes-sigs/kustomize/master/hack/install_kustomize.sh" | bash
          sudo mv kustomize /usr/local/bin/

      - name: Install kubeconform
        run: |
          wget -q https://github.com/yannh/kubeconform/releases/latest/download/kubeconform-linux-amd64.tar.gz
          tar xf kubeconform-linux-amd64.tar.gz
          sudo mv kubeconform /usr/local/bin/

      - name: Valider tous les overlays
        run: |
          for overlay in apps/overlays/*/; do
            echo "Validation de $overlay"
            kustomize build $overlay | kubeconform               -strict               -ignore-missing-schemas
          done

      - name: Vérifier l'absence de secrets en clair
        run: |
          # Interdit : "kind: Secret" non chiffré dans les manifestes
          if grep -rn "^kind: Secret$" apps/ --include="*.yaml"              | grep -v "SealedSecret"; then
            echo "ERREUR : Secret non chiffré détecté — utilisez Sealed Secrets"
            exit 1
          fi
          echo "OK : aucun secret en clair trouvé"
Protection de branche sur repo-infra

Configurez la branche main pour exiger :

  • Au moins 1 reviewer DevOps senior
  • Passage des checks CI (validation des manifestes)
  • Commits signés — audit trail : qui a déployé quoi et quand

Règles d'or

À retenir et appliquer dès le premier jour
  • Un repo infra dédié — non négociable dès que vous avez plusieurs environnements et plusieurs personnes. Les manifestes de prod n'ont rien à faire dans le repo applicatif.
  • Aucun secret en clair dans Git, jamais — Sealed Secrets est la solution la plus pragmatique pour K3s. HashiCorp Vault est pour les équipes ayant déjà une maturité DevOps avancée.
  • Kustomize base + overlays — chaque patch doit être minimal et explicite. Ne copiez jamais un manifeste complet d'un environnement à l'autre.
  • GitOps avec Flux ou ArgoCD — même sur un VPS, n'appliquez jamais kubectl apply manuellement en prod. Ce que Git dit = ce qui tourne.
  • Jamais latest en production — utilisez des tags précis et immutables (v1.4.2, sha-abc123). latest est mutable et non reproductible.
  • Sauvegardez les deux points critiques K3s — la base SQLite (/var/lib/rancher/k3s/server/db/state.db) et la clé maître Sealed Secrets. Leur perte est irréversible.
