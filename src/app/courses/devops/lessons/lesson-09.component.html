Pourquoi CI/CD ?

Le CI/CD (Continuous Integration / Continuous Deployment) automatise le cycle de vie du logiciel : build, test, packaging et déploiement. Sans CI/CD, chaque mise en production est manuelle, lente et risquée.

  git push ──▶ CI Pipeline ──▶ Build ──▶ Test ──▶ Push Image ──▶ Deploy to K8s
                                                                      │
                                                         ┌────────────┼──────────┐
                                                         ▼            ▼          ▼
                                                      Staging    Production   Rollback

GitHub Actions - Concepts

ConceptDescription
WorkflowFichier YAML dans .github/workflows/
TriggerÉvénement déclencheur (push, pull_request, schedule)
JobGroupe d'étapes exécutées sur un runner
StepCommande ou action individuelle
ActionBloc réutilisable (ex: actions/checkout)
SecretVariable chiffrée (tokens, mots de passe)

Pipeline complet - Build, Test, Deploy

.github/workflows/ci-cd.yml
name: CI/CD Pipeline

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  # ── Build & Test ─────────────────────────
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup JDK 21
        uses: actions/setup-java@v4
        with:
          java-version: '21'
          distribution: 'temurin'
          cache: maven

      - name: Build & Test
        run: mvn verify -B

      - name: Upload test results
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: test-results
          path: target/surefire-reports/

  # ── Build & Push Docker Image ────────────
  docker:
    needs: build
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4

      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: |
            ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}
            ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:latest

  # ── Deploy to Staging ────────────────────
  deploy-staging:
    needs: docker
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - uses: actions/checkout@v4

      - name: Set up kubectl
        uses: azure/setup-kubectl@v3

      - name: Configure kubeconfig
        run: echo "${{ secrets.KUBE_CONFIG }}" | base64 -d > kubeconfig
        env:
          KUBECONFIG: kubeconfig

      - name: Deploy to staging
        run: |
          kubectl set image deployment/api-backend \
            api=${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }} \
            -n staging
          kubectl rollout status deployment/api-backend -n staging --timeout=120s

  # ── Deploy to Production (manual) ───────
  deploy-prod:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production   # Requires manual approval
    steps:
      - name: Deploy to production
        run: |
          kubectl set image deployment/api-backend \
            api=${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }} \
            -n production
          kubectl rollout status deployment/api-backend -n production --timeout=180s

Bonnes pratiques CI/CD

Règles essentielles
  • Utilisez des environnements GitHub avec approbation manuelle pour la production
  • Taggez les images avec le SHA du commit, pas :latest
  • Gardez les secrets dans GitHub Secrets, jamais dans le code
  • Exécutez les tests avant le build Docker pour un feedback rapide
  • Utilisez le cache Maven/Gradle pour accélérer les builds
  • Ajoutez un rollback automatique si le health check échoue après déploiement

Travaux Pratiques — Pipeline CI/CD avec GitHub Actions

Prérequis : Un dépôt GitHub, Docker Hub (ou GitHub Container Registry). Ce lab crée un vrai pipeline qui build, teste et pousse l'image Docker à chaque push sur main.

Lab Pipeline Build → Test → Push → Déploiement ~30 min

Objectifs

  • Configurer les secrets GitHub (DOCKERHUB_USERNAME, DOCKERHUB_TOKEN)
  • Créer un workflow qui build et pousse l'image à chaque push
  • Ajouter une étape de tests automatisés
  • Ajouter une étape de déploiement sur le cluster Kind

Étape 1 — Configurer les secrets GitHub

Dans votre dépôt : Settings → Secrets and variables → Actions → New repository secret

Secrets à créer
DOCKERHUB_USERNAME   # votre username Docker Hub
DOCKERHUB_TOKEN      # Access Token Docker Hub (pas votre mot de passe)
                     # → hub.docker.com → Account Settings → Security → New Access Token

Étape 2 — Créer le workflow

Créez le fichier .github/workflows/ci-cd.yml dans votre dépôt :

.github/workflows/ci-cd.yml
name: CI/CD Pipeline

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

env:
  IMAGE_NAME: ${{ secrets.DOCKERHUB_USERNAME }}/mon-api
  IMAGE_TAG: ${{ github.sha }}   # SHA du commit = tag unique et traçable

jobs:
  # ── Job 1 : Tests ────────────────────────────────
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with:
          java-version: '21'
          distribution: 'temurin'
          cache: maven

      - name: Run tests
        run: ./mvnw test

      - name: Upload test report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: test-report
          path: target/surefire-reports/

  # ── Job 2 : Build & Push (seulement sur main) ───
  build-push:
    runs-on: ubuntu-latest
    needs: test
    if: github.ref == 'refs/heads/main'
    steps:
      - uses: actions/checkout@v4

      - name: Login to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: |
            ${{ env.IMAGE_NAME }}:${{ env.IMAGE_TAG }}
            ${{ env.IMAGE_NAME }}:latest

Étape 3 — Observer le pipeline

git add .github/workflows/ci-cd.yml
git commit -m "feat: add CI/CD pipeline"
git push origin main

# GitHub Actions lançe automatiquement le pipeline
# Suivre dans : github.com/<user>/<repo> → onglet Actions

# Simuler un échec : introduire un test qui échoue
# Modifier un test, pousser et observer que le job 'build-push' ne s'exécute PAS
# Le pipeline bloque à l'étape 'test' grâce à needs: test
✓ Résultat attendu

Chaque push sur main exécute les tests, puis (si OK) build et pousse l'image tagée avec le SHA du commit sur Docker Hub. Un test échoué bloque le push de l'image.
