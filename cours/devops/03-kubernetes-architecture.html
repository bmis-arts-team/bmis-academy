Leçon 3 Section 2 - Kubernetes Core

Architecture Kubernetes

Comprendre l'architecture complète de Kubernetes : Control Plane, Nodes, Pods, et le cycle de vie des workloads.

1 - Pourquoi Kubernetes ?

Docker nous permet de conteneuriser nos applications, mais en production, gérer des dizaines (voire des centaines) de containers manuellement devient rapidement ingérable. Voici les problèmes que Docker seul ne résout pas :

  • Mise à l'échelle automatique (Auto-scaling) - Comment ajouter automatiquement des instances quand le trafic augmente ?
  • Self-healing - Si un container plante, qui le redémarre ? Et s'il est sur un nœud qui tombe en panne ?
  • Service Discovery - Comment un service trouve-t-il un autre service sans connaître son IP à l'avance ?
  • Load Balancing - Comment distribuer le trafic entre plusieurs instances d'un même service ?
  • Rolling Updates - Comment déployer une nouvelle version sans temps d'arrêt ?
  • Gestion de la configuration - Comment injecter des variables d'environnement et secrets de manière sécurisée ?
  • Gestion du stockage - Comment persister les données de manière fiable et distribuée ?
Kubernetes (K8s) est un orchestrateur de containers open-source, créé par Google et maintenu par la CNCF (Cloud Native Computing Foundation). Il automatise le déploiement, la mise à l'échelle et la gestion des applications conteneurisées. Le nom vient du grec κυβερνήτης (kubernḗtēs) qui signifie « timonier » ou « pilote ».

En résumé, Docker construit et exécute des containers ; Kubernetes orchestre et gère ces containers à grande échelle.

Toute communication passe par le kube-apiserver. Les utilisateurs interagissent via kubectl, qui envoie des requêtes REST à l'API Server. L'API Server consulte etcd pour l'état du cluster, le scheduler pour le placement des Pods, et le controller manager pour la réconciliation.

3 - Control Plane - Le cerveau du cluster

Le Control Plane est responsable de toutes les décisions globales du cluster : ordonnancement, détection de pannes, réponse aux événements. En production, ses composants sont souvent répliqués sur plusieurs machines pour la haute disponibilité.

3.1 - kube-apiserver

L'API Server est la porte d'entrée unique du cluster Kubernetes. Toute communication - que ce soit depuis kubectl, les composants internes, ou les contrôleurs - passe par lui.

  • Expose une API REST complète (CRUD sur toutes les ressources)
  • Valide et transforme les requêtes (admission controllers)
  • Persiste l'état dans etcd
  • Sert de hub de communication entre tous les composants
  • Supporte l'authentification, l'autorisation (RBAC) et l'admission control
bash Vérifier l'API Server 
# L'API Server écoute sur le port 6443 par défaut
kubectl cluster-info
# Output: Kubernetes control plane is running at https://192.168.49.2:8443

# Accéder directement à l'API (avec proxy)
kubectl proxy --port=8080 &
curl http://localhost:8080/api/v1/namespaces/default/pods

3.2 - etcd

etcd est un magasin clé-valeur distribué qui stocke l'intégralité de l'état du cluster. C'est la source de vérité unique de Kubernetes.

  • Stocke la configuration du cluster, l'état des Pods, des Services, des Secrets, etc.
  • Utilise l'algorithme de consensus Raft pour la réplication
  • Haute disponibilité : recommandé de déployer un nombre impair de nœuds (3, 5, 7)
  • Les sauvegardes régulières d'etcd sont critiques - perdre etcd = perdre le cluster
Sauvegarde etcd : En production, configurez des snapshots automatiques d'etcd. Sans backup, une corruption ou perte d'etcd entraîne la perte de toute la configuration du cluster. Utilisez etcdctl snapshot save pour créer des sauvegardes régulières.
bash Sauvegarde etcd 
# Créer un snapshot d'etcd
ETCDCTL_API=3 etcdctl snapshot save /backup/etcd-snapshot.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

# Vérifier le snapshot
ETCDCTL_API=3 etcdctl snapshot status /backup/etcd-snapshot.db --write-table

3.3 - kube-scheduler

Le Scheduler est responsable de l'affectation des Pods aux nœuds. Quand un nouveau Pod est créé, il n'a pas encore de nœud assigné - c'est le Scheduler qui décide où le placer.

Le processus de décision prend en compte :

  • Ressources disponibles - CPU, mémoire, GPU sur chaque nœud
  • Contraintes d'affinité/anti-affinité - Où le Pod veut (ou ne veut pas) être placé
  • Taints et Tolerations - Nœuds qui repoussent certains Pods
  • Priorités et préemption - Les Pods hautement prioritaires peuvent évincer d'autres Pods
  • Topologie - Zones, régions, contraintes de localisation

3.4 - kube-controller-manager

Le Controller Manager exécute des boucles de réconciliation qui comparent en permanence l'état désiré (ce qui est déclaré dans les manifests YAML) avec l'état actuel du cluster, et prend des actions correctives.

Principaux contrôleurs intégrés :

  • Replication Controller - Garantit le nombre correct de réplicas d'un Pod
  • Node Controller - Surveille la santé des nœuds et réagit quand un nœud tombe
  • Endpoint Controller - Relie les Services aux Pods
  • ServiceAccount Controller - Crée les comptes de service par défaut dans les namespaces
  • Job Controller - Gère l'exécution des Jobs et CronJobs
Boucle de réconciliation : Kubernetes est un système déclaratif. Vous déclarez l'état souhaité (« je veux 3 réplicas de mon API »), et les contrôleurs travaillent en permanence pour atteindre et maintenir cet état. Si un Pod meurt, le contrôleur en crée un nouveau automatiquement.

3.5 - Tableau récapitulatif du Control Plane

Composant Rôle Port par défaut Critique ?
kube-apiserver Point d'entrée REST, hub de communication 6443 Oui - sans lui, aucune opération possible
etcd Stockage clé-valeur, source de vérité 2379 / 2380 Oui - perte = perte du cluster
kube-scheduler Assigner les Pods aux nœuds 10259 Oui - sans lui, les Pods restent en Pending
kube-controller-manager Réconciliation état désiré / actuel 10257 Oui - sans lui, pas de self-healing

4 - Worker Nodes - L'exécution

Les Worker Nodes sont les machines qui exécutent réellement les containers applicatifs. Chaque nœud contient trois composants essentiels.

4.1 - kubelet

Le kubelet est l'agent qui tourne sur chaque nœud du cluster. C'est lui qui s'assure que les containers définis dans les PodSpecs sont bien en cours d'exécution.

  • Reçoit les instructions du Control Plane via l'API Server
  • Démarre, arrête et surveille les containers sur son nœud
  • Rapporte l'état de santé du nœud et des Pods au Control Plane
  • Exécute les liveness probes et readiness probes
  • Monte les volumes nécessaires aux Pods

4.2 - kube-proxy

Le kube-proxy gère les règles réseau sur chaque nœud. Il permet la communication entre les Services Kubernetes et les Pods.

  • Maintient les règles réseau via iptables ou IPVS
  • Assure le load balancing interne entre les Pods d'un Service
  • Gère le routage du trafic entrant vers le bon Pod
  • Mode IPVS : plus performant pour les clusters avec beaucoup de Services

4.3 - Container Runtime

Le Container Runtime est le logiciel responsable de l'exécution effective des containers. Kubernetes utilise l'interface CRI (Container Runtime Interface) pour communiquer avec le runtime.

Docker n'est plus le runtime par défaut ! Depuis Kubernetes 1.24, le support de Docker (via dockershim) a été supprimé. Les runtimes recommandés sont désormais containerd et CRI-O. Vos images Docker continuent de fonctionner - c'est le runtime qui change, pas le format d'image (OCI).

containerd

  • Runtime le plus utilisé en production
  • Léger, rapide, stable
  • Extrait du projet Docker (composant interne)
  • Support natif des images OCI
  • Utilisé par GKE, EKS, AKS par défaut
  • Commande CLI : ctr / nerdctl

CRI-O

  • Conçu spécifiquement pour Kubernetes
  • Très minimal - uniquement ce dont K8s a besoin
  • Utilisé par OpenShift (Red Hat)
  • Conforme aux standards OCI
  • Empreinte mémoire plus faible
  • Idéal pour les environnements hautement sécurisés

5 - Pods - L'unité atomique

5.1 - Qu'est-ce qu'un Pod ?

Un Pod est la plus petite unité déployable dans Kubernetes. Un Pod encapsule un ou plusieurs containers qui partagent :

  • Le même espace réseau - Les containers d'un Pod partagent la même adresse IP et les mêmes ports
  • Les mêmes volumes de stockage - Ils peuvent monter les mêmes volumes pour partager des données
  • Le même namespace Linux - IPC, UTS partagés
  • Le même cycle de vie - Ils sont créés, démarrés et arrêtés ensemble

5.2 - Pourquoi des Pods et non de simples containers ?

Kubernetes n'exécute jamais un container seul - il passe toujours par un Pod. Cette abstraction permet des patterns puissants :

  • Sidecar Pattern - Un container principal + un container auxiliaire (logging, proxy, monitoring)
  • Init Containers - Des containers qui s'exécutent avant le container principal (migration de base de données, attente d'un service)
  • Ambassador Pattern - Un container proxy qui simplifie la communication réseau
  • Adapter Pattern - Un container qui transforme les données de sortie du container principal

5.3 - Cycle de vie d'un Pod

Un Pod passe par plusieurs phases durant son existence :

Phase Description Signification
Pending Le Pod est accepté mais pas encore planifié ou les images se téléchargent En attente de ressources ou de téléchargement d'image
Running Le Pod est lié à un nœud et tous les containers sont créés Au moins un container est en cours d'exécution
Succeeded Tous les containers se sont terminés avec succès Typique pour les Jobs
Failed Tous les containers se sont terminés, au moins un en erreur Investiguer avec kubectl logs
Unknown L'état du Pod ne peut pas être déterminé Problème de communication avec le nœud

5.4 - Manifest YAML d'un Pod

Voici un manifest complet pour un Pod simple :

yaml pod-simple.yaml 
apiVersion: v1
kind: Pod
metadata:
  name: api-backend
  namespace: default
  labels:
    app: api-backend
    environment: development
    team: fintech
spec:
  containers:
    - name: api
      image: openjdk:17-slim
      command: ["java", "-jar", "/app/api.jar"]
      ports:
        - containerPort: 8080
          protocol: TCP
      resources:
        requests:
          memory: "256Mi"
          cpu: "250m"
        limits:
          memory: "512Mi"
          cpu: "500m"
      env:
        - name: SPRING_PROFILES_ACTIVE
          value: "development"
        - name: SERVER_PORT
          value: "8080"
      livenessProbe:
        httpGet:
          path: /actuator/health
          port: 8080
        initialDelaySeconds: 30
        periodSeconds: 10
      readinessProbe:
        httpGet:
          path: /actuator/health/readiness
          port: 8080
        initialDelaySeconds: 10
        periodSeconds: 5
  restartPolicy: Always
Requests vs Limits : Les requests définissent le minimum garanti de ressources pour le Pod (utilisé par le Scheduler pour le placement). Les limits définissent le maximum - si le container dépasse la limite mémoire, il sera tué (OOMKilled). Définissez toujours les deux en production.

5.5 - Pod multi-containers (Sidecar)

Un exemple classique : un container applicatif accompagné d'un sidecar de logging qui collecte et envoie les logs.

yaml pod-sidecar.yaml 
apiVersion: v1
kind: Pod
metadata:
  name: api-with-logging
  labels:
    app: api-backend
spec:
  volumes:
    - name: shared-logs
      emptyDir: {}

  containers:
    # Container principal - l'application
    - name: api
      image: bmis/api-backend:1.0.0
      ports:
        - containerPort: 8080
      volumeMounts:
        - name: shared-logs
          mountPath: /var/log/app
      resources:
        requests:
          memory: "256Mi"
          cpu: "250m"
        limits:
          memory: "512Mi"
          cpu: "500m"

    # Sidecar - collecte des logs
    - name: log-collector
      image: fluent/fluent-bit:latest
      volumeMounts:
        - name: shared-logs
          mountPath: /var/log/app
          readOnly: true
      resources:
        requests:
          memory: "64Mi"
          cpu: "50m"
        limits:
          memory: "128Mi"
          cpu: "100m"

  # Init container - attendre que la base soit prête
  initContainers:
    - name: wait-for-db
      image: busybox:1.36
      command:
        - "sh"
        - "-c"
        - "until nc -z postgres-service 5432; do echo 'Waiting for DB...'; sleep 2; done"

Dans cet exemple :

  • Le Init Container wait-for-db s'exécute en premier et attend que PostgreSQL soit disponible
  • Le container principal api écrit ses logs dans /var/log/app
  • Le sidecar log-collector (Fluent Bit) lit ces logs depuis le même volume partagé et les envoie vers un système centralisé

6 - kubectl - L'outil de commande

kubectl est l'outil en ligne de commande pour interagir avec un cluster Kubernetes. C'est votre interface principale pour gérer toutes les ressources.

6.1 - Commandes de consultation

bash Lister les ressources 
# Lister les pods dans le namespace courant
kubectl get pods

# Lister les pods avec plus de détails (IP, nœud, etc.)
kubectl get pods -o wide

# Lister les pods de TOUS les namespaces
kubectl get pods --all-namespaces
kubectl get pods -A

# Lister les nœuds du cluster
kubectl get nodes

# Lister les services
kubectl get services
kubectl get svc

# Lister TOUTES les ressources
kubectl get all

# Lister avec un format de sortie personnalisé
kubectl get pods -o json
kubectl get pods -o yaml

6.2 - Inspection et débogage

bash Inspecter les ressources 
# Détails complets d'un pod (événements, conditions, volumes…)
kubectl describe pod api-backend

# Voir les logs d'un container
kubectl logs api-backend

# Suivre les logs en temps réel (comme tail -f)
kubectl logs -f api-backend

# Logs d'un container spécifique dans un pod multi-containers
kubectl logs api-with-logging -c log-collector

# Logs des 100 dernières lignes
kubectl logs api-backend --tail=100

# Logs depuis les 5 dernières minutes
kubectl logs api-backend --since=5m

6.3 - Exécution et interaction

bash Interagir avec les Pods 
# Ouvrir un shell dans un Pod
kubectl exec -it api-backend -- /bin/bash

# Exécuter une commande dans un Pod
kubectl exec api-backend -- ls /app

# Ouvrir un shell dans un container spécifique
kubectl exec -it api-with-logging -c api -- /bin/sh

# Copier un fichier depuis/vers un Pod
kubectl cp api-backend:/var/log/app/app.log ./app.log
kubectl cp ./config.yml api-backend:/app/config.yml

# Transférer un port local vers un Pod
kubectl port-forward pod/api-backend 8080:8080

6.4 - Création et gestion

bash Gérer les ressources 
# Appliquer un manifest YAML (créer ou mettre à jour)
kubectl apply -f pod-simple.yaml

# Appliquer tous les fichiers YAML d'un dossier
kubectl apply -f ./k8s/

# Supprimer une ressource depuis un fichier
kubectl delete -f pod-simple.yaml

# Supprimer un pod directement
kubectl delete pod api-backend

# Créer un pod rapidement (sans YAML)
kubectl run nginx-test --image=nginx:latest --port=80

# Voir les événements du cluster
kubectl get events --sort-by='.lastTimestamp'
Alias utiles : Ajoutez ces alias à votre .bashrc ou .zshrc pour gagner du temps : alias k='kubectl', alias kgp='kubectl get pods', alias kgs='kubectl get svc', alias kd='kubectl describe', alias kl='kubectl logs'.

7 - Setup local - Minikube / Kind

Pour apprendre et développer localement, vous pouvez créer un cluster Kubernetes sur votre machine. Les deux outils les plus populaires sont Minikube et Kind.

7.1 - Minikube

Minikube crée un cluster Kubernetes à un seul nœud dans une machine virtuelle ou un container Docker sur votre machine locale.

bash Installation et démarrage Minikube 
# Installation sur Linux
curl -LO https://storage.googleapis.com/minikube/releases/latest/minikube-linux-amd64
sudo install minikube-linux-amd64 /usr/local/bin/minikube

# Installation sur macOS (Homebrew)
brew install minikube

# Installation sur Windows (Chocolatey)
choco install minikube

# Démarrer un cluster (utilise Docker par défaut)
minikube start

# Démarrer avec des ressources personnalisées
minikube start --cpus=4 --memory=8192 --driver=docker

# Vérifier le statut
minikube status

# Ouvrir le dashboard Kubernetes
minikube dashboard

# Arrêter le cluster
minikube stop

# Supprimer le cluster
minikube delete

7.2 - Kind (Kubernetes IN Docker)

Kind crée des clusters Kubernetes en utilisant des containers Docker comme « nœuds ». Il est particulièrement adapté pour le CI/CD et les tests.

bash Installation et utilisation Kind 
# Installation sur Linux
curl -Lo ./kind https://kind.sigs.k8s.io/dl/v0.20.0/kind-linux-amd64
chmod +x ./kind
sudo mv ./kind /usr/local/bin/kind

# Installation sur macOS
brew install kind

# Installation sur Windows
choco install kind

# Créer un cluster simple
kind create cluster --name bmis-dev

# Créer un cluster multi-nœuds
cat <<EOF | kind create cluster --name bmis-multi --config=-
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
  - role: worker
EOF

# Lister les clusters
kind get clusters

# Supprimer un cluster
kind delete cluster --name bmis-dev

7.3 - Comparaison Minikube vs Kind

Critère Minikube Kind
Isolation VM ou container Docker Containers Docker uniquement
Multi-nœuds Supporté (récent) Supporté nativement
Vitesse de démarrage ~1-2 minutes ~30 secondes
Dashboard intégré Oui (minikube dashboard) Non (installation manuelle)
Addons intégrés Ingress, metrics-server, etc. Configuration manuelle
Idéal pour Développement local, apprentissage CI/CD, tests automatisés
Consommation ressources Plus élevée (VM) Plus légère

8 - Premier Pod - Exercice pratique

Objectif : Créer, déployer, vérifier et supprimer votre premier Pod Kubernetes. Cet exercice vous permettra de maîtriser les commandes de base de kubectl.

Étape 1 - Créer le manifest YAML

Créez un fichier mon-premier-pod.yaml avec le contenu suivant :

yaml mon-premier-pod.yaml 
apiVersion: v1
kind: Pod
metadata:
  name: nginx-demo
  labels:
    app: nginx-demo
    exercice: lecon-3
spec:
  containers:
    - name: nginx
      image: nginx:1.25-alpine
      ports:
        - containerPort: 80
      resources:
        requests:
          memory: "64Mi"
          cpu: "50m"
        limits:
          memory: "128Mi"
          cpu: "100m"

Étape 2 - Déployer le Pod

bash Déploiement 
# Appliquer le manifest
kubectl apply -f mon-premier-pod.yaml
# Output: pod/nginx-demo created

# Vérifier que le Pod est en cours d'exécution
kubectl get pods
# NAME         READY   STATUS    RESTARTS   AGE
# nginx-demo   1/1     Running   0          15s

Étape 3 - Inspecter le Pod

bash Inspection 
# Détails complets du Pod
kubectl describe pod nginx-demo

# Voir les logs du container nginx
kubectl logs nginx-demo

# Ouvrir un shell dans le container
kubectl exec -it nginx-demo -- /bin/sh

# Depuis le shell, vérifier nginx
curl localhost:80
# Output: page d'accueil nginx

# Quitter le shell
exit

# Port-forward pour accéder depuis votre navigateur
kubectl port-forward pod/nginx-demo 8080:80
# Ouvrir http://localhost:8080 dans le navigateur

Étape 4 - Nettoyer

bash Nettoyage 
# Supprimer le Pod
kubectl delete -f mon-premier-pod.yaml
# Output: pod "nginx-demo" deleted

# Vérifier la suppression
kubectl get pods
# No resources found in default namespace.
Bravo ! Vous venez de créer, déployer, inspecter et supprimer votre premier Pod Kubernetes. Dans la prochaine leçon, nous verrons comment utiliser les Deployments pour gérer les Pods de manière déclarative avec réplication et rolling updates.

9 - Comment Kubernetes gère notre système fintech

Voyons comment notre stack fintech (Spring Boot, PostgreSQL, Redis, API Gateway) se mappe sur les ressources Kubernetes :

Composant Fintech Ressource K8s Justification
API Spring Boot Deployment + Service (ClusterIP) Stateless - scalable horizontalement, rolling updates
PostgreSQL StatefulSet + PersistentVolumeClaim Stateful - nécessite identité stable et stockage persistant
Redis (Cache) Deployment + Service (ClusterIP) Cache éphémère - peut être redéployé sans perte critique
Redis (Sessions) StatefulSet + PVC Données de session - nécessite persistance
API Gateway Deployment + Service (LoadBalancer) + Ingress Point d'entrée - exposé à l'extérieur avec Ingress
Secrets (mots de passe DB) Secret Données sensibles encodées en base64, montées dans les Pods
Config (variables d'env) ConfigMap Configuration non sensible, injectable dans les containers

10 - Erreurs courantes débutants

Créer des Pods directement en production - Ne créez jamais de Pods nus (kind: Pod) en production. Utilisez toujours un Deployment ou un StatefulSet. Un Pod seul ne sera pas recréé s'il meurt.
Oublier les requests et limits de ressources - Sans resources.requests, le Scheduler ne peut pas placer efficacement les Pods. Sans resources.limits, un Pod peut consommer toutes les ressources d'un nœud et faire tomber les autres Pods.
Utiliser le tag :latest pour les images - Le tag :latest ne garantit pas la version déployée et rend les rollbacks impossibles. Utilisez toujours un tag de version explicite : api-backend:1.2.3.
Ne pas configurer les health checks - Sans livenessProbe et readinessProbe, Kubernetes ne peut pas détecter si votre application est bloquée ou pas prête à recevoir du trafic. Le self-healing ne fonctionne pas sans probes.
Stocker des secrets dans les ConfigMaps - Les ConfigMaps ne sont pas chiffrés. Les mots de passe, clés API et tokens doivent aller dans des Secrets (et idéalement dans un vault externe comme HashiCorp Vault).
Ignorer les namespaces - Tout mettre dans le namespace default crée du désordre. Utilisez des namespaces pour isoler les environnements (dev, staging, prod) et les équipes.

11 - Production best practices

Toujours définir les resource requests et limits - Cela permet au Scheduler de placer intelligemment les Pods et protège contre les « noisy neighbors ». Commencez avec des valeurs conservatrices et ajustez avec les métriques réelles.
Configurer les probes de santé - Ajoutez systématiquement livenessProbe (redémarrer si bloqué), readinessProbe (ne pas envoyer de trafic si pas prêt) et éventuellement startupProbe (pour les applications lentes à démarrer).
Utiliser des labels et annotations - Les labels (app, version, team, environment) permettent de filtrer, sélectionner et organiser les ressources. Les annotations stockent des métadonnées non-sélectives (descriptions, liens vers la documentation).
Versionner tous les manifests YAML - Stockez vos fichiers Kubernetes dans Git aux côtés de votre code applicatif. Cela permet le suivi des changements, les revues de code et les rollbacks déclaratifs (GitOps).
Sauvegarder etcd régulièrement - Programmez des snapshots automatiques d'etcd et testez régulièrement la restauration. En production managée (GKE, EKS, AKS), le fournisseur cloud s'en charge, mais vérifiez la politique de rétention.
Activer RBAC dès le départ - Le Role-Based Access Control limite qui peut faire quoi dans le cluster. Ne donnez jamais le rôle cluster-admin à des comptes de service applicatifs. Appliquez le principe du moindre privilège.
Utiliser des Pod Disruption Budgets (PDB) - Les PDB garantissent qu'un nombre minimum de réplicas reste disponible pendant les opérations de maintenance (drain d'un nœud, mises à jour du cluster).
