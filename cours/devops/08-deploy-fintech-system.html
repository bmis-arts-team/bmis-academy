Déployer le Système Fintech sur Kubernetes

Manifestes complets pour Spring Boot, PostgreSQL, Redis, API Gateway et File Storage - séparation dev/staging/prod.

1 - Vue d'ensemble du système

Avant d'écrire un seul manifeste, il faut comprendre l'architecture complète du système fintech que nous allons déployer. Ce système est composé de plusieurs couches qui communiquent entre elles, et chaque couche sera représentée par un ou plusieurs objets Kubernetes.

Voici l'architecture globale du système BMIS Fintech :

┌─────────────────────────────────────────────────────────────────────────────┐

Chaque composant correspond à un ensemble de manifestes Kubernetes :

  • API Gateway → Ingress resource + annotations NGINX
  • Spring Boot Backend → Deployment (3 replicas) + Service + ConfigMap + Secret
  • PostgreSQL → StatefulSet + Headless Service + PVC + Secret
  • Redis → Deployment + Service + PVC + Secret
  • File Storage → PersistentVolumeClaim monté dans le backend
Pourquoi pas Helm ? Nous utilisons des manifestes YAML bruts avec Kustomize dans cette leçon pour que vous compreniez chaque ligne. En production, vous migrerez vers Helm une fois les concepts maîtrisés.

2 - Structure des manifestes

Nous organisons nos manifestes avec la convention Kustomize : un dossier base/ contenant les ressources communes, et un dossier overlays/ avec les patches spécifiques à chaque environnement.

k8s/
├── base/
│ ├── namespace.yaml
│ ├── spring-boot/
│ │ ├── deployment.yaml
│ │ ├── service.yaml
│ │ └── configmap.yaml
│ ├── postgresql/
│ │ ├── statefulset.yaml
│ │ ├── service.yaml
│ │ └── pvc.yaml
│ ├── redis/
│ │ ├── deployment.yaml
│ │ └── service.yaml
│ ├── api-gateway/
│ │ └── ingress.yaml
│ └── file-storage/
│ └── pvc.yaml
├── overlays/
│ ├── dev/
│ │ ├── kustomization.yaml
│ │ ├── configmap-patch.yaml
│ │ └── secrets.yaml
│ ├── staging/
│ │ ├── kustomization.yaml
│ │ ├── configmap-patch.yaml
│ │ └── secrets.yaml
│ └── prod/
│ ├── kustomization.yaml
│ ├── configmap-patch.yaml
│ ├── secrets.yaml
│ └── hpa.yaml

L'avantage de cette structure : les manifestes de base ne changent jamais entre les environnements. Seuls les overlays contiennent les différences (nombre de replicas, taille des ressources, secrets, etc.).

3 - Namespace

Tout commence par la création d'un namespace dédié. Cela isole complètement notre système fintech des autres applications du cluster et permet d'appliquer des quotas de ressources et des politiques réseau spécifiques.

yaml k8s/base/namespace.yaml 
# Namespace dédié au système fintech BMIS
# Isole les ressources et permet des politiques spécifiques
apiVersion: v1
kind: Namespace
metadata:
  name: bmis-fintech
  labels:
    app.kubernetes.io/part-of: bmis-fintech
    team: bmis-backend
    environment: base
  annotations:
    description: "Système fintech BMIS - Spring Boot + PostgreSQL + Redis"
Convention de nommage : Utilisez toujours des labels cohérents sur toutes vos ressources. Le label app.kubernetes.io/part-of est un standard Kubernetes qui facilite le filtrage et le monitoring.

4 - PostgreSQL - StatefulSet complet

PostgreSQL est le composant le plus critique de notre système. Il stocke toutes les données métier : utilisateurs, transactions, comptes, historiques. Nous utilisons un StatefulSet (et non un Deployment) car PostgreSQL a besoin d'une identité réseau stable et d'un stockage persistant garanti.

4.1 - Headless Service

Le StatefulSet nécessite un Headless Service (clusterIP: None) pour fournir des entrées DNS individuelles à chaque Pod.

yaml k8s/base/postgresql/service.yaml 
# Headless Service pour PostgreSQL
# Fournit un DNS stable : postgresql-0.postgresql-headless.bmis-fintech.svc.cluster.local
apiVersion: v1
kind: Service
metadata:
  name: postgresql-headless
  namespace: bmis-fintech
  labels:
    app: postgresql
    app.kubernetes.io/part-of: bmis-fintech
spec:
  type: ClusterIP
  clusterIP: None
  ports:
    - name: tcp-postgresql
      port: 5432
      targetPort: 5432
  selector:
    app: postgresql

4.2 - StatefulSet

yaml k8s/base/postgresql/statefulset.yaml 
# StatefulSet PostgreSQL - stockage persistant et identité stable
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgresql
  namespace: bmis-fintech
  labels:
    app: postgresql
    app.kubernetes.io/part-of: bmis-fintech
spec:
  serviceName: postgresql-headless
  replicas: 1
  selector:
    matchLabels:
      app: postgresql
  template:
    metadata:
      labels:
        app: postgresql
        app.kubernetes.io/part-of: bmis-fintech
    spec:
      # InitContainer pour corriger les permissions du volume
      initContainers:
        - name: init-permissions
          image: busybox:1.36
          command:
            - sh
            - -c
            - |
              chown -R 999:999 /var/lib/postgresql/data
              chmod 700 /var/lib/postgresql/data
          volumeMounts:
            - name: postgresql-data
              mountPath: /var/lib/postgresql/data

      containers:
        - name: postgresql
          image: postgres:16-alpine
          ports:
            - containerPort: 5432
              name: tcp-postgresql

          # Variables d'environnement depuis le Secret
          env:
            - name: POSTGRES_DB
              valueFrom:
                secretKeyRef:
                  name: postgresql-secret
                  key: POSTGRES_DB
            - name: POSTGRES_USER
              valueFrom:
                secretKeyRef:
                  name: postgresql-secret
                  key: POSTGRES_USER
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: postgresql-secret
                  key: POSTGRES_PASSWORD
            - name: PGDATA
              value: /var/lib/postgresql/data/pgdata

          # Ressources - ajustées par environnement via Kustomize
          resources:
            requests:
              cpu: 250m
              memory: 512Mi
            limits:
              cpu: "1"
              memory: 1Gi

          # Probes de santé
          livenessProbe:
            exec:
              command:
                - pg_isready
                - -U
                - $(POSTGRES_USER)
                - -d
                - $(POSTGRES_DB)
            initialDelaySeconds: 30
            periodSeconds: 10
            timeoutSeconds: 5
            failureThreshold: 6

          readinessProbe:
            exec:
              command:
                - pg_isready
                - -U
                - $(POSTGRES_USER)
                - -d
                - $(POSTGRES_DB)
            initialDelaySeconds: 5
            periodSeconds: 10
            timeoutSeconds: 5
            failureThreshold: 6

          # Montage du volume persistant
          volumeMounts:
            - name: postgresql-data
              mountPath: /var/lib/postgresql/data

  # VolumeClaimTemplate - crée automatiquement un PVC par replica
  volumeClaimTemplates:
    - metadata:
        name: postgresql-data
        labels:
          app: postgresql
      spec:
        accessModes:
          - ReadWriteOnce
        resources:
          requests:
            storage: 10Gi
        storageClassName: standard

Points importants de ce StatefulSet :

  • initContainer - Corrige les permissions du volume avant le démarrage de PostgreSQL (l'utilisateur postgres a l'UID 999)
  • volumeClaimTemplates - Crée automatiquement un PVC de 10Gi. Ce PVC survit à la suppression du Pod
  • livenessProbe - Utilise pg_isready pour vérifier que PostgreSQL répond aux connexions
  • PGDATA - Pointe vers un sous-répertoire pour éviter les conflits avec le point de montage
Pourquoi un seul replica ? PostgreSQL n'est pas conçu pour être répliqué nativement par Kubernetes. Pour la haute disponibilité, utilisez un opérateur comme CloudNativePG ou Zalando Postgres Operator qui gère la réplication streaming.

5 - Redis - Deployment

Redis est utilisé comme cache (données fréquemment accédées) et store de sessions (tokens JWT rafraîchis). Contrairement à PostgreSQL, Redis peut tolérer une perte de données au redémarrage - les caches se reconstruisent automatiquement. Nous utilisons donc un Deployment classique avec un PVC pour la persistance optionnelle.

5.1 - PVC Redis

yaml k8s/base/redis/pvc.yaml 
# PVC pour la persistance Redis (RDB snapshots)
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: redis-data
  namespace: bmis-fintech
  labels:
    app: redis
    app.kubernetes.io/part-of: bmis-fintech
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 2Gi
  storageClassName: standard

5.2 - Deployment Redis

yaml k8s/base/redis/deployment.yaml 
# Deployment Redis - cache et sessions
apiVersion: apps/v1
kind: Deployment
metadata:
  name: redis
  namespace: bmis-fintech
  labels:
    app: redis
    app.kubernetes.io/part-of: bmis-fintech
spec:
  replicas: 1
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
        app.kubernetes.io/part-of: bmis-fintech
    spec:
      containers:
        - name: redis
          image: redis:7-alpine
          ports:
            - containerPort: 6379
              name: tcp-redis

          # Commande avec mot de passe et persistance
          command:
            - redis-server
            - --requirepass
            - $(REDIS_PASSWORD)
            - --appendonly
            - "yes"
            - --appendfsync
            - everysec

          env:
            - name: REDIS_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: redis-secret
                  key: REDIS_PASSWORD

          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 256Mi

          livenessProbe:
            exec:
              command:
                - redis-cli
                - -a
                - $(REDIS_PASSWORD)
                - ping
            initialDelaySeconds: 15
            periodSeconds: 10
            timeoutSeconds: 5

          readinessProbe:
            exec:
              command:
                - redis-cli
                - -a
                - $(REDIS_PASSWORD)
                - ping
            initialDelaySeconds: 5
            periodSeconds: 10

          volumeMounts:
            - name: redis-data
              mountPath: /data

      volumes:
        - name: redis-data
          persistentVolumeClaim:
            claimName: redis-data

5.3 - Service Redis

yaml k8s/base/redis/service.yaml

6 - Spring Boot Backend - Deployment

Le backend Spring Boot est le cœur de l'application. Il expose l'API REST consommée par tous les clients, gère l'authentification JWT, orchestre les transactions financières et communique avec PostgreSQL et Redis.

yaml k8s/base/spring-boot/deployment.yaml 
# Deployment Spring Boot - backend fintech
apiVersion: apps/v1
kind: Deployment
metadata:
  name: bmis-backend
  namespace: bmis-fintech
  labels:
    app: bmis-backend
    app.kubernetes.io/part-of: bmis-fintech
    app.kubernetes.io/component: backend
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: bmis-backend
  template:
    metadata:
      labels:
        app: bmis-backend
        app.kubernetes.io/part-of: bmis-fintech
        app.kubernetes.io/component: backend
    spec:
      # Affinité - répartir les replicas sur différents nœuds
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchExpressions:
                    - key: app
                      operator: In
                      values:
                        - bmis-backend
                topologyKey: kubernetes.io/hostname

      containers:
        - name: bmis-backend
          image: registry.bmis.academy/bmis-backend:1.4.2
          imagePullPolicy: Always
          ports:
            - containerPort: 8080
              name: http

          # Variables d'environnement depuis ConfigMap et Secrets
          envFrom:
            - configMapRef:
                name: bmis-backend-config
            - secretRef:
                name: bmis-backend-secret

          # Ressources - production
          resources:
            requests:
              cpu: 500m
              memory: 512Mi
            limits:
              cpu: "2"
              memory: 1536Mi

          # Startup Probe - laisse le temps à Spring Boot de démarrer
          startupProbe:
            httpGet:
              path: /actuator/health
              port: http
            initialDelaySeconds: 10
            periodSeconds: 5
            failureThreshold: 30
            # Total max : 10 + (5 × 30) = 160 secondes pour démarrer

          # Liveness Probe - redémarre le Pod si l'app est bloquée
          livenessProbe:
            httpGet:
              path: /actuator/health/liveness
              port: http
            initialDelaySeconds: 0
            periodSeconds: 15
            timeoutSeconds: 5
            failureThreshold: 3

          # Readiness Probe - retire le Pod du Service si non prêt
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: http
            initialDelaySeconds: 0
            periodSeconds: 10
            timeoutSeconds: 5
            failureThreshold: 3

          # Volumes montés
          volumeMounts:
            - name: file-storage
              mountPath: /app/uploads
            - name: tmp
              mountPath: /tmp

      volumes:
        - name: file-storage
          persistentVolumeClaim:
            claimName: file-storage-pvc
        - name: tmp
          emptyDir: {}

6.1 - Service Spring Boot

yaml k8s/base/spring-boot/service.yaml 
# Service ClusterIP pour le backend Spring Boot
apiVersion: v1
kind: Service
metadata:
  name: bmis-backend
  namespace: bmis-fintech
  labels:
    app: bmis-backend
    app.kubernetes.io/part-of: bmis-fintech
spec:
  type: ClusterIP
  ports:
    - name: http
      port: 80
      targetPort: 8080
  selector:
    app: bmis-backend

Points clés de ce Deployment :

  • RollingUpdate avec maxUnavailable: 0 - garantit zéro downtime pendant les mises à jour
  • startupProbe - Indispensable pour Spring Boot qui peut prendre 30–60 secondes à démarrer. Sans cette probe, la livenessProbe tuerait le Pod avant qu'il ne soit prêt
  • podAntiAffinity - Répartit les 3 replicas sur des nœuds différents pour la haute disponibilité
  • Volume /tmp - emptyDir pour les fichiers temporaires, évite d'écrire dans le filesystem du container

7 - Spring Boot - ConfigMap

La ConfigMap contient toute la configuration non sensible de l'application. C'est l'équivalent du fichier application.yml, mais géré par Kubernetes et modifiable sans reconstruire l'image Docker.

yaml k8s/base/spring-boot/configmap.yaml 
# ConfigMap - configuration applicative (non sensible)
apiVersion: v1
kind: ConfigMap
metadata:
  name: bmis-backend-config
  namespace: bmis-fintech
  labels:
    app: bmis-backend
    app.kubernetes.io/part-of: bmis-fintech
data:
  # Serveur
  SERVER_PORT: "8080"
  SERVER_SERVLET_CONTEXT_PATH: "/api/v1"

  # Datasource - pointe vers le Service PostgreSQL interne
  SPRING_DATASOURCE_URL: "jdbc:postgresql://postgresql-headless.bmis-fintech.svc.cluster.local:5432/bmis_fintech"
  SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE: "20"
  SPRING_DATASOURCE_HIKARI_MINIMUM_IDLE: "5"
  SPRING_DATASOURCE_HIKARI_CONNECTION_TIMEOUT: "30000"

  # JPA / Hibernate
  SPRING_JPA_HIBERNATE_DDL_AUTO: "validate"
  SPRING_JPA_SHOW_SQL: "false"
  SPRING_JPA_PROPERTIES_HIBERNATE_DIALECT: "org.hibernate.dialect.PostgreSQLDialect"

  # Redis - pointe vers le Service Redis interne
  SPRING_DATA_REDIS_HOST: "redis.bmis-fintech.svc.cluster.local"
  SPRING_DATA_REDIS_PORT: "6379"
  SPRING_DATA_REDIS_TIMEOUT: "5000"

  # Logging
  LOGGING_LEVEL_ROOT: "INFO"
  LOGGING_LEVEL_COM_BMIS: "INFO"
  LOGGING_LEVEL_ORG_SPRINGFRAMEWORK: "WARN"
  LOGGING_LEVEL_ORG_HIBERNATE_SQL: "WARN"

  # Spring Profiles
  SPRING_PROFILES_ACTIVE: "kubernetes"

  # File Storage
  APP_FILE_STORAGE_PATH: "/app/uploads"
  APP_FILE_STORAGE_MAX_SIZE: "10MB"
  APP_FILE_STORAGE_ALLOWED_TYPES: "image/jpeg,image/png,application/pdf"

  # Actuator - exposer les endpoints de monitoring
  MANAGEMENT_ENDPOINTS_WEB_EXPOSURE_INCLUDE: "health,info,metrics,prometheus"
  MANAGEMENT_ENDPOINT_HEALTH_SHOW_DETAILS: "always"
  MANAGEMENT_ENDPOINT_HEALTH_PROBES_ENABLED: "true"
DNS interne Kubernetes : Les URLs des services utilisent le format <service>.<namespace>.svc.cluster.local. C'est la résolution DNS interne du cluster. Depuis le même namespace, postgresql-headless suffit, mais le FQDN est recommandé pour la clarté.

9 - API Gateway - Ingress

L'Ingress est le point d'entrée unique du cluster. Il reçoit le trafic HTTP/HTTPS externe, termine le TLS et route les requêtes vers le service backend. Nous utilisons le NGINX Ingress Controller avec des annotations pour le rate limiting et les headers CORS.

yaml k8s/base/api-gateway/ingress.yaml 
# Ingress - point d'entrée HTTPS avec TLS et rate limiting
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: bmis-ingress
  namespace: bmis-fintech
  labels:
    app.kubernetes.io/part-of: bmis-fintech
  annotations:
    # Classe d'Ingress Controller
    kubernetes.io/ingress.class: nginx

    # TLS - redirection HTTP vers HTTPS
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/force-ssl-redirect: "true"

    # Rate Limiting - protection contre les abus
    nginx.ingress.kubernetes.io/limit-rps: "50"
    nginx.ingress.kubernetes.io/limit-burst-multiplier: "5"
    nginx.ingress.kubernetes.io/limit-connections: "20"

    # Taille maximale du body (upload de fichiers KYC)
    nginx.ingress.kubernetes.io/proxy-body-size: "15m"

    # Timeouts
    nginx.ingress.kubernetes.io/proxy-connect-timeout: "10"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "60"
    nginx.ingress.kubernetes.io/proxy-send-timeout: "60"

    # CORS - autoriser les domaines frontend
    nginx.ingress.kubernetes.io/enable-cors: "true"
    nginx.ingress.kubernetes.io/cors-allow-origin: "https://admin.bmis.academy,https://app.bmis.academy"
    nginx.ingress.kubernetes.io/cors-allow-methods: "GET, POST, PUT, DELETE, PATCH, OPTIONS"
    nginx.ingress.kubernetes.io/cors-allow-headers: "Authorization, Content-Type, X-Requested-With"
    nginx.ingress.kubernetes.io/cors-allow-credentials: "true"
    nginx.ingress.kubernetes.io/cors-max-age: "3600"

    # Headers de sécurité
    nginx.ingress.kubernetes.io/configuration-snippet: |
      more_set_headers "X-Frame-Options: DENY";
      more_set_headers "X-Content-Type-Options: nosniff";
      more_set_headers "X-XSS-Protection: 1; mode=block";
      more_set_headers "Referrer-Policy: strict-origin-when-cross-origin";

    # Let's Encrypt - certificat TLS automatique
    cert-manager.io/cluster-issuer: letsencrypt-prod
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - api.bmis.academy
      secretName: bmis-api-tls
  rules:
    - host: api.bmis.academy
      http:
        paths:
          - path: /api/v1
            pathType: Prefix
            backend:
              service:
                name: bmis-backend
                port:
                  number: 80

Cet Ingress configure :

  • TLS automatique via cert-manager et Let's Encrypt
  • Rate limiting - 50 requêtes par seconde par IP, avec un burst de 250
  • CORS - Seuls les domaines admin et app sont autorisés
  • Headers de sécurité - Protection contre le clickjacking, le MIME sniffing et le XSS
  • Taille de body - 15Mo pour permettre l'upload de documents KYC

10 - File Storage - PVC

Le système fintech doit stocker des fichiers uploadés par les utilisateurs : documents KYC (carte d'identité, justificatif de domicile), reçus de transaction, et avatars. Ces fichiers sont stockés dans un PersistentVolumeClaim monté dans le backend.

yaml k8s/base/file-storage/pvc.yaml 
# PVC pour le stockage de fichiers (documents KYC, reçus, avatars)
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: file-storage-pvc
  namespace: bmis-fintech
  labels:
    app: bmis-backend
    app.kubernetes.io/part-of: bmis-fintech
    component: file-storage
spec:
  accessModes:
    - ReadWriteMany          # Plusieurs Pods doivent pouvoir écrire simultanément
  resources:
    requests:
      storage: 5Gi
  storageClassName: standard  # Utiliser une StorageClass compatible RWX (NFS, EFS, etc.)
ReadWriteMany (RWX) : Comme le backend a 3 replicas, tous les Pods doivent pouvoir lire et écrire sur le même volume simultanément. Cela nécessite une StorageClass compatible RWX comme NFS, AWS EFS, ou Azure Files. Les disques SSD classiques (gp3, pd-ssd) ne supportent que ReadWriteOnce.
Alternative en production : Pour les fichiers statiques à grande échelle, préférez un Object Storage (S3, MinIO, Azure Blob) plutôt qu'un PVC. Le PVC est adapté pour les petits volumes ou les environnements sans Object Storage.

12 - Déploiement complet - Étape par étape

L'ordre de déploiement est crucial. Les dépendances doivent être prêtes avant que les services qui en dépendent ne démarrent. Voici la séquence correcte :

  1. Créer le Namespace

    Le namespace doit exister avant toute autre ressource.

    bash 
    kubectl apply -f k8s/base/namespace.yaml

# Vérifier
kubectl get namespace bmis-fintech
  2. Déployer les Secrets

    Les Secrets doivent être créés avant les Pods qui les référencent, sinon les Pods resteront en état CreateContainerConfigError.

    bash 
    # Appliquer tous les secrets
kubectl apply -f k8s/base/postgresql/secret.yaml
kubectl apply -f k8s/base/redis/secret.yaml
kubectl apply -f k8s/base/spring-boot/secret.yaml

# Vérifier que les secrets sont créés
kubectl get secrets -n bmis-fintech
  3. Déployer PostgreSQL

    La base de données doit être opérationnelle avant le backend. Attendez que le Pod soit Running et Ready.

    bash 
    kubectl apply -f k8s/base/postgresql/service.yaml
kubectl apply -f k8s/base/postgresql/statefulset.yaml

# Attendre que PostgreSQL soit prêt (timeout 120s)
kubectl wait --for=condition=ready pod/postgresql-0 \
  -n bmis-fintech --timeout=120s

# Vérifier les logs
kubectl logs postgresql-0 -n bmis-fintech | tail -5
  4. Déployer Redis

    Le cache Redis doit être disponible avant le backend Spring Boot.

    bash 
    kubectl apply -f k8s/base/redis/pvc.yaml
kubectl apply -f k8s/base/redis/deployment.yaml
kubectl apply -f k8s/base/redis/service.yaml

# Attendre que Redis soit prêt
kubectl wait --for=condition=ready pod -l app=redis \
  -n bmis-fintech --timeout=60s
  5. Déployer le Backend Spring Boot

    Le backend peut maintenant démarrer : PostgreSQL et Redis sont prêts.

    bash 
    kubectl apply -f k8s/base/file-storage/pvc.yaml
kubectl apply -f k8s/base/spring-boot/configmap.yaml
kubectl apply -f k8s/base/spring-boot/deployment.yaml
kubectl apply -f k8s/base/spring-boot/service.yaml

# Attendre que tous les replicas soient prêts
kubectl rollout status deployment/bmis-backend \
  -n bmis-fintech --timeout=300s
  6. Configurer l'Ingress

    L'Ingress est déployé en dernier car il dépend du service backend.

    bash 
    kubectl apply -f k8s/base/api-gateway/ingress.yaml

# Vérifier l'Ingress et l'adresse IP attribuée
kubectl get ingress -n bmis-fintech

# Vérifier le certificat TLS (si cert-manager est installé)
kubectl get certificate -n bmis-fintech
Déploiement avec Kustomize : Si vous utilisez Kustomize, une seule commande remplace toutes les étapes ci-dessus : kubectl apply -k overlays/prod. Kubernetes gère automatiquement l'ordre de création grâce aux dépendances déclarées.

14 - Erreurs courantes

CrashLoopBackOff sur le backend : Le backend Spring Boot essaie de se connecter à PostgreSQL avant que celui-ci ne soit prêt. Solution : Vérifiez l'ordre de déploiement. Ajoutez un initContainer avec busybox qui attend que PostgreSQL réponde sur le port 5432 avant de lancer le conteneur principal.
CreateContainerConfigError : Un Secret ou une ConfigMap référencé dans le Deployment n'existe pas encore dans le namespace. Solution : Déployez toujours les Secrets et ConfigMaps avant les Deployments. Vérifiez les noms avec kubectl get secrets -n bmis-fintech.
PVC en état Pending : Aucun PersistentVolume disponible ne correspond à la StorageClass demandée. Solution : Vérifiez que la StorageClass existe avec kubectl get sc. Pour le développement local (Minikube/Kind), utilisez storageClassName: standard.
ImagePullBackOff : Kubernetes ne peut pas télécharger l'image Docker. Solution : Vérifiez que l'image existe dans le registry, que le tag est correct, et qu'un imagePullSecret est configuré si le registry est privé.
Ingress sans adresse IP : L'Ingress Controller n'est pas installé dans le cluster. Solution : Installez le NGINX Ingress Controller avec kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.9.0/deploy/static/provider/cloud/deploy.yaml.
Connexion Redis refusée : Le mot de passe Redis dans le Secret du backend ne correspond pas au mot de passe configuré dans le Secret Redis. Solution : Assurez-vous que SPRING_DATA_REDIS_PASSWORD et REDIS_PASSWORD ont exactement la même valeur.

15 - Best practices

Toujours spécifier des resource requests ET limits. Sans resource requests, le scheduler Kubernetes ne peut pas prendre de décisions intelligentes sur le placement des Pods. Sans limits, un Pod peut consommer toutes les ressources d'un nœud et impacter les autres applications.
Utiliser des tags d'image spécifiques, jamais latest. Le tag latest est imprévisible : vous ne savez pas quelle version est déployée. Utilisez un tag versionné (1.4.2) ou un digest SHA pour garantir la reproductibilité des déploiements.
Configurer les 3 types de probes pour Spring Boot. La startupProbe protège le démarrage lent, la livenessProbe détecte les blocages, et la readinessProbe retire le Pod du load balancer s'il ne peut pas servir le trafic. Spring Boot Actuator fournit des endpoints dédiés pour chaque probe.
Séparer les secrets par service. Ne mettez pas tous les secrets dans un seul objet Secret. Créez un Secret par composant (PostgreSQL, Redis, Backend, Payment). Cela applique le principe du moindre privilège : chaque Pod n'accède qu'aux secrets dont il a besoin.
Utiliser RollingUpdate avec maxUnavailable: 0. Cela garantit qu'aucun ancien Pod n'est supprimé avant qu'un nouveau Pod ne soit prêt. Combiné avec la readinessProbe, cela assure un zero-downtime deployment.
Tester les manifestes avant de déployer. Utilisez kubectl apply --dry-run=client -f manifest.yaml pour valider la syntaxe, et kubectl diff -k overlays/prod pour voir les changements avant de les appliquer. En CI/CD, ajoutez kubeval ou kubeconform pour la validation automatique des schemas.
Planifier les sauvegardes dès le jour 1. Installez Velero pour les snapshots de PersistentVolumes et configurez des pg_dump périodiques pour PostgreSQL. Testez la restauration régulièrement - une sauvegarde non testée n'est pas une sauvegarde.
