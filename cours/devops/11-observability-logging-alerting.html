Logging & Alerting - ELK Stack

Logging centralisé avec Elasticsearch, Logstash et Kibana - Alerting production avec AlertManager.

1 - Pourquoi le logging centralisé ?

Dans un système distribué déployé sur Kubernetes, les logs sont éparpillés à travers des dizaines - voire des centaines - de pods. Chaque microservice produit ses propres logs, chaque pod a son propre cycle de vie, et quand un pod redémarre ou est remplacé, ses logs disparaissent définitivement.

La commande kubectl logs ne suffit pas :

  • Éphémère - Les logs sont perdus dès qu'un pod est supprimé, crashé ou redémarré. Impossible d'enquêter sur un incident passé.
  • Un pod à la fois - Vous ne pouvez consulter les logs que d'un seul pod. Tracer une requête qui traverse 5 microservices est un cauchemar.
  • Pas de recherche - Aucune possibilité de filtrer, rechercher ou agréger. Vous êtes limité à grep sur du texte brut.
  • Pas de rétention - Kubernetes ne conserve pas un historique configurable. Vous n'avez accès qu'aux logs récents.
  • Pas de corrélation - Impossible de relier les logs d'un service de paiement à ceux du service de notification pour une même transaction.

Le logging centralisé résout tous ces problèmes en collectant, stockant et indexant les logs de tous les services dans un système unique, consultable et durable.

Règle fondamentale - Si vous ne pouvez pas rechercher un log de la semaine dernière en moins de 30 secondes, votre système de logging est insuffisant pour la production.

2.1 - Rôle de chaque composant

  • Filebeat - Agent léger déployé en DaemonSet (un par nœud Kubernetes). Lit les fichiers de logs des conteneurs, enrichit chaque entrée avec les métadonnées Kubernetes (nom du pod, namespace, labels), et transmet à Logstash ou directement à Elasticsearch.
  • Logstash - Moteur de traitement de données. Reçoit les logs de Filebeat, les parse (JSON, grok patterns), les transforme (ajout de champs, normalisation des dates, enrichissement), et les envoie à Elasticsearch. C'est le « ETL » de vos logs.
  • Elasticsearch - Moteur de recherche et d'indexation distribué. Stocke les logs dans des index, les indexe pour une recherche full-text ultra-rapide. Supporte des requêtes complexes, l'agrégation et la rétention configurable.
  • Kibana - Interface web de visualisation. Permet de rechercher des logs, créer des dashboards, configurer des alertes, et visualiser des patterns dans vos données.

3 - Configurer Spring Boot pour le logging structuré

Le premier prérequis pour un logging centralisé efficace est de produire des logs structurés en JSON. Les logs en texte brut (2024-01-15 ERROR Something went wrong) sont difficiles à parser et source d'erreurs. Le JSON est natif pour Elasticsearch.

3.1 - Dépendances Maven

<!-- pom.xml -->
<dependencies>
    <!-- Logstash Logback Encoder - produit du JSON -->
    <dependency>
        <groupId>net.logstash.logback</groupId>
        <artifactId>logstash-logback-encoder</artifactId>
        <version>7.4</version>
    </dependency>

    <!-- Micrometer Tracing - distributed tracing -->
    <dependency>
        <groupId>io.micrometer</groupId>
        <artifactId>micrometer-tracing-bridge-brave</artifactId>
    </dependency>
</dependencies>

3.2 - logback-spring.xml complet

Ce fichier configure Logback pour produire du JSON structuré avec tous les champs nécessaires pour la corrélation distribuée :

<!-- src/main/resources/logback-spring.xml -->
<configuration>

    <!-- ══════ Variables d'environnement ══════ -->
    <springProperty scope="context" name="APP_NAME"
                    source="spring.application.name"
                    defaultValue="unknown-service"/>
    <springProperty scope="context" name="APP_ENV"
                    source="spring.profiles.active"
                    defaultValue="default"/>

    <!-- ══════ Appender Console JSON (Production) ══════ -->
    <appender name="JSON_CONSOLE"
              class="ch.qos.logback.core.ConsoleAppender">
        <encoder class="net.logstash.logback.encoder.LogstashEncoder">
            <!-- Champs personnalisés ajoutés à chaque log -->
            <customFields>
                {"service":"${APP_NAME}","environment":"${APP_ENV}"}
            </customFields>

            <!-- Inclure les informations du MDC (traceId, spanId) -->
            <includeMdcKeyName>traceId</includeMdcKeyName>
            <includeMdcKeyName>spanId</includeMdcKeyName>
            <includeMdcKeyName>userId</includeMdcKeyName>
            <includeMdcKeyName>requestId</includeMdcKeyName>

            <!-- Format du timestamp -->
            <timestampPattern>yyyy-MM-dd'T'HH:mm:ss.SSSZ</timestampPattern>

            <!-- Inclure le stack trace complet pour les exceptions -->
            <throwableConverter
                class="net.logstash.logback.stacktrace.ShortenedThrowableConverter">
                <maxDepthPerThrowable>30</maxDepthPerThrowable>
                <maxLength>2048</maxLength>
                <shortenedClassNameLength>20</shortenedClassNameLength>
            </throwableConverter>
        </encoder>
    </appender>

    <!-- ══════ Appender Console Lisible (Développement) ══════ -->
    <appender name="CONSOLE"
              class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>
                %d{HH:mm:ss.SSS} %highlight(%-5level) [%thread]
                %cyan(%logger{36}) - %msg%n
            </pattern>
        </encoder>
    </appender>

    <!-- ══════ Profils Spring ══════ -->
    <springProfile name="dev">
        <root level="DEBUG">
            <appender-ref ref="CONSOLE"/>
        </root>
    </springProfile>

    <springProfile name="staging | prod">
        <root level="INFO">
            <appender-ref ref="JSON_CONSOLE"/>
        </root>
        <!-- Réduire le bruit des librairies -->
        <logger name="org.hibernate.SQL" level="WARN"/>
        <logger name="org.springframework.web" level="WARN"/>
        <logger name="org.apache.kafka" level="WARN"/>
    </springProfile>

</configuration>

3.3 - MDC (Mapped Diagnostic Context)

Le MDC permet d'attacher des informations contextuelles à chaque log produit dans le cadre d'une requête. C'est essentiel pour la corrélation :

// Filtre HTTP pour injecter le MDC
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class MdcFilter implements Filter {

    @Override
    public void doFilter(ServletRequest request,
                         ServletResponse response,
                         FilterChain chain) throws IOException, ServletException {
        HttpServletRequest httpRequest = (HttpServletRequest) request;

        try {
            // Récupérer ou générer un requestId
            String requestId = httpRequest.getHeader("X-Request-ID");
            if (requestId == null || requestId.isBlank()) {
                requestId = UUID.randomUUID().toString();
            }

            // Injecter dans le MDC - disponible dans tous les logs
            MDC.put("requestId", requestId);
            MDC.put("userId", extractUserId(httpRequest));
            MDC.put("clientIp", httpRequest.getRemoteAddr());
            MDC.put("httpMethod", httpRequest.getMethod());
            MDC.put("uri", httpRequest.getRequestURI());

            // Propager le requestId dans la réponse
            HttpServletResponse httpResponse = (HttpServletResponse) response;
            httpResponse.setHeader("X-Request-ID", requestId);

            chain.doFilter(request, response);
        } finally {
            // TOUJOURS nettoyer le MDC pour éviter les fuites
            MDC.clear();
        }
    }

    private String extractUserId(HttpServletRequest request) {
        // Extraire l'userId du token JWT si présent
        String auth = request.getHeader("Authorization");
        if (auth != null && auth.startsWith("Bearer ")) {
            // Décoder le JWT et extraire le subject
            return JwtUtil.extractSubject(auth.substring(7));
        }
        return "anonymous";
    }
}

4 - Elasticsearch sur Kubernetes

Elasticsearch est le cœur du système ELK. C'est un moteur de recherche distribué qui stocke et indexe vos logs. En production, on déploie un cluster de 3 nœuds minimum pour assurer la haute disponibilité et la réplication des données.

Attention - Elasticsearch est gourmand en mémoire - Chaque nœud Elasticsearch nécessite au minimum 2 Go de RAM (heap JVM), et en production on recommande 4 à 8 Go. Prévoyez des nœuds Kubernetes avec suffisamment de ressources.

4.1 - Headless Service (découverte interne)

# elasticsearch-headless-service.yaml
apiVersion: v1
kind: Service
metadata:
  name: elasticsearch-headless
  namespace: logging
  labels:
    app: elasticsearch
spec:
  clusterIP: None       # Headless - pour la découverte StatefulSet
  selector:
    app: elasticsearch
  ports:
    - name: transport
      port: 9300         # Communication inter-nœuds
      targetPort: 9300
    - name: http
      port: 9200         # API REST
      targetPort: 9200

4.3 - StatefulSet (cluster 3 nœuds)

# elasticsearch-statefulset.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: elasticsearch
  namespace: logging
spec:
  serviceName: elasticsearch-headless
  replicas: 3
  selector:
    matchLabels:
      app: elasticsearch
  template:
    metadata:
      labels:
        app: elasticsearch
    spec:
      # Empêcher deux nœuds ES sur le même nœud K8s
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchExpressions:
                  - key: app
                    operator: In
                    values:
                      - elasticsearch
              topologyKey: kubernetes.io/hostname

      initContainers:
        # ES nécessite vm.max_map_count >= 262144
        - name: sysctl
          image: busybox:1.36
          command: ["sysctl", "-w", "vm.max_map_count=262144"]
          securityContext:
            privileged: true

        # Fixer les permissions du répertoire de données
        - name: fix-permissions
          image: busybox:1.36
          command: ["sh", "-c", "chown -R 1000:1000 /usr/share/elasticsearch/data"]
          volumeMounts:
            - name: data
              mountPath: /usr/share/elasticsearch/data

      containers:
        - name: elasticsearch
          image: docker.elastic.co/elasticsearch/elasticsearch:8.12.0
          ports:
            - containerPort: 9200
              name: http
            - containerPort: 9300
              name: transport
          env:
            - name: node.name
              valueFrom:
                fieldRef:
                  fieldPath: metadata.name
            - name: cluster.name
              value: "bmis-logs"
            - name: discovery.seed_hosts
              value: "elasticsearch-headless"
            - name: cluster.initial_master_nodes
              value: "elasticsearch-0,elasticsearch-1,elasticsearch-2"
            - name: ES_JAVA_OPTS
              value: "-Xms2g -Xmx2g"     # Heap JVM - 50% de la RAM dispo
            - name: xpack.security.enabled
              value: "false"              # Simplification - activer en prod
          resources:
            requests:
              memory: "3Gi"
              cpu: "500m"
            limits:
              memory: "4Gi"
              cpu: "1000m"
          volumeMounts:
            - name: data
              mountPath: /usr/share/elasticsearch/data
          readinessProbe:
            httpGet:
              path: /_cluster/health?local=true
              port: 9200
            initialDelaySeconds: 30
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /_cluster/health?local=true
              port: 9200
            initialDelaySeconds: 60
            periodSeconds: 15

  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: standard
        resources:
          requests:
            storage: 50Gi      # Adapter selon le volume de logs

5 - Logstash - Pipeline de traitement

Logstash reçoit les logs bruts de Filebeat, les transforme (parsing JSON, enrichissement, normalisation), et les envoie à Elasticsearch. C'est le composant de traitement de la stack.

5.1 - ConfigMap pour la pipeline

# logstash-configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: logstash-pipeline
  namespace: logging
data:
  logstash.conf: |
    # ══════════════════════════════════════════════
    # INPUT - Réception des logs depuis Filebeat
    # ══════════════════════════════════════════════
    input {
      beats {
        port => 5044
      }
    }

    # ══════════════════════════════════════════════
    # FILTER - Traitement et enrichissement
    # ══════════════════════════════════════════════
    filter {
      # Parser le message JSON de Spring Boot
      if [message] =~ /^\{/ {
        json {
          source => "message"
          target => "app"
          skip_on_invalid_json => true
        }
      }

      # Extraire le niveau de log si absent
      if [app][level] {
        mutate {
          add_field => { "log_level" => "%{[app][level]}" }
        }
      }

      # Parser les logs non-JSON (legacy)
      if ![app] {
        grok {
          match => {
            "message" => "%{TIMESTAMP_ISO8601:timestamp} %{LOGLEVEL:log_level} \[%{DATA:thread}\] %{JAVACLASS:logger} - %{GREEDYDATA:log_message}"
          }
          tag_on_failure => ["_grok_parse_failure"]
        }
      }

      # Normaliser le timestamp
      date {
        match => ["[app][@timestamp]", "ISO8601"]
        target => "@timestamp"
        remove_field => ["[app][@timestamp]"]
      }

      # Ajouter des métadonnées utiles
      mutate {
        # Supprimer les champs inutiles
        remove_field => ["agent", "ecs", "input", "host"]

        # Renommer pour cohérence
        rename => {
          "[kubernetes][namespace]" => "k8s_namespace"
          "[kubernetes][pod][name]" => "k8s_pod"
          "[kubernetes][labels][app]" => "k8s_app"
        }
      }

      # Identifier les erreurs pour un index séparé
      if [log_level] =~ /ERROR|FATAL/ {
        mutate {
          add_tag => ["error"]
        }
      }
    }

    # ══════════════════════════════════════════════
    # OUTPUT - Envoi vers Elasticsearch
    # ══════════════════════════════════════════════
    output {
      elasticsearch {
        hosts => ["http://elasticsearch:9200"]
        # Index par jour pour faciliter la rétention
        index => "logs-%{k8s_namespace}-%{+YYYY.MM.dd}"
        # Index séparé pour les erreurs
        # (permet des alertes spécifiques)
      }

      # Debug - décommenter pour voir les logs traités
      # stdout { codec => rubydebug }
    }

6 - Filebeat - Agent de collecte

Filebeat est déployé en DaemonSet : un pod Filebeat tourne sur chaque nœud du cluster Kubernetes. Il lit les fichiers de logs des conteneurs depuis /var/log/containers/ et les envoie à Logstash.

6.1 - ConfigMap Filebeat

# filebeat-configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: filebeat-config
  namespace: logging
data:
  filebeat.yml: |
    # ══════ Input - Logs des conteneurs ══════
    filebeat.inputs:
      - type: container
        paths:
          - /var/log/containers/*.log
        # Parser le format Docker/containerd
        processors:
          - add_kubernetes_metadata:
              host: ${NODE_NAME}
              matchers:
                - logs_path:
                    logs_path: "/var/log/containers/"

    # ══════ Filtrage par namespace ══════
    # Ne collecter que les namespaces pertinents
    processors:
      - drop_event:
          when:
            or:
              - equals:
                  kubernetes.namespace: "kube-system"
              - equals:
                  kubernetes.namespace: "kube-public"
              - equals:
                  kubernetes.namespace: "logging"

    # ══════ Output - Envoi vers Logstash ══════
    output.logstash:
      hosts: ["logstash.logging.svc.cluster.local:5044"]
      # Loadbalance entre les instances Logstash
      loadbalance: true

    # ══════ Alternative - Envoi direct à Elasticsearch ══════
    # output.elasticsearch:
    #   hosts: ["elasticsearch.logging.svc.cluster.local:9200"]
    #   index: "filebeat-%{+yyyy.MM.dd}"

    # ══════ Logging interne Filebeat ══════
    logging.level: warning
    logging.to_files: false

8 - Corrélation de logs

Dans un système de microservices, une seule requête utilisateur peut traverser 5 à 10 services. Sans corrélation, il est impossible de reconstituer le parcours complet d'une requête. C'est le problème le plus critique du logging distribué.

8.1 - Request ID across services

Le principe est simple : chaque requête entrante reçoit un identifiant unique qui est propagé à travers tous les appels inter-services :

// Intercepteur RestTemplate/WebClient pour propager le requestId
@Component
public class CorrelationInterceptor implements ClientHttpRequestInterceptor {

    @Override
    public ClientHttpResponse intercept(HttpRequest request,
                                         byte[] body,
                                         ClientHttpRequestExecution execution)
                                         throws IOException {
        // Récupérer le requestId du MDC (injecté par le MdcFilter)
        String requestId = MDC.get("requestId");
        String traceId = MDC.get("traceId");

        if (requestId != null) {
            request.getHeaders().set("X-Request-ID", requestId);
        }
        if (traceId != null) {
            request.getHeaders().set("X-Trace-ID", traceId);
        }

        return execution.execute(request, body);
    }
}

// Configuration du RestTemplate
@Configuration
public class RestTemplateConfig {
    @Bean
    public RestTemplate restTemplate(CorrelationInterceptor interceptor) {
        RestTemplate restTemplate = new RestTemplate();
        restTemplate.setInterceptors(List.of(interceptor));
        return restTemplate;
    }
}

8.2 - Micrometer Tracing (ex-Spring Cloud Sleuth)

Micrometer Tracing (qui remplace Spring Cloud Sleuth) ajoute automatiquement un traceId et un spanId à chaque requête. Chaque service dans la chaîne partage le même traceId, mais a un spanId unique :

# application.yml - Configuration Micrometer Tracing
management:
  tracing:
    sampling:
      probability: 1.0    # 100% des requêtes tracées
    propagation:
      type: b3             # Compatible Zipkin/Brave
      consume: [b3, w3c]
      produce: [b3, w3c]

Flux d'une requête de paiement :

Requête Client → API Gateway → Payment Service → User Service → Notification Service
                 │                │                 │                │
traceId:         abc123           abc123             abc123           abc123
spanId:          span-01          span-02            span-03          span-04

8.3 - Rechercher par traceId dans Kibana

# Dans Kibana Discover - KQL :
app.traceId: "abc123def456"

# Résultat : TOUS les logs de TOUS les services pour cette requête
# Triés par @timestamp, vous voyez le parcours complet :
#
# 14:23:45.100  api-gateway        → Requête reçue POST /api/payments
# 14:23:45.105  payment-service    → Validation du paiement
# 14:23:45.150  user-service       → Vérification du solde utilisateur
# 14:23:45.200  payment-service    → Paiement approuvé, montant: 150.00€
# 14:23:45.210  notification-svc   → Email de confirmation envoyé
# 14:23:45.220  api-gateway        → Réponse 200 OK (120ms)
Toujours inclure des IDs de corrélation - Chaque log doit contenir au minimum : traceId, requestId, userId. Sans ces champs, vos logs sont inutilisables pour le debugging en production. Configurez-les dès le début du projet, pas en urgence après un incident.

9 - AlertManager

Le logging centralisé permet de diagnostiquer les problèmes. Mais comment détecter qu'un problème existe avant que les utilisateurs ne le signalent ? C'est le rôle de l'alerting.

AlertManager est le composant de Prometheus responsable de la gestion des alertes. Il reçoit les alertes déclenchées par Prometheus, les groupe, les déduplique, les achemine vers les bons canaux de notification, et gère les silences et les inhibitions.

9.1 - Architecture de l'alerting

┌──────────────────┐     ┌──────────────────┐     ┌──────────────────┐
│                  │     │                  │     │                  │
│   Prometheus     │────▶│  AlertManager    │────▶│  Notification    │
│                  │     │                  │     │                  │
│  - Évalue les    │     │  - Groupement    │     │  - Slack         │
│    règles        │     │  - Déduplication │     │  - Email         │
│  - Déclenche     │     │  - Routage       │     │  - PagerDuty     │
│    les alertes   │     │  - Inhibition    │     │  - Webhook       │
│                  │     │  - Silences      │     │                  │
└──────────────────┘     └──────────────────┘     └──────────────────┘

9.2 - Concepts clés

  • Groupement - Les alertes similaires sont regroupées en une seule notification. Si 50 pods ont le même problème, vous recevez UNE notification, pas 50.
  • Déduplication - Une alerte déjà envoyée n'est pas renvoyée tant qu'elle est active.
  • Routage - Chaque alerte est acheminée vers le bon canal selon sa sévérité et son type. Les alertes critiques vont à PagerDuty, les warnings à Slack.
  • Inhibition - Si le cluster entier est down (alerte critique), les alertes individuelles de chaque service sont supprimées pour éviter le bruit.
  • Silences - Permet de désactiver temporairement une alerte pendant une maintenance planifiée.

kind: ConfigMap
metadata:
  name: alertmanager-config
  namespace: monitoring
data:
  alertmanager.yml: |
    # ══════════════════════════════════════════════
    # Configuration globale

      resolve_timeout: 5m
      smtp_from: 'alerts@bmis-academy.com'
      smtp_smarthost: 'smtp.gmail.com:587'
      smtp_auth_username: 'alerts@bmis-academy.com'
      smtp_auth_password: 'app-password-here'
      smtp_require_tls: true
      slack_api_url: 'https://hooks.slack.com/services/T00/B00/xxxx'

    # ══════════════════════════════════════════════
    # Templates de notification
    # ══════════════════════════════════════════════
    templates:
      - '/etc/alertmanager/templates/*.tmpl'

    # ══════════════════════════════════════════════
    # Arbre de routage
    # ══════════════════════════════════════════════
    route:
      # Route par défaut
      receiver: 'slack-warnings'
      group_by: ['alertname', 'namespace', 'service']
      group_wait: 30s           # Attendre 30s avant d'envoyer (groupement)
      group_interval: 5m        # Intervalle entre les notifications groupées
      repeat_interval: 4h       # Re-notifier après 4h si toujours actif

      routes:
        # ── Alertes critiques → PagerDuty + Slack ──
        - match:
            severity: critical
          receiver: 'pagerduty-critical'
          group_wait: 10s        # Envoyer rapidement
          repeat_interval: 1h
          continue: true         # Continuer pour aussi envoyer à Slack

        - match:
            severity: critical
          receiver: 'slack-critical'

        # ── Alertes de paiement → Canal dédié ──
        - match_re:
            alertname: 'Payment.*'
          receiver: 'slack-payments'
          group_wait: 15s

        # ── Alertes warning → Slack général ──
        - match:
            severity: warning
          receiver: 'slack-warnings'

        # ── Alertes info → Email uniquement ──
        - match:
            severity: info
          receiver: 'email-team'
          repeat_interval: 12h

    # ══════════════════════════════════════════════
    # Inhibition - Supprimer le bruit
    # ══════════════════════════════════════════════
    inhibit_rules:
      # Si le cluster est down, ne pas alerter sur les services individuels
      - source_match:
          alertname: 'KubeClusterDown'
        target_match_re:
          alertname: '.*'
        equal: ['cluster']

      # Si un nœud est down, ne pas alerter sur ses pods
      - source_match:
          alertname: 'KubeNodeNotReady'
        target_match_re:
          alertname: 'KubePod.*'
        equal: ['node']

    # ══════════════════════════════════════════════
    # Receivers - Canaux de notification
    # ══════════════════════════════════════════════
    receivers:
      - name: 'slack-critical'

            color: 'danger'
            title: '🚨 CRITIQUE - {{ .GroupLabels.alertname }}'
            text: >-

              *Service :* {{ .GroupLabels.service }}

              *Runbook :* {{ .CommonAnnotations.runbook_url }}

      - name: 'slack-warnings'
        slack_configs:
          - channel: '#alerts-warnings'
            color: 'warning'

            text: >-

10 - Alerting Rules

Les règles d'alerte sont définies dans Prometheus et évaluées en continu. Quand une condition est remplie pendant la durée spécifiée (for), l'alerte est déclenchée et envoyée à AlertManager.

En utilisant le Prometheus Operator, les règles sont définies via le CRD PrometheusRule :

10.1 - Règles d'infrastructure

# prometheus-rules-infrastructure.yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: infrastructure-alerts
  namespace: monitoring
  labels:
    release: prometheus     # Label requis par le Prometheus Operator
spec:
  groups:
    # ══════════════════════════════════════════════
    # CPU / Mémoire
    # ══════════════════════════════════════════════
    - name: resource-alerts
      rules:
        # CPU élevé pendant 5 minutes
        - alert: HighCpuUsage
          expr: |
            (
              sum(rate(container_cpu_usage_seconds_total{
                namespace!="kube-system"
              }[5m])) by (pod, namespace)
              /
              sum(kube_pod_container_resource_limits{
                resource="cpu",
                namespace!="kube-system"
              }) by (pod, namespace)
            ) > 0.8
          for: 5m
          labels:
            severity: warning
          annotations:
            summary: "CPU élevé sur {{ $labels.pod }}"
            description: >-
              Le pod {{ $labels.pod }} dans {{ $labels.namespace }}
              utilise plus de 80% de sa limite CPU depuis 5 minutes.
              Valeur actuelle : {{ $value | humanizePercentage }}.
            runbook_url: "https://wiki.bmis.local/runbooks/high-cpu"

        # Mémoire proche de la limite
        - alert: HighMemoryUsage
          expr: |
            (
              container_memory_working_set_bytes{
                namespace!="kube-system"
              }
              /
              kube_pod_container_resource_limits{
                resource="memory",
                namespace!="kube-system"
              }
            ) > 0.85
          for: 5m
          labels:
            severity: warning
          annotations:
            summary: "Mémoire élevée sur {{ $labels.pod }}"
            description: >-
              Le pod {{ $labels.pod }} utilise plus de 85% de sa
              limite mémoire. Risque d'OOMKill imminent.

    # ══════════════════════════════════════════════
    # Stockage
    # ══════════════════════════════════════════════
    - name: storage-alerts
      rules:
        - alert: DiskSpaceLow
          expr: |
            (
              kubelet_volume_stats_available_bytes
              /
              kubelet_volume_stats_capacity_bytes
            ) < 0.15
          for: 10m
          labels:
            severity: warning
          annotations:
            summary: "Espace disque faible sur {{ $labels.persistentvolumeclaim }}"
            description: >-
              Le PVC {{ $labels.persistentvolumeclaim }} dans
              {{ $labels.namespace }} a moins de 15% d'espace libre.
              Capacité restante : {{ $value | humanizePercentage }}.

        - alert: DiskSpaceCritical
          expr: |
            (
              kubelet_volume_stats_available_bytes
              /
              kubelet_volume_stats_capacity_bytes
            ) < 0.05
          for: 5m
          labels:
            severity: critical
          annotations:
            summary: "CRITIQUE - Espace disque < 5% sur {{ $labels.persistentvolumeclaim }}"
            description: >-
              Action immédiate requise. Le PVC {{ $labels.persistentvolumeclaim }}
              est presque plein.

10.2 - Règles applicatives

# prometheus-rules-application.yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: application-alerts
  namespace: monitoring
  labels:
    release: prometheus
spec:
  groups:
    # ══════════════════════════════════════════════
    # Taux d'erreur HTTP
    # ══════════════════════════════════════════════
    - name: http-error-alerts
      rules:
        # Taux d'erreur 5xx élevé
        - alert: HighErrorRate
          expr: |
            (
              sum(rate(http_server_requests_seconds_count{
                status=~"5..",
                namespace="production"
              }[5m])) by (service)
              /
              sum(rate(http_server_requests_seconds_count{
                namespace="production"
              }[5m])) by (service)
            ) > 0.05
          for: 5m
          labels:
            severity: critical
          annotations:
            summary: "Taux d'erreur 5xx > 5% sur {{ $labels.service }}"
            description: >-
              Le service {{ $labels.service }} retourne plus de 5%
              de réponses 5xx depuis 5 minutes. Taux actuel :
              {{ $value | humanizePercentage }}.
            runbook_url: "https://wiki.bmis.local/runbooks/high-error-rate"

        # Latence élevée
        - alert: HighLatency
          expr: |
            histogram_quantile(0.95,
              sum(rate(http_server_requests_seconds_bucket{
                namespace="production"
              }[5m])) by (le, service)
            ) > 2
          for: 5m
          labels:
            severity: warning
          annotations:
            summary: "Latence P95 > 2s sur {{ $labels.service }}"
            description: >-
              Le percentile 95 de la latence du service
              {{ $labels.service }} dépasse 2 secondes.

    # ══════════════════════════════════════════════
    # Pods - CrashLoop et disponibilité
    # ══════════════════════════════════════════════
    - name: pod-alerts
      rules:
        # Pod en CrashLoopBackOff
        - alert: PodCrashLooping
          expr: |
            rate(kube_pod_container_status_restarts_total[15m])
            * 60 * 5 > 0
          for: 5m
          labels:
            severity: critical
          annotations:
            summary: "Pod {{ $labels.pod }} en CrashLoopBackOff"
            description: >-
              Le pod {{ $labels.pod }} dans {{ $labels.namespace }}
              redémarre en boucle. Vérifiez les logs avec :
              kubectl logs {{ $labels.pod }} -n {{ $labels.namespace }}
            runbook_url: "https://wiki.bmis.local/runbooks/crashloop"

        # Application down (target Prometheus inaccessible)
        - alert: ApplicationDown
          expr: up == 0
          for: 2m
          labels:
            severity: critical
          annotations:
            summary: "Application {{ $labels.job }} DOWN"
            description: >-
              La target Prometheus {{ $labels.instance }} du job
              {{ $labels.job }} ne répond plus depuis 2 minutes.

    # ══════════════════════════════════════════════
    # Paiements - Alertes métier
    # ══════════════════════════════════════════════
    - name: payment-alerts
      rules:
        # Pic de paiements échoués
        - alert: PaymentFailureRateSpike
          expr: |
            (
              sum(rate(payment_transactions_total{
                status="failed"
              }[5m]))
              /
              sum(rate(payment_transactions_total[5m]))
            ) > 0.1
          for: 3m
          labels:
            severity: critical
            team: payments
          annotations:
            summary: "Taux d'échec des paiements > 10%"
            description: >-
              Plus de 10% des paiements échouent depuis 3 minutes.
              Taux actuel : {{ $value | humanizePercentage }}.
              Vérifiez le provider de paiement et les logs du
              payment-service.
            runbook_url: "https://wiki.bmis.local/runbooks/payment-failures"

        # Aucun paiement traité (service potentiellement bloqué)
        - alert: NoPaymentsProcessed
          expr: |
            sum(rate(payment_transactions_total[10m])) == 0
          for: 10m
          labels:
            severity: critical
            team: payments
          annotations:
            summary: "Aucun paiement traité depuis 10 minutes"
            description: >-
              Le système de paiement ne traite aucune transaction.
              Vérifiez si le service est opérationnel et si le
              provider de paiement est accessible.

12 - Runbooks et réponse aux incidents

Une alerte sans procédure de réponse est inutile. Les runbooks sont des guides étape par étape qui décrivent comment diagnostiquer et résoudre un problème spécifique.

12.1 - Lier les alertes aux runbooks

Chaque règle d'alerte doit inclure un lien vers son runbook dans les annotations :

# Dans les alerting rules

  summary: "Taux d'erreur élevé"

Quand un ingénieur reçoit l'alerte (Slack, PagerDuty), il clique sur le lien du runbook et suit les étapes :

  1. Évaluer la sévérité - L'alerte affecte-t-elle les utilisateurs ? Quel est l'impact business ?
  2. Diagnostiquer - Consulter les logs (Kibana), les métriques (Grafana), les événements Kubernetes.
  3. Résoudre - Appliquer le correctif (rollback, scale up, redémarrage, fix de config).
  4. Documenter - Écrire un post-mortem si l'incident était significatif.

12.2 - Politique d'escalade

Définissez clairement qui est notifié et quand :

  • Niveau 1 (0-5 min) - L'ingénieur d'astreinte reçoit l'alerte via PagerDuty. Il a 5 minutes pour acquitter.
  • Niveau 2 (5-15 min) - Si pas d'acquittement, l'alerte est escaladée au second on-call et au tech lead.
  • Niveau 3 (15-30 min) - Si toujours pas de réponse, le manager engineering et le CTO sont notifiés.
  • Niveau 4 (30+ min) - Incident majeur. War room, communication aux stakeholders.

12.3 - Rotation d'astreinte (On-Call)

L'astreinte est une responsabilité partagée. Les bonnes pratiques :

  • Rotation hebdomadaire - Chaque ingénieur est d'astreinte une semaine par mois maximum.
  • Binôme primaire/secondaire - Toujours deux personnes d'astreinte pour la redondance.
  • Compensation - Les heures d'astreinte et les interventions nocturnes sont compensées (repos, prime).
  • Handoff documenté - À chaque rotation, un handoff avec les incidents en cours et les points d'attention.
  • Post-mortems - Après chaque incident, un post-mortem sans blame est rédigé et partagé.

13 - Alternatives légères - Loki + Promtail

L'ELK Stack est puissante mais gourmande en ressources. Elasticsearch seul nécessite plusieurs gigaoctets de RAM. Pour les équipes avec des ressources limitées ou des besoins plus simples, Grafana Loki est une alternative intéressante.

13.1 - Loki vs ELK

  • Loki n'indexe que les labels (namespace, pod, service), pas le contenu complet des logs. Cela le rend beaucoup plus léger et moins cher à opérer.
  • Promtail remplace Filebeat - c'est l'agent qui collecte les logs et les envoie à Loki.
  • Grafana sert d'interface de visualisation (au lieu de Kibana), ce qui permet d'avoir métriques + logs dans le même outil.
  • Trade-off - Les recherches full-text sont plus lentes qu'avec Elasticsearch, mais la plupart des recherches se font par labels (service, namespace, level), ce qui est très rapide avec Loki.

13.2 - Architecture Loki

Applications → Promtail (DaemonSet) → Loki (stockage S3/MinIO) → Grafana (UI)

# Installer Loki avec Helm (approche recommandée)
# Ajouter le repo Grafana
helm repo add grafana https://grafana.github.io/helm-charts
helm repo update

# Installer Loki + Promtail
helm install loki grafana/loki-stack \
  --namespace logging \
  --set promtail.enabled=true \
  --set grafana.enabled=false     # Si Grafana existe déjà

Pour les petites équipes et les environnements de développement, Loki est souvent le meilleur choix. Réservez l'ELK Stack aux systèmes qui nécessitent une recherche full-text avancée et un volume de logs important.

14 - Erreurs courantes

Pas de logging structuré - Envoyer des logs en texte brut à Elasticsearch. Le parsing est fragile, les champs sont incohérents entre les services, et les recherches sont peu fiables. Toujours utiliser JSON structuré.
Pas d'IDs de corrélation - Sans traceId et requestId, chaque log est isolé. Impossible de suivre une requête à travers les microservices. C'est comme essayer de résoudre un puzzle sans les bords.
Alert fatigue - Configurer trop d'alertes, ou des seuils trop bas, noie l'équipe sous les notifications. Après quelques semaines, les ingénieurs ignorent les alertes - y compris les vraies. Chaque alerte doit être actionnable et nécessiter une intervention humaine.
Pas de runbooks - Recevoir une alerte « HighErrorRate » à 3h du matin sans documentation de résolution. L'ingénieur d'astreinte perd du temps à chercher quoi faire au lieu de résoudre le problème. Chaque alerte doit avoir un runbook associé.
Logs excessifs en production - Logger en niveau DEBUG en production. Le volume de logs explose, Elasticsearch rame, les coûts de stockage augmentent, et les vrais problèmes sont noyés dans le bruit. Utilisez INFO minimum en production.
Pas de rétention configurée - Laisser Elasticsearch stocker les logs indéfiniment. L'espace disque finit par se remplir, et le cluster devient instable. Configurez des politiques de rétention (ex : 30 jours pour les logs applicatifs, 90 jours pour les logs d'audit).

15 - Best practices

Logging structuré dès le jour 1 - Configurez le format JSON et les IDs de corrélation dès le début du projet. Les ajouter après coup est douloureux et nécessite de re-déployer tous les services.
Séparer les logs par niveau - Envoyez les logs ERROR dans un index séparé pour un accès rapide. Les erreurs représentent moins de 1% du volume mais 99% des investigations.
Alertes actionnables uniquement - Si une alerte ne nécessite pas d'action humaine immédiate, c'est une métrique, pas une alerte. Réservez les notifications pour les situations qui requièrent une intervention.
Tester vos alertes - Déclenchez volontairement chaque alerte pour vérifier qu'elle fonctionne : le routage est correct, la notification arrive, le runbook est accessible, et l'équipe sait quoi faire.
Politique de rétention - Configurez Index Lifecycle Management (ILM) dans Elasticsearch : hot (7 jours, SSD), warm (30 jours, HDD), cold (90 jours, archivage), delete (après 90 jours).
Dashboard de santé globale - Créez un dashboard Kibana/Grafana qui montre en un coup d'œil : nombre d'erreurs, services up/down, latence P95, et alertes actives. C'est la première chose qu'un ingénieur doit consulter le matin.
Ne logguez jamais de données sensibles - Mots de passe, tokens, numéros de carte bancaire, données personnelles (RGPD) ne doivent jamais apparaître dans les logs. Utilisez le masquage ou le filtrage dans Logstash.
