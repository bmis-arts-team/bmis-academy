Leçon 14 Section 8 - Production

Best Practices Production

Scaling, resource limits, health probes, zero-downtime deployment - tout ce qu'il faut pour la production.

1 - La mentalité production

Il y a un gouffre entre « ça marche sur ma machine » et « ça tourne en production pour 50 000 utilisateurs ». En production, chaque erreur coûte de l'argent, chaque seconde de downtime détruit la confiance des clients, et chaque décision d'architecture a des conséquences immédiates.

Avant de déployer quoi que ce soit en production, il faut comprendre trois concepts fondamentaux qui définissent vos engagements envers vos utilisateurs :

1.1 - SLI, SLO, SLA - les trois piliers de la fiabilité

  • SLI (Service Level Indicator) - Une métrique mesurable qui représente la qualité du service. Exemples : taux de réponses réussies (HTTP 2xx), latence p99, taux de disponibilité.
  • SLO (Service Level Objective) - L'objectif interne que vous vous fixez pour chaque SLI. Exemple : « 99.9% des requêtes doivent répondre en moins de 500ms ».
  • SLA (Service Level Agreement) - L'engagement contractuel envers les clients. Si le SLA est violé, il y a des pénalités financières. Le SLA est toujours moins exigeant que le SLO pour avoir une marge de sécurité.

1.2 - Que signifie « 99.9% de disponibilité » ?

Disponibilité Downtime par an Downtime par mois Commentaire
99% 3.65 jours 7.3 heures Inacceptable pour la fintech
99.9% 8.76 heures 43.8 minutes Minimum pour la fintech
99.95% 4.38 heures 21.9 minutes Standard pour les services financiers
99.99% 52.6 minutes 4.38 minutes Difficile à atteindre, coûteux
99.999% 5.26 minutes 26.3 secondes « Five nines » - extrêmement rare
Contexte fintech - Dans un système de transfert d'argent mobile, chaque minute de downtime signifie des transactions bloquées, des clients qui ne peuvent pas envoyer d'argent à leur famille, et potentiellement des millions de francs CFA de transactions perdues. Visez au minimum 99.9% et concevez votre architecture pour 99.95%.

1.3 - Error Budget

L'error budget est le pourcentage d'erreurs que vous « pouvez vous permettre » avant de violer votre SLO. Si votre SLO est de 99.9%, votre error budget est de 0.1%. Cela signifie que sur 1 000 000 de requêtes, vous pouvez en échouer 1 000 sans violer votre objectif.

Quand l'error budget est consommé, l'équipe doit arrêter de déployer de nouvelles features et se concentrer exclusivement sur la fiabilité. C'est un mécanisme puissant pour équilibrer la vélocité de développement et la stabilité du système.

2 - Horizontal Pod Autoscaler (HPA)

Le HPA est le mécanisme principal de Kubernetes pour adapter automatiquement le nombre de répliques d'un Deployment en fonction de la charge. Au lieu de provisionner un nombre fixe de pods, le HPA augmente ou diminue le nombre de pods en temps réel.

2.1 - Comment fonctionne le HPA (boucle de contrôle)

Le HPA fonctionne comme une boucle de contrôle qui s'exécute toutes les 15 secondes (par défaut) :

  1. Observation - Le HPA interroge le Metrics Server pour obtenir les métriques actuelles des pods ciblés.
  2. Calcul - Il compare la valeur actuelle à la valeur cible et calcule le nombre de répliques nécessaires : replicas = ceil(currentReplicas × (currentMetric / targetMetric))
  3. Action - Si le nombre calculé est différent du nombre actuel, le HPA met à jour le Deployment.
  4. Stabilisation - Le HPA attend une période de stabilisation avant de réduire les répliques (pour éviter le « flapping »).

2.2 - Prérequis : Metrics Server

Le HPA ne peut fonctionner que si le Metrics Server est installé dans le cluster. C'est lui qui collecte les métriques CPU et mémoire de chaque pod et les expose via l'API metrics.k8s.io.

# Vérifier si Metrics Server est installé
kubectl top nodes
kubectl top pods -n production

# Installer Metrics Server si absent
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

# Vérifier l'installation
kubectl get deployment metrics-server -n kube-system

2.3 - HPA basé sur le CPU

Le cas le plus courant : scaler en fonction de l'utilisation CPU. Quand la moyenne d'utilisation CPU de tous les pods dépasse le seuil, le HPA ajoute des répliques.

# hpa-cpu.yaml - HPA basé sur le CPU pour le service de paiement
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: payment-service-hpa
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: payment-service
  minReplicas: 3
  maxReplicas: 15
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70    # Scale up quand CPU > 70%
# Créer un HPA rapidement avec kubectl
kubectl autoscale deployment payment-service \
  --namespace=production \
  --cpu-percent=70 \
  --min=3 \
  --max=15

# Vérifier le statut du HPA
kubectl get hpa -n production
kubectl describe hpa payment-service-hpa -n production

2.4 - HPA basé sur la mémoire

# hpa-memory.yaml - HPA basé sur la mémoire
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: notification-service-hpa
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: notification-service
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80    # Scale up quand mémoire > 80%

2.5 - HPA multi-métriques et métriques custom

Le vrai pouvoir du HPA v2 est de combiner plusieurs métriques et d'utiliser des métriques personnalisées (ex : requêtes par seconde via Prometheus).

# hpa-advanced.yaml - HPA complet pour le système fintech
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-gateway-hpa
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-gateway
  minReplicas: 3
  maxReplicas: 20
  metrics:
    # Métrique 1 - CPU
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 65
    # Métrique 2 - Mémoire
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 75
    # Métrique 3 - Custom : requêtes par seconde (via Prometheus Adapter)
    - type: Pods
      pods:
        metric:
          name: http_requests_per_second
        target:
          type: AverageValue
          averageValue: "100"       # Scale up quand > 100 req/s par pod
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300   # Attendre 5 min avant de réduire
      policies:
        - type: Percent
          value: 10                     # Réduire de max 10% à la fois
          periodSeconds: 60
    scaleUp:
      stabilizationWindowSeconds: 30    # Scale up rapidement
      policies:
        - type: Percent
          value: 50                     # Augmenter de max 50% à la fois
          periodSeconds: 60
        - type: Pods
          value: 4                      # Ou ajouter max 4 pods à la fois
          periodSeconds: 60
      selectPolicy: Max                 # Prendre la politique la plus agressive

2.6 - Min/Max replicas - choisir les bonnes valeurs

  • minReplicas - Jamais en dessous de 2 en production (haute disponibilité). Pour les services critiques comme le paiement, 3 minimum.
  • maxReplicas - Basé sur votre capacité de cluster et votre budget. Prévoyez une marge pour les pics (ex : fin de mois pour les salaires, jours fériés).

3 - Vertical Pod Autoscaler (VPA)

Contrairement au HPA qui ajoute des pods, le VPA ajuste les ressources (CPU/mémoire) de chaque pod. Il analyse l'utilisation historique et recommande (ou applique automatiquement) les bonnes valeurs de requests et limits.

3.1 - Quand utiliser VPA vs HPA

Critère HPA VPA
Type de scaling Horizontal (plus de pods) Vertical (plus de ressources par pod)
Idéal pour Services stateless (API, web) Services stateful, bases de données
Redémarrage nécessaire Non Oui (pour appliquer les nouvelles limites)
Combinable avec HPA - Oui, mais pas sur la même métrique
Maturité Stable, intégré à K8s Addon séparé, moins mature 
# vpa-recommendation.yaml - VPA en mode recommandation (le plus sûr)
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: postgres-vpa
  namespace: production
spec:
  targetRef:
    apiVersion: apps/v1
    kind: StatefulSet
    name: postgres
  updatePolicy:
    updateMode: "Off"    # Mode recommandation uniquement - pas de modification auto
  resourcePolicy:
    containerPolicies:
      - containerName: postgres
        minAllowed:
          cpu: 250m
          memory: 512Mi
        maxAllowed:
          cpu: 4000m
          memory: 8Gi
# Consulter les recommandations VPA
kubectl describe vpa postgres-vpa -n production

# Le VPA affiche :
# - Target : les valeurs recommandées
# - Lower Bound : minimum raisonnable
# - Upper Bound : maximum recommandé
# - Uncapped Target : recommandation sans contraintes

4 - Resource Limits - La base de tout

Les resource limits sont probablement la configuration la plus importante pour la stabilité de votre cluster en production. Sans elles, un seul pod gourmand peut faire tomber tout un nœud.

4.1 - Requests vs Limits

  • Requests - La quantité de ressources garantie au pod. Le scheduler utilise cette valeur pour placer le pod sur un nœud qui a suffisamment de capacité. C'est le minimum.
  • Limits - La quantité maximale de ressources que le pod peut utiliser. S'il dépasse la limite mémoire, il est tué (OOMKilled). S'il dépasse la limite CPU, il est throttled (ralenti, mais pas tué).

4.2 - Que se passe-t-il quand une limite est dépassée ?

Ressource Dépassement de la limite Conséquence
Mémoire Le processus utilise plus que limits.memory OOMKilled - Le pod est tué et redémarré. Perte de toutes les données en mémoire.
CPU Le processus demande plus que limits.cpu CPU Throttling - Le pod est ralenti mais continue de tourner. Les requêtes deviennent plus lentes.

4.3 - Comment déterminer les bonnes valeurs

  1. Observer - Déployez sans limits strictes dans un environnement de staging et observez l'utilisation réelle avec kubectl top pods et Grafana pendant 1–2 semaines.
  2. Tests de charge - Utilisez des outils comme k6, JMeter ou wrk pour simuler la charge attendue et mesurer les pics.
  3. Formule de base - requests = utilisation moyenne observée × 1.2 | limits = pic observé × 1.5
  4. Itérer - Ajustez régulièrement en fonction des métriques réelles. Utilisez les recommandations VPA comme guide.

4.4 - Valeurs recommandées pour chaque composant du système fintech

Composant CPU Request CPU Limit Mémoire Request Mémoire Limit
Spring Boot (API Gateway) 250m 500m 256Mi 512Mi
Spring Boot (Payment Service) 250m 500m 256Mi 512Mi
PostgreSQL 500m 1000m 512Mi 1Gi
Redis 100m 250m 128Mi 256Mi
Angular Frontend (Nginx) 50m 100m 64Mi 128Mi
Prometheus 250m 500m 512Mi 1Gi
Elasticsearch 500m 1000m 1Gi 2Gi

4.5 - Classes QoS (Quality of Service)

Kubernetes attribue automatiquement une classe QoS à chaque pod en fonction de ses requests et limits :

Classe QoS Condition Priorité d'éviction
Guaranteed Tous les containers ont requests = limits (CPU et mémoire) Derniers à être évincés
Burstable Au moins un container a des requests définies, mais requests ≠ limits Évincés après les BestEffort
BestEffort Aucun container n'a de requests ni de limits Premiers à être évincés - DANGEREUX

4.6 - LimitRange - Valeurs par défaut pour le namespace

# limitrange.yaml - Imposer des limites par défaut dans le namespace production
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: production
spec:
  limits:
    - type: Container
      default:            # Limits par défaut si non spécifiées
        cpu: 500m
        memory: 512Mi
      defaultRequest:     # Requests par défaut si non spécifiées
        cpu: 100m
        memory: 128Mi
      max:                # Maximum autorisé dans ce namespace
        cpu: 2000m
        memory: 4Gi
      min:                # Minimum requis dans ce namespace
        cpu: 50m
        memory: 64Mi
# Appliquer le LimitRange
kubectl apply -f limitrange.yaml

# Vérifier les limites en place
kubectl describe limitrange default-limits -n production
Ne jamais déployer sans resource limits - Un pod sans limits est un BestEffort. En cas de pression mémoire sur le nœud, Kubernetes le tuera en premier. Un service Spring Boot qui fuit de la mémoire peut consommer 4 Go et faire tomber tout le nœud, impactant tous les autres pods. En fintech, c'est une panne totale du système de paiement.

5 - Health Checks - Les Probes Kubernetes

Les probes permettent à Kubernetes de savoir si votre application fonctionne correctement. Sans elles, Kubernetes ne peut pas détecter qu'un pod est bloqué, en erreur ou pas encore prêt - il continuera à lui envoyer du trafic.

5.1 - Les trois types de probes

Probe Question posée Action si échec Quand l'utiliser
Liveness « L'application est-elle vivante ? » Le pod est redémarré Toujours - détecte les deadlocks, les fuites mémoire bloquantes
Readiness « L'application est-elle prête à recevoir du trafic ? » Le pod est retiré du Service (plus de trafic) Toujours - évite d'envoyer du trafic à un pod pas encore prêt
Startup « L'application a-t-elle fini de démarrer ? » Les autres probes ne sont pas encore activées Quand l'application met du temps à démarrer (Spring Boot, Java)

5.2 - Types de probes : HTTP, TCP, exec

  • HTTP GET - Envoie une requête HTTP à un endpoint. Succès si code 200–399. Le plus courant pour les API.
  • TCP Socket - Tente d'ouvrir une connexion TCP sur un port. Succès si la connexion est établie. Utile pour les bases de données.
  • Exec - Exécute une commande dans le container. Succès si le code de retour est 0. Utile pour des checks plus complexes.

5.3 - Spring Boot Actuator - Les endpoints de santé

Spring Boot fournit des endpoints de santé prêts à l'emploi via Actuator :

# application.yml - Configuration Actuator pour les probes Kubernetes
management:
  endpoints:
    web:
      exposure:
        include: health, info, prometheus
  endpoint:
    health:
      show-details: always
      probes:
        enabled: true           # Active /actuator/health/liveness et /readiness
  health:
    livenessState:
      enabled: true
    readinessState:
      enabled: true
    db:
      enabled: true             # Vérifie la connexion à la base de données
    redis:
      enabled: true             # Vérifie la connexion à Redis

Actuator expose alors trois endpoints :

  • /actuator/health/liveness - Retourne UP si l'application tourne (pas de deadlock)
  • /actuator/health/readiness - Retourne UP si l'application est prête (DB connectée, caches chargés)
  • /actuator/health - Santé globale avec tous les indicateurs

5.4 - Configuration complète des probes pour Spring Boot

# deployment-with-probes.yaml - Toutes les probes configurées
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-service
  namespace: production
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payment-service
  template:
    metadata:
      labels:
        app: payment-service
    spec:
      containers:
        - name: payment-service
          image: bmis/payment-service:1.4.0
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
            limits:
              cpu: 500m
              memory: 512Mi
          # ══════ Startup Probe ══════
          # Spring Boot met 30-60s à démarrer (chargement du contexte, Hibernate)
          # La startup probe empêche la liveness de tuer le pod trop tôt
          startupProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 5
            failureThreshold: 30     # 30 × 5s = 150s max pour démarrer
            timeoutSeconds: 3
          # ══════ Liveness Probe ══════
          # Vérifie que l'app est vivante. Si 3 échecs consécutifs → restart
          livenessProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            periodSeconds: 15
            failureThreshold: 3      # 3 échecs = pod redémarré
            timeoutSeconds: 5
            successThreshold: 1
          # ══════ Readiness Probe ══════
          # Vérifie que l'app peut recevoir du trafic (DB connectée, etc.)
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            periodSeconds: 10
            failureThreshold: 3      # 3 échecs = retiré du Service
            timeoutSeconds: 5
            successThreshold: 1

5.5 - Paramètres clés des probes

Paramètre Description Valeur recommandée
initialDelaySeconds Temps d'attente avant la première vérification 10–30s pour Spring Boot (startup probe prend le relais)
periodSeconds Fréquence de vérification 10–15s (pas trop fréquent pour éviter la charge)
failureThreshold Nombre d'échecs consécutifs avant action 3 - assez tolérant pour les latences réseau temporaires
timeoutSeconds Timeout pour chaque vérification 3–5s - assez long pour les réponses lentes sous charge
successThreshold Nombre de succès avant de considérer le pod sain 1 pour liveness, 1 pour readiness

5.6 - Erreurs courantes avec les probes

Probes trop agressives = cascading restarts - Si votre liveness probe a un periodSeconds: 2 et un failureThreshold: 1, le moindre pic de latence provoque un redémarrage du pod. Le pod redémarre, la charge est redistribuée sur les autres pods, ils deviennent surchargés, leurs probes échouent aussi → tous les pods redémarrent en cascade. C'est la panne totale.
Readiness probe qui vérifie les dépendances externes - Si votre readiness probe vérifie que la base de données est accessible et que la DB tombe, tous les pods deviennent « not ready » en même temps. Votre Service n'a plus aucun endpoint. La liveness probe ne doit vérifier que l'état interne de l'application.

6 - Zero-Downtime Deployment

En fintech, chaque seconde de downtime est une transaction échouée, un client frustré, et potentiellement un client perdu. Le zero-downtime deployment garantit que les mises à jour de l'application se font sans interruption de service.

6.1 - Pourquoi c'est critique

Dans un système de transfert d'argent mobile, imaginez ce scénario :

  1. Un utilisateur initie un transfert de 100 000 FCFA
  2. La requête arrive au pod du service de paiement
  3. Pendant le traitement, vous déployez une nouvelle version
  4. Le pod est tué brutalement
  5. L'argent est débité du compte source, mais jamais crédité sur le compte destination

Pour éviter cette catastrophe, chaque composant de la chaîne de déploiement doit être configuré pour un arrêt gracieux.

6.2 - Spring Boot : Graceful Shutdown

# application.yml - Arrêt gracieux de Spring Boot
server:
  shutdown: graceful                  # Active l'arrêt gracieux (défaut: immediate)

spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s   # Attend 30 secondes pour terminer les requêtes en cours

Quand Kubernetes envoie un signal SIGTERM au pod, Spring Boot :

  1. Arrête d'accepter de nouvelles requêtes
  2. Attend que toutes les requêtes en cours soient terminées (jusqu'au timeout)
  3. Ferme proprement les connexions DB, les consumers Kafka, etc.
  4. Termine le processus

6.3 - Pre-stop Hook et terminationGracePeriodSeconds

# deployment-graceful.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-service
  namespace: production
spec:
  template:
    spec:
      terminationGracePeriodSeconds: 60    # Kubernetes attend 60s max avant de forcer le kill
      containers:
        - name: payment-service
          image: bmis/payment-service:1.4.0
          lifecycle:
            preStop:
              exec:
                command:
                  - /bin/sh
                  - -c
                  - "sleep 10"    # Attend 10s pour que le Service retire le pod des endpoints
          # Le timing :
          # 1. K8s envoie SIGTERM + retire le pod du Service (en parallèle)
          # 2. preStop s'exécute : sleep 10 → laisse le temps au Service de se mettre à jour
          # 3. Spring Boot reçoit SIGTERM et commence l'arrêt gracieux
          # 4. Les requêtes en cours se terminent (max 30s grâce à timeout-per-shutdown-phase)
          # 5. Le pod s'arrête proprement

6.4 - PodDisruptionBudget (PDB)

Le PDB garantit qu'un nombre minimum de pods reste disponible pendant les opérations de maintenance (mises à jour de nœuds, drain, etc.).

# pdb.yaml - PodDisruptionBudget pour le service de paiement
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: payment-service-pdb
  namespace: production
spec:
  minAvailable: 2                  # Au moins 2 pods doivent rester disponibles
  # OU
  # maxUnavailable: 1              # Maximum 1 pod peut être indisponible à la fois
  selector:
    matchLabels:
      app: payment-service
# Vérifier les PDB
kubectl get pdb -n production

# Tester : drainer un nœud (le PDB empêchera l'éviction si le minimum n'est pas respecté)
kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data

6.5 - Connection draining

Le connection draining est le processus de terminaison propre des connexions existantes. Quand un pod est retiré du Service, les requêtes déjà en cours doivent pouvoir se terminer. C'est exactement ce que fait la combinaison preStop hook + graceful shutdown de Spring Boot.

Le flux complet :

  1. Kubernetes envoie SIGTERM au pod et commence à le retirer du Service
  2. Le preStop hook s'exécute (sleep 10s) - laisse le temps à kube-proxy/Ingress de propager le changement
  3. Spring Boot arrête d'accepter les nouvelles connexions
  4. Les requêtes en cours se terminent normalement
  5. Quand toutes les requêtes sont terminées (ou après le timeout), le pod s'arrête

7 - Rolling Update - Configuration pour zéro downtime

Le Rolling Update est la stratégie de déploiement par défaut de Kubernetes. Il remplace les pods un par un, en s'assurant qu'il y a toujours suffisamment de pods disponibles.

7.1 - Configuration optimale

# deployment-rolling.yaml - Rolling update zéro downtime
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-service
  namespace: production
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0          # JAMAIS de pod indisponible - maintenir la capacité totale
      maxSurge: 1                # Ajouter 1 pod supplémentaire pendant la mise à jour
  minReadySeconds: 30            # Attendre 30s après que le pod soit ready avant de continuer
  progressDeadlineSeconds: 600   # Timeout de 10 min - si le déploiement n'avance pas, échec
  selector:
    matchLabels:
      app: payment-service
  template:
    metadata:
      labels:
        app: payment-service
        version: v1.5.0          # Label de version pour le suivi
    spec:
      terminationGracePeriodSeconds: 60
      containers:
        - name: payment-service
          image: bmis/payment-service:1.5.0
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
            limits:
              cpu: 500m
              memory: 512Mi
          startupProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 5
            failureThreshold: 30
          livenessProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            periodSeconds: 15
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            periodSeconds: 10
            failureThreshold: 3
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sh", "-c", "sleep 10"]

7.2 - Déroulement du Rolling Update

Avec 4 répliques, maxUnavailable: 0 et maxSurge: 1 :

  1. Kubernetes crée 1 nouveau pod (v1.5.0) → 4 anciens + 1 nouveau = 5 pods total
  2. Le nouveau pod passe la startup probe, puis la readiness probe
  3. Kubernetes attend minReadySeconds: 30
  4. Un ancien pod (v1.4.0) est terminé gracieusement
  5. Retour à 4 pods (3 anciens + 1 nouveau)
  6. Répétition pour chaque pod, un par un
  7. Résultat final : 4 pods v1.5.0, zéro downtime
# Surveiller le rolling update en temps réel
kubectl rollout status deployment/payment-service -n production

# Historique des rollouts
kubectl rollout history deployment/payment-service -n production

# Rollback rapide en cas de problème
kubectl rollout undo deployment/payment-service -n production

# Rollback vers une révision spécifique
kubectl rollout undo deployment/payment-service -n production --to-revision=3

8 - Blue/Green Deployment

Le déploiement Blue/Green consiste à avoir deux environnements identiques en parallèle. L'un (Blue) reçoit le trafic réel, l'autre (Green) est mis à jour et testé. Quand Green est validé, le trafic bascule instantanément de Blue à Green.

8.1 - Implémentation avec les Services Kubernetes

# deployment-blue.yaml - Version actuelle (Blue)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-service-blue
  namespace: production
spec:
  replicas: 4
  selector:
    matchLabels:
      app: payment-service
      slot: blue
  template:
    metadata:
      labels:
        app: payment-service
        slot: blue
        version: v1.4.0
    spec:
      containers:
        - name: payment-service
          image: bmis/payment-service:1.4.0
---
# deployment-green.yaml - Nouvelle version (Green)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-service-green
  namespace: production
spec:
  replicas: 4
  selector:
    matchLabels:
      app: payment-service
      slot: green
  template:
    metadata:
      labels:
        app: payment-service
        slot: green
        version: v1.5.0
    spec:
      containers:
        - name: payment-service
          image: bmis/payment-service:1.5.0
# service.yaml - Le Service pointe vers le slot actif
apiVersion: v1
kind: Service
metadata:
  name: payment-service
  namespace: production
spec:
  selector:
    app: payment-service
    slot: blue              # ← Changer en "green" pour basculer le trafic
  ports:
    - port: 80
      targetPort: 8080
# Basculer le trafic de Blue vers Green
kubectl patch service payment-service -n production \
  -p '{"spec":{"selector":{"slot":"green"}}}'

# Rollback instantané vers Blue si problème
kubectl patch service payment-service -n production \
  -p '{"spec":{"selector":{"slot":"blue"}}}'

# Supprimer l'ancien environnement une fois validé
kubectl delete deployment payment-service-blue -n production

8.2 - Avantages et inconvénients

Avantages Inconvénients
Rollback instantané (changement de selector) Double les ressources nécessaires
Test complet de Green avant de basculer Plus complexe à gérer
Zéro downtime garanti Les connexions en cours sur Blue peuvent être interrompues
Pas de version mixte pendant la transition Ne résout pas les problèmes de migration de base de données

9 - Canary Deployment

Le déploiement Canary envoie progressivement un petit pourcentage du trafic vers la nouvelle version. Si tout va bien, le pourcentage augmente jusqu'à 100%. Si des erreurs sont détectées, la nouvelle version est retirée avec un impact minimal.

9.1 - Implémentation simple avec les Deployments

La méthode la plus simple : deux Deployments avec le même label app, mais des répliques différentes.

# canary-stable.yaml - Version stable (90% du trafic)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-service-stable
  namespace: production
spec:
  replicas: 9                    # 9 pods = 90% du trafic
  selector:
    matchLabels:
      app: payment-service
      track: stable
  template:
    metadata:
      labels:
        app: payment-service     # Le Service sélectionne ce label
        track: stable
    spec:
      containers:
        - name: payment-service
          image: bmis/payment-service:1.4.0
---
# canary-new.yaml - Nouvelle version (10% du trafic)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-service-canary
  namespace: production
spec:
  replicas: 1                    # 1 pod = 10% du trafic
  selector:
    matchLabels:
      app: payment-service
      track: canary
  template:
    metadata:
      labels:
        app: payment-service     # Même label → le Service distribue aussi ici
        track: canary
    spec:
      containers:
        - name: payment-service
          image: bmis/payment-service:1.5.0
# Le Service sélectionne TOUS les pods avec app: payment-service
apiVersion: v1
kind: Service
metadata:
  name: payment-service
  namespace: production
spec:
  selector:
    app: payment-service         # Sélectionne stable ET canary
  ports:
    - port: 80
      targetPort: 8080

9.2 - Canary avancé avec Ingress NGINX

Pour un contrôle plus précis du pourcentage de trafic, utilisez les annotations de l'Ingress NGINX :

# ingress-canary.yaml - Traffic splitting via Ingress
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: payment-service-canary
  namespace: production
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"    # 10% du trafic vers canary
spec:
  rules:
    - host: api.bmis-fintech.com
      http:
        paths:
          - path: /api/payments
            pathType: Prefix
            backend:
              service:
                name: payment-service-canary
                port:
                  number: 80

9.3 - Argo Rollouts pour le canary avancé

Argo Rollouts est un contrôleur Kubernetes qui remplace les Deployments standards et offre des stratégies de déploiement avancées : canary progressif, blue/green automatisé, et analyse de métriques intégrée.

# rollout-canary.yaml - Argo Rollouts canary progressif
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: payment-service
  namespace: production
spec:
  replicas: 5
  strategy:
    canary:
      steps:
        - setWeight: 5             # 5% du trafic
        - pause: { duration: 5m }  # Observer pendant 5 minutes
        - setWeight: 20            # 20% du trafic
        - pause: { duration: 10m } # Observer pendant 10 minutes
        - setWeight: 50            # 50% du trafic
        - pause: { duration: 10m }
        - setWeight: 80            # 80% du trafic
        - pause: { duration: 5m }
        # 100% automatiquement si aucun problème
      analysis:
        templates:
          - templateName: success-rate
        startingStep: 2            # Commencer l'analyse à partir de l'étape 2
        args:
          - name: service-name
            value: payment-service
  selector:
    matchLabels:
      app: payment-service
  template:
    metadata:
      labels:
        app: payment-service
    spec:
      containers:
        - name: payment-service
          image: bmis/payment-service:1.5.0

10 - Database Migrations en production

Les migrations de base de données sont la partie la plus difficile du zero-downtime deployment. Contrairement au code applicatif, les changements de schéma sont irréversibles et impactent toutes les instances en même temps.

10.1 - Le problème

Pendant un rolling update, vous avez simultanément des pods avec l'ancienne version du code et des pods avec la nouvelle version. Si la nouvelle version nécessite un changement de schéma (nouvelle colonne, table renommée, etc.), l'ancienne version va planter car elle ne connaît pas le nouveau schéma.

10.2 - La règle d'or : migrations backward-compatible uniquement

Migration Compatible ? Explication
Ajouter une colonne nullable ✅ Oui L'ancien code ignore la nouvelle colonne
Ajouter une table ✅ Oui L'ancien code ne l'utilise pas
Supprimer une colonne ❌ Non L'ancien code va faire un SELECT sur la colonne supprimée
Renommer une colonne ❌ Non L'ancien code référence l'ancien nom
Changer le type d'une colonne ❌ Non Peut casser les requêtes existantes
Ajouter une contrainte NOT NULL ❌ Non L'ancien code n'envoie peut-être pas cette valeur

10.3 - Flyway comme Job ou Init Container Kubernetes

# migration-job.yaml - Exécuter la migration AVANT le déploiement
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migration-v1-5-0
  namespace: production
spec:
  backoffLimit: 3
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: flyway
          image: bmis/payment-service:1.5.0
          command:
            - java
            - -cp
            - /app/app.jar
            - org.flywaydb.core.Flyway
            - migrate
          env:
            - name: FLYWAY_URL
              valueFrom:
                secretKeyRef:
                  name: postgres-credentials
                  key: jdbc-url
            - name: FLYWAY_USER
              valueFrom:
                secretKeyRef:
                  name: postgres-credentials
                  key: username
            - name: FLYWAY_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: postgres-credentials
                  key: password

10.4 - Stratégie de migration en plusieurs étapes

Pour les changements non backward-compatible, décomposez en plusieurs déploiements :

  1. Version N - Ajouter la nouvelle colonne (nullable). L'ancien code l'ignore.
  2. Version N+1 - Le nouveau code écrit dans les deux colonnes (ancienne et nouvelle). Migration des données existantes.
  3. Version N+2 - Le nouveau code ne lit plus que la nouvelle colonne. L'ancienne colonne n'est plus utilisée.
  4. Version N+3 - Supprimer l'ancienne colonne. Plus aucun code ne la référence.
Ne jamais faire de changements de schéma destructifs en une seule étape - Renommer une colonne, supprimer une table, changer un type - ces opérations doivent toujours être décomposées en plusieurs versions. C'est plus lent, mais c'est la seule façon de garantir zéro downtime avec une base de données partagée.

11 - Pod Topology & Affinity

Par défaut, le scheduler Kubernetes peut placer tous vos pods sur le même nœud. En production, vous voulez distribuer vos pods sur plusieurs nœuds (et idéalement plusieurs zones de disponibilité) pour résister aux pannes matérielles.

11.1 - Anti-affinity : distribuer les pods sur différents nœuds

# anti-affinity.yaml - Ne jamais placer 2 pods du même service sur le même nœud
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-service
  namespace: production
spec:
  replicas: 4
  selector:
    matchLabels:
      app: payment-service
  template:
    metadata:
      labels:
        app: payment-service
    spec:
      affinity:
        podAntiAffinity:
          # ══════ Règle stricte (requiredDuringSchedulingIgnoredDuringExecution) ══════
          # Le pod ne sera PAS schedulé si un pod identique existe déjà sur le nœud
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchExpressions:
                  - key: app
                    operator: In
                    values:
                      - payment-service
              topologyKey: kubernetes.io/hostname
      containers:
        - name: payment-service
          image: bmis/payment-service:1.5.0

11.2 - Node affinity : cibler des nœuds spécifiques

# node-affinity.yaml - Placer les pods sur des nœuds spécifiques
apiVersion: apps/v1
kind: Deployment
metadata:
  name: postgres
  namespace: production
spec:
  template:
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  # Seulement sur des nœuds avec des SSD
                  - key: disk-type
                    operator: In
                    values:
                      - ssd
                  # Seulement dans la zone eu-west-1a ou eu-west-1b
                  - key: topology.kubernetes.io/zone
                    operator: In
                    values:
                      - eu-west-1a
                      - eu-west-1b

11.3 - Topology Spread Constraints

Les topology spread constraints offrent un contrôle plus fin que l'anti-affinity pour distribuer les pods de manière équilibrée sur les nœuds et les zones.

# topology-spread.yaml - Distribution équilibrée sur les zones et les nœuds
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-service
  namespace: production
spec:
  replicas: 6
  template:
    spec:
      topologySpreadConstraints:
        # Distribution sur les zones de disponibilité
        - maxSkew: 1                  # Max 1 pod de différence entre les zones
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels:
              app: payment-service
        # Distribution sur les nœuds dans chaque zone
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: ScheduleAnyway    # Tolérer si impossible
          labelSelector:
            matchLabels:
              app: payment-service

12 - Disaster Recovery

Le disaster recovery est votre filet de sécurité ultime. Quand tout a échoué - le cluster est corrompu, la base de données est perdue, un datacenter est inondé - vous devez pouvoir restaurer le service dans un délai acceptable.

12.1 - RTO et RPO

  • RTO (Recovery Time Objective) - Le temps maximum acceptable pour restaurer le service après une panne. Exemple : 1 heure.
  • RPO (Recovery Point Objective) - La quantité maximale de données que vous pouvez perdre. Exemple : 15 minutes (= backup toutes les 15 minutes).
Composant RTO cible RPO cible Stratégie
PostgreSQL 30 minutes 5 minutes WAL archiving + pg_basebackup
Redis 15 minutes Tolérant (cache) RDB snapshots, AOF
Cluster K8s 1 heure N/A (GitOps) Velero + GitOps
etcd 30 minutes 1 minute Snapshots automatiques

12.2 - Backup etcd

# Snapshot etcd - la base de données de Kubernetes
ETCDCTL_API=3 etcdctl snapshot save /backup/etcd-snapshot-$(date +%Y%m%d).db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

# Restaurer un snapshot etcd
ETCDCTL_API=3 etcdctl snapshot restore /backup/etcd-snapshot-20260427.db \
  --data-dir=/var/lib/etcd-restored

12.3 - Velero pour le backup du cluster

Velero est l'outil standard pour sauvegarder et restaurer les ressources Kubernetes et les volumes persistants.

# Installer Velero
velero install \
  --provider aws \
  --bucket bmis-k8s-backups \
  --secret-file ./credentials-velero \
  --backup-location-config region=eu-west-1

# Backup complet du namespace production
velero backup create production-backup \
  --include-namespaces production \
  --ttl 720h     # Rétention de 30 jours

# Backup automatique quotidien
velero schedule create daily-backup \
  --schedule="0 2 * * *" \
  --include-namespaces production \
  --ttl 720h

# Restaurer un backup
velero restore create --from-backup production-backup

12.4 - Backup PostgreSQL avec CronJob

# pg-backup-cronjob.yaml - Backup PostgreSQL automatique
apiVersion: batch/v1
kind: CronJob
metadata:
  name: postgres-backup
  namespace: production
spec:
  schedule: "0 */6 * * *"       # Toutes les 6 heures
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: pg-backup
              image: postgres:16-alpine
              command:
                - /bin/sh
                - -c
                - |
                  TIMESTAMP=$(date +%Y%m%d_%H%M%S)
                  BACKUP_FILE="/backups/pg_dump_${TIMESTAMP}.sql.gz"
                  pg_dump -h postgres-primary -U bmis_admin bmis_production | gzip > $BACKUP_FILE
                  echo "Backup created: $BACKUP_FILE"
                  # Nettoyer les backups de plus de 7 jours
                  find /backups -name "pg_dump_*.sql.gz" -mtime +7 -delete
              env:
                - name: PGPASSWORD
                  valueFrom:
                    secretKeyRef:
                      name: postgres-credentials
                      key: password
              volumeMounts:
                - name: backup-storage
                  mountPath: /backups
          volumes:
            - name: backup-storage
              persistentVolumeClaim:
                claimName: postgres-backup-pvc

12.5 - Considérations multi-région

Pour une disponibilité maximale, considérez un déploiement multi-région :

  • Active-Passive - Un cluster principal dans une région, un cluster de secours dans une autre. Le cluster de secours est mis à jour en continu mais ne reçoit pas de trafic. En cas de panne, le DNS bascule vers le cluster de secours.
  • Active-Active - Deux clusters reçoivent du trafic simultanément. Plus complexe (réplication de données, conflits), mais RTO quasi nul.
  • Réplication de données - PostgreSQL avec streaming replication vers la région secondaire. Redis avec replication cross-region.
