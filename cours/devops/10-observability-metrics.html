Métriques - Prometheus & Grafana

Instrumenter Spring Boot, collecter les métriques, et créer des dashboards de monitoring production.

1 - Les 3 piliers de l'observabilité

Un système en production est une boîte noire. Vous ne pouvez pas y mettre de breakpoints, vous ne pouvez pas le debugger en direct, et vous ne pouvez pas demander à un utilisateur de reproduire un bug sous vos yeux. L'observabilité est la capacité à comprendre l'état interne d'un système à partir de ses sorties externes.

L'observabilité repose sur trois piliers fondamentaux :

1.1 - Metrics (Métriques)

Les métriques sont des valeurs numériques mesurées dans le temps. Elles répondent à la question : "Combien ?" et "À quelle vitesse ?". Par exemple : le nombre de requêtes HTTP par seconde, l'utilisation mémoire en pourcentage, le temps de réponse moyen d'une API.

Les métriques sont agrégées - elles ne vous disent pas ce qui s'est passé pour une requête spécifique, mais elles vous montrent les tendances globales. Elles sont peu coûteuses en stockage et en calcul, ce qui les rend idéales pour le monitoring en temps réel et les alertes.

1.2 - Logs (Journaux)

Les logs sont des enregistrements textuels d'événements discrets. Ils répondent à la question : "Que s'est-il passé exactement ?". Un log contient un horodatage, un niveau de sévérité, et un message descriptif. Contrairement aux métriques, les logs sont individuels - chaque entrée correspond à un événement précis.

Les logs sont essentiels pour le debugging post-mortem. Quand une métrique indique un pic d'erreurs, ce sont les logs qui vous disent quelle erreur et pourquoi.

1.3 - Traces (Traces distribuées)

Les traces suivent le parcours d'une requête à travers plusieurs services. Dans une architecture microservices, une seule action utilisateur (par exemple, un paiement) peut traverser 5 à 10 services différents. Une trace vous montre exactement quel service a été appelé, dans quel ordre, et combien de temps chaque appel a pris.

Les traces répondent à la question : "Où est le goulot d'étranglement ?". Elles sont indispensables pour diagnostiquer les problèmes de latence dans les systèmes distribués.

Les trois piliers sont complémentaires - Les métriques vous alertent qu'il y a un problème (ex : taux d'erreur à 15%). Les logs vous disent quel est le problème (ex : NullPointerException dans PaymentService). Les traces vous montrent où est le problème (ex : le service de validation met 8 secondes à répondre). Cette leçon se concentre sur les métriques. Les logs et les alertes seront traités dans la leçon suivante.

2 - Prometheus - Présentation

Prometheus est un système de monitoring et d'alerting open-source, développé initialement chez SoundCloud et maintenant projet gradué de la Cloud Native Computing Foundation (CNCF). C'est le standard de facto pour le monitoring des applications cloud-native et Kubernetes.

2.1 - Modèle Pull-based

Contrairement aux systèmes push-based (comme Graphite ou StatsD) où les applications envoient leurs métriques vers un collecteur central, Prometheus utilise un modèle pull-based : c'est Prometheus qui va chercher (scraper) les métriques auprès de chaque cible à intervalles réguliers (par défaut toutes les 15 secondes).

Avantages du modèle pull :

  • Détection automatique des pannes - Si Prometheus ne peut plus scraper une cible, il sait immédiatement que le service est down.
  • Pas de surcharge réseau - Les applications n'ont pas besoin de pousser des données en permanence. Elles exposent simplement un endpoint HTTP.
  • Contrôle centralisé - L'opérateur décide quelles cibles scraper, à quelle fréquence, et avec quels labels.
  • Facilité de debugging - Vous pouvez visiter l'endpoint /metrics d'une application dans votre navigateur pour voir exactement ce qu'elle expose.

2.2 - Base de données Time Series

Prometheus stocke ses données dans une base de données time series locale, optimisée pour les écritures séquentielles et les requêtes par plage temporelle. Chaque métrique est identifiée par un nom et un ensemble de labels (paires clé-valeur) :

# Format d'une métrique Prometheus
http_server_requests_seconds_count{method="GET", uri="/api/payments", status="200"} 1547
http_server_requests_seconds_count{method="POST", uri="/api/payments", status="201"} 892
http_server_requests_seconds_count{method="GET", uri="/api/payments", status="500"} 23

2.3 - PromQL

PromQL (Prometheus Query Language) est le langage de requête de Prometheus. Il permet de sélectionner, filtrer, agréger et transformer les séries temporelles. C'est un langage fonctionnel puissant que nous détaillerons dans la section 6.

2.4 - Architecture

3 - Instrumenter Spring Boot avec Micrometer

Micrometer est la bibliothèque de métriques de facto pour Spring Boot. C'est une façade - exactement comme SLF4J pour les logs - qui fournit une API unifiée pour instrumenter votre code, indépendamment du backend de monitoring (Prometheus, Datadog, New Relic, etc.).

3.1 - Dépendances Maven

Ajoutez ces deux dépendances à votre pom.xml :

<dependencies>
    <!-- Spring Boot Actuator - expose les endpoints de monitoring -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-actuator</artifactId>
    </dependency>

    <!-- Micrometer Registry Prometheus - formate les métriques pour Prometheus -->
    <dependency>
        <groupId>io.micrometer</groupId>
        <artifactId>micrometer-registry-prometheus</artifactId>
    </dependency>
</dependencies>

Spring Boot auto-configure automatiquement Micrometer quand ces dépendances sont présentes. Aucune configuration Java supplémentaire n'est nécessaire pour les métriques de base.

3.2 - Configuration application.yml

Configurez Spring Boot Actuator pour exposer l'endpoint Prometheus :

# application.yml
management:
  endpoints:
    web:
      exposure:
        include: health, info, prometheus, metrics
  endpoint:
    health:
      show-details: always
      probes:
        enabled: true
    prometheus:
      enabled: true
  metrics:
    tags:
      application: bmis-payment-service
      environment: ${SPRING_PROFILES_ACTIVE:dev}
    distribution:
      percentiles-histogram:
        http.server.requests: true
      percentiles:
        http.server.requests: 0.5, 0.75, 0.95, 0.99
      sla:
        http.server.requests: 50ms, 100ms, 200ms, 500ms, 1s, 5s

Points importants de cette configuration :

  • exposure.include - Liste les endpoints Actuator accessibles via HTTP. prometheus expose /actuator/prometheus.
  • metrics.tags - Ajoute des labels globaux à toutes les métriques. Indispensable pour distinguer les services et les environnements dans Grafana.
  • percentiles-histogram - Active les histogrammes pour les requêtes HTTP, permettant de calculer les percentiles (p50, p95, p99) côté Prometheus.
  • sla - Définit des buckets SLA pour mesurer combien de requêtes répondent en moins de 50ms, 100ms, etc.

Après configuration, l'endpoint est accessible à http://localhost:8080/actuator/prometheus :

# Tester l'endpoint localement
curl http://localhost:8080/actuator/prometheus

3.3 - Métriques exposées par défaut

Sans écrire une seule ligne de code, Spring Boot + Micrometer expose automatiquement des dizaines de métriques :

  • JVM - Utilisation mémoire heap/non-heap, pauses GC, threads actifs, classes chargées
  • HTTP - Nombre de requêtes, temps de réponse, distribution par status code et URI
  • Connexions DB - Pool HikariCP : connexions actives, idle, pending, temps d'attente
  • Cache - Hit/miss ratio pour les caches Caffeine, Redis, EhCache
  • Tomcat - Threads actifs, sessions, requêtes en cours de traitement
  • Logback - Nombre de logs par niveau (ERROR, WARN, INFO)
  • System - CPU usage, file descriptors ouverts, uptime

3.4 - Métriques personnalisées

Les métriques par défaut couvrent l'infrastructure, mais vos métriques business sont celles qui comptent vraiment. Voici comment créer des métriques personnalisées avec Micrometer :

Counter - Compteur de paiements

import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.MeterRegistry;
import org.springframework.stereotype.Service;

@Service
public class PaymentService {

    private final Counter paymentSuccessCounter;
    private final Counter paymentFailureCounter;

    public PaymentService(MeterRegistry registry) {
        this.paymentSuccessCounter = Counter.builder("bmis_payments_total")
            .description("Nombre total de paiements traités")
            .tag("status", "success")
            .register(registry);

        this.paymentFailureCounter = Counter.builder("bmis_payments_total")
            .description("Nombre total de paiements traités")
            .tag("status", "failure")
            .register(registry);
    }

    public PaymentResponse processPayment(PaymentRequest request) {
        try {
            PaymentResponse response = executePayment(request);
            paymentSuccessCounter.increment();
            return response;
        } catch (PaymentException e) {
            paymentFailureCounter.increment();
            throw e;
        }
    }
}

Gauge - Utilisateurs actifs

import io.micrometer.core.instrument.Gauge;
import io.micrometer.core.instrument.MeterRegistry;
import org.springframework.stereotype.Component;

import java.util.concurrent.atomic.AtomicInteger;

@Component
public class ActiveUsersTracker {

    private final AtomicInteger activeUsers = new AtomicInteger(0);

    public ActiveUsersTracker(MeterRegistry registry) {
        Gauge.builder("bmis_active_users", activeUsers, AtomicInteger::get)
            .description("Nombre d'utilisateurs actuellement connectés")
            .tag("service", "payment-service")
            .register(registry);
    }

    public void userConnected() {
        activeUsers.incrementAndGet();
    }

    public void userDisconnected() {
        activeUsers.decrementAndGet();
    }
}

Timer - Temps de réponse d'une API externe

import io.micrometer.core.instrument.Timer;
import io.micrometer.core.instrument.MeterRegistry;
import org.springframework.stereotype.Service;

@Service
public class ExternalBankingService {

    private final Timer bankApiTimer;

    public ExternalBankingService(MeterRegistry registry) {
        this.bankApiTimer = Timer.builder("bmis_bank_api_duration_seconds")
            .description("Temps de réponse de l'API bancaire externe")
            .tag("provider", "stripe")
            .publishPercentiles(0.5, 0.95, 0.99)
            .publishPercentileHistogram()
            .register(registry);
    }

    public BankResponse callBankApi(TransferRequest request) {
        return bankApiTimer.record(() -> {
            // Appel HTTP vers l'API bancaire
            return restTemplate.postForObject(
                "https://api.stripe.com/v1/transfers",
                request,
                BankResponse.class
            );
        });
    }
}

Distribution Summary - Montants des transactions

import io.micrometer.core.instrument.DistributionSummary;
import io.micrometer.core.instrument.MeterRegistry;
import org.springframework.stereotype.Service;

@Service
public class TransactionMetrics {

    private final DistributionSummary transactionAmounts;

    public TransactionMetrics(MeterRegistry registry) {
        this.transactionAmounts = DistributionSummary
            .builder("bmis_transaction_amount")
            .description("Distribution des montants de transactions")
            .baseUnit("EUR")
            .publishPercentiles(0.5, 0.75, 0.95)
            .register(registry);
    }

    public void recordTransaction(double amount) {
        transactionAmounts.record(amount);
    }
}

4 - Métriques clés à surveiller

Toutes les métriques ne se valent pas. Voici les métriques critiques à surveiller pour un système fintech en production, organisées par catégorie :

4.1 - Métriques JVM

Métrique Prometheus Description Seuil d'alerte
jvm_memory_used_bytes{area="heap"} Mémoire heap utilisée par la JVM > 80% du max
jvm_gc_pause_seconds_sum Temps total passé en pauses GC > 500ms sur 5 min
jvm_threads_live_threads Nombre de threads actifs > 300 threads
jvm_memory_used_bytes{area="nonheap"} Mémoire non-heap (Metaspace, code cache) > 90% du max
jvm_classes_loaded_classes Nombre de classes chargées (détection de class leak) Croissance continue

4.2 - Métriques HTTP

Métrique Prometheus Description Seuil d'alerte
rate(http_server_requests_seconds_count[5m]) Taux de requêtes par seconde Variation > 50%
rate(http_server_requests_seconds_count{status=~"5.."}[5m]) Taux d'erreurs 5xx par seconde > 1% du trafic total
histogram_quantile(0.95, ...http_server_requests_seconds_bucket...) Latence p95 - 95% des requêtes répondent en moins de X > 500ms
histogram_quantile(0.99, ...http_server_requests_seconds_bucket...) Latence p99 - les 1% les plus lentes > 2s
histogram_quantile(0.50, ...http_server_requests_seconds_bucket...) Latence médiane (p50) > 100ms

4.3 - Métriques Base de Données

Métrique Prometheus Description Seuil d'alerte
hikaricp_connections_active Connexions DB actuellement utilisées > 80% du pool
hikaricp_connections_idle Connexions DB inactives dans le pool < 2
hikaricp_connections_pending Threads en attente d'une connexion > 0 pendant > 30s
hikaricp_connections_timeout_total Nombre de timeouts de connexion > 0

4.4 - Métriques Redis

Métrique Prometheus Description Seuil d'alerte
redis_keyspace_hits_total Nombre de cache hits Hit ratio < 80%
redis_keyspace_misses_total Nombre de cache misses -
redis_connected_clients Nombre de clients connectés > 500
redis_memory_used_bytes Mémoire utilisée par Redis > 80% de maxmemory

4.5 - Métriques Business (Fintech)

Métrique Prometheus Description Seuil d'alerte
bmis_payments_total{status="success"} Nombre total de paiements réussis Chute > 30%
bmis_payments_total{status="failure"} Nombre total de paiements échoués > 5% du total
bmis_transaction_amount Montant moyen des transactions Variation anormale
bmis_active_users Utilisateurs actuellement connectés Chute soudaine
bmis_user_registrations_total Nombre d'inscriptions utilisateurs Chute > 50%

5 - Déployer Prometheus sur Kubernetes

Il existe deux approches pour déployer Prometheus sur Kubernetes : le Helm chart kube-prometheus-stack (recommandé pour la production) et le déploiement manuel (utile pour comprendre les composants).

5.1 - Option A : kube-prometheus-stack (Helm)

Le chart kube-prometheus-stack déploie en une seule commande : Prometheus, Grafana, Alertmanager, Node Exporter, kube-state-metrics, et les ServiceMonitors pré-configurés pour Kubernetes.

# Ajouter le repo Helm
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update

# Créer le namespace
kubectl create namespace monitoring

# Installer le stack complet
helm install kube-prometheus prometheus-community/kube-prometheus-stack \
  --namespace monitoring \
  --set grafana.adminPassword=BmisSecure2024! \
  --set prometheus.prometheusSpec.retention=30d \
  --set prometheus.prometheusSpec.storageSpec.volumeClaimTemplate.spec.resources.requests.storage=50Gi \
  --set prometheus.prometheusSpec.serviceMonitorSelectorNilUsesHelmValues=false \
  --set alertmanager.alertmanagerSpec.storage.volumeClaimTemplate.spec.resources.requests.storage=10Gi

# Vérifier que tout est déployé
kubectl get pods -n monitoring

5.2 - Option B : Déploiement manuel

Pour comprendre chaque composant, voici le déploiement manuel complet.

Namespace et ConfigMap

# monitoring-namespace.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: monitoring
  labels:
    app.kubernetes.io/part-of: monitoring-stack
---
# prometheus-configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: prometheus-config
  namespace: monitoring
data:
  prometheus.yml: |
    global:
      scrape_interval: 15s
      evaluation_interval: 15s
      scrape_timeout: 10s

    rule_files:
      - "/etc/prometheus/rules/*.yml"

    scrape_configs:
      # Prometheus se scrape lui-même
      - job_name: 'prometheus'
        static_configs:
          - targets: ['localhost:9090']

      # Scraper les pods Kubernetes avec les annotations appropriées
      - job_name: 'kubernetes-pods'
        kubernetes_sd_configs:
          - role: pod
        relabel_configs:
          # Garder uniquement les pods annotés prometheus.io/scrape: "true"
          - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
            action: keep
            regex: true
          # Utiliser le port défini dans l'annotation prometheus.io/port
          - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_port]
            action: replace
            target_label: __address__
            regex: (.+)
            replacement: ${1}
          # Utiliser le path défini dans prometheus.io/path (défaut: /metrics)
          - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_path]
            action: replace
            target_label: __metrics_path__
            regex: (.+)
          # Ajouter des labels pour identifier le namespace et le pod
          - source_labels: [__meta_kubernetes_namespace]
            action: replace
            target_label: kubernetes_namespace
          - source_labels: [__meta_kubernetes_pod_name]
            action: replace
            target_label: kubernetes_pod_name
          - source_labels: [__meta_kubernetes_pod_label_app]
            action: replace
            target_label: app

      # Scraper les services Spring Boot
      - job_name: 'spring-boot-services'
        kubernetes_sd_configs:
          - role: endpoints
            namespaces:
              names:
                - bmis-fintech
        relabel_configs:
          - source_labels: [__meta_kubernetes_service_annotation_prometheus_io_scrape]
            action: keep
            regex: true
          - source_labels: [__meta_kubernetes_service_annotation_prometheus_io_path]
            action: replace
            target_label: __metrics_path__
            regex: (.+)
          - source_labels: [__address__, __meta_kubernetes_service_annotation_prometheus_io_port]
            action: replace
            target_label: __address__
            regex: (.+?)(?::\d+)?;(\d+)
            replacement: $1:$2
          - source_labels: [__meta_kubernetes_service_name]
            action: replace
            target_label: service_name

  - kind: ServiceAccount

  kind: ClusterRole
  name: prometheus

6 - PromQL - Le langage de requête

PromQL est le cœur de Prometheus. Maîtriser PromQL est indispensable pour créer des dashboards pertinents et des alertes efficaces. Voici les requêtes essentielles pour un système Spring Boot en production.

6.1 - Taux de requêtes HTTP (Request Rate)

# Nombre de requêtes HTTP par seconde (toutes les routes)
rate(http_server_requests_seconds_count[5m])

# Taux de requêtes pour un endpoint spécifique
rate(http_server_requests_seconds_count{uri="/api/payments"}[5m])

# Taux d'erreurs 5xx uniquement
rate(http_server_requests_seconds_count{status=~"5.."}[5m])

La fonction rate() calcule le taux de variation par seconde d'un compteur sur une fenêtre temporelle (ici 5 minutes). C'est la fonction la plus utilisée en PromQL.

6.2 - Latence (Percentiles)

# Latence p95 - 95% des requêtes répondent en moins de X secondes
histogram_quantile(0.95,
  rate(http_server_requests_seconds_bucket[5m])
)

# Latence p99 - les 1% les plus lentes
histogram_quantile(0.99,
  rate(http_server_requests_seconds_bucket[5m])
)

# Latence p95 par endpoint
histogram_quantile(0.95,
  sum by (uri, le) (
    rate(http_server_requests_seconds_bucket[5m])
  )
)

# Latence moyenne (moins utile que les percentiles, mais simple)
rate(http_server_requests_seconds_sum[5m])
  /
rate(http_server_requests_seconds_count[5m])
Pourquoi les percentiles et pas la moyenne ? - La moyenne est trompeuse. Si 99% de vos requêtes répondent en 10ms mais 1% en 10 secondes, la moyenne sera ~110ms - ce qui semble correct. Mais 1% de vos utilisateurs ont une expérience catastrophique. Le p99 (10 secondes) révèle le vrai problème.

6.3 - Taux d'erreurs

# Pourcentage d'erreurs HTTP (error rate)
sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
  /
sum(rate(http_server_requests_seconds_count[5m]))
  * 100

# Taux d'erreurs par service
sum by (application) (
  rate(http_server_requests_seconds_count{status=~"5.."}[5m])
)
  /
sum by (application) (
  rate(http_server_requests_seconds_count[5m])
)
  * 100

# Répartition par code de statut HTTP
sum by (status) (
  rate(http_server_requests_seconds_count[5m])
)

6.4 - Métriques JVM

# Utilisation mémoire heap en pourcentage
jvm_memory_used_bytes{area="heap"}
  /
jvm_memory_max_bytes{area="heap"}
  * 100

# Taux de pauses GC (secondes de pause par seconde)
rate(jvm_gc_pause_seconds_sum[5m])

# Nombre de threads actifs
jvm_threads_live_threads

6.5 - Métriques Database (HikariCP)

# Utilisation du pool de connexions en pourcentage
hikaricp_connections_active
  /
(hikaricp_connections_active + hikaricp_connections_idle)
  * 100

# Temps d'attente moyen pour obtenir une connexion
rate(hikaricp_connections_acquire_seconds_sum[5m])
  /
rate(hikaricp_connections_acquire_seconds_count[5m])

# Nombre de connexions en timeout
rate(hikaricp_connections_timeout_total[5m])

6.6 - Métriques Business

# Taux de paiements réussis vs échoués
rate(bmis_payments_total{status="success"}[5m])
rate(bmis_payments_total{status="failure"}[5m])

# Taux de succès des paiements (en pourcentage)
sum(rate(bmis_payments_total{status="success"}[5m]))
  /
sum(rate(bmis_payments_total[5m]))
  * 100

# Montant moyen des transactions (dernières 5 minutes)
rate(bmis_transaction_amount_sum[5m])
  /
rate(bmis_transaction_amount_count[5m])

# Utilisateurs actifs (valeur instantanée)
bmis_active_users

8 - Métriques business vs techniques

Les métriques techniques ne suffisent pas.

La plupart des équipes se concentrent exclusivement sur les métriques techniques : CPU, mémoire, latence, taux d'erreur. Ces métriques sont essentielles pour les ingénieurs, mais elles ne disent rien aux stakeholders business.

Métriques techniques (pour l'équipe ops) :

  • Utilisation CPU/mémoire par pod
  • Latence p95 des requêtes HTTP
  • Taux d'erreurs 5xx
  • Utilisation du pool de connexions DB
  • Temps de pause GC

Métriques business (pour les stakeholders) :

  • Revenu par heure / par jour
  • Taux de conversion (visiteur → inscription → premier paiement)
  • Taux d'échec des paiements par provider
  • Nombre de transactions par minute
  • Montant moyen des transactions
  • Nombre d'utilisateurs actifs en temps réel

Un système peut avoir un CPU à 20%, une latence p95 de 50ms, et zéro erreur 5xx - et pourtant perdre de l'argent parce que le taux d'échec des paiements est à 15% (erreurs gérées côté applicatif, pas des 5xx). Les métriques business détectent les problèmes que les métriques techniques ne voient pas.

Règle d'or : Chaque dashboard Grafana devrait avoir une section "Business KPIs" visible en premier. Les dirigeants ne comprendront pas un graphique de pauses GC, mais ils comprendront "Revenu en baisse de 30% depuis 14h".

9 - Recording Rules

Certaines requêtes PromQL sont coûteuses en calcul. Par exemple, calculer le p95 de latence sur toutes les routes, agrégé par service, nécessite de scanner des millions de points de données. Si Grafana exécute cette requête toutes les 30 secondes pour chaque panel, Prometheus sera surchargé.

Les Recording Rules pré-calculent ces requêtes à intervalles réguliers et stockent le résultat comme une nouvelle série temporelle. Les dashboards Grafana requêtent ensuite cette série pré-calculée - instantanément.

9.1 - Syntaxe YAML

# prometheus-recording-rules.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: prometheus-rules
  namespace: monitoring
data:
  recording-rules.yml: |
    groups:
      - name: bmis_http_rules
        interval: 30s
        rules:
          # Taux de requêtes HTTP par service (pré-calculé)
          - record: bmis:http_request_rate:5m
            expr: sum by (application, uri) (rate(http_server_requests_seconds_count[5m]))

          # Latence p95 par endpoint (pré-calculé)
          - record: bmis:http_latency_p95:5m
            expr: |
              histogram_quantile(0.95,
                sum by (application, uri, le) (
                  rate(http_server_requests_seconds_bucket[5m])
                )
              )

          # Latence p99 par endpoint (pré-calculé)
          - record: bmis:http_latency_p99:5m
            expr: |
              histogram_quantile(0.99,
                sum by (application, uri, le) (
                  rate(http_server_requests_seconds_bucket[5m])
                )
              )

          # Taux d'erreurs HTTP global (pré-calculé)
          - record: bmis:http_error_rate:5m
            expr: |
              sum by (application) (rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
                /
              sum by (application) (rate(http_server_requests_seconds_count[5m]))

      - name: bmis_jvm_rules
        interval: 30s
        rules:
          # Utilisation heap en pourcentage (pré-calculé)
          - record: bmis:jvm_heap_usage_percent
            expr: |
              jvm_memory_used_bytes{area="heap"}
                /
              jvm_memory_max_bytes{area="heap"}
                * 100

          # Taux de pauses GC (pré-calculé)
          - record: bmis:jvm_gc_pause_rate:5m
            expr: rate(jvm_gc_pause_seconds_sum[5m])

      - name: bmis_business_rules
        interval: 30s
        rules:
          # Taux de succès des paiements (pré-calculé)
          - record: bmis:payment_success_rate:5m
            expr: |
              sum(rate(bmis_payments_total{status="success"}[5m]))
                /
              sum(rate(bmis_payments_total[5m]))
                * 100

          # Volume de transactions par minute (pré-calculé)
          - record: bmis:transactions_per_minute:5m
            expr: sum(rate(bmis_payments_total[5m])) * 60

9.2 - Quand utiliser les Recording Rules

  • Requêtes utilisées dans plusieurs dashboards - Si la même requête PromQL apparaît dans 5 panels différents, pré-calculez-la une seule fois.
  • Requêtes coûteuses avec histogram_quantile - Les percentiles sur les histogrammes sont les plus gourmandes en CPU.
  • Agrégations cross-service - Les requêtes qui agrègent des données de tous les services à la fois.
  • Requêtes utilisées dans les alertes - Les alertes sont évaluées fréquemment. Utilisez une recording rule pour éviter de surcharger Prometheus.

Dans Grafana, remplacez simplement la requête complexe par le nom de la recording rule :

# Au lieu de :
histogram_quantile(0.95, sum by (application, uri, le) (rate(http_server_requests_seconds_bucket[5m])))

# Utilisez :
bmis:http_latency_p95:5m

10 - Erreurs courantes

Erreurs à éviter absolument :

1. Trop de métriques personnalisées - Chaque métrique consomme de la mémoire dans Prometheus. 100 métriques bien choisies valent mieux que 10 000 métriques jamais consultées. Concentrez-vous sur les métriques qui déclenchent des actions. Si une métrique n'a jamais déclenché d'alerte ou d'investigation en 6 mois, supprimez-la.

2. Pas de Recording Rules - Les dashboards Grafana avec des requêtes PromQL complexes (notamment histogram_quantile) peuvent mettre Prometheus à genoux. Pré-calculez les requêtes fréquentes avec des recording rules. Votre Prometheus passera de 80% CPU à 15%.

3. Ignorer les métriques business - Monitorer CPU et mémoire ne sert à rien si vous ne savez pas que vos paiements échouent à 20%. Les métriques business (revenu, transactions, conversions) sont celles qui comptent pour votre entreprise. Ajoutez-les en premier.

4. Labels à haute cardinalité - Ajouter un label user_id à une métrique crée une série temporelle par utilisateur. Avec 100 000 utilisateurs, c'est 100 000 séries - Prometheus sera saturé. Les labels doivent avoir une cardinalité faible et bornée : status, method, service, environment - jamais user_id, request_id, ou transaction_id.

5. Pas de rétention configurée - Par défaut, Prometheus garde les données 15 jours. En production, configurez une rétention adaptée (30-90 jours) avec --storage.tsdb.retention.time et un --storage.tsdb.retention.size pour éviter de remplir le disque.

6. Scrape interval trop court - Un scrape toutes les 5 secondes génère 12× plus de données qu'un scrape toutes les 60 secondes. 15 secondes est un bon compromis pour la plupart des cas. N'utilisez 5 secondes que pour les métriques critiques (paiements en temps réel).

7. Ignorer les métriques par défaut de Micrometer - Ne réinventez pas la roue. Spring Boot expose déjà des dizaines de métriques JVM, HTTP et DB. Utilisez-les avant de créer des métriques personnalisées.

11 - Best Practices

Méthode USE (Utilization, Saturation, Errors) - Pour chaque ressource (CPU, mémoire, disque, réseau, pool de connexions) :
  • Utilization - Quel pourcentage de la ressource est utilisé ? (ex : CPU à 75%)
  • Saturation - La ressource est-elle en file d'attente ? (ex : 5 threads en attente d'une connexion DB)
  • Errors - Des erreurs se produisent-elles ? (ex : timeouts de connexion DB)
Appliquez USE à chaque couche : JVM, application, base de données, cache, réseau.
Méthode RED (Rate, Errors, Duration) - Pour chaque service (API endpoint, microservice) :
  • Rate - Combien de requêtes par seconde ? (ex : 500 req/s sur /api/payments)
  • Errors - Quel pourcentage de requêtes échoue ? (ex : 2% d'erreurs 5xx)
  • Duration - Combien de temps prennent les requêtes ? (ex : p95 = 200ms)
RED est complémentaire à USE. USE pour les ressources, RED pour les services.
Les 4 Golden Signals (Google SRE) - Google définit quatre signaux essentiels pour tout système distribué :
  • Latency - Le temps pour traiter une requête (distinguer les requêtes réussies des échouées)
  • Traffic - La demande sur le système (requêtes/seconde, transactions/minute)
  • Errors - Le taux de requêtes qui échouent (explicites 5xx + implicites comme les timeouts)
  • Saturation - À quel point le système est "plein" (queue depth, CPU, mémoire)
Si vous ne pouvez monitorer que 4 choses, monitorez les Golden Signals.
Nommage des métriques - Suivez les conventions Prometheus :
  • Préfixe avec le nom de l'application : bmis_
  • Suffixe avec l'unité : _seconds, _bytes, _total
  • Les compteurs finissent par _total : bmis_payments_total
  • Utilisez des snake_case : http_server_requests_seconds
  • Soyez descriptif : bmis_bank_api_duration_seconds plutôt que bank_time
Dashboard Hierarchy - Organisez vos dashboards en 3 niveaux :
  • Niveau 1 - Overview : Vue globale du système (tous les services, KPIs business). C'est ce que le CTO regarde.
  • Niveau 2 - Service : Détails d'un service spécifique (payment-service, user-service). Pour l'équipe du service.
  • Niveau 3 - Debug : Métriques JVM, GC, pool DB, cache. Pour le debugging et le post-mortem.
Utilisez les variables Grafana ($service, $namespace) pour naviguer entre les niveaux avec des drill-down links.
Versionner les dashboards - Exportez vos dashboards Grafana en JSON et stockez-les dans Git. Provisionnez-les automatiquement via des ConfigMaps Kubernetes. Cela garantit que vos dashboards sont reproductibles, reviewables, et ne sont jamais perdus.
