Leçon 1 Section 1 - Fondations Docker

Docker Deep Dive - Images vs Containers

Comprendre le modèle fondamental de Docker : images, layers, containers, et le cycle de vie complet.

1 - Qu'est-ce que Docker réellement ?

Docker n'est pas une machine virtuelle légère. C'est une erreur fondamentale que beaucoup de développeurs commettent. Docker est une plateforme de containerisation qui utilise les fonctionnalités natives du noyau Linux pour isoler des processus.

Les trois piliers de l'isolation

Docker repose sur trois mécanismes du kernel Linux qui travaillent ensemble pour créer l'illusion d'un environnement isolé :

  • Namespaces - Isolent la visibilité des ressources. Chaque container possède son propre espace de noms pour les processus (PID), le réseau (NET), les points de montage (MNT), les utilisateurs (USER), et les noms d'hôte (UTS).
  • Control Groups (cgroups) - Limitent et mesurent les ressources consommées : CPU, mémoire, I/O disque, bande passante réseau. C'est ce qui empêche un container de monopoliser les ressources de l'hôte.
  • Union Filesystem (OverlayFS) - Permet de superposer des couches de fichiers en lecture seule avec une couche en écriture, créant ainsi le système de layers des images Docker.
Point clé : Un container partage le noyau de l'hôte. Il n'y a pas de noyau séparé, pas de démarrage d'OS. C'est pourquoi un container démarre en millisecondes, là où une VM prend des minutes.

VM vs Container - la vraie différence

Machine Virtuelle
  • Hyperviseur (Type 1 ou Type 2)
  • OS invité complet avec son propre noyau
  • Démarrage en minutes
  • Consomme des Go de RAM
  • Isolation matérielle complète
  • Overhead significatif sur le CPU
  • Image de plusieurs Go
Container Docker
  • Docker Engine (containerd + runc)
  • Partage le noyau de l'hôte
  • Démarrage en millisecondes
  • Consomme des Mo de RAM
  • Isolation au niveau processus
  • Overhead quasi nul
  • Image de quelques Mo à centaines de Mo
BASH Vérifier l'isolation des namespaces 
# Voir les namespaces d'un container en cours d'exécution
docker inspect --format '{{.State.Pid}}' mon-container
# Résultat : 12345

# Lister les namespaces du processus
ls -la /proc/12345/ns/
# lrwxrwxrwx 1 root root 0  ... cgroup -> 'cgroup:[4026532543]'
# lrwxrwxrwx 1 root root 0  ... ipc    -> 'ipc:[4026532541]'
# lrwxrwxrwx 1 root root 0  ... mnt    -> 'mnt:[4026532539]'
# lrwxrwxrwx 1 root root 0  ... net    -> 'net:[4026532544]'
# lrwxrwxrwx 1 root root 0  ... pid    -> 'pid:[4026532542]'

# Voir les limites cgroups du container
docker stats mon-container --no-stream
# CONTAINER   CPU %   MEM USAGE / LIMIT     MEM %
# mon-cont    0.50%   128MiB / 512MiB       25.00%

2 - Images Docker en profondeur

Une image Docker est un modèle immuable en lecture seule qui contient tout le nécessaire pour exécuter une application : le code source, les dépendances, les bibliothèques système, les variables d'environnement et les fichiers de configuration.

Le système de couches (Layers)

Chaque instruction dans un Dockerfile crée une nouvelle couche. Ces couches sont empilées les unes sur les autres grâce à l'Union Filesystem (OverlayFS). L'avantage majeur : les couches sont partagées entre images et mises en cache lors du build.

TEXT Architecture des couches Docker 
┌─────────────────────────────────────────────┐
│         Container Layer (R/W)               │  ← Couche en écriture
│    Fichiers modifiés par l'application      │     (éphémère)
├─────────────────────────────────────────────┤
│  Layer 5: COPY target/*.jar app.jar         │  ← Votre application
├─────────────────────────────────────────────┤
│  Layer 4: RUN addgroup -S spring ...        │  ← Utilisateur non-root
├─────────────────────────────────────────────┤
│  Layer 3: EXPOSE 8080                       │  ← Métadonnée (0 octet)
├─────────────────────────────────────────────┤
│  Layer 2: ENV JAVA_OPTS="-Xmx512m"         │  ← Variable d'env
├─────────────────────────────────────────────┤
│  Layer 1: FROM eclipse-temurin:21-jre-alpine│  ← Image de base
│    ├── Alpine Linux (~5 Mo)                 │     (lecture seule)
│    └── JRE 21 (~80 Mo)                     │
└─────────────────────────────────────────────┘

Comment les layers fonctionnent

Chaque instruction du Dockerfile qui modifie le système de fichiers crée une couche :

Instruction Crée un layer ? Description
FROM Oui Initialise l'image de base, crée le premier layer
RUN Oui Exécute une commande et capture les changements du filesystem
COPY / ADD Oui Copie des fichiers depuis le contexte de build
ENV Oui (minimal) Définit une variable d'environnement
EXPOSE Non (métadonnée) Documente le port exposé
CMD / ENTRYPOINT Non (métadonnée) Définit la commande de démarrage
LABEL Non (métadonnée) Ajoute des métadonnées à l'image
BASH Inspecter les layers d'une image 
# Voir l'historique des layers d'une image
docker history eclipse-temurin:21-jre-alpine

# IMAGE          CREATED       CREATED BY                                      SIZE
# a1b2c3d4e5f6   2 weeks ago   CMD ["jshell"]                                  0B
# <missing>      2 weeks ago   ENV JAVA_HOME=/opt/java/openjdk                 0B
# <missing>      2 weeks ago   RUN /bin/sh -c set -eux; ...                    83.2MB
# <missing>      2 weeks ago   /bin/sh -c #(nop) ADD file:... in /             7.38MB

# Inspecter la taille totale de l'image
docker image inspect eclipse-temurin:21-jre-alpine --format '{{.Size}}'
# 190874368 (environ 182 Mo)

# Voir l'utilisation disque détaillée
docker system df -v
Optimisation du cache : Placez les instructions qui changent rarement en premier dans votre Dockerfile (installation de dépendances système) et celles qui changent souvent en dernier (copie du code source). Docker réutilise les layers en cache tant qu'aucune instruction précédente n'a été modifiée.

3 - Dockerfile - Production Grade

Un Dockerfile de production ne ressemble en rien à un Dockerfile de développement. Nous allons comparer les deux approches, puis construire un Dockerfile multi-stage optimisé pour une application Spring Boot.

❌ Le Dockerfile naïf (à ne JAMAIS utiliser en production)

Mauvaise pratique : Ce Dockerfile produit une image de 800+ Mo, s'exécute en tant que root, inclut le JDK complet (inutile en production), et ne profite pas du cache des layers.
DOCKERFILE Dockerfile.bad - NE PAS UTILISER 
# ❌ MAUVAIS EXEMPLE - Ne faites JAMAIS ça en production

FROM openjdk:21
WORKDIR /app
COPY . .
RUN ./mvnw package -DskipTests
EXPOSE 8080
CMD ["java", "-jar", "target/fintech-api-0.0.1-SNAPSHOT.jar"]

# Problèmes :
# 1. Image de base complète (JDK + outils de build) → 800+ Mo
# 2. Exécution en tant que root → vulnérabilité de sécurité
# 3. Code source inclus dans l'image finale → surface d'attaque
# 4. Pas de .dockerignore → contexte de build énorme
# 5. Aucune limite mémoire JVM → OOMKilled en production
# 6. Pas de health check → pas de monitoring

✅ Le Dockerfile multi-stage optimisé

DOCKERFILE Dockerfile - Production Grade Spring Boot 
# ============================================================
# STAGE 1 : Build - Compilation avec Maven
# ============================================================
FROM eclipse-temurin:21-jdk-alpine AS builder

WORKDIR /build

# 1. Copier uniquement les fichiers de dépendances d'abord
#    → Profite du cache Docker si les dépendances ne changent pas
COPY pom.xml mvnw ./
COPY .mvn .mvn

# 2. Télécharger les dépendances (layer cachée séparément)
RUN ./mvnw dependency:go-offline -B

# 3. Copier le code source (change souvent → layer séparée)
COPY src src

# 4. Compiler l'application
RUN ./mvnw package -DskipTests -B \
    && java -Djarmode=tools -jar target/*.jar extract --layers --launcher

# ============================================================
# STAGE 2 : Runtime - Image minimale de production
# ============================================================
FROM eclipse-temurin:21-jre-alpine AS runtime

# Métadonnées de l'image
LABEL maintainer="equipe-devops@bmis-academy.com"
LABEL version="1.0.0"
LABEL description="Fintech API - Service de gestion bancaire"

# Créer un utilisateur non-root pour la sécurité
RUN addgroup -S spring && adduser -S spring -G spring

# Répertoire de travail
WORKDIR /app

# Copier les layers extraites (optimise les mises à jour)
COPY --from=builder /build/target/extracted/dependencies/ ./
COPY --from=builder /build/target/extracted/spring-boot-loader/ ./
COPY --from=builder /build/target/extracted/snapshot-dependencies/ ./
COPY --from=builder /build/target/extracted/application/ ./

# Changer le propriétaire des fichiers
RUN chown -R spring:spring /app

# Utiliser l'utilisateur non-root
USER spring:spring

# Exposer le port (documentation uniquement)
EXPOSE 8080

# Variables d'environnement JVM optimisées pour les containers
ENV JAVA_OPTS="-XX:+UseContainerSupport \
               -XX:MaxRAMPercentage=75.0 \
               -XX:+UseG1GC \
               -XX:+UseStringDeduplication \
               -Djava.security.egd=file:/dev/urandom"

# Health check intégré
HEALTHCHECK --interval=30s --timeout=10s --start-period=40s --retries=3 \
  CMD wget --quiet --tries=1 --spider http://localhost:8080/actuator/health || exit 1

# Point d'entrée avec les options JVM
ENTRYPOINT ["sh", "-c", "java ${JAVA_OPTS} org.springframework.boot.loader.launch.JarLauncher"]

Le fichier .dockerignore

Sans .dockerignore, Docker envoie tout le répertoire comme contexte de build, y compris .git/, node_modules/, et les fichiers IDE. Cela ralentit considérablement le build.

BASH .dockerignore 
# Contrôle de version
.git
.gitignore

# Build et dépendances
target/
!target/*.jar
node_modules/
.gradle/
build/

# IDE
.idea/
.vscode/
*.iml
*.iws

# Docker
Dockerfile*
docker-compose*
.dockerignore

# Documentation et tests
docs/
*.md
src/test/

# Fichiers système
.DS_Store
Thumbs.db
*.log
Multi-stage = Sécurité + Performance. L'image finale ne contient que le JRE et le JAR. Le code source, Maven, le JDK complet et toutes les dépendances de build restent dans le stage builder et ne font pas partie de l'image finale. Résultat : ~180 Mo au lieu de 800+ Mo.

4 - Cycle de vie des Containers

Un container passe par plusieurs états durant son existence. Comprendre ce cycle de vie est essentiel pour gérer correctement vos déploiements.

TEXT Diagramme d'état d'un container 
                    docker create
    [Image] ──────────────────────────► [Created]
                                            │
                                   docker start
                                            │
                                            ▼
                  docker restart       [Running] ◄─────────────┐
                 ┌──────────────────►      │                   │
                 │                         │                   │
                 │              docker stop │ docker kill       │
                 │                         │                   │
                 │                         ▼                   │
                 │                    [Stopped] ───────────────┘
                 │                         │         docker start
                 │                         │
                 │              docker rm   │
                 │                         │
                 │                         ▼
                 └───────────────── [Removed/Deleted]

    ─── Raccourci ──────────────────────────────────────
    docker run = docker create + docker start (+ attach)

Commandes essentielles du cycle de vie

BASH Gestion du cycle de vie 
# ── Créer et démarrer un container ──
# La commande la plus courante : docker run
docker run -d \
  --name fintech-api \
  --restart unless-stopped \
  -p 8080:8080 \
  -e SPRING_PROFILES_ACTIVE=production \
  -e DATABASE_URL=jdbc:postgresql://db:5432/fintech \
  --memory 512m \
  --cpus 1.0 \
  fintech-api:1.0.0

# ── Voir les containers en cours d'exécution ──
docker ps
# CONTAINER ID   IMAGE               STATUS         PORTS                    NAMES
# a1b2c3d4e5f6   fintech-api:1.0.0   Up 5 minutes   0.0.0.0:8080->8080/tcp   fintech-api

# ── Voir TOUS les containers (y compris arrêtés) ──
docker ps -a

# ── Voir les logs en temps réel ──
docker logs -f --tail 100 fintech-api

# ── Exécuter une commande dans un container en cours ──
docker exec -it fintech-api /bin/sh

# ── Arrêter proprement (SIGTERM, puis SIGKILL après 10s) ──
docker stop fintech-api

# ── Forcer l'arrêt immédiat (SIGKILL) ──
docker kill fintech-api

# ── Redémarrer ──
docker restart fintech-api

# ── Supprimer un container arrêté ──
docker rm fintech-api

# ── Supprimer un container en cours (force) ──
docker rm -f fintech-api

# ── Nettoyer tous les containers arrêtés ──
docker container prune -f

Options critiques de docker run

Option Description Exemple
-d Mode détaché (background) docker run -d nginx
-p host:container Mapping de ports -p 8080:8080
-e VAR=value Variable d'environnement -e SPRING_PROFILES_ACTIVE=prod
-v host:container Monter un volume -v ./data:/var/lib/postgresql/data
--name Nom du container --name fintech-api
--restart Politique de redémarrage --restart unless-stopped

--read-only Filesystem en lecture seule --read-only --tmpfs /tmp

5 - Dockeriser Spring Boot + PostgreSQL + Redis

Passons à la pratique avec un cas d'usage réel : dockeriser notre système fintech complet. Nous allons créer un environnement multi-services avec Docker Compose qui inclut l'API Spring Boot, PostgreSQL pour la persistance, et Redis pour le caching.

Dockerfile multi-stage pour l'API Spring Boot

DOCKERFILE fintech-api/Dockerfile 
# ============================================================
# STAGE 1 : Dépendances Maven (couche cachée séparément)
# ============================================================
FROM eclipse-temurin:21-jdk-alpine AS deps

WORKDIR /build
COPY pom.xml mvnw ./
COPY .mvn .mvn
RUN ./mvnw dependency:go-offline -B

# ============================================================
# STAGE 2 : Compilation
# ============================================================
FROM deps AS builder

WORKDIR /build
COPY src src
RUN ./mvnw package -DskipTests -B

# ============================================================
# STAGE 3 : Image de production
# ============================================================
FROM eclipse-temurin:21-jre-alpine

RUN addgroup -S app && adduser -S app -G app

WORKDIR /app

COPY --from=builder --chown=app:app /build/target/fintech-api-*.jar app.jar

USER app:app

EXPOSE 8080

ENV JAVA_OPTS="-XX:+UseContainerSupport \
               -XX:MaxRAMPercentage=75.0 \
               -XX:+UseG1GC \
               -Djava.security.egd=file:/dev/urandom"

HEALTHCHECK --interval=30s --timeout=10s --start-period=40s --retries=3 \
  CMD wget -qO- http://localhost:8080/actuator/health || exit 1

ENTRYPOINT ["sh", "-c", "java ${JAVA_OPTS} -jar app.jar"]

Docker Compose - Le stack complet

YAML docker-compose.yml 
version: "3.9"

services:
  # ── API Spring Boot ──────────────────────────────────────
  fintech-api:
    build:
      context: ./fintech-api
      dockerfile: Dockerfile
    container_name: fintech-api
    restart: unless-stopped
    ports:
      - "8080:8080"
    environment:
      SPRING_PROFILES_ACTIVE: docker
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/fintech_db
      SPRING_DATASOURCE_USERNAME: fintech_user
      SPRING_DATASOURCE_PASSWORD: ${DB_PASSWORD:?Le mot de passe DB est requis}
      SPRING_DATA_REDIS_HOST: redis
      SPRING_DATA_REDIS_PORT: 6379
      JAVA_OPTS: >-
        -XX:+UseContainerSupport
        -XX:MaxRAMPercentage=75.0
        -XX:+UseG1GC
    deploy:
      resources:
        limits:
          memory: 512M
          cpus: "1.0"
        reservations:
          memory: 256M
          cpus: "0.5"
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    networks:
      - fintech-network
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:8080/actuator/health"]
      interval: 30s
      timeout: 10s
      start_period: 40s
      retries: 3

  # ── PostgreSQL ───────────────────────────────────────────
  postgres:
    image: postgres:16-alpine
    container_name: fintech-postgres
    restart: unless-stopped
    ports:
      - "5432:5432"
    environment:
      POSTGRES_DB: fintech_db
      POSTGRES_USER: fintech_user
      POSTGRES_PASSWORD: ${DB_PASSWORD:?Le mot de passe DB est requis}
      PGDATA: /var/lib/postgresql/data/pgdata
    volumes:
      - postgres-data:/var/lib/postgresql/data
      - ./init-scripts:/docker-entrypoint-initdb.d:ro
    deploy:
      resources:
        limits:
          memory: 256M
          cpus: "0.5"
    networks:
      - fintech-network
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U fintech_user -d fintech_db"]
      interval: 10s
      timeout: 5s
      start_period: 20s
      retries: 5

  # ── Redis (Cache) ────────────────────────────────────────
  redis:
    image: redis:7-alpine
    container_name: fintech-redis
    restart: unless-stopped
    ports:
      - "6379:6379"
    command: >
      redis-server
      --maxmemory 128mb
      --maxmemory-policy allkeys-lru
      --appendonly yes
      --requirepass ${REDIS_PASSWORD:-redis_secret}
    volumes:
      - redis-data:/data
    deploy:
      resources:
        limits:
          memory: 192M
          cpus: "0.25"
    networks:
      - fintech-network
    healthcheck:
      test: ["CMD", "redis-cli", "-a", "${REDIS_PASSWORD:-redis_secret}", "ping"]
      interval: 10s
      timeout: 5s
      retries: 3

# ── Volumes persistants ──────────────────────────────────
volumes:
  postgres-data:
    driver: local
  redis-data:
    driver: local

# ── Réseau isolé ─────────────────────────────────────────
networks:
  fintech-network:
    driver: bridge
    ipam:
      config:
        - subnet: 172.20.0.0/16

Configuration Spring Boot adaptée aux containers

YAML src/main/resources/application-docker.yml 
spring:
  # ── Base de données ──
  datasource:
    url: ${SPRING_DATASOURCE_URL:jdbc:postgresql://postgres:5432/fintech_db}
    username: ${SPRING_DATASOURCE_USERNAME:fintech_user}
    password: ${SPRING_DATASOURCE_PASSWORD}
    hikari:
      maximum-pool-size: 10
      minimum-idle: 5
      connection-timeout: 20000
      idle-timeout: 300000
      max-lifetime: 1200000

  # ── JPA ──
  jpa:
    hibernate:
      ddl-auto: validate
    properties:
      hibernate:
        dialect: org.hibernate.dialect.PostgreSQLDialect
        format_sql: false
        jdbc:
          batch_size: 25

  # ── Redis ──
  data:
    redis:
      host: ${SPRING_DATA_REDIS_HOST:redis}
      port: ${SPRING_DATA_REDIS_PORT:6379}
      password: ${REDIS_PASSWORD:redis_secret}
      timeout: 5000ms

# ── Actuator (Health checks pour Docker/K8s) ──
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus
  endpoint:
    health:
      show-details: when_authorized
      probes:
        enabled: true
  health:
    db:
      enabled: true
    redis:
      enabled: true
    diskspace:
      enabled: true

# ── Logging optimisé pour containers (JSON) ──
logging:
  pattern:
    console: '{"timestamp":"%d{ISO8601}","level":"%p","logger":"%logger{36}","message":"%m"}%n'
  level:
    root: INFO
    com.bmis.fintech: INFO
    org.hibernate.SQL: WARN

# ── Serveur ──
server:
  port: 8080
  shutdown: graceful

spring.lifecycle:
  timeout-per-shutdown-phase: 30s

6 - Registry et Distribution

Un registry Docker est un service de stockage et de distribution d'images Docker. C'est l'équivalent de Maven Central ou npm pour les images de containers.

Comparatif des principaux registries

Registry Fournisseur Repos privés gratuits Cas d'usage
Docker Hub Docker Inc. 1 repo privé Images publiques, open source, prototypage
Amazon ECR AWS Illimités (payant) Intégration ECS/EKS, workloads AWS
Google GCR / Artifact Registry Google Cloud Illimités (payant) Intégration GKE, Cloud Run
Azure ACR Microsoft Illimités (payant) Intégration AKS, Azure DevOps
GitHub GHCR GitHub Illimités (publics gratuits) CI/CD GitHub Actions, repos GitHub
Harbor CNCF (self-hosted) Illimités On-premise, conformité, scan de vulnérabilités

Workflow de publication

BASH Push vers un registry 
# ── Docker Hub ─────────────────────────────────────────────
# 1. Se connecter
docker login

# 2. Taguer l'image avec le format registry/image:tag
docker tag fintech-api:latest bmisacademy/fintech-api:1.0.0
docker tag fintech-api:latest bmisacademy/fintech-api:latest

# 3. Pousser vers le registry
docker push bmisacademy/fintech-api:1.0.0
docker push bmisacademy/fintech-api:latest

# ── Amazon ECR ─────────────────────────────────────────────
# 1. Authentification via AWS CLI
aws ecr get-login-password --region eu-west-1 | \
  docker login --username AWS --password-stdin \
  123456789012.dkr.ecr.eu-west-1.amazonaws.com

# 2. Créer le repository (première fois uniquement)
aws ecr create-repository --repository-name fintech-api

# 3. Taguer et pousser
docker tag fintech-api:1.0.0 \
  123456789012.dkr.ecr.eu-west-1.amazonaws.com/fintech-api:1.0.0

docker push \
  123456789012.dkr.ecr.eu-west-1.amazonaws.com/fintech-api:1.0.0

# ── GitHub Container Registry (GHCR) ──────────────────────
# 1. Authentification avec un Personal Access Token
echo $GITHUB_TOKEN | docker login ghcr.io -u USERNAME --password-stdin

# 2. Taguer et pousser
docker tag fintech-api:1.0.0 ghcr.io/bmis-academy/fintech-api:1.0.0
docker push ghcr.io/bmis-academy/fintech-api:1.0.0

# ── Puller une image depuis un registry ────────────────────
docker pull bmisacademy/fintech-api:1.0.0
Convention de tagging : Utilisez toujours le versioning sémantique (1.0.0, 1.0.1) pour les tags de production. N'utilisez latest qu'en développement. En production, un tag latest rend impossible le rollback et le suivi des déploiements.

7 - Erreurs courantes à éviter

❌ Exécuter en tant que root. Par défaut, les processus dans un container tournent en tant que root. Si un attaquant exploite une vulnérabilité de votre application, il obtient un accès root au container - et potentiellement à l'hôte via une évasion de container.

Solution : Toujours ajouter USER non-root dans votre Dockerfile.
❌ Ne pas utiliser de .dockerignore. Sans .dockerignore, Docker envoie tout le contexte de build au daemon, y compris .git/ (potentiellement des centaines de Mo), node_modules/, les fichiers de log, et les secrets éventuels.

Solution : Créer un .dockerignore exhaustif (voir section 3).
❌ Utiliser une image de base "fat". Utiliser openjdk:21 ou ubuntu:latest comme image de base produit des images de 800+ Mo avec des centaines de paquets inutiles qui augmentent la surface d'attaque.

Solution : Utiliser les variantes -alpine ou -slim. Pour Java : eclipse-temurin:21-jre-alpine.
❌ Stocker des secrets dans l'image. Les secrets (mots de passe, clés API, certificats) codés en dur dans le Dockerfile ou copiés dans l'image sont visibles par quiconque a accès à l'image via docker history.

Solution : Utiliser des variables d'environnement, Docker Secrets, ou un gestionnaire de secrets externe (Vault, AWS Secrets Manager).
❌ Ignorer le cache des layers. Copier tout le code source avant d'installer les dépendances invalide le cache à chaque modification de code, forçant la ré-installation de toutes les dépendances.

Solution : Copier pom.xml / package.json d'abord, installer les dépendances, puis copier le code source.
❌ Utiliser le tag latest en production. Le tag latest est mutable - il pointe vers une image différente à chaque push. Impossible de savoir quelle version tourne en production ou de faire un rollback fiable.

Solution : Utiliser des tags immuables avec versioning sémantique : fintech-api:1.2.3 ou le SHA du commit Git : fintech-api:abc123f.

8 - Bonnes pratiques pour la production

✅ Images minimales. Utilisez toujours des images de base Alpine ou distroless. Pour Java, eclipse-temurin:21-jre-alpine donne une image d'environ 180 Mo au lieu de 800 Mo. Moins de paquets = moins de vulnérabilités = surface d'attaque réduite.
✅ Multi-stage builds systématiques. Séparez le build du runtime. Le stage de build contient Maven/Gradle, le JDK, le code source. Le stage de runtime ne contient que le JRE et l'artefact compilé. Aucun outil de build en production.
✅ Health checks à tous les niveaux. Configurez des HEALTHCHECK dans le Dockerfile, des health checks dans docker-compose.yml, et des readiness/liveness probes dans Kubernetes. Utilisez /actuator/health de Spring Boot Actuator.
✅ Limites de ressources obligatoires. Définissez toujours --memory et --cpus pour chaque container. Sans limites, un container peut consommer toutes les ressources de l'hôte et provoquer un OOM (Out of Memory) qui tue d'autres containers.
✅ Logs en JSON vers stdout/stderr. En production, configurez vos applications pour écrire les logs en format JSON sur stdout et stderr. Docker capture automatiquement ces flux. Les outils comme ELK Stack, Loki ou CloudWatch parsent ensuite le JSON structuré.
✅ Scan de vulnérabilités automatisé. Intégrez un scanner de vulnérabilités dans votre pipeline CI/CD. Utilisez docker scout cves, Trivy, ou Snyk pour détecter les CVE dans vos images avant chaque déploiement.
BASH Scanner les vulnérabilités 
# Scanner avec Docker Scout (intégré à Docker Desktop)
docker scout cves fintech-api:1.0.0

# Scanner avec Trivy (open source, très populaire)
trivy image fintech-api:1.0.0

# Scanner avec Trivy en mode strict (échoue si vulnérabilité HIGH ou CRITICAL)
trivy image --exit-code 1 --severity HIGH,CRITICAL fintech-api:1.0.0

# Résultat typique :
# fintech-api:1.0.0 (alpine 3.19.1)
# Total: 0 (HIGH: 0, CRITICAL: 0)
# ✅ Aucune vulnérabilité détectée
✅ Shutdown gracieux. Configurez votre application pour gérer le signal SIGTERM proprement. Spring Boot le fait nativement avec server.shutdown=graceful. Cela permet de terminer les requêtes en cours avant l'arrêt, évitant les erreurs 502 lors des redéploiements.
