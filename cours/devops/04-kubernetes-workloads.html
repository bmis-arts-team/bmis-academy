Leçon 4 Section 2 - Kubernetes Core

Deployments & StatefulSets

Gérer les workloads stateless et stateful - stratégies de déploiement, rolling updates et rollbacks.

1 - ReplicaSet - La base

Un ReplicaSet garantit qu'un nombre spécifié de réplicas (copies identiques) d'un Pod est en cours d'exécution à tout moment. Si un Pod tombe, le ReplicaSet en crée automatiquement un nouveau pour maintenir le compte souhaité.

Le ReplicaSet utilise un sélecteur de labels pour identifier les Pods qu'il gère. Tous les Pods dont les labels correspondent au sélecteur sont « adoptés » par le ReplicaSet.

En pratique, vous ne créez presque jamais un ReplicaSet directement. Vous utilisez un Deployment, qui crée et gère automatiquement un ReplicaSet pour vous. Le Deployment ajoute des fonctionnalités essentielles comme les rolling updates et les rollbacks que le ReplicaSet seul ne possède pas.
yaml replicaset-exemple.yaml 
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: api-backend-rs
  labels:
    app: api-backend
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api-backend
  template:
    metadata:
      labels:
        app: api-backend
    spec:
      containers:
        - name: api-backend
          image: bmis/api-backend:1.0.0
          ports:
            - containerPort: 8080

Ce ReplicaSet maintient 3 Pods identiques. Si vous supprimez manuellement un Pod, le ReplicaSet en recréera un immédiatement. Cependant, si vous changez l'image (par exemple de 1.0.0 à 1.1.0), le ReplicaSet ne mettra pas à jour les Pods existants - il faudrait les supprimer manuellement. C'est précisément ce que le Deployment automatise.

2 - Deployment - Le workload standard

Le Deployment est la ressource la plus utilisée dans Kubernetes. Il gère un ReplicaSet qui lui-même gère les Pods. La chaîne est : Deployment → ReplicaSet → Pods. Le Deployment ajoute la gestion des mises à jour (rolling updates) et des rollbacks.

2.1 - Structure complète d'un Deployment

Voici un Deployment complet pour une application Spring Boot, avec chaque champ important expliqué :

yaml deployment-spring-boot.yaml 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-backend                    # Nom unique du Deployment
  namespace: fintech                   # Namespace cible
  labels:
    app: api-backend                   # Labels du Deployment lui-même
    version: "1.2.0"
    team: backend
spec:
  replicas: 3                          # Nombre de Pods souhaités
  selector:
    matchLabels:
      app: api-backend                 # Doit correspondre aux labels du template
  template:                            # Template du Pod
    metadata:
      labels:
        app: api-backend               # Labels des Pods (doivent matcher selector)
        version: "1.2.0"
    spec:
      containers:
        - name: api-backend
          image: bmis/api-backend:1.2.0   # Image avec tag de version explicite
          imagePullPolicy: IfNotPresent   # Ne pull que si l'image n'existe pas localement
          ports:
            - containerPort: 8080         # Port exposé par le container
              protocol: TCP
          env:
            - name: SPRING_PROFILES_ACTIVE
              value: "production"
            - name: SERVER_PORT
              value: "8080"
            - name: DB_HOST
              value: "postgres-headless.fintech.svc.cluster.local"
          resources:
            requests:                     # Ressources minimales garanties
              memory: "256Mi"
              cpu: "250m"
            limits:                       # Ressources maximales autorisées
              memory: "512Mi"
              cpu: "500m"

2.2 - Les champs clés expliqués

spec.replicas - Le nombre de Pods identiques que Kubernetes doit maintenir. Si un Pod meurt, un nouveau est créé. Si vous changez cette valeur, Kubernetes ajuste automatiquement le nombre de Pods.

spec.selector.matchLabels - Le sélecteur qui détermine quels Pods sont gérés par ce Deployment. Les labels définis ici doivent correspondre exactement aux labels dans spec.template.metadata.labels. C'est un contrat : le Deployment ne gère que les Pods qui portent ces labels.

spec.template - Le « moule » utilisé pour créer chaque Pod. Il contient les métadonnées (labels) et la spécification du Pod (containers, volumes, etc.). Chaque modification du template déclenche un rolling update.

resources.requests - Les ressources garanties pour le container. Le Scheduler utilise ces valeurs pour placer le Pod sur un nœud disposant de suffisamment de ressources. Un Pod ne sera jamais schedulé sur un nœud qui n'a pas assez de ressources libres pour satisfaire les requests.

resources.limits - Les ressources maximales que le container peut consommer. Si le container dépasse la limite mémoire, il est tué (OOMKilled). Si il dépasse la limite CPU, il est throttlé (ralenti).

imagePullPolicy - Contrôle quand Kubernetes télécharge l'image :

  • Always - Toujours pull l'image (défaut si tag est :latest)
  • IfNotPresent - Pull seulement si l'image n'est pas en cache local (défaut si tag de version explicite)
  • Never - N'utilise que l'image locale, ne pull jamais

3 - Rolling Update Strategy

La stratégie de rolling update (mise à jour progressive) est le mécanisme par défaut de Kubernetes pour déployer une nouvelle version de votre application sans temps d'arrêt. Kubernetes remplace les anciens Pods par les nouveaux de manière graduelle.

3.1 - Comment ça fonctionne, étape par étape

  1. Vous modifiez le template du Deployment (par exemple, changement de version d'image)
  2. Kubernetes crée un nouveau ReplicaSet avec la nouvelle configuration
  3. Le nouveau ReplicaSet commence à créer des Pods avec la nouvelle version
  4. Kubernetes attend que les nouveaux Pods soient Ready (passent la readinessProbe)
  5. L'ancien ReplicaSet réduit progressivement le nombre de Pods
  6. Le processus continue jusqu'à ce que tous les Pods soient sur la nouvelle version
  7. L'ancien ReplicaSet est conservé (avec 0 réplicas) pour permettre un rollback

3.2 - Configuration de la stratégie

yaml deployment-rolling-strategy.yaml 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-backend
  namespace: fintech
spec:
  replicas: 4
  strategy:
    type: RollingUpdate           # Stratégie de mise à jour (défaut)
    rollingUpdate:
      maxUnavailable: 1           # Max 1 Pod indisponible pendant le rollout
      maxSurge: 1                 # Max 1 Pod supplémentaire au-dessus de replicas
  selector:
    matchLabels:
      app: api-backend
  template:
    metadata:
      labels:
        app: api-backend
    spec:
      containers:
        - name: api-backend
          image: bmis/api-backend:1.3.0
          ports:
            - containerPort: 8080
          resources:
            requests:
              memory: "256Mi"
              cpu: "250m"
            limits:
              memory: "512Mi"
              cpu: "500m"

maxUnavailable - Le nombre maximum de Pods qui peuvent être indisponibles pendant la mise à jour. Peut être un nombre absolu (ex : 1) ou un pourcentage (ex : 25%). Avec 4 replicas et maxUnavailable: 1, il y aura toujours au moins 3 Pods en service.

maxSurge - Le nombre maximum de Pods supplémentaires qui peuvent être créés au-dessus du nombre souhaité de replicas. Avec 4 replicas et maxSurge: 1, Kubernetes peut avoir jusqu'à 5 Pods temporairement pendant le déploiement.

Exemple concret - Avec replicas: 4, maxUnavailable: 1 et maxSurge: 1 lors d'un rolling update :
  • Minimum de Pods actifs à tout moment : 4 - 1 = 3
  • Maximum de Pods total (ancien + nouveau) : 4 + 1 = 5
Kubernetes crée 1 nouveau Pod, attend qu'il soit Ready, puis supprime 1 ancien Pod. Puis crée le suivant, et ainsi de suite.

3.3 - Surveiller un rolling update

bash Surveiller le rollout 
# Déclencher un rolling update en changeant l'image
kubectl set image deployment/api-backend api-backend=bmis/api-backend:1.3.0 -n fintech

# Surveiller le rollout en temps réel
kubectl rollout status deployment/api-backend -n fintech
# Waiting for deployment "api-backend" rollout to finish: 2 out of 4 new replicas have been updated...
# Waiting for deployment "api-backend" rollout to finish: 3 out of 4 new replicas have been updated...
# deployment "api-backend" successfully rolled out

# Voir les ReplicaSets (ancien et nouveau)
kubectl get rs -n fintech
# NAME                      DESIRED   CURRENT   READY   AGE
# api-backend-7d8f9c6b4d    4         4         4       30s    ← nouveau
# api-backend-5b6f7a8c3e    0         0         0       2h     ← ancien (conservé)

# Voir les événements du Deployment
kubectl describe deployment api-backend -n fintech
Stratégie Recreate : Il existe une alternative au RollingUpdate appelée Recreate. Cette stratégie supprime tous les anciens Pods avant de créer les nouveaux, ce qui cause un temps d'arrêt. Utilisez-la uniquement pour les workloads qui ne supportent pas deux versions simultanées (par exemple, des migrations de schéma de base de données).

4 - Rollback - Revenir en arrière

L'un des plus grands avantages des Deployments est la capacité de revenir instantanément à une version précédente. Kubernetes conserve l'historique des ReplicaSets (par défaut les 10 dernières révisions), ce qui permet un rollback rapide.

bash Commandes de rollback 
# Voir l'historique des déploiements
kubectl rollout history deployment/api-backend -n fintech
# REVISION  CHANGE-CAUSE
# 1         kubectl apply --filename=deployment.yaml --record
# 2         kubectl set image deployment/api-backend api-backend=bmis/api-backend:1.2.0
# 3         kubectl set image deployment/api-backend api-backend=bmis/api-backend:1.3.0

# Voir les détails d'une révision spécifique
kubectl rollout history deployment/api-backend -n fintech --revision=2

# Rollback à la révision précédente (immédiat)
kubectl rollout undo deployment/api-backend -n fintech

# Rollback à une révision spécifique
kubectl rollout undo deployment/api-backend -n fintech --to-revision=1

# Vérifier le statut du rollback
kubectl rollout status deployment/api-backend -n fintech

# Mettre en pause un rollout en cours (utile pour vérifier)
kubectl rollout pause deployment/api-backend -n fintech

# Reprendre un rollout en pause
kubectl rollout resume deployment/api-backend -n fintech
Bonne pratique : Utilisez l'option --record lors de vos déploiements (kubectl apply -f deployment.yaml --record) pour enregistrer la commande utilisée dans l'historique. Cela facilite l'identification de la cause de chaque révision. Vous pouvez aussi configurer le nombre de révisions conservées via spec.revisionHistoryLimit dans votre Deployment.

5 - StatefulSet - Pour les workloads avec état

Un StatefulSet est conçu pour les applications qui nécessitent un état persistant, une identité réseau stable et un déploiement ordonné. Contrairement aux Deployments qui traitent tous les Pods comme interchangeables, chaque Pod d'un StatefulSet est unique et irremplaçable.

5.1 - Quand utiliser un StatefulSet ?

  • Bases de données - PostgreSQL, MySQL, MongoDB (chaque instance a ses propres données)
  • Files de messages - Kafka, RabbitMQ (les brokers ont des identités uniques)
  • Caches avec persistance - Redis en mode persistant (les données doivent survivre aux redémarrages)
  • Systèmes distribués avec leadership - ZooKeeper, etcd (les nœuds doivent se connaître mutuellement)

5.2 - Différences avec un Deployment

Les StatefulSets fournissent trois garanties que les Deployments ne donnent pas :

  • Identité réseau stable - Chaque Pod reçoit un nom DNS prédictible et persistant (ex : postgres-0, postgres-1, postgres-2). Même après un redémarrage, le Pod récupère le même nom.
  • Déploiement et suppression ordonnés - Les Pods sont créés dans l'ordre (0, 1, 2…) et supprimés dans l'ordre inverse (2, 1, 0). Le Pod N+1 n'est pas créé tant que le Pod N n'est pas Ready.
  • Stockage persistant stable - Chaque Pod est lié à son propre PersistentVolumeClaim (PVC). Si le Pod est recréé, il retrouve exactement le même volume de données.

5.3 - Prérequis : Headless Service

Un StatefulSet nécessite un Headless Service (Service avec clusterIP: None) pour fournir l'identité réseau aux Pods. Ce service ne fait pas de load balancing - il crée des entrées DNS individuelles pour chaque Pod.

yaml headless-service-postgres.yaml 
apiVersion: v1
kind: Service
metadata:
  name: postgres-headless
  namespace: fintech
  labels:
    app: postgres
spec:
  clusterIP: None               # Headless Service - pas de VIP
  selector:
    app: postgres
  ports:
    - port: 5432
      targetPort: 5432
      protocol: TCP
      name: postgres

Grâce à ce Headless Service, chaque Pod du StatefulSet obtient un enregistrement DNS de la forme :

<pod-name>.<service-name>.<namespace>.svc.cluster.local

Exemple : postgres-0.postgres-headless.fintech.svc.cluster.local

5.4 - StatefulSet complet pour PostgreSQL

yaml statefulset-postgres.yaml 
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
  namespace: fintech
  labels:
    app: postgres
spec:
  serviceName: postgres-headless       # Référence au Headless Service
  replicas: 1                          # Single-master pour commencer
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
        - name: postgres
          image: postgres:16-alpine
          ports:
            - containerPort: 5432
              name: postgres
          env:
            - name: POSTGRES_DB
              value: "fintech_db"
            - name: POSTGRES_USER
              valueFrom:
                secretKeyRef:
                  name: postgres-credentials
                  key: username
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: postgres-credentials
                  key: password
            - name: PGDATA
              value: "/var/lib/postgresql/data/pgdata"
          resources:
            requests:
              memory: "256Mi"
              cpu: "250m"
            limits:
              memory: "512Mi"
              cpu: "500m"
          volumeMounts:
            - name: postgres-data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:                # PVC créé automatiquement pour chaque Pod
    - metadata:
        name: postgres-data
      spec:
        accessModes: [ "ReadWriteOnce" ]
        storageClassName: standard
        resources:
          requests:
            storage: 10Gi

5.5 - Convention de nommage des Pods

Contrairement aux Deployments qui génèrent des suffixes aléatoires (ex : api-backend-7d8f9c6b4d-x2k9p), les Pods d'un StatefulSet ont des noms prévisibles et ordonnés :

  • postgres-0 - Premier Pod (master)
  • postgres-1 - Deuxième Pod (réplica)
  • postgres-2 - Troisième Pod (réplica)

Si postgres-1 tombe, Kubernetes le recrée avec exactement le même nom (postgres-1) et le même PVC (postgres-data-postgres-1), garantissant que le Pod retrouve ses données.

6 - StatefulSet vs Deployment - Comparaison

Critère Deployment StatefulSet
Cas d'usage Applications stateless (API, frontend, workers) Applications stateful (bases de données, message brokers)
Identité des Pods Interchangeables, noms aléatoires Uniques, noms ordonnés (app-0, app-1…)
Réseau IP aléatoire, accès via Service (ClusterIP) DNS stable par Pod via Headless Service
Stockage Volumes partagés ou éphémères PVC dédié par Pod (volumeClaimTemplates)
Ordre de déploiement Parallèle (tous en même temps) Séquentiel (0, puis 1, puis 2…)
Ordre de suppression Parallèle Séquentiel inversé (2, puis 1, puis 0)
Rolling update Remplace les Pods (nouveau ReplicaSet) Met à jour dans l'ordre inverse (dernier Pod d'abord)
Scaling Rapide, horizontal Plus lent, séquentiel
Prérequis Aucun service obligatoire Headless Service obligatoire
Exemples concrets Spring Boot API, React frontend, microservices PostgreSQL, Kafka, Redis (persistant), ZooKeeper
Règle simple : Si votre application peut être arrêtée et redémarrée n'importe où sans perte de données ni impact fonctionnel → Deployment. Si elle a besoin de conserver des données entre les redémarrages ou d'une identité réseau fixe → StatefulSet.

7 - Deployment pour Spring Boot - Production-Ready

Voici un Deployment complet, prêt pour la production, pour une application Spring Boot. Il inclut les probes de santé, les limites de ressources, les variables d'environnement injectées depuis des ConfigMaps et Secrets, et une stratégie de rolling update robuste.

yaml deployment-api-production.yaml 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-backend
  namespace: fintech
  labels:
    app: api-backend
    version: "2.1.0"
    team: backend
    environment: production
spec:
  replicas: 3                            # 3 réplicas pour la haute disponibilité
  revisionHistoryLimit: 5                # Conserver 5 anciennes révisions pour rollback
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1                  # Toujours au moins 2 Pods disponibles
      maxSurge: 1                        # Max 4 Pods temporairement
  selector:
    matchLabels:
      app: api-backend
  template:
    metadata:
      labels:
        app: api-backend
        version: "2.1.0"
    spec:
      containers:
        - name: api-backend
          image: bmis/api-backend:2.1.0  # JAMAIS :latest en production
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 8080
              protocol: TCP
              name: http

          # ── Variables d'environnement depuis ConfigMap ──
          envFrom:
            - configMapRef:
                name: api-backend-config     # Injecte toutes les clés du ConfigMap
          env:
            # ── Variables depuis Secret ──
            - name: SPRING_DATASOURCE_USERNAME
              valueFrom:
                secretKeyRef:
                  name: postgres-credentials
                  key: username
            - name: SPRING_DATASOURCE_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: postgres-credentials
                  key: password
            - name: JWT_SECRET
              valueFrom:
                secretKeyRef:
                  name: jwt-secret
                  key: secret-key

          # ── Ressources CPU / Mémoire ──
          resources:
            requests:
              memory: "384Mi"
              cpu: "250m"
            limits:
              memory: "768Mi"
              cpu: "1000m"

          # ── Probe de démarrage (Spring Boot peut être lent à démarrer) ──
          startupProbe:
            httpGet:
              path: /actuator/health
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 5
            failureThreshold: 30       # 10 + (5 × 30) = max 160s pour démarrer

          # ── Probe de vivacité (redémarrer si bloqué) ──
          livenessProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            periodSeconds: 15
            failureThreshold: 3        # 3 échecs consécutifs → restart

          # ── Probe de disponibilité (ne pas envoyer de trafic si pas prêt) ──
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            periodSeconds: 10
            failureThreshold: 3
Ne jamais utiliser :latest en production. Le tag :latest est mutable - il peut pointer vers des images différentes selon le moment du pull. Cela rend les rollbacks impossibles et crée des incohérences entre les Pods. Utilisez toujours un tag de version sémantique explicite : bmis/api-backend:2.1.0.

7.1 - Les probes expliquées pour Spring Boot

startupProbe - Vérifie si l'application a fini de démarrer. Spring Boot peut prendre 20-60 secondes au démarrage (chargement du contexte Spring, connexion à la base, etc.). Tant que la startupProbe n'a pas réussi, les autres probes sont désactivées. Cela évite que Kubernetes ne tue un Pod en cours de démarrage.

livenessProbe - Vérifie si l'application est vivante. Si cette probe échoue (3 fois consécutives avec les paramètres ci-dessus), Kubernetes redémarre le container. Utilisez l'endpoint /actuator/health/liveness qui vérifie seulement si la JVM répond, sans vérifier les dépendances externes.

readinessProbe - Vérifie si l'application est prête à recevoir du trafic. Si cette probe échoue, le Pod est retiré du Service (plus de trafic entrant) mais n'est pas redémarré. Utilisez /actuator/health/readiness qui vérifie aussi les connexions à la base de données et autres dépendances.

8 - StatefulSet pour PostgreSQL - Production-Ready

Voici un StatefulSet complet pour PostgreSQL en production, avec un Headless Service, un initContainer pour l'initialisation, et des volumeClaimTemplates pour la persistance des données.

yaml postgres-headless-service.yaml 
apiVersion: v1
kind: Service
metadata:
  name: postgres-headless
  namespace: fintech
  labels:
    app: postgres
spec:
  clusterIP: None
  selector:
    app: postgres
  ports:
    - port: 5432
      targetPort: 5432
      name: postgres
yaml statefulset-postgres-production.yaml 
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
  namespace: fintech
  labels:
    app: postgres
    version: "16"
spec:
  serviceName: postgres-headless
  replicas: 1                           # Single-master
  updateStrategy:
    type: RollingUpdate
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      # ── Init Container : préparer le répertoire de données ──
      initContainers:
        - name: init-permissions
          image: busybox:1.36
          command:
            - sh
            - -c
            - |
              mkdir -p /var/lib/postgresql/data/pgdata
              chown -R 999:999 /var/lib/postgresql/data
          volumeMounts:
            - name: postgres-data
              mountPath: /var/lib/postgresql/data

      containers:
        - name: postgres
          image: postgres:16-alpine
          ports:
            - containerPort: 5432
              name: postgres
          env:
            - name: POSTGRES_DB
              value: "fintech_db"
            - name: POSTGRES_USER
              valueFrom:
                secretKeyRef:
                  name: postgres-credentials
                  key: username
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: postgres-credentials
                  key: password
            - name: PGDATA
              value: "/var/lib/postgresql/data/pgdata"

          resources:
            requests:
              memory: "256Mi"
              cpu: "250m"
            limits:
              memory: "1Gi"
              cpu: "1000m"

          # ── Probe de vivacité : pg_isready ──
          livenessProbe:
            exec:
              command:
                - pg_isready
                - -U
                - $(POSTGRES_USER)
                - -d
                - fintech_db
            initialDelaySeconds: 30
            periodSeconds: 10
            failureThreshold: 3

          # ── Probe de disponibilité ──
          readinessProbe:
            exec:
              command:
                - pg_isready
                - -U
                - $(POSTGRES_USER)
                - -d
                - fintech_db
            initialDelaySeconds: 5
            periodSeconds: 5
            failureThreshold: 3

          volumeMounts:
            - name: postgres-data
              mountPath: /var/lib/postgresql/data

  # ── PVC créé automatiquement pour chaque Pod ──
  volumeClaimTemplates:
    - metadata:
        name: postgres-data
      spec:
        accessModes: [ "ReadWriteOnce" ]
        storageClassName: standard
        resources:
          requests:
            storage: 20Gi
Pourquoi un initContainer ? PostgreSQL nécessite que le répertoire de données (PGDATA) soit détenu par l'utilisateur postgres (UID 999). L'initContainer s'exécute avant le container principal et configure les permissions correctement. Sans cela, PostgreSQL refuserait de démarrer avec une erreur de permission.
volumeClaimTemplates : Contrairement aux volumes classiques, les PVC créés par un volumeClaimTemplate ne sont pas supprimés quand le StatefulSet est supprimé. C'est voulu - cela protège vos données. Vous devez supprimer les PVC manuellement si vous voulez libérer le stockage : kubectl delete pvc postgres-data-postgres-0 -n fintech.

9 - StatefulSet pour Redis - Avec persistance

Redis est souvent utilisé comme cache éphémère (Deployment suffit), mais dans notre système fintech, Redis stocke aussi des sessions utilisateur et des données de rate-limiting qui doivent survivre aux redémarrages. Un StatefulSet avec persistance est alors nécessaire.

yaml redis-headless-service.yaml 
apiVersion: v1
kind: Service
metadata:
  name: redis-headless
  namespace: fintech
  labels:
    app: redis
spec:
  clusterIP: None
  selector:
    app: redis
  ports:
    - port: 6379
      targetPort: 6379
      name: redis
yaml statefulset-redis.yaml 
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: redis
  namespace: fintech
  labels:
    app: redis
spec:
  serviceName: redis-headless
  replicas: 1
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
    spec:
      containers:
        - name: redis
          image: redis:7-alpine
          ports:
            - containerPort: 6379
              name: redis
          command:
            - redis-server
            - "--appendonly"
            - "yes"                      # Activer la persistance AOF
            - "--appendfsync"
            - "everysec"                 # Sync AOF chaque seconde
            - "--maxmemory"
            - "256mb"
            - "--maxmemory-policy"
            - "allkeys-lru"              # Politique d'éviction LRU

          resources:
            requests:
              memory: "128Mi"
              cpu: "100m"
            limits:
              memory: "384Mi"
              cpu: "500m"

          livenessProbe:
            exec:
              command:
                - redis-cli
                - ping
            initialDelaySeconds: 10
            periodSeconds: 10
            failureThreshold: 3

          readinessProbe:
            exec:
              command:
                - redis-cli
                - ping
            initialDelaySeconds: 5
            periodSeconds: 5
            failureThreshold: 3

          volumeMounts:
            - name: redis-data
              mountPath: /data

  volumeClaimTemplates:
    - metadata:
        name: redis-data
      spec:
        accessModes: [ "ReadWriteOnce" ]
        storageClassName: standard
        resources:
          requests:
            storage: 5Gi
AOF (Append Only File) - Redis écrit chaque opération d'écriture dans un fichier journal. En cas de crash, Redis replay ce fichier au redémarrage pour restaurer l'état. L'option appendfsync everysec offre un bon compromis entre performance et durabilité (perte maximale d'une seconde de données).

10 - Scaling - Mise à l'échelle

Kubernetes facilite le scaling horizontal (ajout/retrait de Pods) de vos workloads. Le scaling peut être manuel (commande kubectl) ou automatique (Horizontal Pod Autoscaler).

10.1 - Scaling manuel

bash Commandes de scaling 
# Scaler un Deployment à 5 réplicas
kubectl scale deployment/api-backend --replicas=5 -n fintech

# Vérifier le scaling
kubectl get deployment api-backend -n fintech
# NAME          READY   UP-TO-DATE   AVAILABLE   AGE
# api-backend   5/5     5            5           2h

# Scaler un StatefulSet (séquentiel : 1 → 2 → 3)
kubectl scale statefulset/postgres --replicas=3 -n fintech

# Réduire le nombre de réplicas (scale down)
kubectl scale deployment/api-backend --replicas=2 -n fintech

# Scaler à zéro (arrêter tous les Pods sans supprimer le Deployment)
kubectl scale deployment/api-backend --replicas=0 -n fintech

# Voir les Pods en temps réel pendant le scaling
kubectl get pods -n fintech -w

10.2 - Horizontal Pod Autoscaler (HPA) - Aperçu

Le HPA ajuste automatiquement le nombre de réplicas d'un Deployment en fonction de métriques observées (CPU, mémoire, métriques custom). Il nécessite le Metrics Server installé dans le cluster.

yaml hpa-api-backend.yaml 
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-backend-hpa
  namespace: fintech
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-backend
  minReplicas: 2                   # Minimum 2 Pods (haute disponibilité)
  maxReplicas: 10                  # Maximum 10 Pods
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70   # Scale up si CPU moyen > 70%
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80   # Scale up si mémoire moyenne > 80%
bash Commandes HPA 
# Créer un HPA rapidement via la CLI
kubectl autoscale deployment api-backend \
  --min=2 --max=10 --cpu-percent=70 -n fintech

# Voir le statut du HPA
kubectl get hpa -n fintech
# NAME              REFERENCE              TARGETS   MINPODS   MAXPODS   REPLICAS   AGE
# api-backend-hpa   Deployment/api-backend  45%/70%   2         10        3          1h

# Détails du HPA
kubectl describe hpa api-backend-hpa -n fintech
Attention : Le HPA ne fonctionne que si vous avez défini des resources.requests sur vos containers. Sans requests, Kubernetes ne peut pas calculer le pourcentage d'utilisation. Le Metrics Server doit aussi être installé : minikube addons enable metrics-server (sur Minikube).

11 - Erreurs courantes

Utiliser un Deployment pour une base de données - Un Deployment traite les Pods comme interchangeables. Si le Pod PostgreSQL est recréé, il perd son volume et ses données. Les bases de données nécessitent un StatefulSet avec volumeClaimTemplates pour garantir la persistance.
Utiliser le tag :latest pour les images - Le tag :latest est mutable et non déterministe. Deux kubectl apply successifs peuvent déployer des versions différentes. Utilisez toujours un tag de version explicite (api-backend:2.1.0) pour garantir la reproductibilité et permettre les rollbacks.
Ne pas définir de resource requests et limits - Sans requests, le Scheduler ne peut pas placer intelligemment les Pods. Sans limits, un Pod peut consommer toutes les ressources d'un nœud et provoquer un OOMKill en cascade sur les autres Pods.
Ne pas configurer les probes de santé - Sans livenessProbe, Kubernetes ne détecte pas si votre application est bloquée (deadlock, boucle infinie). Sans readinessProbe, du trafic est envoyé à des Pods qui ne sont pas encore prêts, causant des erreurs 503.
Oublier le Headless Service pour un StatefulSet - Sans Headless Service, les Pods du StatefulSet n'ont pas d'identité réseau stable. Les autres composants ne peuvent pas les adresser individuellement. Le champ spec.serviceName du StatefulSet doit correspondre au nom du Headless Service.
Scaler un StatefulSet PostgreSQL sans réplication - Augmenter les réplicas d'un StatefulSet PostgreSQL ne crée pas automatiquement une réplication master-slave. Chaque nouveau Pod est indépendant. Pour la réplication PostgreSQL, utilisez un opérateur comme CloudNativePG ou Zalando Postgres Operator.

12 - Best practices

Toujours utiliser des tags d'image immutables - Utilisez le digest SHA256 ou des tags de version sémantique (ex : 2.1.0). Ne jamais utiliser :latest en production. Cela garantit que chaque déploiement est reproductible et que les rollbacks fonctionnent correctement.
Configurer les trois probes pour les applications web - startupProbe pour les applications lentes à démarrer (Spring Boot, JVM), livenessProbe pour détecter les blocages, readinessProbe pour contrôler le trafic entrant. Utilisez les endpoints Spring Boot Actuator : /actuator/health/liveness et /actuator/health/readiness.
Définir des resource requests ET limits - Les requests permettent au Scheduler de placer les Pods intelligemment. Les limits protègent contre les fuites mémoire et la surconsommation CPU. Commencez avec des valeurs conservatrices et ajustez en observant les métriques réelles.
Utiliser revisionHistoryLimit - Configurez le nombre de révisions conservées (par défaut 10). Cela contrôle combien d'anciens ReplicaSets sont gardés pour les rollbacks. En production, 5 à 10 révisions sont un bon compromis.
Séparer ConfigMaps et Secrets - Utilisez envFrom.configMapRef pour la configuration non sensible et env.valueFrom.secretKeyRef pour les données sensibles (mots de passe, tokens). Ne codez jamais les valeurs en dur dans le manifest du Deployment.
Utiliser des Pod Disruption Budgets (PDB) - Un PDB garantit qu'un nombre minimum de Pods reste disponible lors des opérations de maintenance (drain d'un nœud, mise à jour du cluster). Exemple : minAvailable: 2 assure que 2 Pods API restent toujours actifs.
Préférer les opérateurs pour les bases de données - Pour PostgreSQL, Redis, Kafka en production, utilisez des opérateurs Kubernetes dédiés (CloudNativePG, Redis Operator, Strimzi). Ils gèrent automatiquement la réplication, les backups, les failovers et les mises à jour.
