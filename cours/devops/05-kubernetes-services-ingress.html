Leçon 5 Section 2 - Kubernetes Core

Services & Ingress

Exposer vos applications - ClusterIP, NodePort, LoadBalancer et Ingress Controller.

1 - Pourquoi les Services ?

Dans Kubernetes, les Pods sont éphémères. Un Deployment peut recréer, supprimer ou déplacer un Pod à tout moment. Chaque fois qu'un Pod est recréé, il reçoit une nouvelle adresse IP. Si votre application Spring Boot communique directement avec l'IP d'un Pod PostgreSQL, cette connexion sera cassée dès que le Pod sera recréé.

C'est là qu'interviennent les Services : ils fournissent un point d'accès réseau stable vers un ensemble de Pods, quelles que soient leurs IP actuelles.

1.1 - Le mécanisme des label selectors

Un Service identifie les Pods cibles grâce aux label selectors. Le Service ne connaît pas les Pods individuellement - il connaît simplement les labels à rechercher. Le composant kube-proxy maintient les règles de routage réseau sur chaque nœud pour rediriger le trafic vers les Pods correspondants.

Fonctionnement interne : Quand un Service est créé, un objet Endpoints est automatiquement créé. Cet objet contient la liste des IP:port de tous les Pods qui correspondent au selector. Le controller endpoints surveille en permanence les Pods et met à jour cette liste lorsque des Pods apparaissent ou disparaissent.
yaml Relation Pod ↔ Service 
# Le Deployment crée des Pods avec le label app: api-backend
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-backend
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api-backend
  template:
    metadata:
      labels:
        app: api-backend          # ← Ce label est la clé
        version: "2.1.0"
    spec:
      containers:
        - name: api
          image: bmis/api-backend:2.1.0
          ports:
            - containerPort: 8080

---
# Le Service sélectionne les Pods via le même label
apiVersion: v1
kind: Service
metadata:
  name: api-backend-svc
spec:
  selector:
    app: api-backend              # ← Match avec le label du Pod
  ports:
    - port: 80                    # Port exposé par le Service
      targetPort: 8080            # Port du container
      protocol: TCP

Le Service api-backend-svc redirigera tout le trafic entrant sur le port 80 vers le port 8080 de l'un des 3 Pods. Le load balancing entre les réplicas est automatique (round-robin par défaut).

2 - ClusterIP - Communication interne

ClusterIP est le type de Service par défaut. Il attribue une adresse IP virtuelle interne au cluster, accessible uniquement depuis l'intérieur du cluster. C'est le type le plus utilisé pour la communication entre microservices.

2.1 - Exemple : Service Spring Boot interne

yaml clusterip-service.yaml 
apiVersion: v1
kind: Service
metadata:
  name: api-backend-svc
  namespace: fintech
  labels:
    app: api-backend
    tier: backend
spec:
  type: ClusterIP                     # Type par défaut
  selector:
    app: api-backend
  ports:
    - name: http
      port: 80                        # Port du Service
      targetPort: 8080                # Port du container Spring Boot
      protocol: TCP
    - name: actuator
      port: 8081                      # Port pour les métriques
      targetPort: 8081
      protocol: TCP

2.2 - Résolution DNS interne

Kubernetes intègre un serveur DNS (CoreDNS) qui enregistre automatiquement chaque Service. Un Pod peut accéder au Service en utilisant différents formats DNS :

bash Formats DNS Kubernetes 
# Format court (même namespace)
curl http://api-backend-svc

# Format avec namespace
curl http://api-backend-svc.fintech

# Format FQDN complet
curl http://api-backend-svc.fintech.svc.cluster.local

# Avec le port spécifique
curl http://api-backend-svc.fintech.svc.cluster.local:80/api/v1/accounts
Cas d'usage typique : Le backend Spring Boot communique avec PostgreSQL via un ClusterIP Service postgres-svc.fintech.svc.cluster.local:5432. La base de données n'a jamais besoin d'être exposée à l'extérieur du cluster - un ClusterIP est parfait pour ça.

3 - NodePort - Accès depuis l'extérieur (dev)

Un Service de type NodePort expose l'application sur un port statique de chaque nœud du cluster. Il ouvre un port dans la plage 30000-32767 sur tous les nœuds, permettant un accès externe via <NodeIP>:<NodePort>.

3.1 - YAML NodePort

yaml nodeport-service.yaml 
apiVersion: v1
kind: Service
metadata:
  name: api-backend-nodeport
  namespace: fintech
spec:
  type: NodePort
  selector:
    app: api-backend
  ports:
    - name: http
      port: 80                        # Port interne du Service
      targetPort: 8080                # Port du container
      nodePort: 31080                 # Port ouvert sur chaque nœud (30000-32767)
      protocol: TCP
bash Accéder via NodePort 
# Accès depuis l'extérieur du cluster
curl http://192.168.1.100:31080/api/v1/health

# Minikube - ouvrir automatiquement dans le navigateur
minikube service api-backend-nodeport -n fintech

# Obtenir l'URL du service dans minikube
minikube service api-backend-nodeport -n fintech --url
NodePort n'est PAS pour la production : Les ports dans la plage 30000-32767 ne sont pas standards (pas de port 80/443), il n'y a pas de TLS natif, pas de load balancing intelligent, et chaque nœud expose le port (surface d'attaque élargie). Utilisez NodePort uniquement en développement local avec Minikube ou Kind.

4 - LoadBalancer - Production externe

Le type LoadBalancer demande au fournisseur cloud de provisionner un load balancer externe. C'est le moyen standard d'exposer un service individuel directement sur Internet avec une IP publique.

4.1 - YAML LoadBalancer

yaml loadbalancer-service.yaml 
apiVersion: v1
kind: Service
metadata:
  name: api-backend-lb
  namespace: fintech
  annotations:
    # Annotations spécifiques au cloud provider
    service.beta.kubernetes.io/aws-load-balancer-type: "nlb"
    service.beta.kubernetes.io/aws-load-balancer-scheme: "internet-facing"
    service.beta.kubernetes.io/aws-load-balancer-cross-zone-load-balancing-enabled: "true"
spec:
  type: LoadBalancer
  selector:
    app: api-backend
  ports:
    - name: http
      port: 80
      targetPort: 8080
      protocol: TCP
    - name: https
      port: 443
      targetPort: 8443
      protocol: TCP
bash Vérifier le LoadBalancer 
# Vérifier l'IP externe assignée
kubectl get svc api-backend-lb -n fintech

# Résultat typique sur AWS :
# NAME             TYPE           CLUSTER-IP     EXTERNAL-IP
# api-backend-lb   LoadBalancer   10.96.45.12    a1b2c3-abc.eu-west-1.elb.amazonaws.com

# Attendre que l'IP soit assignée (peut prendre 1-2 minutes)
kubectl get svc api-backend-lb -n fintech -w
Intégration cloud : Sur AWS, un Service LoadBalancer crée un ELB (Elastic Load Balancer) ou NLB (Network Load Balancer). Sur GCP, il crée un Google Cloud Load Balancer. Sur Azure, un Azure Load Balancer. Chaque load balancer a un coût mensuel - c'est pourquoi on préfère utiliser un seul Ingress Controller plutôt qu'un LoadBalancer par service.

6 - Headless Service

Un Headless Service est un Service sans ClusterIP (clusterIP: None). Au lieu de fournir une IP virtuelle unique, il retourne directement les adresses IP de chaque Pod individuel via des enregistrements DNS de type A.

C'est essentiel pour les StatefulSets où chaque Pod a une identité unique et doit être adressé individuellement (par exemple, un cluster PostgreSQL avec un primary et des replicas).

6.1 - YAML Headless Service pour PostgreSQL

yaml headless-postgres.yaml 
apiVersion: v1
kind: Service
metadata:
  name: postgres-headless
  namespace: fintech
  labels:
    app: postgres
spec:
  clusterIP: None                     # ← Headless !
  selector:
    app: postgres
  ports:
    - name: postgresql
      port: 5432
      targetPort: 5432
      protocol: TCP

---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
  namespace: fintech
spec:
  serviceName: postgres-headless      # ← Référence au Headless Service
  replicas: 3
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
        - name: postgres
          image: postgres:16-alpine
          ports:
            - containerPort: 5432
          env:
            - name: POSTGRES_DB
              value: fintech_db
            - name: POSTGRES_USER
              valueFrom:
                secretKeyRef:
                  name: postgres-credentials
                  key: username
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: postgres-credentials
                  key: password
          volumeMounts:
            - name: postgres-data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
    - metadata:
        name: postgres-data
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: gp3
        resources:
          requests:
            storage: 20Gi
bash DNS du Headless Service 
# Chaque Pod reçoit un DNS individuel stable :
# postgres-0.postgres-headless.fintech.svc.cluster.local
# postgres-1.postgres-headless.fintech.svc.cluster.local
# postgres-2.postgres-headless.fintech.svc.cluster.local

# Vérifier la résolution DNS depuis un Pod
kubectl exec -it debug-pod -- nslookup postgres-headless.fintech.svc.cluster.local

# Résultat : retourne les IP de CHAQUE Pod (pas une seule IP virtuelle)
# Name: postgres-headless.fintech.svc.cluster.local
# Address: 10.244.1.15
# Address: 10.244.2.23
# Address: 10.244.3.11
Quand utiliser un Headless Service ? Quand vos Pods ne sont pas interchangeables : clusters de bases de données (PostgreSQL, MySQL), caches distribués (Redis Cluster), brokers de messages (Kafka), ou tout StatefulSet nécessitant une identité stable par Pod.

7 - Ingress Controller

7.1 - Qu'est-ce qu'un Ingress ?

Un Ingress est une ressource Kubernetes qui gère le routage HTTP/HTTPS externe vers les Services internes du cluster. Il opère au Layer 7 (couche application du modèle OSI), ce qui lui permet de prendre des décisions de routage basées sur les noms d'hôte, les chemins URL, les en-têtes HTTP, et même les cookies.

7.2 - Pourquoi pas un LoadBalancer par service ?

Imaginez une architecture fintech avec 5 microservices, chacun exposé via un Service LoadBalancer :

  • Coût : 5 × ~20 $/mois = 100 $/mois rien qu'en load balancers
  • Complexité DNS : 5 IP publiques à gérer, 5 certificats TLS à maintenir
  • Pas de routage intelligent : Chaque LB est indépendant, impossible de router /api vers un service et /admin vers un autre

Avec un Ingress Controller, vous n'avez besoin que d'un seul LoadBalancer qui route intelligemment le trafic vers tous vos services internes.

7.3 - Controllers populaires

Controller Maintenu par Points forts
NGINX Ingress Controller Kubernetes Community Le plus utilisé, documentation riche, très stable
Traefik Traefik Labs Auto-discovery, dashboard intégré, Let's Encrypt natif
HAProxy Ingress HAProxy Technologies Haute performance, configuration avancée du load balancing
AWS ALB Ingress Amazon Intégration native AWS, utilise les ALB directement

7.4 - Installer NGINX Ingress Controller

bash Installation NGINX Ingress Controller 
# Méthode 1 : Installation via le manifeste officiel
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.10.1/deploy/static/provider/cloud/deploy.yaml

# Méthode 2 : Installation via Helm (recommandé en production)
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm repo update

helm install ingress-nginx ingress-nginx/ingress-nginx \
  --namespace ingress-nginx \
  --create-namespace \
  --set controller.replicaCount=2 \
  --set controller.resources.requests.memory=256Mi \
  --set controller.resources.requests.cpu=100m

# Vérifier l'installation
kubectl get pods -n ingress-nginx
kubectl get svc -n ingress-nginx

# Résultat attendu :
# NAME                                    TYPE           CLUSTER-IP     EXTERNAL-IP
# ingress-nginx-controller                LoadBalancer   10.96.12.45    203.0.113.50

# Pour Minikube - activer l'addon Ingress
minikube addons enable ingress

8 - Ingress Resource - Exemples complets

8.1 - Routage basé sur l'hôte (Host-based)

Chaque sous-domaine est routé vers un Service différent :

yaml ingress-host-based.yaml 
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: bmis-host-routing
  namespace: fintech
  annotations:
    nginx.ingress.kubernetes.io/proxy-body-size: "10m"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "60"
spec:
  ingressClassName: nginx
  rules:
    - host: api.bmis.cm
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: api-backend-svc
                port:
                  number: 80

    - host: admin.bmis.cm
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: admin-frontend-svc
                port:
                  number: 80

    - host: partner.bmis.cm
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: partner-frontend-svc
                port:
                  number: 80

8.2 - Routage basé sur le chemin (Path-based)

Différents chemins URL sont routés vers différents Services sur le même hôte :

yaml ingress-path-based.yaml 
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: bmis-path-routing
  namespace: fintech
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$2
    nginx.ingress.kubernetes.io/use-regex: "true"
spec:
  ingressClassName: nginx
  rules:
    - host: api.example.com
      http:
        paths:
          # /v1/* → Service Spring Boot principal
          - path: /v1(/|$)(.*)
            pathType: ImplementationSpecific
            backend:
              service:
                name: spring-boot-svc
                port:
                  number: 80

          # /admin/* → Application Angular d'administration
          - path: /admin(/|$)(.*)
            pathType: ImplementationSpecific
            backend:
              service:
                name: angular-admin-svc
                port:
                  number: 80

          # /docs/* → Documentation Swagger
          - path: /docs(/|$)(.*)
            pathType: ImplementationSpecific
            backend:
              service:
                name: swagger-ui-svc
                port:
                  number: 8080

8.3 - Terminaison TLS avec cert-manager

La terminaison TLS est gérée au niveau de l'Ingress. cert-manager automatise l'obtention et le renouvellement des certificats Let's Encrypt.

bash Installation cert-manager 
# Installer cert-manager via Helm
helm repo add jetstack https://charts.jetstack.io
helm repo update

helm install cert-manager jetstack/cert-manager \
  --namespace cert-manager \
  --create-namespace \
  --set installCRDs=true
yaml clusterissuer-letsencrypt.yaml 
# ClusterIssuer pour Let's Encrypt (production)
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: devops@bmis.cm
    privateKeySecretRef:
      name: letsencrypt-prod-key
    solvers:
      - http01:
          ingress:
            class: nginx
yaml ingress-tls.yaml 
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: bmis-tls-ingress
  namespace: fintech
  annotations:
    cert-manager.io/cluster-issuer: "letsencrypt-prod"
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/force-ssl-redirect: "true"
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - api.bmis.cm
        - admin.bmis.cm
      secretName: bmis-tls-secret         # cert-manager crée ce Secret automatiquement
  rules:
    - host: api.bmis.cm
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: api-backend-svc
                port:
                  number: 80
    - host: admin.bmis.cm
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: admin-frontend-svc
                port:
                  number: 80

9 - Architecture du routage fintech

Voici comment le système fintech BMIS utilise Ingress pour router le trafic vers les différentes applications. Un seul Ingress Controller (NGINX) gère tout le trafic entrant, avec terminaison TLS et routage intelligent.

9.1 - Schéma du routage

Flux de trafic :
Internet → DNS (CloudFlare) → LoadBalancer (NGINX Ingress) → Routage par host :
• api.bmis.cm → Service api-backend-svc → Pods Spring Boot (3 réplicas)
• admin.bmis.cm → Service admin-frontend-svc → Pods Angular Admin (2 réplicas)
• partner.bmis.cm → Service partner-frontend-svc → Pods Angular Partner (2 réplicas)

10 - ExternalName Service

Un Service de type ExternalName crée un alias DNS vers un service externe au cluster. Aucun proxy n'est créé - c'est un simple CNAME DNS. C'est utile pour mapper des services managés (AWS RDS, ElastiCache, etc.) dans le DNS interne de Kubernetes.

yaml externalname-rds.yaml 
# Mapper un service RDS externe dans le DNS Kubernetes
apiVersion: v1
kind: Service
metadata:
  name: postgres-external
  namespace: fintech
spec:
  type: ExternalName
  externalName: fintech-db.abc123xyz.eu-west-1.rds.amazonaws.com
yaml spring-boot-config.yaml - Utilisation 
# Dans la config Spring Boot, utilisez le nom du Service Kubernetes
# au lieu de l'URL RDS complète
spring:
  datasource:
    url: jdbc:postgresql://postgres-external.fintech.svc.cluster.local:5432/fintech_db
    # Si vous migrez vers un PostgreSQL interne plus tard,
    # changez uniquement le Service - pas la config applicative
Avantage : Vos applications référencent toujours un nom de Service Kubernetes. Si vous migrez d'un RDS externe vers un PostgreSQL hébergé dans le cluster, il suffit de changer le type du Service de ExternalName à ClusterIP - aucune modification du code applicatif n'est nécessaire.

11 - Debugging des Services

Quand un Service ne fonctionne pas comme prévu, voici les commandes de diagnostic essentielles :

11.1 - Vérifier les Endpoints

bash Diagnostic des Services 
# 1. Vérifier que le Service existe et a des endpoints
kubectl get endpoints api-backend-svc -n fintech

# Résultat OK :
# NAME              ENDPOINTS                                      AGE
# api-backend-svc   10.244.1.15:8080,10.244.2.23:8080,10.244.3.11:8080   5d

# Résultat PROBLÈME - pas d'endpoints :
# NAME              ENDPOINTS   AGE
# api-backend-svc         5d
# → Les labels du selector ne matchent aucun Pod !

11.2 - Décrire le Service

bash Describe et Port-forward 
# 2. Détails complets du Service
kubectl describe service api-backend-svc -n fintech

# 3. Vérifier les labels des Pods
kubectl get pods -n fintech --show-labels

12 - Erreurs courantes

Selector qui ne matche aucun Pod - L'erreur la plus fréquente. Le label dans le selector du Service (app: api-backend) doit correspondre exactement aux labels définis dans le template.metadata.labels du Deployment. Une simple faute de frappe suffit pour que le Service n'ait aucun endpoint.
targetPort incorrect - Le targetPort du Service doit correspondre au containerPort du Pod. Si votre Spring Boot écoute sur 8080 mais que le Service pointe vers 80, aucune connexion ne passera.
Utiliser NodePort en production - Les ports non-standards (30000+), l'absence de TLS, et l'exposition sur chaque nœud font de NodePort un choix inadapté à la production. Utilisez un Ingress Controller avec TLS.
Oublier les health checks - Sans readinessProbe, Kubernetes enverra du trafic vers des Pods qui ne sont pas encore prêts (démarrage Spring Boot). Le Service ajoutera le Pod aux endpoints dès qu'il est Running, même si l'application n'a pas fini de démarrer.
Pas de resource requests/limits - Un Pod sans limites de ressources peut consommer toute la mémoire d'un nœud et provoquer des OOMKills en cascade sur les autres Pods du même nœud.
Ignorer les logs de l'Ingress Controller - Les erreurs 502/503/504 sont souvent liées à des problèmes de routage, de timeout ou de backend indisponible. Consultez toujours les logs du controller NGINX pour comprendre les erreurs HTTP.

13 - Best practices

Utiliser ClusterIP par défaut - La grande majorité des Services n'ont pas besoin d'être exposés à l'extérieur du cluster. Les bases de données, caches et services internes doivent rester en ClusterIP. Seul le trafic entrant passe par l'Ingress Controller.
Un seul Ingress Controller pour tout le cluster - Évitez de multiplier les LoadBalancers. Un seul Ingress Controller NGINX avec plusieurs ressources Ingress est plus économique, plus simple à gérer et plus sécurisé.
Automatiser les certificats TLS avec cert-manager - Ne gérez jamais les certificats manuellement. cert-manager + Let's Encrypt renouvelle automatiquement les certificats 30 jours avant leur expiration.
Nommer les ports dans les Services - Utilisez toujours l'attribut name dans la définition des ports (name: http, name: grpc). C'est requis si le Service expose plusieurs ports, et c'est une bonne pratique même avec un seul port.
Configurer les readinessProbes sur tous les Pods exposés - Le readinessProbe garantit que seuls les Pods réellement prêts reçoivent du trafic. Pour Spring Boot, utilisez /actuator/health/readiness.
Activer le rate limiting sur l'Ingress - Protégez vos APIs contre les abus en configurant limit-rps et limit-burst-multiplier dans les annotations NGINX Ingress. Pour les APIs financières, c'est critique.
Ajouter les en-têtes de sécurité - Configurez les en-têtes HTTP de sécurité (X-Frame-Options, X-Content-Type-Options, Strict-Transport-Security) au niveau de l'Ingress via les annotations server-snippets.
Surveiller les métriques de l'Ingress Controller - NGINX Ingress expose des métriques Prometheus. Configurez des alertes sur le taux d'erreurs 5xx, la latence P99 et le nombre de connexions actives.
