Leçon 7 Section 2 - Kubernetes Core

Persistent Volumes & Namespaces

Stockage persistant et isolation des environnements - deux concepts essentiels pour la production.

1 - Le défi du stockage dans Kubernetes

Les Pods sont éphémères. Quand un Pod est supprimé, recréé ou déplacé vers un autre nœud, tout ce qui se trouve dans son système de fichiers est perdu définitivement. C'est le comportement par défaut de Kubernetes, et c'est un problème majeur pour toute application qui stocke des données : bases de données, fichiers uploadés, caches persistants, logs applicatifs.

Imaginez une base de données PostgreSQL qui s'exécute dans un Pod. Sans stockage persistant, chaque redémarrage du Pod signifie la perte totale de toutes les données - utilisateurs, transactions, historiques. C'est évidemment inacceptable en production.

1.1 - Différence avec Docker

Avec Docker, les volumes résolvent ce problème simplement : un volume Docker est monté depuis l'hôte vers le conteneur, et les données persistent même si le conteneur est supprimé. Cependant, Docker fonctionne sur une seule machine.

Kubernetes orchestre des conteneurs sur plusieurs nœuds. Un Pod peut être reprogrammé sur un nœud complètement différent. Le volume Docker local du nœud A n'est pas accessible depuis le nœud B. C'est pourquoi Kubernetes a besoin d'un système de stockage plus sophistiqué : les Persistent Volumes.

Le cycle de vie est découplé : Dans Kubernetes, le stockage a son propre cycle de vie, indépendant du Pod. Un PersistentVolume existe avant le Pod, et continue d'exister après sa suppression. C'est la clé de la persistance des données.

1.2 - Les types de volumes éphémères

Avant de plonger dans les volumes persistants, notons que Kubernetes offre aussi des volumes éphémères utiles :

yaml Volumes éphémères - emptyDir et configMap 
# emptyDir : volume temporaire partagé entre les conteneurs d'un même Pod
# Les données sont perdues quand le Pod est supprimé
spec:
  containers:
    - name: app
      volumeMounts:
        - name: cache-volume
          mountPath: /tmp/cache
    - name: sidecar-logger
      volumeMounts:
        - name: cache-volume
          mountPath: /var/log/app
  volumes:
    - name: cache-volume
      emptyDir: {}          # Créé vide, détruit avec le Pod

emptyDir est utile pour le partage de fichiers temporaires entre conteneurs d'un même Pod (pattern sidecar). Mais pour la persistance réelle, il faut passer aux PersistentVolumes.

2 - PersistentVolume (PV)

Un PersistentVolume est une ressource de stockage au niveau du cluster, provisionnée par un administrateur ou dynamiquement par une StorageClass. C'est un « morceau » de stockage dans le cluster qui a un cycle de vie indépendant de tout Pod individuel.

2.1 - Manifest YAML d'un PersistentVolume

yaml pv-example.yaml 
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-postgres-data
  labels:
    type: local
    app: postgresql
spec:
  capacity:
    storage: 20Gi                      # Taille du volume
  accessModes:
    - ReadWriteOnce                    # Un seul nœud en lecture/écriture
  persistentVolumeReclaimPolicy: Retain # Politique de réclamation
  storageClassName: manual             # Classe de stockage
  hostPath:                            # Type de stockage (dev uniquement !)
    path: /data/postgres               # Chemin sur le nœud hôte

2.2 - Access Modes

Les accessModes définissent comment le volume peut être monté par les nœuds :

Mode Abréviation Description Cas d'usage
ReadWriteOnce RWO Lecture/écriture par un seul nœud Base de données (PostgreSQL, MySQL)
ReadOnlyMany ROX Lecture seule par plusieurs nœuds Fichiers de configuration, assets statiques
ReadWriteMany RWX Lecture/écriture par plusieurs nœuds Fichiers partagés (uploads, documents KYC)
Attention : Tous les types de stockage ne supportent pas tous les modes. Par exemple, AWS EBS ne supporte que ReadWriteOnce. Pour ReadWriteMany, il faut utiliser un stockage réseau comme NFS, EFS (AWS), ou Azure Files.

2.3 - Reclaim Policies

La reclaim policy détermine ce qui arrive au PersistentVolume quand le PersistentVolumeClaim associé est supprimé :

Politique Comportement Usage recommandé
Retain Le PV est conservé avec ses données. L'administrateur doit le nettoyer manuellement. Production - données critiques
Delete Le PV et le stockage sous-jacent sont supprimés automatiquement. Environnements temporaires (dev, test)
Recycle Le contenu est effacé (rm -rf /volume/*) et le PV est rendu disponible. Déprécié. Ne plus utiliser

2.4 - Types de stockage backend

Le spec d'un PV spécifie le type de stockage sous-jacent. Voici les principaux :

yaml Exemples de backends de stockage 
# ❌ hostPath - Développement UNIQUEMENT (données sur le nœud local)
spec:
  hostPath:
    path: /data/postgres

# ✅ NFS - Stockage réseau partagé
spec:
  nfs:
    server: 192.168.1.100
    path: /exports/postgres-data

# ✅ AWS EBS (Elastic Block Store)
spec:
  awsElasticBlockStore:
    volumeID: vol-0a1b2c3d4e5f67890
    fsType: ext4

# ✅ GCE Persistent Disk
spec:
  gcePersistentDisk:
    pdName: postgres-disk
    fsType: ext4

# ✅ Azure Disk
spec:
  azureDisk:
    diskName: postgres-disk
    diskURI: /subscriptions/.../postgres-disk
Ne jamais utiliser hostPath en production ! Les données sont liées à un seul nœud. Si le Pod est reprogrammé sur un autre nœud, les données ne suivent pas. hostPath est uniquement pour le développement local avec Minikube ou Kind.

3 - PersistentVolumeClaim (PVC)

Un PersistentVolumeClaim est une demande de stockage par un utilisateur ou une application. C'est l'interface entre le Pod (qui a besoin de stockage) et le PersistentVolume (qui fournit le stockage). Le PVC décrit ce dont l'application a besoin - taille, mode d'accès, classe de stockage - et Kubernetes trouve un PV correspondant.

3.1 - Manifest YAML d'un PVC

yaml pvc-postgres.yaml 
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-pvc
  namespace: fintech
spec:
  accessModes:
    - ReadWriteOnce             # Doit correspondre au PV
  resources:
    requests:
      storage: 20Gi             # Taille demandée (≤ capacité du PV)
  storageClassName: manual       # Doit correspondre au PV

3.2 - Comment le PVC se lie au PV

Quand un PVC est créé, Kubernetes cherche un PV qui satisfait les critères :

  1. La capacité du PV est ≥ à la demande du PVC
  2. L'accessMode du PV correspond à celui du PVC
  3. La storageClassName correspond
  4. Le PV est dans l'état Available (non lié à un autre PVC)

Une fois lié, le PVC passe en état Bound et le PV ne peut plus être utilisé par un autre PVC. La relation est 1:1.

bash Vérifier l'état de liaison 
# Voir l'état des PV
kubectl get pv
# NAME              CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS   CLAIM
# pv-postgres-data  20Gi       RWO            Retain           Bound    fintech/postgres-pvc

# Voir l'état des PVC
kubectl get pvc -n fintech
# NAME           STATUS   VOLUME            CAPACITY   ACCESS MODES   STORAGECLASS
# postgres-pvc   Bound    pv-postgres-data  20Gi       RWO            manual

3.3 - Utiliser un PVC dans un Pod / Deployment

Une fois le PVC créé et lié, on le monte dans un Pod via volumes et volumeMounts :

yaml deployment-postgres-avec-pvc.yaml 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: postgresql
  namespace: fintech
spec:
  replicas: 1                         # Base de données : 1 seule réplica
  selector:
    matchLabels:
      app: postgresql
  template:
    metadata:
      labels:
        app: postgresql
    spec:
      containers:
        - name: postgresql
          image: postgres:16-alpine
          ports:
            - containerPort: 5432
          env:
            - name: POSTGRES_DB
              value: fintech_db
            - name: POSTGRES_USER
              valueFrom:
                secretKeyRef:
                  name: postgres-secret
                  key: username
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: postgres-secret
                  key: password
          volumeMounts:
            - name: postgres-storage
              mountPath: /var/lib/postgresql/data  # Répertoire de données PostgreSQL
              subPath: pgdata                      # Sous-répertoire (évite les conflits)
          resources:
            requests:
              cpu: 250m
              memory: 512Mi
            limits:
              cpu: "1"
              memory: 1Gi
      volumes:
        - name: postgres-storage
          persistentVolumeClaim:
            claimName: postgres-pvc                # Référence au PVC
Le subPath est important pour PostgreSQL : PostgreSQL exige que le répertoire de données soit vide ou contienne une base valide. Certains types de volume créent un dossier lost+found à la racine. Le subPath: pgdata monte le volume dans un sous-répertoire propre, évitant ce conflit.

4 - StorageClass - Provisionnement dynamique

Créer manuellement des PersistentVolumes avant chaque PVC est fastidieux et ne passe pas à l'échelle. C'est là qu'interviennent les StorageClasses : elles permettent le provisionnement dynamique - Kubernetes crée automatiquement un PV quand un PVC le demande.

4.1 - Qu'est-ce que le provisionnement dynamique ?

Avec le provisionnement dynamique :

  1. L'administrateur crée une StorageClass qui décrit le type de stockage disponible
  2. L'utilisateur crée un PVC qui référence cette StorageClass
  3. Kubernetes appelle automatiquement le provisioner de la StorageClass pour créer un PV
  4. Le PV est automatiquement lié au PVC

Plus besoin de pré-provisionner des PV manuellement. Le workflow devient : StorageClass → PVC → PV (auto) → Pod.

4.2 - StorageClass pour différents providers

yaml storageclass-aws-gp3.yaml 
# AWS EBS gp3 - Stockage SSD haute performance
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: ebs.csi.aws.com          # Provisioner CSI pour AWS EBS
parameters:
  type: gp3                           # Type de volume EBS
  iops: "3000"                        # IOPS provisionnées
  throughput: "125"                    # Mo/s
  encrypted: "true"                   # Chiffrement au repos
reclaimPolicy: Retain                  # Conserver les données en production
allowVolumeExpansion: true             # Permettre l'extension de volume
volumeBindingMode: WaitForFirstConsumer # Lier au moment du scheduling
yaml storageclass-gce-ssd.yaml 
# GCE Persistent Disk SSD
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: pd.csi.storage.gke.io    # Provisioner CSI pour GCE
parameters:
  type: pd-ssd                        # SSD persistant
reclaimPolicy: Retain
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
yaml storageclass-local-path.yaml (développement) 
# Rancher local-path - Développement local (Kind, k3s)
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: local-path
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"  # StorageClass par défaut
provisioner: rancher.io/local-path
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer

4.3 - PVC avec StorageClass (provisionnement dynamique)

Le PVC référence simplement la StorageClass. Kubernetes s'occupe du reste :

yaml pvc-dynamique.yaml 
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
  namespace: fintech
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: fast-ssd           # Référence la StorageClass
  resources:
    requests:
      storage: 50Gi                    # Taille demandée
# → Kubernetes crée automatiquement un PV de 50Gi avec un volume EBS gp3

4.4 - StorageClass par défaut

Si un PVC ne spécifie pas de storageClassName, Kubernetes utilise la StorageClass par défaut du cluster. Celle-ci est marquée par l'annotation storageclass.kubernetes.io/is-default-class: "true".

bash Voir la StorageClass par défaut 
# Lister les StorageClasses - celle avec (default) est la classe par défaut
kubectl get storageclass
# NAME                   PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE
# fast-ssd               ebs.csi.aws.com         Retain          WaitForFirstConsumer
# standard (default)     kubernetes.io/aws-ebs   Delete          Immediate
Toujours utiliser le provisionnement dynamique en production. Les StorageClasses automatisent la création de volumes, garantissent la cohérence de la configuration (chiffrement, type de disque, IOPS), et évitent les erreurs humaines. Le provisionnement statique (PV manuels) devrait être réservé aux cas très spécifiques (stockage existant à importer).

5 - Volumes dans notre système fintech

Notre système fintech a plusieurs composants qui nécessitent du stockage persistant. Voici les manifests complets pour chaque besoin :

5.1 - PostgreSQL - Données de la base

La base de données est le composant le plus critique. Les données des comptes, transactions et utilisateurs doivent absolument survivre aux redémarrages :

yaml postgres-storage.yaml 
---
# StorageClass pour les bases de données (SSD haute performance)
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: db-fast-ssd
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
  iops: "5000"
  throughput: "250"
  encrypted: "true"
reclaimPolicy: Retain
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
---
# PVC pour PostgreSQL
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
  namespace: bmis-prod
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: db-fast-ssd
  resources:
    requests:
      storage: 100Gi

5.2 - Redis - Persistance du cache

Redis est utilisé comme cache et broker de messages. Même si les données peuvent être reconstituées, la persistance évite un cache froid après chaque redémarrage :

yaml redis-storage.yaml 
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: redis-data
  namespace: bmis-prod
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: db-fast-ssd
  resources:
    requests:
      storage: 10Gi
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: redis
  namespace: bmis-prod
spec:
  replicas: 1
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
    spec:
      containers:
        - name: redis
          image: redis:7-alpine
          args: ["--appendonly", "yes"]   # Activer la persistance AOF
          ports:
            - containerPort: 6379
          volumeMounts:
            - name: redis-storage
              mountPath: /data
          resources:
            requests:
              cpu: 100m
              memory: 256Mi
            limits:
              cpu: 500m
              memory: 1Gi
      volumes:
        - name: redis-storage
          persistentVolumeClaim:
            claimName: redis-data

5.3 - Uploads de fichiers (documents KYC, images)

Les fichiers uploadés par les utilisateurs (documents KYC, pièces d'identité, justificatifs) doivent être accessibles par plusieurs Pods simultanément. On utilise ReadWriteMany avec un stockage réseau :

yaml uploads-storage.yaml 
---
# StorageClass pour les fichiers partagés (EFS sur AWS)
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: shared-files
provisioner: efs.csi.aws.com
parameters:
  provisioningMode: efs-ap
  fileSystemId: fs-0a1b2c3d4e5f67890
  directoryPerms: "700"
reclaimPolicy: Retain
---
# PVC pour les uploads - ReadWriteMany
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: kyc-uploads
  namespace: bmis-prod
spec:
  accessModes:
    - ReadWriteMany                    # Accessible par plusieurs Pods
  storageClassName: shared-files
  resources:
    requests:
      storage: 200Gi
---
# Deployment du service KYC avec le volume partagé
apiVersion: apps/v1
kind: Deployment
metadata:
  name: kyc-service
  namespace: bmis-prod
spec:
  replicas: 3                          # Plusieurs réplicas accèdent au même volume
  selector:
    matchLabels:
      app: kyc-service
  template:
    metadata:
      labels:
        app: kyc-service
    spec:
      containers:
        - name: kyc-service
          image: bmis/kyc-service:1.0.0
          ports:
            - containerPort: 8080
          volumeMounts:
            - name: uploads
              mountPath: /app/uploads
          resources:
            requests:
              cpu: 200m
              memory: 512Mi
            limits:
              cpu: "1"
              memory: 1Gi
      volumes:
        - name: uploads
          persistentVolumeClaim:
            claimName: kyc-uploads

6 - volumeClaimTemplates dans StatefulSet

Un StatefulSet gère les workloads avec état (bases de données, systèmes distribués). Contrairement à un Deployment, chaque Pod d'un StatefulSet a une identité stable et un stockage dédié. Le mécanisme clé est le volumeClaimTemplates : il crée automatiquement un PVC unique pour chaque Pod.

6.1 - PostgreSQL StatefulSet avec volumeClaimTemplates

yaml postgres-statefulset.yaml 
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgresql
  namespace: bmis-prod
spec:
  serviceName: postgresql-headless     # Service headless obligatoire
  replicas: 3                          # 3 instances PostgreSQL
  selector:
    matchLabels:
      app: postgresql
  template:
    metadata:
      labels:
        app: postgresql
    spec:
      containers:
        - name: postgresql
          image: postgres:16-alpine
          ports:
            - containerPort: 5432
              name: postgres
          env:
            - name: POSTGRES_DB
              value: fintech_db
            - name: PGDATA
              value: /var/lib/postgresql/data/pgdata
            - name: POSTGRES_USER
              valueFrom:
                secretKeyRef:
                  name: postgres-secret
                  key: username
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: postgres-secret
                  key: password
          volumeMounts:
            - name: postgres-data      # Correspond au volumeClaimTemplate
              mountPath: /var/lib/postgresql/data
          resources:
            requests:
              cpu: 500m
              memory: 1Gi
            limits:
              cpu: "2"
              memory: 4Gi
  volumeClaimTemplates:                # ← Crée un PVC par Pod
    - metadata:
        name: postgres-data            # Nom utilisé dans volumeMounts
      spec:
        accessModes:
          - ReadWriteOnce
        storageClassName: db-fast-ssd
        resources:
          requests:
            storage: 50Gi

Avec ce StatefulSet, Kubernetes crée automatiquement 3 PVC distincts :

bash PVC créés automatiquement 
kubectl get pvc -n bmis-prod
# NAME                          STATUS   VOLUME          CAPACITY   STORAGECLASS
# postgres-data-postgresql-0    Bound    pvc-abc123...   50Gi       db-fast-ssd
# postgres-data-postgresql-1    Bound    pvc-def456...   50Gi       db-fast-ssd
# postgres-data-postgresql-2    Bound    pvc-ghi789...   50Gi       db-fast-ssd

# Chaque Pod a son propre volume persistant :
# postgresql-0 → postgres-data-postgresql-0
# postgresql-1 → postgres-data-postgresql-1
# postgresql-2 → postgres-data-postgresql-2
Les PVC des StatefulSets ne sont pas supprimés automatiquement. Quand un StatefulSet est supprimé ou réduit, les PVC persistent. C'est une protection contre la perte de données. Il faut les supprimer manuellement si nécessaire : kubectl delete pvc postgres-data-postgresql-2 -n bmis-prod.

7 - Namespaces - Isolation logique

Un Namespace est une division logique du cluster Kubernetes. Il permet de séparer les ressources (Pods, Services, Deployments, ConfigMaps, Secrets, PVC) en groupes isolés au sein du même cluster physique. C'est l'équivalent de « dossiers » dans un système de fichiers, mais pour les objets Kubernetes.

7.1 - Pourquoi les Namespaces ?

Sans namespaces, toutes les ressources cohabitent dans le même espace. Avec des dizaines de microservices, des environnements de dev/staging/prod, et plusieurs équipes, cela devient rapidement ingérable. Les namespaces apportent :

  • Isolation des environnements - dev, staging et prod dans le même cluster
  • Séparation des équipes - chaque équipe travaille dans son namespace
  • Quotas de ressources - limiter les ressources CPU/mémoire par namespace
  • Politiques réseau - contrôler la communication entre namespaces
  • RBAC - droits d'accès différenciés par namespace

7.2 - Namespaces par défaut

Chaque cluster Kubernetes est créé avec 4 namespaces par défaut :

Namespace Description
default Namespace par défaut pour les ressources sans namespace explicite
kube-system Composants système de Kubernetes (kube-dns, kube-proxy, etcd, scheduler)
kube-public Ressources accessibles publiquement (rarement utilisé)
kube-node-lease Objets Lease pour la détection de santé des nœuds

7.3 - Créer et utiliser des Namespaces

bash Commandes kubectl pour les namespaces 
# Créer un namespace avec kubectl
kubectl create namespace bmis-dev
kubectl create namespace bmis-staging
kubectl create namespace bmis-prod

# Lister les namespaces
kubectl get namespaces
# NAME              STATUS   AGE
# default           Active   30d
# kube-system       Active   30d
# kube-public       Active   30d
# kube-node-lease   Active   30d
# bmis-dev          Active   5s
# bmis-staging      Active   4s
# bmis-prod         Active   3s

# Définir le namespace par défaut pour kubectl
kubectl config set-context --current --namespace=bmis-prod

# Voir les Pods d'un namespace spécifique
kubectl get pods -n bmis-staging

# Voir les Pods de TOUS les namespaces
kubectl get pods --all-namespaces
kubectl get pods -A              # Raccourci

7.4 - Manifest YAML d'un Namespace

yaml namespace-prod.yaml 
apiVersion: v1
kind: Namespace
metadata:
  name: bmis-prod
  labels:
    environment: production
    team: bmis
    project: fintech
bash Appliquer le namespace 
kubectl apply -f namespace-prod.yaml
# namespace/bmis-prod created

8 - Namespaces pour notre système

Dans notre système fintech BMIS, nous utilisons les namespaces pour séparer les environnements de déploiement. Chaque environnement a son propre namespace avec ses propres ressources, configurations et secrets :

8.1 - Structure des namespaces

yaml namespaces.yaml 
---
apiVersion: v1
kind: Namespace
metadata:
  name: bmis-dev
  labels:
    environment: development
    team: bmis
---
apiVersion: v1
kind: Namespace
metadata:
  name: bmis-staging
  labels:
    environment: staging
    team: bmis
---
apiVersion: v1
kind: Namespace
metadata:
  name: bmis-prod
  labels:
    environment: production
    team: bmis

8.2 - Déployer la même application dans différents namespaces

Le même manifest peut être déployé dans différents namespaces en changeant simplement le champ namespace ou en utilisant le flag -n :

bash Déploiement multi-environnement 
# Déployer en dev
kubectl apply -f deployment.yaml -n bmis-dev

# Déployer en staging
kubectl apply -f deployment.yaml -n bmis-staging

# Déployer en production
kubectl apply -f deployment.yaml -n bmis-prod

# Voir les Pods dans chaque environnement
kubectl get pods -n bmis-dev
kubectl get pods -n bmis-staging
kubectl get pods -n bmis-prod

8.3 - Communication inter-namespace

Par défaut, les Pods de différents namespaces peuvent communiquer entre eux. Un Service est accessible depuis un autre namespace via son nom DNS complet (FQDN) :

yaml Communication cross-namespace 
# Format DNS complet pour accéder à un Service d'un autre namespace :
# <service-name>.<namespace>.svc.cluster.local

# Exemples dans notre système :
# Depuis bmis-dev, accéder au PostgreSQL de bmis-prod :
spring:
  datasource:
    url: jdbc:postgresql://postgresql.bmis-prod.svc.cluster.local:5432/fintech_db

# Depuis n'importe quel namespace, accéder au cache Redis de bmis-prod :
spring:
  redis:
    host: redis.bmis-prod.svc.cluster.local
    port: 6379

# Dans le même namespace, le nom court suffit :
spring:
  datasource:
    url: jdbc:postgresql://postgresql:5432/fintech_db
DNS interne Kubernetes : Chaque Service obtient une entrée DNS automatique au format <service>.<namespace>.svc.cluster.local. Dans le même namespace, le nom court (postgresql) suffit. Pour la communication cross-namespace, utilisez toujours le FQDN.

9 - Resource Quotas par namespace

Les Resource Quotas permettent de limiter la quantité totale de ressources qu'un namespace peut consommer. C'est essentiel pour empêcher un environnement de dev gourmand de monopoliser les ressources du cluster au détriment de la production.

9.1 - ResourceQuota

yaml resourcequota-staging.yaml 
apiVersion: v1
kind: ResourceQuota
metadata:
  name: staging-quota
  namespace: bmis-staging
spec:
  hard:
    # Limites de calcul
    requests.cpu: "4"                  # Total CPU demandé max : 4 cores
    requests.memory: 8Gi              # Total mémoire demandée max : 8 Gi
    limits.cpu: "8"                   # Total CPU limité max : 8 cores
    limits.memory: 16Gi              # Total mémoire limitée max : 16 Gi

    # Limites d'objets
    pods: "20"                        # Maximum 20 Pods dans ce namespace
    services: "10"                    # Maximum 10 Services
    persistentvolumeclaims: "5"       # Maximum 5 PVC
    configmaps: "20"                  # Maximum 20 ConfigMaps
    secrets: "20"                     # Maximum 20 Secrets

    # Limites de stockage
    requests.storage: 100Gi           # Total stockage PVC max : 100 Gi

9.2 - LimitRange

Tandis que le ResourceQuota limite le total du namespace, le LimitRange définit les limites par conteneur ou Pod individuel. Il impose des minimums, maximums et valeurs par défaut :

yaml limitrange-staging.yaml 
apiVersion: v1
kind: LimitRange
metadata:
  name: staging-limits
  namespace: bmis-staging
spec:
  limits:
    - type: Container
      default:                         # Limites par défaut (si non spécifiées dans le Pod)
        cpu: 500m
        memory: 512Mi
      defaultRequest:                  # Requests par défaut
        cpu: 100m
        memory: 128Mi
      max:                             # Maximum par conteneur
        cpu: "2"
        memory: 4Gi
      min:                             # Minimum par conteneur
        cpu: 50m
        memory: 64Mi
    - type: PersistentVolumeClaim
      max:
        storage: 50Gi                  # PVC max 50 Gi en staging
      min:
        storage: 1Gi                   # PVC min 1 Gi
LimitRange et ResourceQuota sont complémentaires : Le LimitRange garantit que chaque conteneur a des limites raisonnables (empêche un seul Pod de tout consommer). Le ResourceQuota garantit que le namespace entier reste dans ses limites. En production, utilisez toujours les deux ensemble.

10 - Kustomize pour la gestion multi-environnement

Kustomize est un outil intégré à kubectl qui permet de personnaliser les manifests Kubernetes sans les dupliquer. Au lieu de copier les mêmes fichiers YAML pour chaque environnement et modifier quelques valeurs, Kustomize utilise un système de base + overlays.

10.1 - Structure de dossiers

bash Arborescence Kustomize 
k8s/
├── base/                          # Manifests communs à tous les environnements
│   ├── kustomization.yaml
│   ├── deployment.yaml
│   ├── service.yaml
│   └── configmap.yaml
└── overlays/                      # Personnalisations par environnement
    ├── dev/
    │   ├── kustomization.yaml
    │   ├── namespace.yaml
    │   └── replica-patch.yaml
    ├── staging/
    │   ├── kustomization.yaml
    │   ├── namespace.yaml
    │   └── resource-patch.yaml
    └── prod/
        ├── kustomization.yaml
        ├── namespace.yaml
        ├── replica-patch.yaml
        └── resource-patch.yaml

10.2 - Fichiers Kustomize

yaml k8s/base/kustomization.yaml 
# Base - ressources communes
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - deployment.yaml
  - service.yaml
  - configmap.yaml
commonLabels:
  app: bmis-api
  managed-by: kustomize
yaml k8s/overlays/prod/kustomization.yaml 
# Overlay Production
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base                        # Référence vers la base
  - namespace.yaml
namespace: bmis-prod                  # Applique le namespace à toutes les ressources
patches:
  - path: replica-patch.yaml          # Patchs spécifiques à la prod
  - path: resource-patch.yaml
images:
  - name: bmis/api-backend            # Override de l'image
    newTag: "2.1.0"                   # Version de production
yaml k8s/overlays/prod/replica-patch.yaml 
# Patch pour augmenter les réplicas en production
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-backend
spec:
  replicas: 5                         # 5 réplicas en prod (vs 1 en dev)

10.3 - Appliquer avec Kustomize

bash Commandes Kustomize 
# Prévisualiser ce qui sera appliqué (dry-run)
kubectl kustomize overlays/prod

# Appliquer la configuration de production
kubectl apply -k overlays/prod

# Appliquer la configuration de staging
kubectl apply -k overlays/staging

# Appliquer la configuration de dev
kubectl apply -k overlays/dev
Kustomize vs Helm : Kustomize est parfait pour les configurations simples à moyennes avec peu de variations entre environnements. Pour des configurations très complexes avec des boucles, des conditions et des templates réutilisables, considérez Helm. Les deux peuvent cohabiter dans un même projet.

11 - Erreurs courantes

Utiliser hostPath en production - Les données sont liées à un seul nœud. Si le Pod est reprogrammé sur un autre nœud, les données sont perdues. Utilisez toujours un stockage réseau (EBS, NFS, EFS, Azure Disk) ou des StorageClasses avec provisionnement dynamique.
Ne pas utiliser de StorageClass - Le provisionnement manuel de PV est une source d'erreurs et ne passe pas à l'échelle. Définissez des StorageClasses pour chaque type de besoin (SSD rapide pour les BDD, stockage partagé pour les fichiers, stockage standard pour les logs) et laissez Kubernetes provisionner dynamiquement.
Aucun Resource Quota sur les namespaces - Sans quotas, un namespace en développement peut consommer toutes les ressources du cluster et impacter la production. Définissez toujours des ResourceQuotas et des LimitRanges, même généreux, sur chaque namespace non critique.
Tout déployer dans le namespace default - C'est l'erreur la plus fréquente des débutants. Le namespace default devrait rester presque vide. Créez des namespaces dédiés par environnement, par équipe ou par application pour une meilleure organisation, sécurité et gestion des ressources.
Oublier subPath pour PostgreSQL - Sans subPath, PostgreSQL peut échouer au démarrage à cause du dossier lost+found créé par certains systèmes de fichiers. Utilisez toujours subPath: pgdata pour les volumes PostgreSQL.
Ne pas définir de reclaimPolicy: Retain en production - La politique par défaut des StorageClasses est souvent Delete. Si un PVC est accidentellement supprimé, le volume et toutes les données sont perdus. En production, utilisez toujours Retain pour les données critiques.

12 - Best practices

Toujours utiliser le provisionnement dynamique - Créez des StorageClasses adaptées à chaque besoin et laissez Kubernetes provisionner les PV automatiquement. Réservez le provisionnement statique aux cas très spécifiques (import de stockage existant).
Chiffrer les volumes au repos - Activez le chiffrement dans les paramètres de la StorageClass (encrypted: "true" pour EBS). Les données financières et personnelles doivent toujours être chiffrées, au repos comme en transit.
Utiliser volumeBindingMode: WaitForFirstConsumer - Ce mode retarde la création du volume jusqu'au scheduling du Pod. Cela garantit que le volume est créé dans la même zone de disponibilité que le nœud, évitant les problèmes de montage cross-AZ.
Activer allowVolumeExpansion - Permettez l'extension des volumes dans vos StorageClasses. Cela vous permettra d'augmenter la taille d'un PVC sans recréer le volume, simplement en modifiant la taille dans le manifest et en réappliquant.
Un namespace par environnement, pas par microservice - Regroupez les microservices d'un même environnement dans un seul namespace (bmis-prod, bmis-staging). Cela simplifie la communication inter-services et la gestion des quotas.
Appliquer des labels cohérents aux namespaces - Utilisez des labels comme environment, team, project sur vos namespaces. Cela facilite les Network Policies, le RBAC et le monitoring (par ex. filtrer les métriques Grafana par label environment).
Sauvegarder régulièrement les PV - Utilisez des outils comme Velero pour créer des snapshots réguliers de vos PersistentVolumes. En cas de corruption ou de suppression accidentelle, vous pourrez restaurer les données rapidement.
Utiliser Kustomize ou Helm pour le multi-environnement - Ne dupliquez jamais les manifests YAML entre les environnements. Utilisez Kustomize (base + overlays) ou Helm (charts + values) pour gérer les variations de configuration entre dev, staging et production.
