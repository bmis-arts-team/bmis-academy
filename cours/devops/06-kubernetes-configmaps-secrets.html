Leçon 6 Section 2 - Kubernetes Core

ConfigMaps & Secrets

Externaliser la configuration et sécuriser les données sensibles - le pilier de toute application cloud-native.

1 - Le problème : configuration hardcodée

Imaginez un développeur qui écrit ceci dans son application.yml Spring Boot :

yaml application.yml - MAUVAISE PRATIQUE 
spring:
  datasource:
    url: jdbc:postgresql://192.168.1.45:5432/fintech_db
    username: admin
    password: SuperSecret123!
  redis:
    host: 192.168.1.50
    port: 6379
    password: RedisP@ss2024

payment:
  mtn-momo:
    api-key: sk_live_abc123def456
  orange-money:
    api-key: sk_live_xyz789ghi012

Ce code pose plusieurs problèmes critiques :

  • Mots de passe en clair dans le code source - Si le dépôt Git est compromis, toutes les clés API et mots de passe sont exposés.
  • Adresses IP hardcodées - En passant de développement à production, il faut modifier le code, recompiler et redéployer l'image Docker.
  • Pas de séparation des environnements - Le même fichier pour dev, staging et prod ? Impossible de gérer proprement.
  • Violation du principe Twelve-Factor App - Le facteur III (Configuration) exige que la configuration soit stockée dans l'environnement, jamais dans le code.
The Twelve-Factor App - Facteur III : « La configuration d'une application est tout ce qui est susceptible de varier entre les déploiements (staging, production, environnements de développement, etc.). Cela inclut les informations de connexion aux bases de données, les identifiants pour les services externes, et les valeurs propres à chaque déploiement. » La configuration doit être strictement séparée du code.

1.1 - Pourquoi application.yml seul ne suffit pas dans Kubernetes

Dans un environnement Kubernetes, votre application Spring Boot est empaquetée dans une image Docker immuable. Cette image est la même en développement, en staging et en production. Si la configuration est embarquée dans l'image, vous devez reconstruire une image pour chaque environnement - ce qui va à l'encontre du principe d'immuabilité.

Kubernetes résout ce problème avec deux ressources dédiées :

  • ConfigMap - Pour la configuration non-sensible (URLs, ports, niveaux de log, noms de profils).
  • Secret - Pour les données sensibles (mots de passe, clés API, certificats TLS).

Ces deux objets permettent d'injecter la configuration au moment du déploiement, sans modifier l'image Docker. La même image peut être utilisée partout - seule la configuration change.

2 - ConfigMap - Configuration non-sensible

Un ConfigMap est un objet Kubernetes qui stocke des données de configuration sous forme de paires clé-valeur. Il peut contenir des variables d'environnement simples, des fichiers de configuration complets, ou des arguments de ligne de commande.

2.1 - Ce qu'un ConfigMap peut stocker

  • Variables d'environnement - DATABASE_HOST=postgres-service, SERVER_PORT=8080
  • Fichiers de configuration complets - Un fichier application.yml, un nginx.conf, un redis.conf
  • Arguments CLI - Des paramètres à passer au conteneur au démarrage
Limite de taille : Un ConfigMap est limité à 1 Mo de données. Pour des fichiers de configuration plus volumineux, utilisez un volume persistant.

2.2 - Créer un ConfigMap depuis la ligne de commande

Depuis des valeurs littérales

bash Création depuis des littéraux 
# Créer un ConfigMap avec des paires clé=valeur
kubectl create configmap app-config \
  --from-literal=DATABASE_HOST=postgres-service \
  --from-literal=DATABASE_PORT=5432 \
  --from-literal=REDIS_HOST=redis-service \
  --from-literal=REDIS_PORT=6379 \
  --from-literal=SERVER_PORT=8080 \
  --from-literal=LOG_LEVEL=INFO

# Vérifier le contenu
kubectl get configmap app-config -o yaml

# Décrire le ConfigMap
kubectl describe configmap app-config

Depuis un fichier

bash Création depuis un fichier 
# Créer un ConfigMap depuis un fichier de configuration
kubectl create configmap spring-config \
  --from-file=application.yml=./config/application.yml

# Créer depuis un répertoire entier
kubectl create configmap nginx-config \
  --from-file=./nginx-configs/

# Vérifier
kubectl get configmap spring-config -o yaml

2.3 - ConfigMap en manifeste YAML

yaml configmap-basic.yaml 
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: fintech
  labels:
    app: api-backend
    environment: production
data:
  # Paires clé-valeur simples
  DATABASE_HOST: "postgres-service"
  DATABASE_PORT: "5432"
  DATABASE_NAME: "fintech_db"
  REDIS_HOST: "redis-service"
  REDIS_PORT: "6379"
  SERVER_PORT: "8080"
  LOG_LEVEL: "INFO"
  SPRING_PROFILES_ACTIVE: "prod"

2.4 - ConfigMap complet pour Spring Boot application.yml

Un cas d'usage très courant : stocker un fichier application.yml complet dans un ConfigMap et le monter comme volume dans le Pod.

yaml configmap-spring-boot.yaml - Configuration complète 
apiVersion: v1
kind: ConfigMap
metadata:
  name: spring-boot-config
  namespace: fintech
data:
  application.yml: |
    server:
      port: 8080
      shutdown: graceful

    spring:
      application:
        name: fintech-api
      datasource:
        url: jdbc:postgresql://${DATABASE_HOST}:${DATABASE_PORT}/${DATABASE_NAME}
        username: ${DATABASE_USERNAME}
        hikari:
          maximum-pool-size: 20
          minimum-idle: 5
          connection-timeout: 30000
      redis:
        host: ${REDIS_HOST}
        port: ${REDIS_PORT}
      jpa:
        hibernate:
          ddl-auto: validate
        show-sql: false
        properties:
          hibernate:
            format_sql: false
            dialect: org.hibernate.dialect.PostgreSQLDialect

    logging:
      level:
        root: INFO
        com.bmis.fintech: DEBUG
        org.springframework.web: INFO
      pattern:
        console: "%d{yyyy-MM-dd HH:mm:ss} [%thread] %-5level %logger{36} - %msg%n"

    management:
      endpoints:
        web:
          exposure:
            include: health,metrics,prometheus
      endpoint:
        health:
          show-details: when_authorized

3 - Utiliser un ConfigMap dans un Pod

Il existe trois méthodes pour injecter les données d'un ConfigMap dans un Pod. Chaque méthode a ses avantages et ses cas d'usage.

3.1 - Méthode 1 : envFrom (toutes les clés comme variables d'environnement)

La méthode la plus simple : toutes les clés du ConfigMap deviennent automatiquement des variables d'environnement dans le conteneur.

yaml deployment-envfrom.yaml 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-backend
  namespace: fintech
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api-backend
  template:
    metadata:
      labels:
        app: api-backend
    spec:
      containers:
      - name: api
        image: bmis/fintech-api:1.4.0
        ports:
        - containerPort: 8080
        envFrom:
        - configMapRef:
            name: app-config    # Toutes les clés de app-config
                                # deviennent des env vars

3.2 - Méthode 2 : env avec valueFrom (clés spécifiques)

Plus granulaire : vous choisissez exactement quelles clés extraire du ConfigMap, et vous pouvez renommer les variables d'environnement.

yaml deployment-valuefrom.yaml 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-backend
  namespace: fintech
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api-backend
  template:
    metadata:
      labels:
        app: api-backend
    spec:
      containers:
      - name: api
        image: bmis/fintech-api:1.4.0
        ports:
        - containerPort: 8080
        env:
        - name: SPRING_DATASOURCE_URL
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: DATABASE_HOST
        - name: SPRING_REDIS_HOST
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: REDIS_HOST
        - name: SERVER_PORT
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: SERVER_PORT

3.3 - Méthode 3 : volumeMount (monter comme fichier)

Idéal pour les fichiers de configuration complets. Le ConfigMap est monté comme un volume, et chaque clé devient un fichier dans le répertoire cible.

yaml deployment-volume.yaml 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-backend
  namespace: fintech
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api-backend
  template:
    metadata:
      labels:
        app: api-backend
    spec:
      containers:
      - name: api
        image: bmis/fintech-api:1.4.0
        ports:
        - containerPort: 8080
        volumeMounts:
        - name: config-volume
          mountPath: /app/config        # Le fichier sera à
          readOnly: true                # /app/config/application.yml
      volumes:
      - name: config-volume
        configMap:
          name: spring-boot-config      # Le ConfigMap contenant
                                        # application.yml

3.4 - Comparaison des trois méthodes

Méthode Cas d'usage Mise à jour auto Granularité
envFrom Injecter toutes les clés rapidement Non - redémarrage nécessaire Tout ou rien
env + valueFrom Sélectionner des clés spécifiques, renommer Non - redémarrage nécessaire Clé par clé
volumeMount Fichiers complets (application.yml, nginx.conf) Oui - kubelet sync (~60s) Fichier entier
Attention : Les ConfigMaps ne sont PAS faits pour les secrets. Les données d'un ConfigMap sont stockées en clair dans etcd et visibles par quiconque a accès au namespace. N'y mettez jamais de mots de passe, clés API, certificats ou tout autre donnée sensible. Utilisez les Secrets pour cela.

4 - Secret - Données sensibles

Un Secret est un objet Kubernetes conçu pour stocker des données sensibles : mots de passe, tokens, clés API, certificats TLS. Contrairement aux ConfigMaps, les Secrets bénéficient de protections supplémentaires (bien que limitées par défaut).

4.1 - Types de Secrets

Type Valeur du champ type Usage
Opaque Opaque Type par défaut - données arbitraires (mots de passe, clés API)
Docker Registry kubernetes.io/dockerconfigjson Identifiants pour un registry Docker privé
TLS kubernetes.io/tls Certificats TLS (clé privée + certificat)
Basic Auth kubernetes.io/basic-auth Identifiants username/password
SSH Auth kubernetes.io/ssh-auth Clé SSH privée
Service Account Token kubernetes.io/service-account-token Token d'un ServiceAccount (créé automatiquement)

4.2 - Créer un Secret depuis la ligne de commande

bash Création d'un Secret Opaque 
# Créer un Secret avec des valeurs littérales
kubectl create secret generic db-credentials \
  --namespace=fintech \
  --from-literal=DATABASE_USERNAME=fintech_admin \
  --from-literal=DATABASE_PASSWORD='Xk9#mP2$vL7@nQ4!' \
  --from-literal=REDIS_PASSWORD='R3d!s_S3cur3_2024'

# Vérifier (les valeurs sont encodées en base64)
kubectl get secret db-credentials -n fintech -o yaml

# Décoder une valeur spécifique
kubectl get secret db-credentials -n fintech \
  -o jsonpath='{.data.DATABASE_PASSWORD}' | base64 --decode

4.3 - Secret en manifeste YAML

Les valeurs dans le champ data doivent être encodées en base64. Vous pouvez aussi utiliser le champ stringData pour des valeurs en clair (Kubernetes les encodera automatiquement).

yaml secret-base64.yaml - Avec encodage base64 
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
  namespace: fintech
  labels:
    app: api-backend
type: Opaque
data:
  # Valeurs encodées en base64
  # echo -n 'fintech_admin' | base64  → ZmludGVjaF9hZG1pbg==
  DATABASE_USERNAME: ZmludGVjaF9hZG1pbg==
  # echo -n 'Xk9#mP2$vL7@nQ4!' | base64
  DATABASE_PASSWORD: WGs5I21QMiR2TDdAblE0IQ==
  # echo -n 'R3d!s_S3cur3_2024' | base64
  REDIS_PASSWORD: UjNkIXNfUzNjdXIzXzIwMjQ=
yaml secret-stringdata.yaml - Avec stringData (plus lisible) 
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
  namespace: fintech
type: Opaque
stringData:
  # Valeurs en clair - Kubernetes encode en base64 automatiquement
  DATABASE_USERNAME: fintech_admin
  DATABASE_PASSWORD: "Xk9#mP2$vL7@nQ4!"
  REDIS_PASSWORD: "R3d!s_S3cur3_2024"
base64 n'est PAS du chiffrement ! L'encodage base64 est un simple encodage réversible, pas une méthode de sécurité. N'importe qui ayant accès au Secret Kubernetes peut décoder les valeurs avec echo 'WGs5...' | base64 --decode. La sécurité des Secrets repose sur le contrôle d'accès RBAC, le chiffrement at-rest dans etcd, et les politiques réseau - pas sur base64.

4.4 - Utiliser un Secret dans un Pod

Les Secrets s'injectent exactement comme les ConfigMaps, avec les mêmes trois méthodes :

yaml Injection de Secret - envFrom et env 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-backend
  namespace: fintech
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api-backend
  template:
    metadata:
      labels:
        app: api-backend
    spec:
      containers:
      - name: api
        image: bmis/fintech-api:1.4.0
        ports:
        - containerPort: 8080
        # Méthode 1 : envFrom - toutes les clés du Secret
        envFrom:
        - secretRef:
            name: db-credentials
        # Méthode 2 : env - clés spécifiques
        env:
        - name: JWT_SECRET
          valueFrom:
            secretKeyRef:
              name: jwt-secret
              key: JWT_SIGNING_KEY
        # Volume pour certificats TLS
        volumeMounts:
        - name: tls-certs
          mountPath: /etc/tls
          readOnly: true
      volumes:
      # Méthode 3 : volume - monter comme fichiers
      - name: tls-certs
        secret:
          secretName: tls-certificates
          defaultMode: 0400     # Permissions restrictives

5.5 - Deployment complet référençant ConfigMap et Secret

yaml deployment-fintech-complete.yaml - Production Ready 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: fintech-api
  namespace: fintech-prod
  labels:
    app: fintech-api
    version: "1.4.0"
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: fintech-api
  template:
    metadata:
      labels:
        app: fintech-api
        version: "1.4.0"
      annotations:
        # Force le redéploiement si le ConfigMap change
        checksum/config: "{{ sha256sum configmap-fintech.yaml }}"
    spec:
      serviceAccountName: fintech-api-sa
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        fsGroup: 1000
      containers:
      - name: api
        image: bmis/fintech-api:1.4.0
        imagePullPolicy: Always
        ports:
        - name: http
          containerPort: 8080
        - name: management
          containerPort: 9090

        # ── Variables d'environnement depuis ConfigMap ──
        envFrom:
        - configMapRef:
            name: fintech-app-config

        # ── Variables d'environnement depuis Secret ──
        - secretRef:
            name: fintech-credentials

        # ── Fichiers de configuration montés ──
        volumeMounts:
        - name: spring-config
          mountPath: /app/config
          readOnly: true
        - name: tls-certs
          mountPath: /etc/tls
          readOnly: true

        # ── Health checks ──
        readinessProbe:
          httpGet:
            path: /actuator/health/readiness
            port: management
          initialDelaySeconds: 30
          periodSeconds: 10
        livenessProbe:
          httpGet:
            path: /actuator/health/liveness
            port: management
          initialDelaySeconds: 60
          periodSeconds: 15

        # ── Ressources ──
        resources:
          requests:
            cpu: 500m
            memory: 512Mi
          limits:
            cpu: "2"
            memory: 1Gi

      volumes:
      - name: spring-config
        configMap:
          name: spring-profiles-config
      - name: tls-certs
        secret:
          secretName: fintech-tls-cert
          defaultMode: 0400

5.6 - application.yml avec placeholders d'environnement

Dans votre code Spring Boot, le fichier application.yml embarqué dans l'image Docker utilise des placeholders ${ENV_VAR} qui seront remplacés par les valeurs injectées via ConfigMap et Secret :

yaml src/main/resources/application.yml - Dans le code source 
server:
  port: ${SERVER_PORT:8080}
  shutdown: ${SERVER_SHUTDOWN:graceful}

spring:
  application:
    name: fintech-api
  profiles:
    active: ${SPRING_PROFILES_ACTIVE:dev}

  datasource:
    url: jdbc:postgresql://${DATABASE_HOST:localhost}:${DATABASE_PORT:5432}/${DATABASE_NAME:fintech_db}
    username: ${DATABASE_USERNAME:postgres}
    password: ${DATABASE_PASSWORD:postgres}
    hikari:
      maximum-pool-size: 20

  redis:
    host: ${REDIS_HOST:localhost}
    port: ${REDIS_PORT:6379}
    password: ${REDIS_PASSWORD:}
    database: ${REDIS_DATABASE:0}

payment:
  mtn-momo:
    api-key: ${MTN_MOMO_API_KEY:}
    api-secret: ${MTN_MOMO_API_SECRET:}
    subscription-key: ${MTN_MOMO_SUBSCRIPTION_KEY:}
  orange-money:
    api-key: ${ORANGE_MONEY_API_KEY:}
    api-secret: ${ORANGE_MONEY_API_SECRET:}
  stripe:
    secret-key: ${STRIPE_SECRET_KEY:}
    webhook-secret: ${STRIPE_WEBHOOK_SECRET:}

security:
  jwt:
    secret: ${JWT_SECRET:dev-secret-key-not-for-production}
    expiration: ${JWT_EXPIRATION:3600000}

logging:
  level:
    root: ${LOG_LEVEL_ROOT:INFO}
    com.bmis.fintech: ${LOG_LEVEL_APP:DEBUG}
    org.hibernate.SQL: ${LOG_LEVEL_SQL:DEBUG}

management:
  server:
    port: ${MANAGEMENT_PORT:9090}
  endpoints:
    web:
      exposure:
        include: health,metrics,prometheus
  metrics:
    export:
      prometheus:
        enabled: ${METRICS_ENABLED:true}
Pattern ${VAR:default} : La syntaxe ${DATABASE_HOST:localhost} signifie « utiliser la variable d'environnement DATABASE_HOST, et si elle n'existe pas, utiliser localhost par défaut ». Ce pattern permet à l'application de fonctionner en local (dev) sans aucune configuration Kubernetes, tout en utilisant les ConfigMaps/Secrets en production.

6 - Séparation par environnement

En production, vous ne déployez pas la même configuration en dev, staging et prod. Kubernetes offre plusieurs stratégies pour gérer cette séparation.

6.1 - Stratégie par Namespace

La méthode la plus simple : chaque environnement a son propre namespace, avec ses propres ConfigMaps et Secrets.

bash Création des namespaces 
# Créer les namespaces pour chaque environnement
kubectl create namespace fintech-dev
kubectl create namespace fintech-staging
kubectl create namespace fintech-prod

# Appliquer les ConfigMaps spécifiques à chaque namespace
kubectl apply -f config/dev/configmap.yaml -n fintech-dev
kubectl apply -f config/staging/configmap.yaml -n fintech-staging
kubectl apply -f config/prod/configmap.yaml -n fintech-prod

# Appliquer les Secrets
kubectl apply -f secrets/dev/secrets.yaml -n fintech-dev
kubectl apply -f secrets/staging/secrets.yaml -n fintech-staging
kubectl apply -f secrets/prod/secrets.yaml -n fintech-prod

6.2 - Kustomize overlays

Kustomize est intégré nativement à kubectl et permet de gérer des variantes de configuration sans duplication. Vous définissez une base commune et des overlays par environnement.

yaml base/kustomization.yaml 
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - deployment.yaml
  - service.yaml
configMapGenerator:
  - name: app-config
    literals:
      - SERVER_PORT=8080
      - LOG_LEVEL_ROOT=INFO
yaml overlays/prod/kustomization.yaml 
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: fintech-prod
resources:
  - ../../base
configMapGenerator:
  - name: app-config
    behavior: merge
    literals:
      - LOG_LEVEL_ROOT=WARN
      - SPRING_PROFILES_ACTIVE=prod
patchesStrategicMerge:
  - replica-patch.yaml
bash Utilisation de Kustomize 
# Prévisualiser la configuration prod
kubectl kustomize overlays/prod/

# Appliquer la configuration prod
kubectl apply -k overlays/prod/

# Appliquer la configuration dev
kubectl apply -k overlays/dev/

7 - Mise à jour et rechargement

Que se passe-t-il lorsque vous modifiez un ConfigMap ou un Secret déjà utilisé par des Pods en cours d'exécution ? La réponse dépend de la méthode d'injection utilisée.

7.1 - Variables d'environnement : pas de mise à jour automatique

Quand un ConfigMap ou Secret est injecté via envFrom ou env, les variables d'environnement sont définies au moment du démarrage du Pod. Si vous modifiez le ConfigMap, les Pods existants conservent les anciennes valeurs. Il faut redémarrer les Pods pour appliquer les nouvelles valeurs.

bash Redémarrage progressif (rolling restart) 
# Modifier le ConfigMap
kubectl edit configmap fintech-app-config -n fintech-prod

# OU appliquer un fichier modifié
kubectl apply -f configmap-fintech.yaml -n fintech-prod

# Forcer un rolling restart du Deployment
kubectl rollout restart deployment/fintech-api -n fintech-prod

# Suivre l'avancement du rollout
kubectl rollout status deployment/fintech-api -n fintech-prod

# En cas de problème, rollback
kubectl rollout undo deployment/fintech-api -n fintech-prod

7.2 - Volume monté : mise à jour automatique

Quand un ConfigMap est monté comme volume, le kubelet synchronise automatiquement les fichiers montés avec le contenu du ConfigMap. Cette synchronisation prend environ 60 à 90 secondes par défaut (configurable via --sync-frequency du kubelet).

Attention aux sous-chemins : Si vous utilisez subPath dans votre volumeMount, la mise à jour automatique ne fonctionne pas. Les fichiers montés via subPath ne sont jamais mis à jour. Utilisez le montage de répertoire complet si vous avez besoin de la mise à jour automatique.

7.3 - Spring Cloud Kubernetes Config Watcher

Pour les applications Spring Boot, Spring Cloud Kubernetes offre un mécanisme de rechargement automatique de la configuration sans redémarrer le Pod.

yaml application.yml - Config watcher Spring Cloud 
# Dépendance Maven requise :
# spring-cloud-starter-kubernetes-client-config

spring:
  cloud:
    kubernetes:
      config:
        enabled: true
        name: fintech-app-config     # Nom du ConfigMap à surveiller
        namespace: fintech-prod
        enable-api: true
      reload:
        enabled: true
        mode: event                  # Réaction aux événements K8s
        strategy: refresh            # Rafraîchir le contexte Spring
        period: 15000                # Intervalle de vérification (ms)
        monitoring-config-maps: true
        monitoring-secrets: true
java AppConfig.java - Bean rechargeable 
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.cloud.context.config.annotation.RefreshScope;
import org.springframework.stereotype.Component;

@Component
@RefreshScope   // Ce bean sera recréé quand la config change
@ConfigurationProperties(prefix = "payment")
public class PaymentConfig {

    private MtnMomoConfig mtnMomo;
    private OrangeMoneyConfig orangeMoney;

    // getters, setters...

    public static class MtnMomoConfig {
        private String apiKey;
        private String apiSecret;
        // getters, setters...
    }

    public static class OrangeMoneyConfig {
        private String apiKey;
        private String apiSecret;
        // getters, setters...
    }
}
Méthode d'injection Mise à jour auto Action requise
envFrom / env Non kubectl rollout restart
Volume (sans subPath) Oui (~60-90s) L'application doit surveiller le fichier
Volume (avec subPath) Non kubectl rollout restart
Spring Cloud K8s Watcher Oui (temps réel) Aucune - rechargement automatique

8 - Sécuriser les Secrets en production

Par défaut, les Secrets Kubernetes sont simplement encodés en base64 et stockés en clair dans etcd. En production, cela n'est absolument pas suffisant. Voici les mesures de sécurité indispensables.

8.1 - Chiffrement at-rest dans etcd

Activez le chiffrement des Secrets au repos dans etcd pour qu'ils ne soient plus lisibles en cas d'accès direct au stockage.

yaml encryption-config.yaml - Configuration kube-apiserver 
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
    providers:
      # aescbc est le provider recommandé pour le chiffrement
      - aescbc:
          keys:
            - name: key1
              # Clé de chiffrement AES-256 (32 octets en base64)
              secret: "dGhpcyBpcyBhIDMyIGJ5dGUga2V5IGZvciBhZXM="
      # Le provider identity permet de lire les anciens Secrets
      # non chiffrés pendant la migration
      - identity: {}
bash Activer le chiffrement dans kube-apiserver 
# Ajouter l'argument au kube-apiserver
# (dans le manifeste du pod kube-apiserver)
--encryption-provider-config=/etc/kubernetes/encryption-config.yaml

# Re-chiffrer tous les Secrets existants
kubectl get secrets --all-namespaces -o json | \
  kubectl replace -f -

# Vérifier qu'un Secret est bien chiffré dans etcd
ETCDCTL_API=3 etcdctl get /registry/secrets/fintech-prod/db-credentials \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

8.2 - RBAC pour les Secrets

Restreignez l'accès aux Secrets à l'aide de rôles RBAC. Seuls les ServiceAccounts et utilisateurs autorisés doivent pouvoir lire les Secrets.

yaml rbac-secrets.yaml 
# Rôle qui autorise uniquement la lecture des Secrets
# dans le namespace fintech-prod
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: secret-reader
  namespace: fintech-prod
rules:
- apiGroups: [""]
  resources: ["secrets"]
  verbs: ["get", "list"]         # Pas de create, update, delete
  resourceNames:                 # Limiter à des Secrets spécifiques
    - "fintech-credentials"
    - "fintech-tls-cert"

---
# Lier le rôle au ServiceAccount de l'application
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: fintech-api-secret-binding
  namespace: fintech-prod
subjects:
- kind: ServiceAccount
  name: fintech-api-sa
  namespace: fintech-prod
roleRef:
  kind: Role
  name: secret-reader
  apiGroup: rbac.authorization.k8s.io

8.3 - Gestionnaires de secrets externes

Pour une sécurité maximale, utilisez un gestionnaire de secrets dédié plutôt que les Secrets natifs de Kubernetes.

8.4 - Sealed Secrets par Bitnami

Sealed Secrets résout un problème fondamental : comment stocker des Secrets dans Git sans risque ? Le principe est simple : vous chiffrez les Secrets avec une clé publique, et seul le contrôleur Sealed Secrets dans le cluster peut les déchiffrer avec la clé privée.

bash Utilisation de Sealed Secrets 
# 1. Installer le contrôleur Sealed Secrets
kubectl apply -f https://github.com/bitnami-labs/sealed-secrets/releases/download/v0.24.0/controller.yaml

# 2. Installer kubeseal (CLI)
brew install kubeseal    # macOS
# ou télécharger depuis GitHub Releases

# 3. Créer un Secret classique (ne sera PAS appliqué)
kubectl create secret generic db-credentials \
  --namespace=fintech-prod \
  --from-literal=DATABASE_PASSWORD='Pr0d#Db_2024!' \
  --dry-run=client -o yaml > secret.yaml

# 4. Chiffrer avec kubeseal → crée un SealedSecret
kubeseal --format yaml < secret.yaml > sealed-secret.yaml

# 5. Le SealedSecret peut être commité dans Git en toute sécurité !
git add sealed-secret.yaml
git commit -m "feat: add sealed database credentials"

# 6. Appliquer - le contrôleur le déchiffre en Secret natif
kubectl apply -f sealed-secret.yaml
Règle absolue : Ne commitez JAMAIS de fichiers Secret Kubernetes (kind: Secret) dans Git. Même si les valeurs sont en base64, elles sont triviales à décoder. Utilisez Sealed Secrets, un gestionnaire externe, ou des variables d'environnement CI/CD pour injecter les secrets.

9 - External Secrets Operator

L'External Secrets Operator (ESO) est un opérateur Kubernetes qui synchronise automatiquement les secrets depuis des fournisseurs externes (Vault, AWS, Azure, GCP) vers des Secrets Kubernetes natifs.

9.1 - Architecture

L'ESO introduit deux CRDs (Custom Resource Definitions) principaux :

  • SecretStore / ClusterSecretStore - Définit la connexion au fournisseur externe (Vault, AWS, etc.)
  • ExternalSecret - Définit quels secrets récupérer et comment les mapper vers un Secret Kubernetes
bash Installation de l'External Secrets Operator 
# Installer via Helm
helm repo add external-secrets https://charts.external-secrets.io
helm install external-secrets external-secrets/external-secrets \
  --namespace external-secrets \
  --create-namespace
yaml Exemple avec AWS Secrets Manager 
# 1. SecretStore - connexion à AWS Secrets Manager
apiVersion: external-secrets.io/v1beta1
kind: SecretStore
metadata:
  name: aws-secret-store
  namespace: fintech-prod
spec:
  provider:
    aws:
      service: SecretsManager
      region: eu-west-1
      auth:
        jwt:
          serviceAccountRef:
            name: fintech-api-sa

---
# 2. ExternalSecret - synchroniser un secret depuis AWS
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: fintech-credentials
  namespace: fintech-prod
spec:
  refreshInterval: 1h              # Synchroniser toutes les heures
  secretStoreRef:
    name: aws-secret-store
    kind: SecretStore
  target:
    name: fintech-credentials      # Nom du Secret K8s créé
    creationPolicy: Owner
  data:
    - secretKey: DATABASE_PASSWORD
      remoteRef:
        key: fintech/prod/database  # Chemin dans AWS Secrets Manager
        property: password
    - secretKey: REDIS_PASSWORD
      remoteRef:
        key: fintech/prod/redis
        property: password
    - secretKey: MTN_MOMO_API_KEY
      remoteRef:
        key: fintech/prod/payment/mtn
        property: api_key
Avantage clé : Avec l'ESO, vos développeurs n'ont jamais accès aux valeurs réelles des secrets. Ils déclarent simplement un ExternalSecret qui référence un chemin dans Vault ou AWS. L'opérateur s'occupe de la synchronisation. Cela élimine le risque de fuite via des fichiers YAML commitant.

10 - Erreurs courantes

Committer des Secrets dans Git - L'erreur la plus grave et la plus fréquente. Une fois qu'un secret est dans l'historique Git, il est compromis pour toujours, même si vous le supprimez dans un commit ultérieur. L'historique Git conserve tout. Vous devrez faire un git filter-branch ou utiliser BFG Repo Cleaner, et surtout révoquer et remplacer immédiatement tous les secrets exposés.
Utiliser un ConfigMap pour des mots de passe - Les ConfigMaps sont lisibles par tous les utilisateurs ayant accès au namespace. Ils ne bénéficient d'aucune protection spéciale. Les mots de passe, clés API et tokens doivent toujours être dans des Secrets, jamais dans des ConfigMaps.
Croire que base64 = chiffrement - echo 'bW9uX3NlY3JldA==' | base64 --decode → mon_secret. Base64 est un encodage trivial, pas un mécanisme de sécurité. Tout le monde peut décoder vos Secrets si vous ne mettez pas en place le chiffrement at-rest et les politiques RBAC.
Ne pas configurer de RBAC sur les Secrets - Par défaut, tout ServiceAccount dans un namespace peut lire tous les Secrets de ce namespace. Sans RBAC restrictif, un Pod compromis peut accéder à tous les secrets de l'environnement. Limitez l'accès avec des Roles et RoleBindings explicites.
Hardcoder les chaînes de connexion - jdbc:postgresql://192.168.1.45:5432/mydb dans le code ou dans l'image Docker rend votre application non-portable. Utilisez des variables d'environnement avec des valeurs par défaut : ${DATABASE_HOST:localhost}. L'adresse IP changera entre les environnements - votre image Docker ne devrait pas.

11 - Best practices production

Séparer ConfigMap et Secret - Ne mélangez jamais la configuration non-sensible et les données sensibles. Utilisez un ConfigMap pour les URLs, ports et niveaux de log, et un Secret pour les mots de passe et clés API. Cette séparation permet de gérer les accès RBAC de manière granulaire.
Utiliser stringData plutôt que data - Dans vos manifestes Secret, préférez stringData pour écrire les valeurs en clair (Kubernetes les encode automatiquement). Cela évite les erreurs d'encodage base64 et rend les fichiers plus lisibles. Attention : ne commitez jamais ces fichiers dans Git !
Un ConfigMap par responsabilité - Ne mettez pas toute votre configuration dans un seul ConfigMap géant. Séparez par responsabilité : app-config pour les paramètres applicatifs, spring-profiles pour les profils Spring, nginx-config pour la configuration du reverse proxy. Cela facilite les mises à jour ciblées.
Annotation de checksum pour le rollout - Ajoutez une annotation checksum/config calculée à partir du contenu du ConfigMap dans le template du Pod. Quand le ConfigMap change, le checksum change, et Kubernetes déclenche automatiquement un rolling update. Outils comme Helm supportent cela nativement avec {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}.
Immutabilité des ConfigMaps - Depuis Kubernetes 1.21, vous pouvez marquer un ConfigMap comme immutable: true. Cela empêche toute modification accidentelle et améliore les performances du cluster (le kubelet ne surveille plus les changements). Pour mettre à jour, créez un nouveau ConfigMap avec un nom versionné (app-config-v2) et mettez à jour le Deployment.
Rotation régulière des secrets - Mettez en place une politique de rotation des secrets : changez les mots de passe et clés API régulièrement (tous les 90 jours minimum). Utilisez un gestionnaire de secrets externe (Vault, AWS Secrets Manager) avec rotation automatique pour les environnements de production critiques.
Audit et monitoring - Activez l'audit logging de Kubernetes pour tracer tous les accès aux Secrets. Configurez des alertes pour les accès anormaux (lecteur inattendu, nombre d'accès élevé). Les gestionnaires de secrets comme Vault fournissent des audit logs détaillés nativement.
Tester la configuration en CI/CD - Validez vos ConfigMaps et Secrets (structure, clés attendues) dans votre pipeline CI/CD avant le déploiement. Utilisez kubectl apply --dry-run=client pour vérifier la syntaxe, et des tests d'intégration pour valider que l'application démarre correctement avec la configuration fournie.
